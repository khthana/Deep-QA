## 3. #33 คืออะไร และตัดสินใจอะไรไว้บ้าง

- **สี่ id ในคำขอเดียว เป็นของสอง grain** กิจกรรมกับสัปดาห์เป็นของ **ตอนเรียน** หมวดคะแนนกับ CLO
  เป็นของ **การเปิดสอน** ทุกตัวถูกตรวจกับ**รายการชุดเดียวกับที่ picker ใช้** ไม่ใช่กับ foreign key
  เพราะสามในสี่ FK ยอมรับ id ของ grain อื่น และ `activities.score_ratio_id` ไม่มี composite key เลย
- **บันทึกแทนที่แถว CLO ทั้งชุดในทรานแซกชันเดียว** key ของ `activity_clo_mapping` คือลำดับ และไม่มี
  อะไรนอกตารางอ้างถึง id ของแถว — ลบทิ้งแล้วเขียนใหม่จึงเป็นรูปที่ทำให้ *บันทึกครั้งที่สองคือการแก้*

  (`activity_scores` ผูกกับ `subject_clo` ไม่ใช่กับแถว mapping จึงกลายเป็นคะแนนกำพร้าแบบเงียบ ๆ)
- **ไม่บังคับผลรวม 100** BR-11 อ่านได้สองแบบในเอกสารต้นทางและเกณฑ์ของ #33 ไม่ได้ขอทั้งสองอย่าง

**ตารางคิวเดินมือถูกก๊อปส่งต่อมาโดยไม่มีใครตรวจ** (ใหม่) — ฉบับก่อนหน้าบอกว่า #25 #28 #29 #30
ยังค้างอยู่ ทั้งที่ทั้งสี่ใบเดินจบตั้งแต่ 28 ส.ค. ผู้ใช้เป็นคนทักว่าน่าจะเดินหมดแล้ว และการนับช่องสุดท้าย
ของทุกใบใช้เวลาไม่กี่วินาที **นับจากใบตรวจเสมอ อย่ายกตารางจาก handoff ฉบับก่อนมาโดยไม่นับใหม่:**

```bash
for f in docs/acceptance/*.md; do echo "$f ☐=$(grep -c '| ☐ |' $f) ◐=$(grep -c '| ◐ |' $f)"; done
```

**`restore` ของ harness เขียนทับทุกไฟล์ใน `FILES` ไม่ใช่แค่ไฟล์ที่มัตแตนต์แตะ** (ใหม่ · กินงานไป
สองรอบ) — การแก้ไฟล์ในชุดหลัง `save` ครั้งล่าสุดจะหายเงียบ ๆ ตอน restore ครั้งถัดไป แม้จะแก้คนละไฟล์
กับที่กำลังกวาด กฎที่เขียนไว้ใน `mutation/README.md` แล้ว: **อย่าแก้ไฟล์ในชุดระหว่างที่กวาดค้างอยู่**
และ **`save` เป็นคำสั่งแรกของสคริปต์กวาดเสมอ**

**อย่าให้ assertion ของ e2e เทียบกับคำตอบของ API ที่เติม control นั้นเอง** (ใหม่) — ถ้าความผิดพลาด
อยู่ที่ query ทั้งสองข้างจะโตพร้อมกันและ assertion มองไม่เห็นอะไร ให้เทียบกับ seed ซึ่ง route
ขยับไม่ได้ — นี่คือสิ่งที่การกวาดมีไว้เพื่อ

**อย่าฆ่า node ที่พอร์ต 3100/5100 โดยไม่ดูก่อนว่าอะไรรันอยู่** — เคยฆ่า webServer ของชุด e2e
ที่กำลังรัน ผลคือรอบนั้นจบแบบ *did not run* พร้อม exit 0 ซึ่งอ่านเผิน ๆ เหมือนผ่าน

**clone อื่นที่ยังชี้ `master`** — สาขาหลักถูกเปลี่ยนชื่อ `master` → `main` ฝั่ง server เมื่อ
17 ส.ค. 2569 clone เก่าบนเครื่องอื่นซ่อมด้วย:

```bash
git branch -m master main && git fetch origin --prune && git branch -u origin/main main
```

เก็บข้อนี้ไว้ในทุก handoff จนกว่าจะยืนยันว่าทุก clone ถูกซ่อมหมดแล้ว

**อย่า `git add` อะไรใน `DEEP-QA-BACKEND/` หรือ `_local/`** — `.env` มีคริเดนเชียลจริง `uploads/`
เป็นงานของนักศึกษาจริง และ repository นี้เป็น public

**อย่าพิมพ์ภาษาไทยผ่าน Bash** (cp874 `UnicodeEncodeError`) — ใช้ Write tool หรือสคริปต์ Python
`io.open(..., encoding='utf-8', newline='\n')` · และ `python mutation/<file>.py list` พิมพ์ `\r`
ท้ายบรรทัดบน Windows ต้อง `| tr -d '\r'` ก่อน grep

**รีสตาร์ต backend ก่อนเดินใบตรวจด้วยมือ** — `node server.js` ไม่มี reload

**สภาพเครื่อง ณ จบเซสชัน** — สแตกเดินมือยังเปิดค้าง: backend `node server.js` ที่ 3000 (ตัวที่
