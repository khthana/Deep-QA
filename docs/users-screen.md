# หน้าผู้ใช้งาน (`/main/users`)

กฎสิบสองข้อนี้เป็นคำตอบของเจ้าของงานเมื่อ 22 พ.ย. 2569 (การซักของ `/grill-with-docs`) ต่อข้อสังเกตว่า หน้า *ผู้ใช้งาน*
ของระบบใหม่มี UI ต่างจากโปรแกรมเดิม (`DEEP-QA-FRONTEND/src/components/content/AdminContent/UserMangement/`) และเจ้าของงาน
ชอบแบบเดิมมากกว่า · `docs/06` §Out of Scope บอกว่าการเปลี่ยน UI เป็นคำถามของเจ้าของงาน และนี่คือคำตอบ — ทุกข้อเป็น
ทางที่แนะนำ ยกเว้นข้อ 4 ซึ่งเจ้าของงานเลือกให้**เอาการลบกลับมา**สำหรับบัญชีที่ไม่มีอะไรอ้างถึง

ระบบนี้ใช้งานจริง ไม่ใช่การจำลองวิทยานิพนธ์ *แบบเดิม* จึงหมายถึงรูปและทางเดินของหน้าจอเดิม ไม่ใช่กลไกของมัน —
กฎที่ระบบใหม่ตั้งไว้แล้ว (สิทธิ์ตัดสินที่ server ตาม ADR-0002, ประโยคของ Notice, `docs/ui-form-layout.md`,
`docs/org-unit-names.md`) ยังใช้กับทุกข้อ

## กฎ

### ตาราง

1. **คอลัมน์**: ลำดับ · รหัสผู้ใช้งาน · ชื่อ สกุล (ไทย) · ชื่อ สกุล (อังกฤษ) · อีเมล · บทบาท · ช่วงเวลาใช้งาน · สถานะ ·
   ดำเนินการ — ห้าคอลัมน์แรก และ *สถานะ* *ดำเนินการ* มาจากของเดิม **ด้วยถ้อยคำของเดิม** · *บทบาท* และ *ช่วงเวลาใช้งาน*
   เป็นของระบบใหม่ที่เก็บไว้ · ตัวกรองบทบาทและสถานะยังอยู่ · **ลำดับนับต่อข้ามหน้า** (หน้า 2 เริ่มที่ 11) ไม่ใช่นับ 1 ใหม่
   ทุกหน้าอย่างของเดิม · ชื่อแต่ละภาษามีคำนำหน้าของภาษานั้น และบัญชีที่ไม่มีชื่อในภาษานั้นอ่าน `—` ไม่ตกไปใช้อีกภาษา

   *บันทึก 23 พ.ย. 2569 (#302)* — ข้อนี้เดิมเขียนคอลัมน์สุดท้ายว่า *จัดการ* และหัวคอลัมน์ด้วยคำย่อ · ของเดิม
   (`UserTable.js` `userColumns`) เขียน *ดำเนินการ* และทุกหน้าของระบบใหม่ก็เขียนอย่างนั้นตั้งแต่ #271 · เจ้าของงานตอบสี่ข้อ
   เมื่อวันนี้: *ดำเนินการ* · คำหัวคอลัมน์ของเดิมตรงตัว · ลำดับนับต่อข้ามหน้า · สวิตช์อย่างเดียวไม่มีคำข้าง (ข้อ 2)
2. **สถานะเป็นสวิตช์แบบเดิม** กดแล้วถามยืนยันก่อนเปลี่ยน (คำถามของ #86 ยังอยู่) · สวิตช์ของบัญชีตัวเองกดไม่ได้ (#84) ·
   ชื่อที่เข้าถึงได้คือ *สถานะ ‹ชื่อ›* · **ไม่มีคำข้างสวิตช์** อย่างของเดิม (คำตอบของเจ้าของงาน 23 พ.ย. 2569) — คนอ่านสถานะ
   จากตำแหน่งของปุ่มและสี โปรแกรมอ่านหน้าจออ่านจาก `aria-checked` · สวิตช์ไม่ขยับจนกว่าคำถามจะถูกตอบและรายการถูกอ่านใหม่
3. **แก้ไขเป็นไอคอนสีเทาแบบเดิม** (`FaUserEdit`) ไม่มีคำกำกับ · ชื่อที่เข้าถึงได้คือ *แก้ไข ‹ชื่อ›* และมี tooltip
4. **ลบเป็นถังขยะแบบเดิม แสดงทุกแถว** อยู่ในคอลัมน์ *ดำเนินการ* ข้างไอคอนแก้ไข กดแล้วถามยืนยัน แล้ว server ตัดสิน — ดู *การลบบัญชี* ด้านล่าง
5. **ปุ่ม *แสดงประวัติการใช้งาน* มุมขวาบน** พาไปหน้าประวัติ (ข้อ 11)

### หน้าแก้ไข

6. **เป็นหน้าแยก** รหัสบัญชีอยู่ใน URL · หัวคือ *แก้ไขข้อมูลผู้ใช้งานระบบ* ตามด้วยชื่อ · ปุ่ม *แสดงรายชื่อผู้ใช้งานทั้งหมด*
   พากลับไปตารางที่**หน้าและตัวกรองที่มาจาก** ซึ่งเก็บไว้ใน URL ของหน้าแก้ไข ไม่ใช่กลับไปหน้า 1 ที่ไม่มีตัวกรอง ·
   ปุ่มย้อนกลับของเบราว์เซอร์ให้ผลเดียวกัน
7. **แท็บ *ข้อมูลทั่วไป*** เปิดมาเป็นโหมดดู ช่องถูกปิด · ปุ่ม *แก้ไขข้อมูล* บนแถบแท็บเปลี่ยนเป็น *บันทึกข้อมูล* และ *ยกเลิก* ·
   ช่องภาควิชา หลักสูตร และช่วงเวลาใช้งานยังอยู่ · จัดวางตาม `docs/ui-form-layout.md`
8. **แท็บ *สิทธิ์ของระบบ*** แสดงสิทธิ์เป็นการ์ด (*สิทธิ์ :* · *คณะ / ภาควิชา / หลักสูตร :* ตามชนิดของขอบเขต) พร้อมบรรทัดเล็ก
   *ผู้กำหนด · เมื่อ* · ปุ่ม *เพิ่มสิทธิ์* บนแถบแท็บเปิด dialog — สะกดถูก ไม่ใช่ *เพิ่มสิทธ์* ของเดิม ให้ตรงกับชื่อแท็บ ·
   ยกเลิกสิทธิ์ด้วยถังขยะพร้อมยืนยัน · **ไม่มีกฎห้ามยกเลิกสิทธิ์ใบสุดท้าย** — กฎนั้นของเดิมอยู่แค่ฝั่ง client และ server
   ไม่มี จอจึงไม่ถือกฎที่ server ไม่ถือ (#11)
9. **แผงประวัติออกจากหน้าแก้ไข** ประวัติเปิดได้จากหน้าประวัติที่เดียว

### เพิ่มผู้ใช้

10. **เป็น dialog** ช่องชุดเดียวกับแท็บ *ข้อมูลทั่วไป* บวกสิทธิ์แรก และรหัสผ่านเฉพาะบทบาทที่ต้องใช้ (`FULL_ADMIN`,
    `EXT_ASSESSOR`) · จัดวางตาม `docs/ui-form-layout.md` · เลื่อนภายในได้ สูงไม่เกิน `max-h-[90vh]`

### ประวัติการใช้งาน

11. **ตารางรวมของทุกบัญชีแบบเดิม** พร้อมช่องค้นหา · คอลัมน์ ผู้ใช้งาน · กิจกรรม (ป้ายสี) · วันที่ · เวลา · รหัสผู้ใช้งาน ·
    **ทำกับข้อมูล** — คอลัมน์สุดท้ายเป็นของ #13 ที่เก็บไว้ เพราะตารางรวมที่ไม่บอกว่าทำกับใครตอบไม่ได้ว่าใครระงับใคร ·
    ปุ่ม *แสดงรายชื่อผู้ใช้งาน* ไว้กลับ · **เมนูด้านข้าง *ประวัติการใช้งาน* เอาออก** · แบ่งหน้าและค้นหาที่ server ·
    admin เห็นเฉพาะกิจกรรมของบัญชีที่ตัวเองเอื้อมถึง ตามกฎเดียวกับประวัติทีละบัญชีในวันนี้

### ข้อความแจ้งผล

12. **คง Notice** ไม่เปลี่ยนเป็น Snackbar ของเดิม — หน้านี้ใช้แบบเดียวกับทุกหน้า และข้อความที่หายเองจะหายก่อนคนอ่านคำปฏิเสธ
    ที่บอกทางออกทัน · ถ้าจะเปลี่ยนเป็น Snackbar ต้องเป็นตั๋วที่เปลี่ยนทั้งระบบ

## การลบบัญชี

ของเดิมลบบัญชีทิ้งได้ทุกบัญชี · ระบบใหม่ไม่มีการลบ เพราะ user story 19 เขียนว่า *create, edit and deactivate* ·
เจ้าของงานให้เอากลับมาโดยมีเงื่อนไข และ user story 19 ถูกแก้ตาม (22 พ.ย. 2569)

**ลบได้เมื่อ** บัญชีนั้น

- ไม่ได้เป็นผู้สอนของ section ใด (`course_sections_teacher` ซึ่ง `RESTRICT` อยู่แล้ว)
- ไม่ได้เป็นผู้สร้างหรือผู้แก้ล่าสุดของระเบียนใด (คอลัมน์ `created_by` `updated_by` `uploaded_by` `performed_by` ทุกตาราง)
  และไม่ได้เป็นผู้กำหนดสิทธิ์ใบใด (`user_roles.assigned_by`) — คอลัมน์เหล่านี้เป็น `ON DELETE SET NULL` ฐานข้อมูลจึง
  ไม่กัน และการลบจะลบชื่อผู้ทำออกจากระเบียนเงียบ ๆ
- **ประวัติของบัญชีนั้นมีแต่เรื่องของตัวเอง**: เข้าระบบ ออกจากระบบ สลับบทบาท และเปลี่ยนรหัสผ่าน · บรรทัดที่ทำกับข้อมูลหรือ
  บัญชีอื่นแม้แต่บรรทัดเดียวทำให้ลบไม่ได้ เพราะ `user_log` เป็น `ON DELETE CASCADE` และบรรทัดนั้นคือบันทึกเดียวว่าใครทำอะไร
  กับข้อมูลของคนอื่น — การลบรายวิชาหรือการยกเลิกสิทธิ์ไม่เหลือร่องรอยที่อื่น

สิทธิ์ของบัญชีที่ถูกลบ ประวัติเรื่องของตัวเอง และรูปโปรไฟล์ หายไปกับการลบ (`CASCADE`) · บรรทัดในประวัติของ admin ที่สร้าง
หรือกำหนดสิทธิ์ให้บัญชีนั้น**ยังอยู่** เพราะเป็นของ admin และ `target_id` เป็นข้อความ ไม่ใช่ foreign key (CONTEXT.md
*Activity log entry*)

**ถ้าลบไม่ได้** server ปฏิเสธพร้อมประโยคที่บอกเหตุผลและทางออก — สวิตช์สถานะอยู่ในแถวเดียวกัน ทางออกจึงเอื้อมถึงได้ (#60, #178) ·
ถ้อยคำของประโยคเป็นของเจ้าของงาน ผู้ลงมือร่างให้ดูก่อนลงมือ · การลบบัญชีตัวเองถูกปฏิเสธเช่นเดียวกับการระงับบัญชีตัวเอง
ส่วนสิทธิ์ว่าใครลบได้ใช้ขอบเขตเดียวกับใครแก้บัญชีนั้นได้ (ADR-0002)
