# ตรวจรับด้วยมือ — #15 Programs

`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #15

ครึ่งแรกอยู่ที่ `backend/test/programs.test.js` (19 subtests) — ทุกเกณฑ์ที่พิสูจน์ได้ที่ seam เดียว
ของเราคือ HTTP surface ของ backend ถูกพิสูจน์ที่นั่นแล้ว รวมทั้งสองข้อที่เกณฑ์ข้อ 9 เรียกชื่อมาเอง
คือ *การปฏิเสธข้ามภาควิชา* กับ *ปิดการใช้งานแทนการลบ* ที่เหลือลงมาอยู่ในตารางข้างล่างเพราะ
docs/06 §Testing Decisions ระบุว่า **"Frontend components are not unit-tested"**

เกณฑ์สองข้อพิสูจน์ที่อื่น และควรรู้ว่าที่ไหน

- **ข้อ 6 (ถามยืนยันก่อนลบ)** เป็น dialog ล้วน ๆ ไม่มีอะไรให้ server ยืนยัน — request ที่มาถึงคือ
  request ที่ตั้งใจส่ง จึงอยู่ในตารางข้างล่างอย่างเดียว
- **ข้อ 7 (import ผ่านโมดูลกลาง)** เป็นข้อความเกี่ยวกับ *ผู้เรียกสามราย* และสองรายคือหน้าผู้ใช้งาน
  กับหน้าภาควิชา พิสูจน์โดย `users.test.js` และ `departments.test.js` ซึ่ง **ไม่ถูกแก้เลย**
  ในตั๋วนี้ — นั่นคือความหมายของคำว่าใช้ซ้ำ

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ข้อมูลหลัก → ข้อมูลหลักสูตร* (`/main/programs`)

seed มีหลักสูตรสองรายการ คือ `0501` กับ `0503` และ **ทั้งคู่อยู่ในภาควิชา `05` และมีข้อมูลอ้างอิงอยู่**
(PLO, รายวิชาในหลักสูตร, นักศึกษา, ผลการเรียน) หลักสูตรที่จะลบได้จริงจึงต้องสร้างเองในข้อ 1
ส่วนภาควิชา `01` ยังไม่มีหลักสูตรเลย และ `dept.admin.01@` เป็นผู้ดูแลของภาควิชานั้น — สองอย่างนี้
คือคู่ที่ใช้เดินข้อ 3

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`npm run seed` ใหม่หลังเดินจบ** ก่อนเริ่มตั๋วถัดไป

## สิ่งที่ยังไม่ปิดใน #15

1. **`?active=1` ยังไม่มีหน้าจอไหนเรียกใช้** — เกณฑ์ข้อ 4 มีสองครึ่ง ครึ่งที่ว่า "หยุดปรากฏใน
   รายการให้เลือก" ทำเป็นพารามิเตอร์ไว้แล้วและมีเทสต์ยืนยัน แต่หน้าจอที่ *ให้เลือก* หลักสูตร
   (นักศึกษา #17, รายวิชาในหลักสูตร #18, PLO #19 เป็นต้นไป) ยังไม่มีสักหน้า ตัวพารามิเตอร์จึงมี
   ผู้เรียกที่ระบุชื่อได้แล้วแต่ยังไม่มีอยู่จริง — ตั๋วเหล่านั้นต้องส่ง `active=1` เมื่อทำถึง

2. **การเพิ่ม/แก้/ลบหลักสูตรยังไม่ถูกบันทึกลง `user_log`** — เหมือน #14 ข้อ 2 และด้วยเหตุผลเดียวกัน
   ควรเป็นตั๋วเดียวสำหรับ "บันทึกการแก้ไขข้อมูลหลักทุกหน้า" ไม่ใช่ทำทีละหน้า

3. **`<Pager>` ยังไม่ถูกแยกเป็นคอมโพเนนต์** — ตกทอดมาจาก #14 ข้อ 3 และตอนนี้เป็นหน้าที่ห้าแล้ว
   (Users, HistoryPanel, ActivityPanel, Departments, Programs) เหตุผลที่ยังไม่ทำไม่เปลี่ยน:
   การแยกต้องแก้หน้าจอที่ส่งมอบไปแล้วสี่หน้า จึงควรเป็น commit ของตัวเองที่เดิน checklist ใหม่ทั้งหมด

4. **ไม่มีตัวกรองตามภาควิชาบนหน้านี้** — ผู้ดูแลคณะที่มีหลายภาควิชาต้องเลื่อนหาเอา #16 ขอตัวกรอง
   ตามภาควิชาไว้สำหรับรายวิชา ถ้าทำที่นั่นแล้วควรย้อนมาทำที่นี่ด้วยเป็นตั๋วเดียวกัน

5. **ลบหลักสูตรถามฐานข้อมูลแทนที่จะนับล่วงหน้า** — หน้าจอบอกได้แค่ว่า "ถ้ามีข้อมูลอ้างอิงจะปิดการ
   ใช้งานให้แทน" ไม่ได้บอกว่ามีอะไรอ้างอิงอยู่บ้าง เหตุผลเดียวกับ #14 ข้อ 4 คือรายการห้าตารางที่
   เขียนด้วยมือจะล้าสมัยทันทีที่มีตารางที่หก ถ้าอยากได้ข้อความละเอียดกว่านี้ต้องเปิดตั๋ว

6. **`department_id` บน PUT ยังเป็น "ไม่ส่งมาแปลว่าไม่เปลี่ยน" ในขณะที่ฟิลด์อื่นเป็น "ไม่ส่งมาแปลว่าล้าง"**
   — `year` ถูกแก้ให้แทนที่เหมือนชื่อแล้วในรอบรีวิว (ไม่งั้นล้างปีจากฟอร์มไม่ได้เลย) เหลือภาควิชา
   ที่ยังยกเว้นอยู่ เพราะการเว้นคอลัมน์ภาควิชาไม่ควรแปลว่าต้องการล้างภาควิชาของหลักสูตรทิ้ง
   ยังเป็นความไม่สม่ำเสมอที่คนอ่าน API ครั้งแรกอาจสะดุด และควรเป็นตั๋วที่ตัดสินใจพร้อมกันทุก route

7. **การนำเข้ายังเป็น CSV ไม่ใช่ `.xlsx`** — ตกทอดมาจาก #11 ข้อ 1 และตอนนี้เป็นการตัดสินใจของ
   `lib/importer` ที่เดียวสำหรับทุกหน้าจอ

8. **บล็อกตอบกลับของการนำเข้าตอนนี้ซ้ำกันสามที่แล้ว** — #14 ข้อ 8 ตั้งไว้ว่า "พอถึงหน้าจอที่สาม
   หรือสี่ควรทบทวน" หน้าจอที่สามมาถึงแล้ว (`users`, `departments`, `programs`) แปดบรรทัดนั้น
   เหมือนกันทุกตัวอักษร ต่างแค่ชื่อคีย์ของผลสำเร็จ ควรเปิดตั๋วย้ายเข้าไปเป็น helper ที่รับชื่อคีย์

9. **`lib/fields.js` แยกออกมาแล้ว แต่ยังไม่ครอบคลุมทุกอย่างที่ซ้ำ** — `trimmed`, `blankToNull`,
   `isDuplicate`, `isReferenced` ถูกย้ายออกจาก `routes/users.js`, `routes/departments.js` และ
   `routes/programs.js` มาอยู่ที่เดียวแล้วในรอบรีวิวนี้ ส่วนที่ยังซ้ำอยู่คือบล็อกตอบกลับของการนำเข้า
   (ข้อ 8) และรูปแบบ `read*()` ที่ทุกหน้าจอเขียนเองด้วยมือ ซึ่งยังไม่ควรรวบเพราะกฎของแต่ละหน้าต่างกันจริง

10. **`reachable` และรายการกรองด้วย `department_id` ไม่ใช่ `program_id`** — `coveredScopes` คืน
    รหัสคณะ ภาควิชา และหลักสูตรมาในชุดเดียวกันโดยไม่มีการรับประกันว่ารหัสข้ามตารางจะไม่ชนกัน
    การกรองหลักสูตรด้วย "ภาควิชาที่เอื้อมถึง" จึงตรงกับกฎที่ตั๋วเขียนไว้มากกว่า และไม่พลาดกรณี
    หลักสูตรที่รหัสบังเอิญไปตรงกับรหัสภาควิชาอื่น ถ้าจะให้แน่นกว่านี้ต้องแยก namespace ของ
    `scope_id` ซึ่งเป็นเรื่องของ ADR ไม่ใช่ของตั๋วนี้

11. **การลบหลักสูตรจริง ๆ ทิ้ง grant ของ `PROG_MANAGER` ที่ผูกกับหลักสูตรนั้นค้างไว้** —
    `user_roles.scope_id` ไม่มี FK ฐานข้อมูลจึงไม่ตอบ 23503 และไม่มีการปิดการใช้งานให้แทน
    รายการอ้างอิงที่ตั๋วเขียนไว้ (PLO, รายวิชาในหลักสูตร, นักศึกษา, การเปิดสอน) ไม่ได้พูดถึง grant
    แต่ผลที่ได้คือ grant ที่ชี้ไปยังหลักสูตรที่ไม่มีอยู่แล้ว ควรเปิดตั๋วให้ตัดสินใจว่าจะกัน
    การลบไว้ หรือจะถอน grant ตามไปด้วย
