## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ข้อมูลหลัก → ข้อมูลหลักสูตร* (`/main/programs`)

seed มีหลักสูตรสองรายการ คือ `0501` กับ `0503` และ **ทั้งคู่อยู่ในภาควิชา `05` และมีข้อมูลอ้างอิงอยู่**
(PLO, รายวิชาในหลักสูตร, นักศึกษา, ผลการเรียน) หลักสูตรที่จะลบได้จริงจึงต้องสร้างเองในข้อ 1
ส่วนภาควิชา `01` ยังไม่มีหลักสูตรเลย และ `dept.admin.01@` เป็นผู้ดูแลของภาควิชานั้น — สองอย่างนี้
คือคู่ที่ใช้เดินข้อ 3

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`npm run seed` ใหม่หลังเดินจบ** ก่อนเริ่มตั๋วถัดไป

## รายการที่ต้องเดิน

ทุกแถวเดินจบแล้ว — ครึ่ง HTTP ด้วย `curl` และครึ่งหน้าจอบนเบราว์เซอร์ ดูสองหัวข้อท้ายไฟล์
ช่องสุดท้ายเคยมีสามค่าระหว่างเดิน

- **☑** เดินจบแล้ว — ทั้งแถวพิสูจน์ได้ที่ HTTP และผลจริงบันทึกไว้ในหัวข้อ *ผลการเดินด้วย curl* ข้างล่าง
- **◐** ครึ่งของ server เดินแล้วและผ่าน ส่วนที่เหลือคือสิ่งที่หน้าจอวาด (แถบสี ตาราง dropdown) ยังต้องมีคนดู
- **☐** ยังไม่ได้เดิน — เป็นพฤติกรรมของเบราว์เซอร์ล้วน ไม่มีคำขอไปถึง server ให้ตรวจ

### ที่ครึ่ง server ยังไม่ได้เดิน

แถว *ลบแถวสุดท้ายของหน้าสุดท้ายแล้วไม่ค้างหน้าว่าง* ทำเครื่องหมายเป็นแถวเบราว์เซอร์ แต่จริง ๆ
มีครึ่งของ server ที่ยังไม่ได้ยิง: `stepBack` ใน `Programs.js` จะทำงานก็ต่อเมื่อ DELETE *ลบจริง*
(`deactivated` ไม่จริง) ตอนเดินมี `0527` อยู่หน้า 2 ตัวเดียวแล้วแต่ไม่ได้ลบมัน ผู้เดินด้วย
เบราว์เซอร์จึงต้องเลือกแถวที่ไม่มีอะไรอ้างอิงเท่านั้น มิฉะนั้นได้ปิดใช้งานแทนและแถวไม่หายไป
จากหน้า การไม่ถูกพากลับจึงจะถูกแล้ว ไม่ใช่ข้อผิดพลาด

แถวที่ว่า `committee.0501@` เปิด `/api/programs` ไม่ได้ ยิงเฉพาะ route รายการ ส่วน
`GET /api/programs/:programId` ไม่ได้ยิง — ทั้งสอง route อยู่หลัง `requireRole(...MAINTAINERS)`
ตัวเดียวกัน แต่ที่บันทึกไว้คือ route แรกเท่านั้น

### ที่แก้ในเอกสารนี้ระหว่างเดิน

บัญชี `com2@` ที่เอกสารอ้างถึงไม่มีอยู่ใน seed — ที่มีคือ `committee.0501@` กับ
`committee.0503@` และสองแถวนั้นต้องการคนละตัว แถวข้อ 5 ต้องเป็น `committee.0501@`
เพราะ grant ของบัญชีนั้นผูกกับหลักสูตร `0501` ที่กำลังถูกปิดพอดี

## ผลการเดินบนเบราว์เซอร์

เดินเมื่อ 19 สิงหาคม 2569 โดยอาจารย์ที่ปรึกษา บน `frontend` ที่ `http://localhost:5000` คุยกับ
backend ตัวเดียวกับที่เดิน curl เดินเป็นห้าชุดเรียงตามสถานะข้อมูลที่ต่อกัน: ฟอร์ม → สิทธิ์ผู้ดูแล
ภาควิชา → การลบ → ภาควิชาที่ปิดใช้งาน → นำเข้าไฟล์และแบ่งหน้า **ทุกแถวผ่าน** รวมถึงสามแถวที่
เสี่ยงที่สุดในเช็คลิสต์นี้

- ภาควิชาที่ปิดใช้งานแล้วและเป็นภาควิชาของหลักสูตรที่กำลังแก้ ขึ้นเป็น `05 … (ปิดใช้งาน)` ที่เลือก
  อยู่แต่กดไม่ได้ ส่วน `01` ที่ปิดเหมือนกันแต่ไม่ใช่ของหลักสูตรนี้ ไม่อยู่ในรายการ และ **บันทึกผ่าน**
  — `<option disabled>` ที่เป็นค่าปัจจุบันไม่ได้ทำให้ฟอร์มส่งไม่ได้อย่างที่กลัวไว้
- แบนเนอร์สองแบบของการลบเลือกถูกทั้งคู่: `0505` ที่ไม่มีอะไรอ้างอิงได้ *ลบหลักสูตรเรียบร้อยแล้ว*
  และหายจากตาราง ส่วน `0501` ได้ *มีข้อมูลอื่นอ้างอิงอยู่ ระบบจึงปิดการใช้งานแทนการลบ* และยังอยู่
- แถวสุดท้ายของหน้าสุดท้าย (11 รายการ หน้า 2 มีแถวเดียว) ถูกลบแล้วพากลับหน้า 1 เอง — `stepBack`
  ทำงานจริง และครึ่ง server ของแถวนั้นที่ curl ไม่ได้ยิงไว้ ก็ถูกยิงไปพร้อมกันตรงนี้

### สองอย่างที่การเดินบนหน้าจอเจอ

1. **บันทึกแล้วจอไม่เลื่อนขึ้นไปหาแบนเนอร์** (#55) — พื้นที่เนื้อหาใน `Mainpage.js:92` เลื่อนของตัวเอง
   (`overflow-y-auto`) ฟอร์มเพิ่มหลักสูตรสูงพอที่คนกรอกจะค้างอยู่ครึ่งล่าง พอบันทึกเสร็จแบนเนอร์
   ไปอยู่บนสุดนอกสายตา แถวใหม่โผล่ในตารางแต่คำยืนยันไม่ถูกเห็น เกิดขึ้นตอนเดินจริงและทำให้
   เข้าใจไปว่าแบนเนอร์ไม่ทำงาน กระทบทุกหน้าที่มีฟอร์มยาว ไม่ใช่เฉพาะหน้านี้
2. **อัปโหลดไฟล์ผิดชนิดแล้วข้อความไม่บอกว่าผิดชนิด** (#56) — เอาไฟล์หลักสูตรใส่กล่องนำเข้าของหน้า
   *ข้อมูลภาควิชา* ได้ *ข้อมูลภาควิชาไม่ครบถ้วนหรือไม่ถูกต้อง* ซ้ำทุกแถว ซึ่งอ่านแล้วเหมือนข้อมูล
   ในไฟล์ผิด ทั้งที่ปัญหาคือหัวคอลัมน์ไม่ใช่ของแบบฟอร์มนั้นเลย ไม่มีอะไรถูกบันทึก (กฎทั้งไฟล์หรือ
   ไม่เอาเลยทำงานถูก) แต่คนเดินเสียเวลาไปหาที่ผิดในไฟล์
