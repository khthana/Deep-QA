## สิ่งที่ตั๋วเขียนไว้แล้วโค้ดไม่ทำตาม และทำไม

**เกณฑ์ข้อ 8 ของตั๋วเขียนว่า *"Faculty and Department Admins can manage PLOs within their scope"*
แต่โค้ดไม่ให้ `FACULTY_ADMIN` เข้าหน้านี้เลย** — [#79](https://github.com/khthana/Deep-QA/issues/79)
กลับคำตัดสินนั้นหลังจากตั๋วนี้ถูกเขียน และระบุ **A09 ซึ่งคือหน้านี้** ไว้ตรง ๆ ว่า
*"เมื่อสร้าง ห้ามใส่ `FACULTY_ADMIN` ลงใน MAINTAINERS ของ route และห้ามใส่รายการเมนูลง `FacultyAdmin.js`"*
เหตุผลคือคณะถือ *รายชื่อ* ภาควิชาและหลักสูตร ส่วนสิ่งที่อยู่ *ข้างใน* หลักสูตรเป็นของภาควิชากับกรรมการหลักสูตร
ข้อความในตั๋วเก่ากว่า #79 จึงถือ #79 เป็นข้อยุติ และเขียนไว้ตรงนี้แทนที่จะให้ checklist ขัดกับโค้ดอย่างเงียบ ๆ

**การลบข้อหลักที่ยังมีข้อย่อย ถูกปฏิเสธ ไม่ใช่ปิดการใช้งาน** — ตั๋วบอกกรณีอ้างอิงไว้สองกรณี
(subject mapping กับ CLO) แต่ `parent_outcome_id` ก็เป็น `ON DELETE RESTRICT` เหมือนกัน
ถ้าปล่อยให้ `deleteOrDeactivate` จัดการ ข้อหลักที่มีข้อย่อยจะถูก *ปิดการใช้งาน* เงียบ ๆ
ทั้งที่คนกดคือคนที่ตั้งใจจะ *ลบ* และข้อย่อยยังเรียงอยู่ใต้มันเหมือนเดิม จึงถามเรื่องข้อย่อยก่อน
แล้วตอบด้วยประโยคที่บอกว่าต้องทำอะไร — เป็นแถวหนึ่งใน checklist นี้ ไม่ใช่ผลข้างเคียงของ helper ที่หยิบมาใช้

**หน้านี้ไม่มีการแบ่งหน้า** ทุกหน้าข้อมูลหลักอื่นแบ่งสิบแถว หน้านี้ไม่แบ่งโดยตั้งใจ —
ข้อย่อยที่อยู่หน้าสองขณะที่ข้อหลักอยู่หน้าหนึ่งไม่ใช่ต้นไม้ และไม่มีวิธีประกอบกลับที่ฝั่งหน้าจอ

ย่อหน้าข้างบนคือสิ่งที่ [#101](https://github.com/khthana/Deep-QA/issues/101) อธิบายผิด — ตั๋วนั้นเขียนว่า
*ห้าหน้าของ `0501` มาก่อนแถวแรกของ `0503`* ซึ่งเป็นคำอธิบายของหน้าที่**ไม่มีอยู่จริง**
ความจริงแย่กว่านั้น คือ 56 แถวต่อกันในการเลื่อนเดียว โดยไม่มี *หน้า 1 จาก 6* บอกว่ายังมีอะไรต่อ
**การวัดก่อนเชื่อคำวินิจฉัยของตั๋ว** — `grep -c Pager frontend/src/pages/Plos.js` ตอบ 0

**หน้าพี่น้องสี่หน้าที่ตั๋วสั่งให้อ่าน ถูกอ่านแล้ว และไม่มีหน้าไหนเปลี่ยน** ([#101](https://github.com/khthana/Deep-QA/issues/101)) — `Offerings`, `ProgramSubjects`,
`Rubrics` และ `Students` ยังมี *ทุกหลักสูตร* ทั้งสี่หน้า และทั้งสี่หน้า**แบ่งหน้า** — หน้านี้กับ #20
เป็นสองหน้าเดียวที่ไม่แบ่ง สิ่งที่ตัดสินอยู่ที่ schema ไม่ใช่รสนิยม คือ `UNIQUE (program_id, outcome_code)`:
รหัส PLO เป็นอันเดียวในห้าหน้าที่ชี้แถวได้*เฉพาะภายในหลักสูตร* (`rubric_code` เป็น `UNIQUE` ทั้งระบบ)
สี่หน้านั้นจึงไม่ถูกแก้ในตั๋วนี้ และการอ่านนั้นถูกบันทึกไว้ตรงนี้ ไม่ใช่ใน CLAUDE.md ที่เดียว

**บัญชีที่ไม่ได้ดูแลหลักสูตรใดเลย เห็นประโยคของตัวเอง — แต่ไม่มีอะไรทดสอบมัน**
เมื่อตัวกรองเป็นสิ่งจำเป็น บัญชีที่ไม่มีหลักสูตรในสิทธิ์จะไม่มีคำขอใดส่งออกไปเลย หน้าจึงต้อง
หยุดหมุนเอง ไม่งั้น *กำลังโหลด…* ค้างไว้ตลอดไป ซึ่งคือข้อบกพร่องที่ #43 เจอ
แต่ทุกบัญชีใน seed เข้าถึงอย่างน้อยหนึ่งหลักสูตร (#102 ใส่ `0101` ให้ `01` ไปแล้ว) จึง**ไม่มีแถว
ใน seam ไหนที่เดินมาถึงข้อความนี้ได้** คำตอบที่ซื่อตรงคือ *ยังไม่มีเทสต์* ไม่ใช่การเงียบ

**หน้านี้ไม่มีการนำเข้าไฟล์** ตั๋วไม่ได้ขอ และรูปทรงต้นไม้ทำให้ไฟล์แบนต้องอ้างข้อหลักด้วยรหัสที่ยังไม่มีตัวตน
ถ้าจะทำควรเป็นตั๋วของตัวเอง

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js:58`
อีเมลต้องพิมพ์เต็มรวมโดเมน `@kmitl.ac.th` — อีเมลหรือรหัสผ่านที่ผิดทำให้ server ตอบ 401
และหน้าจอขึ้นกล่อง *Session หมดอายุ* ทับประโยคจริงไว้ หลงทางง่ายมาก ([#97](https://github.com/khthana/Deep-QA/issues/97))
เมนูที่ใช้ตลอดเอกสารนี้คือ *ผลการเรียนรู้ → กำหนดผลการเรียนรู้ระดับหลักสูตร PLO* (`/main/plos`)

**ต้อง restart backend ก่อนเดิน** — process ที่ค้างจากตั๋วก่อนจะตอบ *ไม่พบเส้นทางที่เรียกบนเซิร์ฟเวอร์นี้*
ให้ทุก route ของ #19 (นั่นคือสิ่งที่ #95 ทำให้มันบอกตรง ๆ แทนที่จะโทษการเชื่อมต่อ)

**seed เปลี่ยนไปในตั๋วนี้ ต้อง `npm run seed` ใหม่ก่อนเดิน** หลักสูตร `0503` เพิ่งได้ต้นไม้ PLO ของตัวเอง
สองข้อ (`PLO-1` กับ `PLO-2` พร้อมข้อย่อยสองข้อของ `PLO-2`) และมันมีอยู่เพื่อสองแถวในใบนี้โดยเฉพาะ

- **`0503` มี `PLO-1` เป็นของตัวเอง คนละข้อกับ `PLO-1` ของ `0501`** — นี่คือเกณฑ์ข้อ 5 ทั้งข้อ
  schema เดิมบังคับให้ `outcome_code` ไม่ซ้ำทั้งระบบ ซึ่งห้ามสิ่งนี้ไว้พอดี
- **`PLO-2` ของ `0503` ถูกตั้งลำดับให้อยู่ *เหนือ* `PLO-1`** — บทเรียนจาก
  [#96](https://github.com/khthana/Deep-QA/issues/96) คือ `0501` ตั้ง `sequence_order` เท่ากับเลขในรหัสทุกข้อ
  เรียงตามลำดับกับเรียงตามรหัสจึงให้ผลเหมือนกันเป๊ะ และ assertion ไหนก็ผ่านทั้งคู่
  สองแถวนี้เป็นที่เดียวใน seed ที่การเรียงสองแบบไม่ตรงกัน จึงเป็นที่เดียวที่เกณฑ์ข้อ 4 พิสูจน์ได้

`0501` มี `PLO-1` ถึง `PLO-13` พร้อมข้อย่อย และข้อ 1, 2, 3, 5, 6, 7, 8, 12 ถูกรายวิชา `01076105` map ไว้
— แปดข้อนี้คือข้อที่ลบไม่ออกและจะถูกปิดการใช้งานแทน

**`PLO-14` ไม่มีอยู่ใน seed** — แถวที่เอ่ยถึงมันเป็นแถว ⚙ ซึ่ง `19a-plos.spec.js`
สร้างมันเองใน schema ของ e2e และคนเดินด้วยมือไม่ต้องเดิน แถวการซ้อนสองแถวข้างล่าง
จึงชี้ไปที่ `PLO-12` กับข้อย่อยสองข้อของมันที่ seed ให้มาแล้วแทน

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`npm run seed` ใหม่หลังเดินจบ** ก่อนเริ่มตั๋วถัดไป

## รายการที่ต้องเดิน

- **☑** เดินด้วยมือจบแล้ว หรือพิสูจน์ที่ seam HTTP แล้ว — **สองอย่างนี้เป็น ☑ เท่ากัน** ⚙ สงวนไว้ให้ browser seam เท่านั้น และแถวบอกเองว่าอะไรพิสูจน์มัน (`CLAUDE.md` §Marks on the sheets · [#194](https://github.com/khthana/Deep-QA/issues/194))

- **☐** ยังไม่ได้เดิน
- **⚙** ครอบคลุมด้วย browser seam แล้ว (#65) ไม่ต้องเดินด้วยมือซ้ำ แถวบอกไฟล์ที่ครอบคลุมไว้ และมาร์กนี้ได้มาเมื่อมัตแตนต์ฆ่า assertion ของแถวนั้นเอง — **ถ้าแถวนั้นพูดถึงสิ่งที่วาดด้วย (เมนู ถ้อยคำ สี) ครึ่งนั้นยังเป็นงานของคนเดิน และแถวจะเขียนกำกับไว้** (`CLAUDE.md` §Two test seams · [#194](https://github.com/khthana/Deep-QA/issues/194))

อีกเก้าแถวเดินด้วยมือทีละแถว ติ๊กจากสิ่งที่ผู้เดินเห็นและรายงานกลับมาเท่านั้น ส่วนอีกสองแถวที่เหลือเป็นของ [#107](https://github.com/khthana/Deep-QA/issues/107) กับ [#101](https://github.com/khthana/Deep-QA/issues/101) พิสูจน์ที่ seam ของ HTTP ไม่ใช่ด้วยการเดิน

**สิ่งที่การเดินจับได้ และเทสต์สองชั้นจับไม่ได้**

ข้อหลักในคอลัมน์ *รหัส* ใช้ `font-medium` (น้ำหนัก 500) ส่วนข้อย่อยเป็นค่าปกติของ `td` (400)
บนฟอนต์ไทยขนาดเล็กสองค่านี้แยกด้วยตาไม่ออก ผู้เดินรายงานว่า *เหมือนจะเท่ากัน*
ขณะที่แถวในใบนี้อ้างว่าข้อหลักเป็น *ตัวหนา* ซึ่งคือ `font-bold` คนละ token กัน
แก้ `frontend/src/pages/Plos.js` เป็น `font-bold` แล้วให้ผู้เดินดูซ้ำ คราวนี้เห็นชัด
และเขียนชื่อ token กำกับลงในแถวนั้นแล้ว เพื่อไม่ให้คนอ่านรอบหน้าต้องตีความคำว่า *ตัวหนา* เอง

> บทเรียนเดียวกับ `สีเหลือง` ที่จริง ๆ เป็น `amber-700`:
> **เขียนใบเดินงานด้วยชื่อ token ไม่ใช่ด้วยคำที่ตาคนใช้**

browser seam ยืนยันได้แค่ว่าแถวข้อย่อยอยู่ *ถัดจาก* แถวข้อหลัก คำถามว่าคนอ่านแล้วเห็นเป็นต้นไม้ไหม
มีแต่ตาคนตอบได้ และคำตอบแรกคือ *ไม่*

**สองอย่างที่พบระหว่างเตรียมเดิน เปิดเป็น [#97](https://github.com/khthana/Deep-QA/issues/97) แล้ว**

- `frontend/src/api/client.js:80` ยกกล่อง *Session หมดอายุ* เมื่อได้ 401 ทุกกรณีโดยไม่ดู `reason`
  ทั้งที่ server แยก `anonymous` / `expired` / `invalid` มาให้แล้ว และ `AuthContext.js:45` ก็อ่าน `reason` ถูก
  ผิดเกณฑ์ข้อ 6 ของ #10 ตรง ๆ
- `frontend/src/pages/Login.js:88` เรียก `post('/api/auth/login', …)` โดยไม่ทำเครื่องหมาย anonymous
  จึงเป็นเหยื่อรายแรกของข้อบน — อีเมลหรือรหัสผ่านผิดได้กล่อง *Session หมดอายุ* ทับประโยคจริง
  ซึ่งกินเวลาการเดินรอบนี้ไปหลายรอบก่อนจะรู้ว่าไม่ใช่เรื่อง session เลย

ตอนเขียนตั๋วเจอที่ที่สาม `backend/routes/auth.js:124` ส่งออกแค่ `message` ทิ้ง `reason`
ของ `refuse(401, 'credentials')` ไป ฝั่ง client จึงแยกสองกรณีนี้ไม่ได้แม้จะอยากแยก

**ที่ต้องทำหลังเดินจบ** หลายแถวเขียนข้อมูลจริงลงฐาน — `PLO-12-1-1` ถูกสร้างขึ้นและยังอยู่
`npm run seed` ใน `db/` ล้างได้ และควรล้างก่อนเริ่มตั๋วถัดไป

## #211 — ยามที่ ref ถือพิกัด ไม่ใช่ตัว loader (15 ต.ค. 2569)

#208 ให้แฟ้มหน้าจอสิบเก้าแฟ้มรูปเดียวกัน: handler อ่านตัว loader **สด** ออกมาจาก ref ที่เก็บมันไว้
จอนี้อยู่นอกประชากรนั้น เพราะ `onScreen` ถือ *หลักสูตร* ที่เลือกไว้ ไม่ใช่ตัว loader — ซึ่งตอบคำถาม
*ตัวกรองยังอยู่ที่เดิมไหม* ได้ครบถ้วน (#133 — แถว 2 กับแถว 7 ของ `133a` ยืนอยู่บนมัน) และตอบคำถาม
ถัดไปไม่ได้เลย: *loader ตัวไหนควรเป็นผู้อ่าน* ผู้เรียกสามรายของแฟ้มนี้จึงส่ง loader ที่ตัวเองปิดทับไว้
ต่อไป และกลไกที่สองของ #208 ยังมีชีวิตอยู่ที่สองรายในนั้น

`load` ยก `loading` ก่อนถาม และลดลงเฉพาะเมื่อ `isCurrent()` loader ที่ `program` ของมันเป็นหลักสูตร
ที่จอ **ออกมาแล้ว** จึงยกที่ว่างขึ้นโดยไม่มีใครลด: `finally` ของมันเองปฏิเสธตัวเอง ส่วนการอ่านที่มาแทน
ลดที่ว่างของตัวเองไปนานแล้ว ตารางจึงค้างอยู่ที่ *กำลังโหลด…* ใต้ประโยคสำเร็จของการลบ หรือใต้แถบ
คำปฏิเสธของการอ่านที่ล้ม ทั้งสองประโยคถูกพูดจริง

### ทำไม loader ที่ค้างต้องเป็นผู้อ่าน *คนสุดท้าย*

การย้ายตัวกรองเฉย ๆ ไม่พอ มันสร้าง `load` ตัวใหม่ และ effect ที่ผูกกับ `load` อ่านหลักสูตรใหม่ทันที
แล้วลดที่ว่างลงเมื่อคำตอบนั้นมาถึง การอ่านที่ค้างซึ่งมาถึงภายหลังจึงถูกปฏิเสธและไม่ลดอะไรลง ซึ่งเป็น
สิ่งที่ #133 ขอไว้พอดี ความผิดต้องให้ loader ที่ค้าง **ถูกเรียก** หลังการอ่านสดนิ่งแล้ว และนั่นคือสิ่งที่
handler ทำ: มันอ่านรายการซ้ำเมื่อคำขอของตัวเองกลับมา ทั้งสองแถวจึงกักคำขอของ handler ไว้ที่ route
ย้ายตัวกรองระหว่างที่มันค้าง ปล่อยให้รายการใหม่มาถึงและถูกวาด แล้วจึงปล่อยคำตอบของ handler ไป

### ทางเข้าสองทาง และทางที่สามที่ไปไม่ถึง

- **ลบ** (`confirmRemoval`) — `DELETE` ค้างอยู่ขณะที่ตารางและตัวกรองยังถูกวาด กล่องคำถามเป็น
  `bg-black/50` เต็มจอที่กินคลิก (#199 วัดไว้) ทางเข้าของทางนี้จึงเป็นแป้นพิมพ์: `ConfirmDialog`
  ไม่ขัง focus (#204) และ `<select>` ที่ได้ focus ตอบ ArrowDown **ทางนั้นปิดแล้วเมื่อ
  [#217](https://github.com/khthana/Deep-QA/issues/217) ลง 18 ต.ค. 2569** (#204 ปิดเมื่อ 18 ต.ค. 2569 ด้วยครึ่งที่ประกาศ
  ซึ่งไม่ขังอะไร แล้ว #217 ลงครึ่งที่ขังในวันเดียวกัน) **ทางเข้าวันนี้คือกด *ยกเลิก* ปิดคำถามขณะที่
  `DELETE` ยังค้างอยู่ แล้วย้ายตัวกรองด้วยเมาส์** ซึ่งเป็นสถานการณ์เดิมที่ไม่ต้องมีข้อบกพร่องอื่น
  มาเปิดทางให้ (#203) — แถวของทางนี้ใน `211a` ถูกเล็งใหม่ตามนั้น ไม่ได้เหลือไว้เป็นตาข่าย
- **แก้ไขที่ถูกปฏิเสธ** (`catch` ของ `openEditor`) — ไม่มีอะไรวาดทับอะไรเลย ฟอร์มขึ้นเมื่อคำตอบมาถึง
  เท่านั้น ตัวกรองจึงเป็นคลิกเมาส์ธรรมดา ทางนี้ไม่รอใคร และเป็นแถวที่บอกว่าเรื่องนี้ไม่ใช่เชิงอรรถ
  ของการเข้าถึง สิ่งที่มันต้องมีคือคำปฏิเสธ ซึ่ง `gate` แต่งให้เป็น 409 — แถวที่เพื่อนร่วมงานเพิ่งลบไป
  เหตุผลเดียวกับที่ `139a` แต่งคำปฏิเสธขึ้นแทนที่จะทำให้เกิดจริง
- **บันทึก** (`save`) เป็นผู้เรียกรายที่สาม และ **ไปไม่ถึง** กลไกนี้เชิงโครงสร้าง — ด้วยเหตุผล
  ที่เป็น **ลำดับ** ไม่ใช่ฟอร์ม: `save` ล้าง `editing` แล้วเรียก loader ใน tick เดียวกัน จึงไม่มีขณะใด
  ที่ตัวกรองอยู่บนจอพร้อมกับ loader ที่ยังไม่ถูกเรียก · *ฟอร์มแทนที่ตารางตลอดเวลาที่การเขียนค้าง*
  เป็นจริงกับ **การเขียน** และไม่จริงกับ **การอ่านซ้ำ**: `setEditing(null)` อยู่ก่อน `await` ของ loader
  ตารางและตัวกรองจึงกลับมาบนจอขณะที่คำขอการอ่านซ้ำยังค้าง ซึ่งเป็นสิ่งที่คอมเมนต์ของแถว 7 ใน
  `133a` วัดไว้อยู่แล้ว (วัดลำดับในแฟ้มเมื่อ 15 ต.ค. 2569 · ครึ่งแรกของประโยคนี้เขียนผิดตอนแรก
  และ review ของตั๋วนี้จับได้ในวันเดียวกัน — ข้อสรุปถูก เหตุผลครึ่งหนึ่งผิด ซึ่งเป็นชนิดที่หมดอายุ
  ผิดวัน) · ข้อเรียกร้องเรื่องคำตอบที่ถูกแทนของผู้เรียกรายนี้เป็นของ `133a` แถว 7 และยังเป็นของมันต่อไป

ทุกแขน คือลบจริงไม่ใช่ปิดการใช้งาน ซึ่งอ่านใต้ seam และเป็นข้อเรียกร้องของแขน เพราะคำตอบ
`200 deactivated` จะทำให้จอพูดประโยคอีกประโยค แล้วตัวอ่านจะนับ `0` และแขนจะอ่านเหมือน
*ไม่มีใครพูด* (#164 — ตัวอ่านที่ตาบอดตอบ *ไม่เคย* ทั้งบนจอที่พังและจอที่ดี)

**แขนที่สามคือสิ่งที่ตั๋วเป็นเรื่องของมัน** ขณะการอ่านใหม่ค้าง: ฉากคลุม **0** ชั้น · ปุ่มยืนยัน
**0** ปุ่ม · ตัวกรอง **ไม่ถูกปิด** กล่องถูกเก็บไปแล้วด้วย `setRemoving(null)` ซึ่งรันก่อนการรอ
ฉะนั้นไม่ต้องมีผู้กระทำคนที่สอง ไม่ต้องกดอะไรซ้ำ และไม่มีอะไรให้ยกเลิก — ต่างจากสองแถวของ #211
ที่ต้องกักการลบและกด ยกเลิก ก่อนถึงตัวกรอง นี่คือเหตุผลว่าทำไมหมายเหตุของ `onScreen`
ไม่ได้คลุมกรณีนี้: ประโยคที่ว่า *"the dialog behind ลบ leaves it drawn"* พูดถึงช่วงที่กล่อง
**ยังเปิดอยู่** (#220)

**ย่อหน้าที่ตั๋วอ่านจากโค้ดถูก และการวัดยืนยัน ไม่ได้หักล้าง** ซึ่งเป็นด้านที่พบน้อยกว่าของ #66
สิ่งที่การวัดอ่านได้คือ **ผล** — ประโยคอยู่บนจอเหนือรายการของ `0503` — ไม่ใช่สองอนุประโยคแยกกัน
ที่ seam นี้ไม่มีอะไรแยก `reloaded` ออกจาก `showing.current === sent` ได้ การอ่านโค้ดเป็นผู้บอกว่า
ทั้งคู่ยังเป็นจริงเพราะเหตุใด และที่วัดได้คือจอทำตามนั้น

### สิ่งที่สองแขนสุดท้ายแก้ในคำถามของตั๋วเอง

สี่แขนแรกกดอยู่ในหน้าต่างทั้งหมด จึงบอกได้แค่ *เกิดอะไรขึ้นเมื่อการกดลงในหน้าต่าง* ซึ่งยังไม่พอ
แยกทางแยกชนิดของ #52 #199 — ระบบถือสองพฤติกรรมโดยมีนาฬิกาที่มองไม่เห็นเป็นผู้เลือก — ออกจาก
พฤติกรรมเดียวที่ไปถึงได้สองทาง เพราะสิ่งที่ตัดสินคือ *การกดเดียวกันนอกหน้าต่าง* จบต่างกันไหม
สองตัวควบคุมจึงถูกวัดทั้งสองฝั่งและอ่านเป็นตาราง ไม่ใช่เถียง (#148 #149)

| ตัวควบคุม | กดในหน้าต่าง | กดหลังประโยคขึ้นแล้ว | สองช่องตรงกันไหม |
|---|---|---|---|
| ตัวกรองหลักสูตร | ประโยคอยู่เหนือ `0503` | ประโยค **ยังอยู่** เหนือ `0503` | ตรงกัน |
| เพิ่มผลการเรียนรู้ | ไม่เคยขึ้นเลย | ขึ้นแล้วถูกเก็บไปตอนกด | ปลายทางตรงกัน — ไม่มีประโยคบนจอ |

**หน้าต่างไม่ใช่สาเหตุ** แขนที่ห้าไม่กักอะไรเลย ไม่มีการแข่งกัน และจบที่เดียวกับแขนที่สอง
กับที่สาม เพราะ **ไม่มีอะไรเก็บประโยคเมื่อตัวกรองขยับ**: `setNotice(null)` ถูกเรียกจากปุ่มที่
เขียน `showing.current` เท่านั้น ลำดับนี้จึงไม่ต้องมีหน้าต่าง ไม่ต้องมีผู้กระทำคนที่สอง และไม่ต้อง
มีจังหวะใดเป็นพิเศษ — ต้องมีแค่คนขยับตัวกรองหลังกด ลบ ซึ่งแปลว่าถ้อยคำ *"ในหน้าต่าง"* ของตั๋ว
แคบกว่าทางเข้าที่มีจริง (#179 — ตั๋วที่ตั้งชื่อการแข่งกันตั้งชื่อหน้าต่าง ไม่ใช่ประชากรของทางเข้า)

ช่องของ **เพิ่มผลการเรียนรู้** ต่างกันแค่ *เมื่อไร* ไม่ต่างกันที่ปลายทาง: ในหน้าต่างประโยคไม่เคยขึ้น
เพราะตัวกั้นทำงาน นอกหน้าต่างประโยคขึ้นแล้วการกดของคนนั้นเองเก็บมันไป ทั้งสองทางคนไม่เหลือ
ประโยคอยู่บนจอ

### เครื่องมือที่ตั๋วตั้งชื่อไว้วัดหน้าต่างผิดช่วง

### รายละเอียดที่การวัดต้องเลือก และเหตุผล

- **ติดตั้ง route ก่อนกด ไม่ใช่หลังคำตอบของการลบมาถึง** ติดหลังจะเป็นธงที่จับคู่กับเหตุการณ์
  ภายหลัง (#168) — handler รันบนเหตุการณ์เดียวกันนั้น การอ่านใหม่จึงออกไปได้ก่อน route ลงที่
  สิ่งที่ทำให้ติดก่อนได้คือการอ่านตั้งต้นของ `0501` ถูกตอบและวาดเสร็จไปแล้วใน `openOn`
  คำขอ GET ของ `0501` ที่เหลือจึงมีแต่การอ่านใหม่เอง
- **ไม่ใช้ `filterTo` ในแขนที่กัก** `waitForList` ของมันรับคำขอ `/api/plos` ใด ๆ รวมถึงตัวที่
  ถูกกักอยู่ แขนเหล่านั้นจึงรอคำตอบของ `0503` ด้วย query ของมันเอง (#218 — ตัวจับที่ตอบคำถาม
  สองข้อพร้อมกันแคบลงให้ข้อเดียวไม่ได้)
- **รอให้กล่องหลุดจากเอกสารก่อนอ่านจำนวนฉากคลุม** คำตอบกับการวาดเป็นสองจังหวะ (#132)
- **ตัวอ่านเฟรมใช้ `support/frame-sampler.js` ของร่วม** ไม่ใช่สำเนาในแฟ้มนี้ เพราะไม่มีข้อเรียกร้อง
  ของแถวไหนอยู่ในมัน (#171) สำเนาที่เคยเขียนไว้มีเหตุผลเท็จกำกับ: ตัวนับที่ `window.__sightings`
  เป็นหนึ่งตัวต่อหนึ่งหน้า จึงไม่มีอะไรชนกัน
- **สองแขนสุดท้ายอ่านแถบประโยคเองด้วย `getByRole('status')`** ไม่ใช่ผ่านตัวอ่านเฟรม เพราะคำถาม
  ของมันคือ *ประโยคยังยืนอยู่ไหมหลังการกด* แขนที่ห้าอ่าน **ครั้งเดียว** ที่จุดนิ่ง เพราะในแขนนั้น
  ไม่มีอะไรเรียก `setNotice(null)` การอ่านแบบรีทรายที่นั่นจะเป็นข้อเรียกร้องที่ล้มไม่ได้ (#50)
  ส่วนแขนที่หกรีทรายได้ เพราะที่นั่นโค้ดที่ถูกวัดเองเป็นผู้เก็บแถบ ซึ่งเป็นข้อยกเว้นของ #214
- **ข้อที่ถูกลบอ่านจากฐานข้อมูล ไม่ใช่จากบัญชีรายชื่อในแฟ้ม** ถามว่าอะไรไม่มีใครชี้อยู่ ด้วยสาม

  ที่ข้อเรียกร้องนั้น ไม่ใช่ตอบผิด (#126)

### เงื่อนไขที่ทำให้บันทึกนี้หมดอายุ

- **ตัวกรองที่สองบนจอนี้** — กุญแจคือ `program` ตัวเดียว เพราะ `load` ถามด้วยค่านั้นค่าเดียว
  ถ้ามีตัวกรองหรือหน้าเข้ามา กุญแจต้องกว้างขึ้นพร้อมกัน ไม่งั้นประโยคจะถูกเก็บไว้ใต้การอ่านที่
  ไม่ใช่การอ่านที่คนเห็น โดยไม่มีอะไรบอก (#185, #207)
- **`waiting` ถูกอ่านเป็น loader** — docblock ของมันเขียนห้ามไว้ และ `dead-loaders.js` หา loader
  **จาก ref** ฉะนั้นมันมองไม่เห็น ref ที่ถือพิกัด (#208) และมองไม่เห็น ref ที่ถือประโยคด้วย
- **ยามของ `save` ที่จอนี้ไม่มี** — เป็นการตัดสินใจของ #202 ที่ลงวันกำกับไว้ที่จุดนั้น ถ้ามันเปลี่ยน
  ประโยคที่ส่งต่อจะถูกติดกุญแจในเงื่อนไขอื่น · **เงื่อนไขข้อนี้เกิดขึ้นบ่ายวันเดียวกัน**:
  [#242](https://github.com/khthana/Deep-QA/issues/242) ปลด *ยกเลิก* ซึ่งเป็นเงื่อนไขที่ #202
  เขียนกำกับตัวเองไว้ ฉะนั้นการส่งต่อประโยคอยู่ใต้ `if (showing.current === sent)` ตั้งแต่
  28 ต.ค. 2569 · กุญแจตอบว่า**ประโยคนี้เป็นของหลักสูตรไหน** และตอบไม่ได้ว่า**ฟอร์มที่ถามถูก
  แทนด้วยฟอร์มอื่นแล้วหรือยัง** เพราะหลักสูตรเป็นตัวเดิมทั้งสองฝั่งของ *ยกเลิก* (#205, #207)
  สิ่งที่คนเห็นไม่เปลี่ยน — `load` ก็เงียบอยู่แล้วเมื่อกุญแจไม่ตรง — ที่เปลี่ยนคือ ref ไม่ถูกเขียน

ไม่ถือธงอะไรเลย คำตอบนั้นลงที่สามจอ — ภาควิชา หลักสูตร รายวิชา — และ**เหตุผลที่เจ้าของงานให้เป็น
ประโยคเกี่ยวกับสามจอนั้น เงียบเรื่องพี่น้องของมัน** สำมะโนด้วย**กลไก** ไม่ใช่ด้วยชื่อจอ (#174) คือ
นับว่าช่องกรอกแต่ละช่องถือธงอะไร ให้ประชากรอีก **สี่** ฟอร์ม ซึ่งคือ
[#242](https://github.com/khthana/Deep-QA/issues/242)

ทั้งสี่จอแม่เขียน `const busy = writing || reading` เหมือนกันทุกตัวอักษร ฉะนั้น `busy` เป็นจริง
ขณะที่**การอ่านหรือการเขียนใด ๆ ของหน้า**ค้างอยู่ ไม่ใช่ขณะที่ฟอร์มนี้ส่งการบันทึก และเพราะ
`finally` ของ `save` ปล่อย `writing` **หลัง** `await` ของการอ่านรายการใหม่ ลำดับที่คนพบคือ
บันทึกสำเร็จ → ฟอร์มปิด → กด *เพิ่มผลการเรียนรู้* → **ฟอร์มใหม่ถูกวาดโดยที่ทุกช่องปิด** จนการอ่านรอบนั้นลง
หน้าต่างคือหนึ่งรอบ HTTP ไม่ใช่หนึ่งเฟรม ไม่ต้องมีนาฬิกาอะไรเลือกให้ (#199) และ**ไม่ต้องมีนักแสดง
คนที่สอง**

### วัดก่อน ไม่ใช่เถียง

ตั๋วสั่งข้อนี้เป็นข้อแรก (#141 — ให้วัดว่าสร้างได้ไหม) **แปดแถวที่แฟ้มมีอยู่ตอนนั้นรันกับโค้ดที่ยังไม่แก้เมื่อ
28 ต.ค. 2569 ได้แดงแปดจากแปด** แต่ละแถวตายที่ข้อยืนยันที่มันถูกตั้งชื่อตาม ฉะนั้นนี่เป็น
**ข้อบกพร่องที่คนพบได้วันนี้ ไม่ใช่คำถามของเจ้าของงาน** — รูปถูกตัดสินไปแล้วเมื่อ 26 ต.ค. 2569
สิ่งที่เหลือคือประชากร · และการรันแบบนั้นคือสิ่งที่บอกว่าแถวใหม่วัดอะไรได้ ก่อนจะเขียนมัตแตนต์ของมัน
(#203)

**ตัวเลขที่เคยอยู่ที่นี่คือ *แดงแปดจากเก้า* ซึ่งผิด — แก้เมื่อ 29 ต.ค. 2569 จากการรีวิว** ตอนรันนั้น
แฟ้มมีแปดแถวและแดงทั้งแปด แถวที่เก้า — แถวคำปฏิเสธของจอผลการเรียนรู้ — ถูกเขียน**ทีหลัง**และไม่เคย
ถูกอ่านกับโค้ดที่ยังไม่แก้เลย สิ่งที่วัดมันคือ `242:ploreported` ซึ่งเป็นงานของมัตแตนต์ ไม่ใช่ของการรัน
ก่อนแก้ (#115) · ประโยคเดิมบอกเป็นนัยว่ามีแถวหนึ่งเขียวกับโค้ดเก่า ซึ่งจะเป็นแถวที่วัดอะไรไม่ได้ (#203)
และไม่มีแถวนั้น · ร่างแรกก่อนแปดแถวมีสี่แถว จอละแถว และแดงทั้งสี่ ซึ่งเป็นการวัดที่ทำให้แถวถูกแยกใหม่

**สิ่งที่การวัดเปลี่ยนในการออกแบบแถว** ร่างแรกอ่าน *ยกเลิก* ไว้กลางแถวแรก แล้วทั้งสี่แถวแรกตายที่
นั่นกับโค้ดที่ยังไม่แก้ และขั้นที่ตั๋วสั่งให้วัด — ฟอร์มที่เปิดทีหลังยังพิมพ์ได้ไหม — **ไม่ถูกอ่านเลย**
เพราะแถวรายงานข้อยืนยันตัวแรกที่ตาย (#88) ข้ออ้างนั้นจึงย้ายไปอยู่แถวที่สอง และถูก**อ่านเป็นข้ออ้าง
ก่อนถูกกด** เพราะการกดตัวควบคุมที่ปิดอยู่ตายที่ timeout ไม่ใช่ที่ข้ออ้างของแถว (#139)

### การ์ดสามบรรทัดที่ลงมาพร้อมกัน

เหตุผลสองจุดใน `frontend/src/pages/Plos.js` เขียนไว้ตั้งแต่ #202 ว่าการ์ด
`showing.current === sent` ของ `save` เป็นประโยคที่ไม่มีแถวและไม่มีมัตแตนต์ไปถึง (#97)
**เพราะ** *ยกเลิก* ถูกปิดด้วย `busy` — และเขียนเงื่อนไขหมดอายุของตัวเองไว้ด้วยว่าวันที่ *ยกเลิก*
เลิกถูกปิด จุดนั้นต้องได้สามบรรทัดที่ `confirmRemoval` มีอยู่แล้ว **วันนั้นคือวันนี้** ฉะนั้นการแก้มา
พร้อมการ์ดนั้น ไม่ได้มาลำพัง: `setEditing(null)` การส่งต่อประโยค และ `report(error)` อยู่ใต้
`if (showing.current === sent)` ทั้งสามจุด และเหตุผลที่เขียนไว้ถูกเขียนใหม่ว่าเงื่อนไขของมัน
เกิดขึ้นแล้ว (#54 — บันทึกลงวันกำกับ ไม่ใช่ลบ)

### เงื่อนไขที่ทำให้บันทึกนี้หมดอายุ

- **`finally` ของ `save` ปล่อย `writing` ก่อน `await` ของการอ่านรายการใหม่** — หน้าต่างที่แถวแรก
  เดินคือช่วงที่การอ่านนั้นค้าง ถ้าลำดับนั้นเปลี่ยน แถวแรกจะไม่มีหน้าต่างของตัวเอง
- **ตัวควบคุมที่เปิดฟอร์มได้ `disabled`** — *เพิ่มผลการเรียนรู้* ไม่มี `disabled` เลย ซึ่งเป็นสิ่งที่ทำให้ทางเข้านี้
  ไม่ต้องแข่งกับใคร วันที่มันถูกปิด แถวทั้งสองจะรอสิ่งที่ไม่มีใครจะทำ และตายที่ timeout (#77)
- **ธงของฟอร์มกลายเป็นตัวนับ** — `sending` เป็นบูลีนของการบันทึกครั้งเดียวที่ฟอร์มนี้ส่ง ถ้ามันกลายเป็น
  ตัวนับของหน้า มัตแตนต์ `pagewide` จะกลับไปเป็นโค้ดจริง และข้ออ้างของแถวแรกจะเปลี่ยนความหมาย (#142)
- **ช่องที่แถวอ่านถูกเปลี่ยน attribute** — สองช่องต่อจอถูกเลือกจาก**ที่ยึดของมัตแตนต์** ไม่ใช่จากจอ
  (#121) และสองจอในสี่อ่านช่องตัวเลขด้วย `step` ซึ่งเป็นข้อตั้งของการอ่านนั้น ไม่ใช่ข้ออ้าง (#85, #111)

### สิ่งที่รีวิวของใบนี้จับได้ และวัดแล้ว (29 ต.ค. 2569)

**ข้ออ้างของบันทึกนี้ว่า *การคืนค่าของทั้งเก้าจอของตระกูลนี้คือ `{editing ? <ฟอร์ม/> : <ตาราง/>}`*
เป็นจริงแต่ไม่ครบที่ `Offerings.js`** — จอนั้นมี **กิ่งที่สอง** ที่วาดแทนที่รายการเหมือนกัน คือ
`if (viewing) { return (<div><Notice …/><SectionsPanel …/></div>) }` ซึ่งเอาตาราง ตัวแบ่งหน้าและ
ตัวกรองออกทั้งหมดและยังวาด `<Notice>` อยู่ ส่วนตัวสะท้อนที่ลงไปรู้จักแค่ฟอร์ม
(`formShown.current = Boolean(opening)`) ประโยคที่ผูกไว้กับการอ่านรายการจึงพูดทับแผงตอนเรียนได้
ซึ่งเป็นสปีชีส์เดียวกับใบนี้ · **ทางเข้าคือการแข่งกันหนึ่งทางและไม่มีพี่น้องที่ไม่แข่ง** (#179): กด
*จัดการตอนเรียน* ระหว่างที่การอ่านรายการของการลบยังค้าง ถ้ารอบ `getOffering` ของแผงลงก่อน
การอ่านรายการ `viewing` ถูกตั้งแล้วและ `formShown.current` ยังเป็น `false` · ทางตรงข้ามปิดอยู่แล้ว
เพราะการยกเลิกการเปิดรายวิชาทำ `setViewing(null)` ก่อนส่งประโยคต่อ

**แต่การขยายกลไกให้ครอบกิ่งนั้นไม่ใช่งานของใบนี้ เพราะจอนั้นตัดสินเรื่องนี้ไปแล้วในทางตรงข้าม** —
`save` ของการเปิดรายวิชาใหม่พูดประโยค *ขั้นต่อไปคือเพิ่มตอนเรียน* ที่การอ่านรายการ แล้วทำ
`if (mine) await refresh(offering.id, ask)` ต่อทันที คือเอาแผงมาวาดแทนรายการใต้ประโยคนั้นเอง
โดยเจตนา กฎที่เคยใช้กับจอนี้แล้วคือการตัดสิน ไม่ใช่บรรทัดฐานที่เอามาชั่งน้ำหนัก (#196) และสิ่งที่
คนอ่านเป็นของเจ้าของงาน (`docs/06` §Out of Scope) จึงเป็น
[#250](https://github.com/khthana/Deep-QA/issues/250) พร้อมสามตัวเลือกและราคาของแต่ละข้อ ·
**และสำมะโนมองไม่เห็นเรื่องนี้** เพราะจุดที่พูดของ `Offerings.js` มีครบทั้งสาม part มันจึงรายงาน
`held` นี่เป็นเรื่องความครอบคลุม ไม่ใช่เรื่องการไม่มี (#226) ข้อจำกัดข้อที่เจ็ดใน docblock ของมัน
จึงถูกเขียนไว้พร้อมเลขใบนั้น

**การผูกใหม่ตอนส่งหน้าต่อทิ้ง `held`** — บรรทัด `waiting.current = { of: readOf(lastPage, …),
said: waiting.current.said }` ใน `load` ของเจ็ดจอในตระกูลนี้ จากแปดแฟ้มที่ถือบรรทัดนี้
(`SubjectStudents.js` อีกแฟ้มหนึ่งไม่มี `held` อยู่แล้ว) สร้างประโยคขึ้นใหม่เป็น
`{ of, said }` คือ **ไม่มี `held`** ติดไป · วัดแล้วว่าไม่มีประโยคไหนหาย: ถ้าฟอร์มปิดก่อนการอ่านที่
ถูกส่งต่อลง effect ที่พูดตอนปิดคืนค่าตั้งแต่ `!held?.held` คือไม่พูดและไม่ล้าง ประโยคจึงรอดและ
ถูกพูดโดยการอ่านรอบถัดไป ซึ่งเป็นการอ่านที่วาดรายการ · สถานการณ์นี้ไปถึงได้เฉพาะในหน้าต่าง
เดียวกับที่ `#209` อ่าน คือต้องมีฟอร์มเปิดอยู่ตอนที่หน้าที่เลยปลายถูกส่งต่อ **ไม่มีอะไรถือข้อนี้ไว้**
และเงื่อนไขที่ทำให้มันไปถึงได้โดยไม่ต้องแข่งคือตัวควบคุมที่ย้ายหน้าได้โดยไม่ถูกฟอร์มบัง

**และข้อที่เทียบคีย์ใน effect ที่พูดตอนปิดอ่านค่าของเรนเดอร์ (`page` และตัวกรอง) ขณะที่ตัวจัดการ
ผูกด้วย `onPage.current`** — ไปถึงไม่ได้ด้วยเหตุผลเดียวกับข้อ `of ===` ที่เขียนไว้ข้างบน คือ
ตัวแบ่งหน้าและตัวกรองอยู่ในกิ่งที่ฟอร์มแทนที่ ทั้งเก้าจอ (29 ต.ค. 2569 — ที่ `Offerings.js`
แผงก็แทนที่ทั้งสองอย่างด้วย)

## #247 — ประโยคของแถวที่ตกนอกตัวกรองของตารางเอง (29 ต.ค. 2569)

`PloForm` ปิดช่อง **หลักสูตร** ด้วย `sending || editing` ฉะนั้นตอน *เพิ่ม* ช่องนั้นเปิดอยู่ และ
`draft.program_id` เป็นหลักสูตรอะไรก็ได้ที่สิทธิ์ของคนนั้นถึง — รูปที่ `parentPool` กับความเห็น
ข้าง `nameOf` ตั้งใจรองรับ ส่วน `load` อ่าน `listPlos({ program_id: program })` คือหลักสูตรของ
**ตาราง** อย่างเดียว และตั้งแต่ [#238](https://github.com/khthana/Deep-QA/issues/238)
`save` ฝากประโยคไว้ด้วยกุญแจของการอ่านนั้น ฉะนั้นการอ่านลงจอ กุญแจตรง และประโยค *บันทึกข้อมูลเรียบร้อยแล้ว* ขึ้นเหนือรายการที่ **ไม่มี**
แถวที่เพิ่งบันทึกไป โดยไม่มีอะไรบนจอบอกว่ามันไปอยู่ที่ไหน · นี่ไม่ใช่ข้อถดถอยของ #238 เพราะก่อนใบนั้น
ประโยคนี้ก็ขึ้นเหนือรายการเดิมเหมือนกัน #238 เปลี่ยนว่า **ใคร** พูด และสิ่งที่คนอ่านเป็นของเจ้าของงาน
(`docs/06` §Out of Scope) [#247](https://github.com/khthana/Deep-QA/issues/247)
จึงถูกเปิดเป็นตั๋วชนิดคำถาม

### การวัดก่อนเขียนคำถามให้เจ้าของงาน แก้ประชากรของตั๋ว และเพิ่มตัวเลือกข้อที่ห้า

  ตกนอกตัวกรองของตารางเอง**

### สิ่งที่ใบนี้ไม่ได้พูด

- **ถ้อยคำที่คนอ่าน และตำแหน่งที่มันขึ้นบนจอ ยังเป็นของเจ้าของงาน** (`docs/06` §Out of Scope)
  ประโยคที่ลงคือประโยคที่เจ้าของงานอ่านตอนเลือกข้อ จ และข้อ ค — *ย้ายตารางไปที่หลักสูตรที่บันทึก* —
  ยังเป็นคำถามของเฟสสองได้ ไม่ใช่สิ่งที่ใบนี้ปิด
- **ไม่ได้พูดว่าแถวที่อยู่ในตัวกรองแต่อยู่หน้าอื่นจะว่าอะไร** — *อยู่นอกตัวกรอง* กับ *อยู่หน้าอื่น
  ของตัวกรองเดียวกัน* เป็นสองเรื่อง จอนี้ไม่มีตัวแบ่งหน้าเลย และเรื่องที่สองเป็นของ
  [#209](https://github.com/khthana/Deep-QA/issues/209) กับ [#239](https://github.com/khthana/Deep-QA/issues/239)
- **`%` กับ `_` ในคำค้นของ `Users.js`** ยังอ่านไม่ได้ที่ตะเข็บนี้ เหตุผลพร้อมเงื่อนไขอยู่ข้าง
  `outsideTheFilters` ในโค้ด
- **[#251](https://github.com/khthana/Deep-QA/issues/251) ถูกเปิดแล้วหักล้างในชั่วโมงเดียวกัน** — ข้ออ้างว่าบัญชีที่สร้างแล้วถูกซ่อน

  ฉะนั้นสถานการณ์นั้นสร้างจากจอไม่ได้ และไม่มีที่บนจอให้พูด (#232 — คำถามของเจ้าของงานเป็นโมฆะถ้า
  คำตอบข้อหนึ่งชี้ไปที่สถานะที่ระบบรับไม่ได้) · การวัดถูกเขียนไว้ในคอมเมนต์ของใบนั้นและใน
  `Users.js`
