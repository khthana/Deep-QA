## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ข้อมูลหลัก → ข้อมูลภาควิชา* (`/main/departments`)

seed มีภาควิชาสองรายการ และ **ทั้งสองมีข้อมูลอ้างอิงอยู่** — `05` มีหลักสูตร 0501/0503 กับรายวิชา
และ `01` มีบัญชี `dept.admin.01@` อยู่ ภาควิชาที่จะลบได้จึงต้องสร้างเองในข้อ 1

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`npm run seed` ใหม่หลังเดินจบ** ก่อนเริ่มตั๋วถัดไป

## รายการที่ต้องเดิน

ช่องสุดท้ายมีสามค่า

- **☑** เดินจบแล้ว
- **☐** ยังไม่ได้เดิน
- **⚙** ครอบคลุมด้วย browser seam แล้ว (#65) ไม่ต้องเดินด้วยมือซ้ำ แถวบอกไฟล์ที่ครอบคลุมไว้ ถ้าแถวนั้นพูดถึงสิ่งที่วาดด้วย (เมนู ถ้อยคำ สี) ครึ่งนั้นยังเป็นงานของคนเดิน และแถวจะเขียนกำกับไว้

ข้อ 8 ที่เปิด `http://localhost:3000/api/departments` ตรง ๆ ยังเป็น ☐ โดยตั้งใจ — มันเป็นข้อความที่ seam ของ backend พิสูจน์ไว้ครบทั้งเจ็ด endpoint ใน `departments.test.js` อยู่แล้ว การเขียน spec ที่ยิง API ตรง ๆ จาก Playwright จะเป็นสำเนาของการทดสอบที่มีอยู่ ไม่ใช่การพิสูจน์สิ่งใหม่

**ข้อบกพร่องที่ browser seam จับได้ตอนเขียนแถวไฟล์ว่าง (ข้อ 7)** — server ตอบ 400 พร้อม `errors: []` และ `ImportPanel` ถามว่า `error.details` มีไหม ซึ่ง array ว่างเป็น truthy หน้าจอจึงขึ้นหัวข้อ *ไม่ได้บันทึกรายการใด...* คร่อมตารางเปล่า และกลืนข้อความ *ไม่พบข้อมูลในไฟล์ที่นำเข้า* ทิ้ง แก้แล้วที่ `error.details?.length` ซึ่งมีผลกับทุกหน้าจอที่ใช้กล่องนำเข้านี้

## การเดินด้วยมือ — 21 ส.ค. 2569

ยี่สิบแถวเดินรวดเดียวโดยคนที่นั่งอยู่หน้าจอ ไม่ใช่โดยตัวขับอัตโนมัติ เรียงใหม่เป็นเจ็ดช่วงให้สถานะ
ไหลต่อกันโดยไม่ต้องย้อน — สร้าง `07` แล้วใช้มันเป็นตัวทดสอบการลบ ใช้ `05` ที่ลบไม่ได้เป็นตัวทดสอบ
ทางออกคือปิดการใช้งาน แล้วค่อยไล่บัญชีจากผู้ดูแลคณะไปผู้ดูแลภาควิชาไป Central Admin
ฐานข้อมูลถูก `reset` + `migrate` + `seed` ก่อนเริ่มและหลังจบ เพราะช่วง A–D เขียนของจริงลงทะเบียน

สามแถวที่ให้ผลมากที่สุด

- **ข้อ 3 (ลบภาควิชาที่มีคนอ้างอิงอยู่)** ตอบเป็นคำที่บอกทางออก ไม่ใช่ *เกิดข้อผิดพลาดในระบบ*
  และ `dept.admin.05@` ยังเข้าใช้งานได้ตามปกติขณะที่ภาควิชาถูกปิดอยู่ — การปิดใช้งานเป็นการแก้ข้อมูล
  ไม่ใช่การถอน grant ของคนเงียบ ๆ ซึ่งเป็นสองอย่างที่ระบบมักทำปนกัน
- **ข้อ 6 กับข้อ 8 อ่านคู่กัน** — แบบฟอร์มไม่มีคอลัมน์คณะให้กรอกเลย แต่ทุกแถวที่นำเข้ามี
  `faculty_id` เป็น `ENG` และเมื่อยิง `POST /api/departments` ตรง ๆ พร้อม `faculty_id: 'SCI'`
  ก็ได้ 403 และไม่มี `Z1` เกิดขึ้น ด้านหนึ่งคือไม่มีช่องให้ปลอม อีกด้านคือปลอมมาก็ไม่รับ (ADR-0002)
- **ข้อ 9 (หน้าผู้ใช้งานยังนำเข้าได้เหมือนเดิม)** อัปโหลดแบบฟอร์มซ้ำสองครั้ง ครั้งแรกได้
  *นำเข้าสำเร็จ 1 รายการ* ครั้งที่สองได้กล่องแดง *ไม่ได้บันทึกรายการใด กรุณาแก้ไขแถวต่อไปนี้
  แล้วอัปโหลดใหม่* พร้อมตารางบรรทัด/สาเหตุ — บรรทัดที่ 2 *รหัสผู้ใช้นี้ถูกใช้งานแล้ว* หน้าตา
  เหมือนของหน้าภาควิชาทุกอย่าง ซึ่งคือสิ่งที่แถวนี้ถาม การรวมโค้ดใน #14 ไม่ได้ทำหน้าที่ส่งมอบไปแล้วพัง

ข้อบกพร่องที่การเดินด้วยมือเปิดออกมาคือ [#91](https://github.com/khthana/Deep-QA/issues/91)
ซึ่งเขียนไว้เป็นข้อ 9 ของ *สิ่งที่ยังไม่ปิดใน #14* ข้างล่าง และ
[#92](https://github.com/khthana/Deep-QA/issues/92) ที่เจอระหว่างทางแต่เป็นของหน้าจอ #10
ไม่ใช่ของเอกสารนี้ — กล่อง *Session หมดอายุ* ที่กดปุ่มแล้วออกไม่ได้ ทั้งสองอยู่ในชั้นที่ browser seam
ไม่ครอบคลุมและการอ่านโค้ดไม่เจอ เพราะโค้ดไม่ได้เขียนผิด มันแค่ไม่มีบรรทัดที่ควรจะมี

ข้อ 8 แถว *ผู้ดูแลคณะเห็นเฉพาะภาควิชาของคณะตัวเอง* เดินได้เท่าที่ข้อมูลให้ — seed มีคณะเดียว
จึงเห็นทั้งหมดอยู่แล้ว แถวนี้จะแยกได้จริงเมื่อมีคณะที่สอง และไม่ควรอ่านว่าพิสูจน์ขอบเขตแล้ว

## แถบแจ้งผลที่ค้างอยู่ — #91 ปิดเมื่อ 22 ส.ค. 2569

ข้อบกพร่องที่การเดินด้วยมือของข้อ 1 เปิดออกมา แถบแจ้งผลถูกเขียนทับอย่างเดียว ไม่เคยถูกล้าง จึงค้างอยู่ข้ามการกระทำที่ไม่เกี่ยวกับมัน — แถบแดงยังอยู่หลังกด *ยกเลิก* ฟอร์มที่ทำให้มันขึ้น และคำว่า *บันทึกข้อมูลเรียบร้อยแล้ว* ลอยอยู่เหนือฟอร์มเปล่าที่ยังไม่ได้บันทึกอะไร

ที่แก้คือทุกจุดที่ **การกระทำใหม่เริ่มต้น** ล้างแถบทิ้ง คือเปิดฟอร์ม ยกเลิกฟอร์ม กดลบเพื่อเปิดกล่องยืนยัน และปิดกล่องยืนยัน ส่วนจุดที่ **การกระทำจบลง** ไม่แตะ เพราะ `save` กับ `confirmRemoval` ตั้งแถบที่เป็นคำตอบของสิ่งที่เพิ่งเกิด ความต่างข้อนี้คือเหตุผลที่มันเป็นการแก้ทีละบรรทัดในหกหน้าจอ ไม่ใช่ helper ตัวเดียว — `setEditing(null)` แปลว่า *ยกเลิก* ที่หนึ่ง และแปลว่า *บันทึกแล้วปิดฟอร์ม* อีกที่หนึ่ง helper ที่ล้างทั้งสองที่จะลบแถบสำเร็จทิ้งทันทีที่เพิ่งตั้งมันขึ้นมา

#91 เขียนไว้ว่านี่เป็นแถวชั้นหน้าตาที่ browser seam ไม่ครอบคลุม **ซึ่งไม่ใช่** การถามว่าอิลิเมนต์หนึ่งยังอยู่บนหน้าจอไหมหลังการคลิก เป็นพฤติกรรม ไม่ใช่หน้าตา สิ่งที่เป็นหน้าตาจริง ๆ คือแถบเป็นสีแดงหรือเขียว และถ้อยคำถูกหรือไม่ ซึ่งสเปกไม่ได้ยึดไว้เลย `e2e/tests/14c-departments-notice.spec.js` จึงยึดสองทางที่การเดินด้วยมือเจอจริง บนหน้าจอที่เจอมัน

มีกรณีหนึ่งที่เสียของไปจริงและรับไว้โดยรู้ตัว การลบภาควิชาที่มีอะไรอ้างอิงอยู่ถูกปฏิเสธ พร้อมถ้อยคำที่บอกทางออกว่าให้ปิดใช้งานแทน และการคลิกที่ทำตามคำแนะนำนั้นคือปุ่ม *แก้ไข* ซึ่งตอนนี้ล้างประโยคที่ให้คำแนะนำไปด้วย ที่ยอมเสียเพราะทางเลือกอีกทางแย่กว่า — แถบแดงที่บอกว่าลบภาควิชาหนึ่งไม่ได้ ค้างอยู่เหนือฟอร์มของอีกภาควิชาหนึ่ง ซึ่งคือ #91 ทั้งดุ้น ถ้าภายหลังพบว่าคนต้องการถ้อยคำนั้นระหว่างอยู่ในฟอร์ม ที่ของมันคือ*ในฟอร์ม* ไม่ใช่แถบที่อยู่ยืนยาวกว่าฟอร์ม

| มัตแตนต์ | ยึดอะไรไว้ |
|---|---|
| `91:keepcancelled` | เอา `setNotice(null)` ออกจาก `onCancel` ของฟอร์ม — แถว *a refusal does not outlive the form that caused it* ของ `14c` ตาย อีกสองแถวยังผ่าน |
| `91:keepsaved` | เอา `setNotice(null)` ออกจากปุ่ม *เพิ่มภาควิชา* — แถว *a success does not outlive the action it reports* ตาย อีกสองแถวยังผ่าน |
| `91:keepbeforeupload` | ปิด `onStart?.()` ใน `ImportPanel.js` — แถว *an upload clears the banner from whatever came before it* ตาย อีกสองแถวยังผ่าน |

การรีวิวโค้ดหลังแก้เสร็จเจอจุดที่การแก้รอบแรกเดินข้ามไป คือ **การอัปโหลดไฟล์** `ImportPanel` เป็นที่เดียวที่การกระทำใหม่เริ่มได้โดยไม่แตะฟอร์มและไม่แตะกล่องยืนยัน จึงไม่มี `setNotice(null)` ที่ไหนมาถึงมัน แถบจากการกระทำก่อนหน้าจึงยังลอยอยู่เหนือผลการนำเข้า แก้ด้วย prop ใหม่ `onStart` ที่หน้าจอทั้งหกส่งเข้าไป — แก้ที่ component เดียว ครอบทั้งหกหน้าจอ

แถวที่สามของ `14c` ฉบับแรกเป็น **assertion ที่ฆ่าไม่ได้** และมัตแตนต์เป็นคนจับได้ ฉบับแรกอัปโหลดไฟล์ที่มีแต่หัวตาราง ซึ่งถูกปฏิเสธโดยไม่มีรายงานรายบรรทัด คำปฏิเสธนั้นจึงกลายเป็นแถบของหน้าจอเองและ*เขียนทับ*แถบเดิมอยู่แล้ว ไม่ว่าจะมีอะไรมาล้างหรือไม่ ฉบับที่แก้แล้วใช้ไฟล์ที่ถูกปฏิเสธ*พร้อมรายงานรายบรรทัด* ซึ่ง `ImportPanel` วาดตารางของตัวเอง และไม่แตะแถบของหน้าจอเลย คำถามจึงเป็นคำถามจริง — บทเรียนเดียวกับ #64 คนละสัปดาห์

อีกห้าหน้าจอที่ #91 ระบุไว้ (`Users`, `Programs`, `ProgramSubjects`, `Subjects`, `Students`) ได้การแก้ชุดเดียวกันบรรทัดต่อบรรทัด แต่ไม่มีสเปกของตัวเอง หน้าภาควิชาเป็นที่ที่กติกาถูกพิสูจน์ ส่วนอีกห้าหน้าเป็นการกระจายกฎเดิม จึงยืนยันด้วยตา

### การเดินด้วยมือของห้าหน้าจอที่เหลือ — 22 ส.ค. 2569

เดินโดยคนที่นั่งอยู่หน้าจอ ไม่ใช่โดยตัวขับอัตโนมัติ ฐานข้อมูลถูก `reset` + `migrate` + `seed` ก่อนเริ่ม ทุกหน้าเดินรูปแบบเดียวกัน — ทำให้เกิดแถบแดงแล้วกด *ยกเลิก* ทำให้เกิดแถบเขียวแล้วเปิดฟอร์มใหม่ ทำให้เกิดแถบเขียวแล้วอัปโหลดไฟล์ และ (เฉพาะหน้าที่มีปุ่มลบ) ทำให้เกิดแถบเขียวแล้วกด *ลบ* เพื่อดูว่าแถบหายตั้งแต่ตอนกล่องยืนยันเปิด ไม่ใช่ตอนลบสำเร็จ **ทั้งห้าหน้ารายงานกลับมาว่าตรงกับที่ช่อง *ต้องเห็นอะไร* เขียนไว้ทุกข้อ ไม่พบข้อบกพร่องใหม่**

| หน้าจอ | บัญชีที่ใช้เดิน | ข้อที่เดิน |
|---|---|---|
| ข้อมูลผู้ใช้งาน | `admin@` | 1, 2, 3 — ไม่มีปุ่มลบ |
| ข้อมูลหลักสูตร | `faculty.admin@` | 1, 2, 3, 4 |
| ข้อมูลรายวิชา | `dept.admin.05@` | 1, 2, 3, 4 |
| รายวิชาในหลักสูตร | `dept.admin.05@` | 1, 2, 3, 4 |
| ข้อมูลนักศึกษากลาง | `dept.admin.05@` | 1, 2, 3 — ไม่มีปุ่มแก้ไขและไม่มีปุ่มลบ |

ข้อที่ 3 ของทุกหน้าใช้ไฟล์ที่ถูกปฏิเสธ**พร้อมรายงานรายบรรทัด** โดยตั้งใจ ไฟล์ที่ถูกปฏิเสธแบบไม่มีรายงาน — ไฟล์เปล่า — จะกลายเป็นแถบของหน้าจอเองและเขียนทับแถบเดิมอยู่แล้ว ทำให้แยกไม่ออกว่าอะไรล้างอะไร เป็นกับดักเดียวกับที่มัตแตนต์จับได้ตอนเขียน `14c` ฉบับแรก ใบเดินงานจึงแจกไฟล์ที่มีแถวซ้ำกับ seed ไปให้ทั้งห้าหน้า ซึ่งแปลว่าการเดินทั้งรอบไม่ได้เขียนอะไรลงฐาน ยกเว้นนักศึกษาสองคนที่หน้า *ข้อมูลนักศึกษากลาง* จำเป็นต้องเพิ่มจริงเพื่อให้ได้แถบเขียว เพราะหน้านั้นไม่มีปุ่มแก้ไข — seed ใหม่หลังเดินจบแล้ว

## ตัวเลขที่ถูกลบออกจาก `14b` — 22 ส.ค. 2569

`14b` เคยอ่านจำนวนแถวหลังอัปโหลดไฟล์เปล่าไว้หนึ่งจุด ไฟล์ที่ไม่มีแถวไม่มีอะไรให้เขียน จึงไม่มีมัตแตนต์ตัวใดทำให้ตัวเลขนั้นขยับได้ มันจึงผ่านเสมอไม่ว่าโค้ดจะเป็นอย่างไร และถูกลบทิ้ง สิ่งที่แถวนี้พิสูจน์จริงคือถ้อยคำปฏิเสธ กับการที่แถบ *นำเข้าสำเร็จ* ไม่ขึ้นมา

ข้ออ้างว่า *การนำเข้าที่ถูกปฏิเสธไม่เขียนอะไรเลย* พิสูจน์ที่บรรทัด 124 ของไฟล์เดียวกัน ซึ่ง `reload` แล้วเปิดรายการใหม่ก่อนอ่าน มัตแตนต์ `11-12:M9` เปลี่ยน `ROLLBACK` เป็น `COMMIT` ใน `backend/lib/importer.js` ฆ่าบรรทัดนั้นได้จริง (ได้ 7 ที่ควรเป็น 6) และเป็นแถวแรกที่ล้มในไฟล์ ไม่ใช่แถวที่อยู่ก่อนหน้า ไฟล์นี้เป็น `mode: 'serial'` แถวถัดจากนั้นจึงถูกข้าม รายละเอียดทั้งหมดอยู่ใน [#64](https://github.com/khthana/Deep-QA/issues/64) และในหัวข้อ *Reading a number off the screen* ของ `e2e/README.md`

## ไฟล์ผิดกล่อง — #56 ปิดเมื่อ 22 ส.ค. 2569

ข้อบกพร่องที่โผล่ระหว่างเดินใบตรวจรับของ #15 ด้วยมือ ไฟล์หลักสูตรถูกอัปโหลดเข้ากล่องนำเข้าของหน้า **ข้อมูลภาควิชา** และคำตอบที่ได้คือรายงานรายบรรทัด บอกว่าบรรทัดที่ 2 ถึงบรรทัดสุดท้าย *ข้อมูลภาควิชาไม่ครบถ้วนหรือไม่ถูกต้อง* ทั้งที่ข้อมูลในไฟล์นั้นถูกต้องทุกแถว สิ่งที่ผิดคือกล่อง ไม่ใช่ข้อมูล และต้องเปิดฐานข้อมูลดูจึงจะรู้

ทุกแถวล้มด้วยเหตุผลเดียวกันแปลว่าไฟล์ผิดรูป ไม่ใช่ข้อมูลผิด และ `backend/lib/importer.js` เป็นที่เดียวที่มองเห็นข้อนี้ได้ เพราะมันถือทั้งแถวและผลของทุกแถวไว้พร้อมกัน `parseTable` คืน `headers` มาให้อยู่แล้วตั้งแต่ #14 แต่ `importRows` ทิ้งไป ตอนนี้รับไว้และถามก่อนอ่านแถวใด ๆ ว่าหัวคอลัมน์มีคอลัมน์ที่ตัวอ่านของหน้านั้นขาดไม่ได้ครบหรือไม่ ถ้าไม่ครบ ตอบ `{ ok: false, wrongTemplate: true }` และ `sendImport` แปลเป็นถ้อยคำ **หัวคอลัมน์ในไฟล์ไม่ตรงกับแบบฟอร์มของหน้านี้ — ตรวจว่าดาวน์โหลดแบบฟอร์มมาจากหน้าถูกหรือไม่** พร้อม `errors: []`

### ทำไมไม่เทียบกับ `IMPORT_COLUMNS` ทั้งชุด

ตั๋วเขียนว่าให้เทียบหัวคอลัมน์กับ *คอลัมน์ที่แบบฟอร์มประกาศไว้* ซึ่งอ่านตรงตัวคือ `IMPORT_COLUMNS` แต่ทำอย่างนั้นแล้วจะชนกับการตัดสินใจที่ `backend/lib/csv.js` เขียนไว้ตั้งแต่ #14 ว่า *หัวคอลัมน์ที่ระบบไม่รู้จักให้เก็บไว้ ไม่ใช่ปฏิเสธ ไฟล์ที่ส่งออกมาจากที่อื่นย่อมมีคอลัมน์ที่ระบบนี้ไม่ได้ใช้ และการปฏิเสธเพราะเหตุนั้นจะทำให้มีแต่แบบฟอร์มของระบบเท่านั้นที่นำเข้าได้* การเทียบทั้งชุดยังปฏิเสธไฟล์ที่ลบคอลัมน์**ที่ไม่บังคับ**ออก เช่นชื่อภาษาอังกฤษของภาควิชาหรือของหลักสูตร ซึ่งนำเข้าได้อยู่แล้วก่อนตั๋วนี้ — เป็นการถอยหลังที่ตั๋วไม่ได้ขอ

สิ่งที่ตัวเลือกนี้เทียบจึงเป็น `required` คือคอลัมน์ที่ `readRow` ของหน้านั้นปฏิเสธแถวเพราะไม่มี ซึ่งเป็นสับเซตของ `IMPORT_COLUMNS` ทุกหน้า และเป็นพารามิเตอร์ใหม่ที่ทั้งหกกล่องส่งเข้าไป

| หน้าจอ | `required` | ที่มา |
|---|---|---|
| ข้อมูลผู้ใช้งาน | `user_id`, `email` | ชื่อจะเป็นไทยหรืออังกฤษก็ได้ หัวคอลัมน์พูดว่า "อย่างใดอย่างหนึ่ง" ไม่ได้ |
| ข้อมูลภาควิชา | `department_id`, `department_name_th` | ชื่ออังกฤษไม่บังคับ |
| ข้อมูลหลักสูตร | `program_id`, `program_name_th`, `department_id` | |
| รายวิชาในหลักสูตร | `program_id`, `subject_id`, `subject_type` | ทั้งสามตัว `readPairing` ปฏิเสธแถวเพราะขาดตัวใดตัวหนึ่ง |
| ข้อมูลนักศึกษากลาง | `student_id`, `first_name_th`, `last_name_th`, `program_id` | `admission_year` คำนวณจากรหัส ไม่ได้อ่านจากไฟล์ |
| ข้อมูลรายวิชา | `subject_id`, `subject_name_th`, `subject_name_en`, `credits`, `department_id` | คำอธิบายสองคอลัมน์ไม่บังคับ แต่ชื่ออังกฤษ **บังคับ** เพราะ `readSubject` ปฏิเสธแถวที่ขาดไป ต่างจากภาควิชาและหลักสูตรที่ชื่ออังกฤษไม่บังคับ อย่าไปตัดออกเพราะเห็นว่าไม่เหมือนกัน |

`department_id` เป็นคอลัมน์ที่แบบฟอร์มของภาควิชาและของหลักสูตรมีเหมือนกัน กฎแบบ "ไม่มีคอลัมน์ไหนตรงกันเลย" จึงจับกรณีที่ตั๋วรายงานมาไม่ได้ — สิ่งที่จับได้คือ `department_name_th` ที่ไฟล์หลักสูตรไม่มี

### ลำดับกับไฟล์เปล่า

การตรวจหัวคอลัมน์ถูกถาม**หลัง**การตรวจไฟล์เปล่า ไฟล์ที่ไม่มีอะไรเลยก็ไม่มีหัวคอลัมน์เหมือนกัน ถ้าตรวจหัวก่อน คนที่อัปโหลดไฟล์เปล่าจะถูกบอกให้ไปดาวน์โหลดแบบฟอร์มใหม่ ทั้งที่แบบฟอร์มของเขาถูกอยู่แล้ว ก่อนตั๋วนี้ไม่มีชุดทดสอบไหนยึดลำดับนี้ไว้ — ชุดทดสอบเดิมอัปโหลด `csvOf([])` ซึ่งมีบรรทัดหัวอยู่ #56 จึงเพิ่มแถวที่อัปโหลด body เปล่าจริง ๆ เพื่อให้มัตแตนต์ `firstcheck` มีอะไรให้ฆ่า

### สิ่งที่ประโยคนี้เดาแทนคนอ่าน

ถ้อยคำที่ใช้ยกมาจากตั๋วตรงตัว และครึ่งหลังของมัน — *ตรวจว่าดาวน์โหลดแบบฟอร์มมาจากหน้าถูกหรือไม่* — ระบุ**สาเหตุ** ที่เซิร์ฟเวอร์แยกไม่ออกจริง สิ่งที่เซิร์ฟเวอร์รู้คือหัวคอลัมน์ขาดคอลัมน์ที่ตัวอ่านต้องใช้ ซึ่งเกิดได้อย่างน้อยสามทาง คือเอาไฟล์ของหน้าอื่นมาลง (กรณีที่ตั๋วรายงาน) เอาแบบฟอร์มที่ถูกมาแล้วลบคอลัมน์บังคับทิ้ง หรือหัวคอลัมน์มีอักขระที่มองไม่เห็นติดอยู่ — `.trim()` ตัดช่องว่างรวมทั้ง NBSP ออกให้ แต่ zero-width space (U+200B) ไม่ใช่ช่องว่างจึงรอด และคอลัมน์นั้นจะกลายเป็นชื่ออื่นทันที

สองกรณีหลังจะได้คำแนะนำที่ไม่ตรงกับสิ่งที่เขาทำ เขาดาวน์โหลดมาจากหน้าถูกแล้ว เก็บถ้อยคำนี้ไว้ตามตั๋วด้วยสองเหตุผล หนึ่งคือทางแก้ที่ประโยคบอกใช้ได้กับทั้งสามกรณี ดาวน์โหลดแบบฟอร์มของหน้านี้มาใหม่แล้วกรอกลงไปทำให้ทุกกรณีจบ สองคือก่อนตั๋วนี้ทั้งสามกรณีได้รายงานรายบรรทัดที่บอกว่าข้อมูลเสีย ซึ่งชี้ผิดหนักกว่า

ถ้ากรณีที่สองหรือสามโผล่ขึ้นมาในการเดินด้วยมือจริง สิ่งที่ต้องกลับมาแก้คือประโยคนี้ประโยคเดียว อยู่ที่ `REFUSALS.importWrongTemplate` ที่เดียว ทั้งหกกล่องใช้ร่วมกัน

| `56:strict` | เปลี่ยน `required` ของภาควิชาเป็น `IMPORT_COLUMNS` ทั้งชุด คือทางเลือกที่ปฏิเสธไป — ฆ่าแถวที่อัปโหลดไฟล์ซึ่งมีคอลัมน์แปลกปลอมและไม่มีชื่ออังกฤษ แถวไฟล์ผิดกล่องยังผ่าน แถวที่ตายเป็นแถวที่ #56 เขียนขึ้นเองพร้อมกับมัตแตนต์ตัวนี้ ไม่ใช่แถวเก่า — ก่อนตั๋วนี้ไม่มีชุดทดสอบไหนอัปโหลดไฟล์ที่ขาดคอลัมน์ไม่บังคับเลย (แถวที่ 6 ของ `14b` มีคอลัมน์ชื่ออังกฤษอยู่ในหัว เพียงแต่เว้นค่าว่างไว้ `strict` จึงไม่ฆ่ามัน) สิ่งที่มัตแตนต์ตัวนี้พิสูจน์จึงเป็นว่าแถวใหม่แถวนั้นมองเห็นความต่างระหว่างสองกฎจริง ไม่ใช่ว่ากฎที่เลือกไม่ได้ถูกเฝ้าอยู่ก่อนแล้ว ถ้าไปใช้กฎเข้มโดยไม่มีแถวนี้ มันจะเป็นการถอยหลังแบบเงียบ ๆ |

แถว `#56` ใน `14b` ไม่ได้ยึดแค่ถ้อยคำ แต่ยึดว่า**ไม่มีตารางรายงาน**อยู่บนหน้าจอ และจำนวนแถวในตารางไม่ขยับ ตัว `ImportPanel` ไม่ต้องแก้อะไรเลย เพราะมันส่งคำปฏิเสธที่ไม่มี `details` ต่อให้แถบของหน้าจอเองอยู่แล้ว — พฤติกรรมที่ #14 ข้อ 7 วางไว้และ #91 ยึดไว้

### ที่ครอบไปถึง

ตั๋วเขียนว่า "กล่องนำเข้าทั้งสามกล่อง" ซึ่งเป็นจำนวนตอนที่เปิดตั๋ว ตอนนี้มีหกกล่อง และการแก้อยู่ใน `lib/importer` จึงถึงทั้งหก แต่ละ route ต้องส่ง `required` ของตัวเองเข้าไป กล่องที่ลืมส่งจะเงียบ ๆ ไม่มีการตรวจ — ทั้งหกส่งครบแล้ว ตรวจได้ด้วย `grep -n "required:" backend/routes/*.js`

ที่ยึดไว้ด้วยชุดทดสอบจริงมีสองหน้า คือ **ข้อมูลภาควิชา** กับ **ข้อมูลหลักสูตร** ซึ่งเป็นคู่ที่ตั๋วรายงานมาและเป็นคู่ที่แชร์คอลัมน์กัน อีกสี่หน้าได้กฎเดียวกันจาก `lib/importer` ตัวเดียวกัน และ `required` ของแต่ละหน้าอ่านมาจาก `readRow` ของหน้านั้นตรง ๆ

## สิ่งที่ยังไม่ปิดใน #14

1. **ยังไม่มีหน้าจอจัดการคณะ** — ภาควิชาผูกกับคณะจาก grant ที่สวมอยู่ จึงไม่ต้องมีช่องให้เลือก
   แต่ตัวคณะเองยังไม่มีหน้าจอสร้าง/แก้ไข (seed ใส่ `ENG` มาให้ตายตัว) ถ้าจะทำ ต้องเปิดตั๋วใหม่
   และตั๋วนั้นจะเป็นของใครต้องตัดสินก่อน เพราะไม่มีบทบาทใดใน CONTEXT.md ที่ระบุว่าดูแลคณะ

2. **การเพิ่ม/แก้/ลบภาควิชายังไม่ถูกบันทึกลง `user_log`** — ตั๋วนี้ไม่ได้ขอ และการบันทึกต้องเพิ่ม
   activity code สามตัว กับ `target_kind = 'DEPARTMENT'` และป้ายภาษาไทยในหน้าประวัติ ไม่งั้นหน้าจอ
   จะแสดงรหัสดิบ ควรเปิดตั๋วเดียวสำหรับ "บันทึกการแก้ไขข้อมูลหลักทุกหน้า" มากกว่าทำทีละหน้า
3. **`<Pager>` ยังไม่ถูกแยกเป็นคอมโพเนนต์** — #13 ตั้งเงื่อนไขไว้ว่าจะแยกเมื่อมีหน้าจอที่สี่
   ตอนนี้ครบแล้ว (Users, HistoryPanel, ActivityPanel, Departments) แต่การแยกต้องแก้หน้าจอที่ส่งมอบ
   ไปแล้วสามหน้า ซึ่งมี `react-scripts build` เป็นตาข่ายอย่างเดียว — build ที่ผ่านไม่ได้บอกว่าปุ่มยัง
   เปลี่ยนหน้าได้ จึงควรเป็น commit ของตัวเองที่เดิน checklist ของทั้งสามหน้าใหม่ ไม่ใช่พ่วงมากับตั๋วนี้
4. **ลบภาควิชาถามฐานข้อมูลแทนที่จะนับล่วงหน้า** — หน้าจอบอกได้แค่ว่า "ถ้ามีข้อมูลอ้างอิงจะลบไม่ได้"
   ไม่ได้บอกว่ามีอะไรอ้างอิงอยู่บ้างและกี่รายการ ทำแบบนั้นได้ด้วยการนับ `programs`/`users`/`subjects`/`student`
   ก่อนลบ แต่รายการที่เขียนด้วยมือจะล้าสมัยทันทีที่มีตารางที่ห้า และคำตอบจะกลายเป็น 500 เงียบ ๆ
   ตอนนี้จึงปล่อยให้ 23503 เป็นคนตัดสิน ซึ่งครบถ้วนโดยโครงสร้าง ถ้าอยากได้ข้อความละเอียดกว่านี้ต้องเปิดตั๋ว
5. **ไม่มีตัวกรองหรือช่องค้นหาบนหน้านี้** — เกณฑ์ข้อ 4 ขอแค่การแบ่งหน้า และคณะหนึ่งมีภาควิชาไม่กี่สิบ
   รายการ ถ้าภายหลังมีหลายคณะจนหายาก ค่อยเปิดตั๋ว
6. **การนำเข้ายังเป็น CSV ไม่ใช่ `.xlsx`** — ด้วยเหตุผลเดียวกับ #11 ข้อ 1 (`xlsx@0.18.5`
   มีช่องโหว่ที่ยังไม่มี patch) และตอนนี้เป็นการตัดสินใจของ `lib/importer` ที่เดียวสำหรับทุกหน้าจอ
7. **เหตุผลของแถวที่ผิดยังหยาบไป** — `readDepartment` ตอบ *ข้อมูลภาควิชาไม่ครบถ้วนหรือไม่ถูกต้อง*
   เหมือนกันหมดสำหรับสี่กรณีที่ต่างกัน (ไม่มีรหัส, ไม่มีชื่อไทย, รหัสยาวเกิน, ชื่อยาวเกิน) ทั้งที่แถวซ้ำ
   บอกได้ถึงขั้นว่าซ้ำกับบรรทัดไหน เกณฑ์ข้อ 7 ขอ "เหตุผล" ซึ่งข้อความนี้ก็เป็นเหตุผล แต่ถ้าจะให้
   แก้ไฟล์ได้โดยไม่ต้องเดา ควรแยกเป็นสี่ข้อความ — เป็นตั๋วของ `lib/importer` ร่วมกับทุกหน้าจอ
8. **บล็อกตอบกลับของการนำเข้าซ้ำกันระหว่าง `routes/users.js` กับ `routes/departments.js`** —
   แปดบรรทัดที่แปลง `{ empty }` / `{ errors }` เป็น 400 นั้นเหมือนกันทุกตัวอักษร ต่างแค่ชื่อคีย์ของ
   ผลสำเร็จ `lib/importer` จงใจไม่รับหน้าที่นี้เพราะ body ของแต่ละหน้าจอไม่เหมือนกัน แต่พอถึงหน้าจอ
   ที่สามหรือสี่ควรทบทวนว่าจะย้ายเข้าไปเป็น helper ตัวเล็ก ๆ ที่รับชื่อคีย์เป็นพารามิเตอร์หรือไม่
   — **ปิดแล้วใน #59** หน้าจอที่สี่ (`subjects`) มาถึงจริง และ `sendImport` ใน `lib/importer`
   รับชื่อคีย์เป็นพารามิเตอร์เดียวตามที่คาดไว้ ไม่ต้องเดินด้วยมือซ้ำ เพราะสามสาขาของบล็อกนี้
   (ว่าง / มีแถวผิด / สำเร็จ) ถูก assert ไว้ครบทั้งสี่ route ในชุดทดสอบ backend อยู่แล้ว
9. **แถบแจ้งผลไม่ถูกล้างเมื่อผู้ใช้เริ่มการกระทำใหม่** — เจอตอนเดินข้อ 1 ด้วยมือ (21 ส.ค. 2569)
   ปฏิเสธเพราะรหัสซ้ำแล้วกด *ยกเลิก* แถบแดงยังอยู่ และบันทึกสำเร็จแล้วกด *เพิ่มภาควิชา* ใหม่
   แถบเขียว *บันทึกข้อมูลเรียบร้อยแล้ว* ยังลอยอยู่เหนือฟอร์มที่ยังไม่ได้บันทึกอะไร `notice` ใน
   `frontend/src/pages/Departments.js` ถูกเขียนทับด้วยข้อความถัดไปเท่านั้น ไม่เคยถูกล้าง และหน้าจอ
   อีกห้าหน้าที่ใช้รูปแบบเดียวกันก็เหมือนกันหมด — เปิดเป็น
   [#91](https://github.com/khthana/Deep-QA/issues/91) แล้ว เป็นแถวชั้นหน้าตาที่ browser seam
   ไม่ครอบคลุม และห้าแถวของข้อ 1 เดินผ่านได้ทั้งที่ข้อบกพร่องนี้อยู่ตรงนั้น เพราะไม่มีแถวไหน
   พูดถึงสิ่งที่แถบทำ *หลังจาก* การกระทำจบลง

## บันทึกที่กดซ้ำได้ระหว่างที่การเขียนยังไม่กลับ — #142 (19 ก.ย. 2569)

`frontend/src/pages/Departments.js` เคยมีธง `busy` ตัวเดียว ทั้งการอ่านแถวของ *แก้ไข* และการเขียน (บันทึก ลบ)
ถือมันไว้ และ `finally` ของการอ่านปลดมันเสมอ ไม่ว่าหลังจากนั้นจะมีการเขียนหยิบธงไปแล้วหรือไม่ การอ่านที่
มาถึงช้าจึงคืนปุ่ม *บันทึก* ให้ระหว่างที่การเขียนยังไม่กลับ ตอนนี้การเขียนถือ `writing` การอ่านถือ `reading`
และปุ่มกับกล่องยืนยันปิดด้วย `writing || reading` การอ่านยังปลดธงของตัวเองเสมอเหมือนที่เคยปลด
ธงตัวเดียว สิ่งเดียวที่เปลี่ยนคือมันไม่ได้ปลด `writing` — JSX ไม่ได้เปลี่ยน เหตุผลอยู่บน
`frontend/src/pages/Departments.js`

วัดก่อนแก้บนข้อมูลภาควิชาที่ `8bb9a92` ลำดับของตั๋ว (อ่าน อ่านอีกแถว บันทึก) แดงตามที่ตั๋วบอก
ส่วน *อ่านแล้วลบ* กับ *บันทึกแล้วลบ* ไม่ใช่ทางเข้า กล่องยืนยันเปิดมาแบบถูกปิดทั้งสองกรณี สิ่งเดียวที่ปลดธง
ของงานอื่นก่อนเวลาได้จึงเป็นการอ่าน เพราะเป็นสิ่งเดียวที่ตารางยอมให้เริ่มระหว่างที่ธงยกอยู่ และมันทำได้
สองลำดับ — การอ่านที่ถูกแทนแล้ว (ลำดับของตั๋ว) กับการอ่านที่ยังเป็นคำขอปัจจุบัน ซึ่งเริ่มจากตารางหลัง
สิ่งที่ส่งการเขียนถูกปิดด้วย *ยกเลิก* ลำดับหลังมี *ยกเลิก* สองตัวให้กด — ของกล่องยืนยันซึ่งไม่เคยถูกปิด
และของฟอร์มซึ่งกดได้ระหว่างบันทึกแค่บนข้อมูลภาควิชา หลักสูตร และรายวิชา อีกสี่ฟอร์มปิดมันด้วยธง
*แถวที่เรียกสองทางเข้าคือสองแถว* (#66) ทั้งสองทางจึงเป็นแถวบนจอนี้

## คำตอบของการบันทึก ปิดฟอร์มที่ส่งมันไป ไม่ใช่ฟอร์มที่มันเจอ — #146 (20 ก.ย. 2569)

`save` ของ `frontend/src/pages/Departments.js` เคยจบด้วย `setEditing(null)` กับประโยคสำเร็จ
โดยไม่ถามอะไรเลย
การเขียนไม่มีอะไรมารื้อทิ้ง คำตอบของมันจึงมาถึงหน้าจอที่ขยับไปแล้วได้ — *ยกเลิก*
กดได้ระหว่างที่การเขียนยังไม่กลับ ตารางที่มันกลับไปไม่ปิดปุ่มไหนเลย และ *แก้ไข* หรือ *เพิ่ม…*
เปิดฟอร์มที่สอง
ฟอร์มที่สองจึงถูกปิดไปพร้อมสิ่งที่พิมพ์ค้างไว้
และประโยคของการบันทึกครั้งก่อนมาขึ้นในที่ที่อ่านได้ว่า
เป็นเรื่องของรายการที่คนกำลังมองอยู่ ตอนนี้ `showing` จำ **สิ่งล่าสุดที่เปิดขึ้นบนจอนี้**
ทุกตัวควบคุมที่เปิดอะไรขึ้นมาเขียนมัน และคำตอบที่เจอการเปิดอื่นไม่ปิดอะไรและไม่พูดอะไร ทั้งประโยคสำเร็จ
และคำปฏิเสธ — คำถามเดียวกับที่ #139 ให้การอ่านถาม ที่ปลายของการเขียน (#133) เหตุผลทั้งหมดอยู่บน
`frontend/src/pages/Departments.js`

สิ่งที่ไม่ได้เปลี่ยนคือสิ่งที่หน้าจอปิดการใช้งาน *ยกเลิก* ยังกดได้ระหว่างการบันทึก
เพราะนั่นเป็นการเปลี่ยน UI ซึ่งเป็นคำถาม
ไม่ใช่การแก้ (`docs/06` §Out of Scope) และการโหลดรายการใหม่ทำเสมอ ไม่ว่าการเทียบจะออกทางไหน (#131)

ทุกแถวข้างล่าง **เดินด้วยมือไม่ได้** มันต้องการคำขอที่ถูกกักไว้จนกว่าแถวจะปล่อย ซึ่ง
`e2e/support/gate.js` ทำให้
การเขียนที่ถูกกักถูกตอบด้วย 200 หรือ 409 ที่แต่งขึ้น จึงไม่มีแถวไหนเขียนฐานข้อมูล เข้าด้วย
`faculty.admin@kmitl.ac.th`
ครอบคลุมโดย describe *ข้อมูลภาควิชา (Departments.js)* ใน `146a-save-closes-a-later-form.spec.js`
จุดรอของแถวที่การบันทึกสำเร็จคือการโหลดรายการ
ที่ตามมา — การปิดฟอร์มที่ข้อบกพร่องจะวาด commit ไปก่อนคำขอนั้นถูกส่ง — แล้วอ่านครั้งเดียวหลังจากนั้น
250 ms ส่วนแถวคำปฏิเสธไม่มีจุดแบบนั้น (คำปฏิเสธไม่โหลดอะไรใหม่
และประโยคที่ถูกต้องคือประโยคที่ไม่ถูกวาด)
จึงนับจากตอนที่คำตอบถึงหน้า ตัวเลขนั้นตัดสินผลได้ (#52) สิ่งที่ค้ำมันคือการกวาดข้างล่าง

**คำถามที่ตั๋วฝากไว้ ถูกตอบแล้ว (20 ก.ย. 2569)** ร่างแรกให้ *ยกเลิก* เขียน `null` ลง `showing`
การบันทึกที่ถูก *ยกเลิก* แซงโดยไม่มีฟอร์มที่สองมาแทน จึงเงียบทั้งประโยคสำเร็จและคำปฏิเสธ —
คนที่กด *บันทึก* ไม่ได้ยินอะไรเลยเกี่ยวกับการเขียนที่ตัวเองสั่ง ตั๋วฝากเรื่องนี้ไว้เองว่าเป็น
*คำถามเรื่องสิ่งที่คนเห็น แบบเดียวกับ #143* ซึ่ง `docs/06` §Out of Scope บอกว่าเป็นคำถาม
ไม่ใช่การแก้ คำตอบของอาจารย์คือ **ให้ขึ้นเหมือนเดิมเมื่อไม่มีใครมาแทน**

`showing` จึงไม่ได้แปลว่า *ฟอร์มไหนเปิดอยู่* อีกต่อไป แต่แปลว่า **สิ่งล่าสุดที่เปิดขึ้นบนจอนี้**
— *ยกเลิก* ไม่เขียนมัน และการบันทึกที่ปิดฟอร์มของตัวเองก็ไม่เขียน `null` จึงเหลือความหมายเดียว
คือ *ยังไม่มีอะไรเปิดขึ้นเลย* บรรทัดที่เทียบ (`showing.current === sent`) ไม่ถูกแตะเลย
สิ่งที่เปลี่ยนคือใครเขียน ref บ้าง

และเพราะ *ยกเลิก* ไม่เขียน ref แล้ว หน้าต่างที่ผู้ตรวจโค้ดเคยชี้ก็เป็นจริงขึ้นมา — *แก้ไข*
ของจอนี้เปิดฟอร์มจากการอ่าน ระหว่างที่การอ่านยังไม่กลับจึงไม่มีฟอร์มใดบนจอเลย และการบันทึก
ที่ถูกกักข้ามช่วงนั้นจะเจอการเปิดของตัวเอง แล้ววางประโยคไว้เหนือฟอร์มที่กำลังจะถูกวาด ref
จึงถูกเขียน *ตอนกด* ไม่ใช่ตอนการอ่านกลับ — *ถามด้วยการกด ไม่ใช่ด้วยแถว* (#139)
ตอนที่ผู้ตรวจขอแถวนี้ ยังไม่มีทางเข้าไปในหน้าต่างนั้นได้ (#102) คำตอบของคำถามข้างบน
คือสิ่งที่เปิดมัน

### วัดซ้ำทั้งใบ หลังคำตอบของอาจารย์ที่ปรึกษา (20 ก.ย. 2569)

คำตอบเปลี่ยน*ความหมาย*ของ `showing` ไม่ใช่รูปของการเทียบ มัตแตนต์เดิมยี่สิบหกตัวจึงเกาะที่เดิม
ทั้งหมด แต่ *สมอที่ยังอยู่ไม่ได้แปลว่ายังพิสูจน์อะไรได้ มีแต่การกวาดที่บอกได้* (#107) และไฟล์
`146a` โตจาก 31 เป็น 49 แถว ตัวเลขทุกตัวข้างบนจึงหมดอายุพร้อมกัน กวาดใหม่ทั้งใบ 42 ตัว
ทีละตัว — baseline **49 ผ่านทั้ง 49** ทุกรันใช้เวลา 2.6–3.0 นาทีเท่า baseline และทุกรัน
ล้ม + ผ่าน = 49 พอดี ไม่มีตัวไหนหยุดแอปพลิเคชัน และไม่มีแถวไหนหายไปจากการรัน

- `146:departmentsclosewins` **ล้ม 3 ผ่าน 46** ที่ทางเข้าสองทางเดิมของจอรายการ — *a save that
  lands after แก้ไข leaves the form it found open* และ *a save that lands after เพิ่ม leaves what
  was typed where it was* ซึ่งเป็นบรรทัดเดียวกันในโค้ด — บวกแถวใหม่ *a save that lands while the
  next row is being read says nothing* เพราะ guard ที่จำแค่ว่า*มีอะไรเปิดอยู่ไหม*
  ก็พูดทับฟอร์มที่กำลังจะถูกวาดเหมือนกัน
- `146:departmentsrefusalwins` **ล้ม 1 ผ่าน 48** ที่แถว *a save refused after the screen moved on
  says nothing over the new form*
- `146:departmentscancelclears` **ล้ม 2 ผ่าน 47** ที่สองแถวที่คำตอบเพิ่มเข้ามา — *a save that
  nothing took the place of says what it did* และ *a refusal that nothing took the place of is
  still said* ซึ่งใบนี้ถือแถวคำปฏิเสธของทรงนี้ไว้ให้ทั้งกลุ่ม
- `146:departmentsshowingatthelanding` **ล้ม 1 ผ่าน 48** ที่แถวหน้าต่างการอ่าน *a save that lands
  while the next row is being read says nothing* แถวเดียว ซึ่งเป็นการแยกที่ `closewins` ทำไม่ได้ —
  ตัวหนึ่งบอกว่ามีคนอ่าน ref ตัวนี้ อีกตัวบอกว่าอ่านมัน*ตอนกด*

ทุกตัวล้มที่ assertion ของแถว ไม่ใช่ที่ timeout และตัวที่ล้มคือแถวที่ชื่อของมันบอก อ่านจากชื่อเทสต์
ที่ตาย ไม่ใช่จากจำนวน
