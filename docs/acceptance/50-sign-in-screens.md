# ตรวจรับด้วยมือ — #50 หน้าจอลงชื่อเข้าใช้

`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #50

ใบนี้ต่างจากใบอื่นตรงที่มันเกิดขึ้น *ทีหลัง* หน้าจอที่มันถือเกณฑ์ไว้ [#8](https://github.com/khthana/Deep-QA/issues/8)
ปิดไปด้วยครึ่งฝั่ง server — เส้นทางรหัสผ่าน เส้นทาง Google cookie ของ session และคำปฏิเสธทั้งชุด —
ตอนนั้นยังไม่มี frontend ให้สร้างครึ่งฝั่งหน้าจอ CRA เข้ามาพร้อม [#10](https://github.com/khthana/Deep-QA/issues/10)
และหน้าจอลงชื่อเข้าใช้จึงถูกสร้างขึ้น *ข้างใน* #10 ในฐานะผลพลอยได้ ผลก็คือ **หน้าจอเดียวที่ทุกคนในระบบต้องผ่าน
เป็นหน้าจอเดียวที่ไม่มีใบตรวจรับอยู่ข้างหลัง** เกณฑ์ฝั่งหน้าจอของ #8 ถูกถือไว้โดยตั๋วที่ปิดไปแล้ว
ใบนี้คือการปิดช่องนั้น — ข้อ 4 ใน *สิ่งที่ยังไม่ปิดใน #10*

ไฟล์ที่ใบนี้ครอบคลุม: `pages/Login.js` · `components/LoginForm.js` · `components/LoginGoogle.js` ·
`pages/UserNotFound.js` ที่ **ถูกลบไปในตั๋วนี้** และ `pages/SelectApp.js` ที่ **#66 ลบในวันรุ่งขึ้น**

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`

**`.env` ที่เครื่องนี้ไม่ได้ตั้งค่า Google** (`cp .env.example .env` ทิ้งไว้ว่างโดยตั้งใจ และมีหมายเหตุบอกไว้)
นั่นคือ *เงื่อนไขที่ถูกต้อง* สำหรับแถวที่ 5 ไม่ใช่ข้อจำกัดของการเดิน — เป็นสภาพที่นักพัฒนาทุกคนเจอ

## รายการที่ต้องเดิน

ช่องสุดท้ายมีสี่ค่า

- **☑** เดินจบแล้ว
- **◐** เดินไปครึ่งเดียว
- **☐** ยังไม่ได้เดิน
- **⚙** ครอบคลุมด้วย browser seam แล้ว แถวบอกไฟล์และการกลายพันธุ์ที่พิสูจน์มันไว้

| # | เกณฑ์ | ทำอะไร | ต้องเห็นอะไร | ✓ |
|---|---|---|---|---|
| 1 | **ทุกกุญแจในรายการ** ไปถึงคนอ่านเป็นคำของ server เอง | เปิด `http://localhost:5000/login?error=outsideValidity` แล้วไล่ทีละกุญแจใน `GOOGLE_REFUSAL_REASONS` | แถบแดงอ่านว่า *บัญชีนี้อยู่นอกช่วงเวลาที่กำหนดให้ใช้งาน* ไม่ใช่ *เข้าสู่ระบบด้วย Google ไม่สำเร็จ* — ครอบคลุมโดย `e2e/tests/50a-sign-in.spec.js` (row 1) ซึ่งอ่านรายการจาก backend แล้ววนทุกตัว เทียบกับ `REFUSALS[reason]` ทีละตัว (`googlerefusalmissesone`, `refusalalwaysfallback`) | ⚙ |
| 1 | (ครึ่งที่สอง) **รายการนั้นคือเหตุผลทั้งหมดที่กฎสร้างได้จริง** | — | `GOOGLE_REFUSAL_REASONS` ตรงกับ `refuse()` ที่ `admit` และ `resolveGoogleAccount` เรียกใช้ ครบทุกตัวไม่ขาดไม่เกิน — พิสูจน์ที่ seam HTTP (`auth.test.js` *the list of reasons is the list the rules can actually produce*) ซึ่ง**อ่านซอร์สของสองฟังก์ชันนั้นออกมาเทียบ** ไม่ได้ใช้รายการที่คนพิมพ์ไว้ · **แถวนี้แยกออกมาโดยตั้งใจ** แถวบนวนตามรายการ ดังนั้นการลบกุญแจออกจากรายการทำให้ลูปสั้นลงเฉย ๆ ไม่มีอะไรล้ม ⚙ ที่กินความถึงคำว่า *ทุกเหตุผล* จึงเป็น ⚙ ที่ไม่ได้มาจริง | ☑ |
| 2 | เหตุผลที่ยังไม่มีใครเขียนคำไว้ ยังพูดอะไรบางอย่าง ไม่ใช่เงียบ | เปิด `/login?error=aReasonFromAFutureTicket` | แถบแดงอ่านว่า *เข้าสู่ระบบด้วย Google ไม่สำเร็จ* และฟอร์มยังกรอกได้ — ครอบคลุมโดย `50a` (row 2) (`refusalneverdrawn`) | ⚙ |
| 3 | มาถึงหน้าลงชื่อเข้าใช้ตามปกติ ไม่มีคำปฏิเสธค้างอยู่ | เปิด `http://localhost:5000/` | ไม่มีแถบแดงเลย — ครอบคลุมโดย `50a` (row 3) (`refusalalwayssomething`) | ⚙ |
| 4 | **แถบคำปฏิเสธอ่านออกจริง** | ทำแถวที่ 1 แล้ว **มอง** | ข้อความอยู่นานพอจะอ่านจบ สีและขนาดแยกออกจากเนื้อหารอบข้างได้ · **เดินเมื่อ 6 ก.ย. 2569 ตอนที่แถบยังหายเองใน 3 วินาที** และคำถามที่แถวนี้ถามคือ *ตอนที่มันอยู่* มันอ่านออกไหม — ซึ่งยังเป็นคำถามเดิม [#85](https://github.com/khthana/Deep-QA/issues/85) ปิดไปในวันเดียวกัน แถบไม่หายเองแล้ว คำตอบของแถวนี้จึงเปลี่ยนจาก *อ่านทันถ้ามองอยู่* เป็น *อ่านทัน* | ☑ |
| 5 | กด *Login With Google* บนเซิร์ฟเวอร์ที่ไม่ได้ตั้งค่า Google แล้วได้คำอธิบาย ไม่ใช่หน้า JSON | เข้าหน้าลงชื่อเข้าใช้ แล้วกดปุ่ม Google | กลับมาที่หน้าลงชื่อเข้าใช้ ที่ `/login?error=googleUnavailable` พร้อมข้อความ *ยังไม่ได้ตั้งค่าการเข้าสู่ระบบด้วย Google บนเซิร์ฟเวอร์นี้* **ไม่ใช่** `{"message":...}` บน `localhost:3000` — ครอบคลุมโดย `50a` (row 4) (`googleunavailableisjson`) | ⚙ |
| 6 | รหัสผ่านผิด ได้คำของ server ไม่ใช่ประโยคที่หน้าจอแต่งเอง | `teacher.one@kmitl.ac.th` กับรหัสผ่านมั่ว | *อีเมลหรือรหัสผ่านไม่ถูกต้อง* ขึ้นในแถบ ที่อยู่ยังเป็น `/` และฟอร์มยังกรอกต่อได้ — ครอบคลุมโดย `50a` (row 5) (`wrongpasswordinventsasentence`) | ⚙ |
| 6 | (ครึ่งที่สอง) รหัสผ่านผิดแล้ว**ไม่มีอะไรมาทับ**ประโยคนั้น | เหมือนแถวบน แล้วมองทั้งจอ | แถบคำปฏิเสธคือสิ่งเดียวบนจอ **ไม่มี**กล่อง *Session หมดอายุ* คลุมทับ — ครอบคลุมโดย `50a` (rows 6–7) (`credentialsisanexpiry`) · **แถวนี้เคยเป็น ☐ เพราะเกณฑ์ยังไม่จริง** `client.js` ยิง `sessionExpiredListener` ทุก 401 ที่ผู้เรียกไม่ได้ติดธง `anonymous` และ `POST /api/auth/login` ก็เป็นหนึ่งในนั้น กล่องเต็มจอจึงขึ้นทับประโยคที่บอกว่ารหัสผ่านผิด บอกคนที่ยังไม่เคยมี session ว่า session ของเขาจบแล้ว และปุ่มเดียวของมันพากลับมาที่หน้าเดิม — ปิดที่ [#97](https://github.com/khthana/Deep-QA/issues/97) เมื่อ 6 ก.ย. 2569 | ⚙ |
| 6 | (ครึ่งที่สาม) อีเมลที่ไม่มีในระบบ ก็เงียบแบบเดียวกัน | อีเมลที่ไม่มีใครใช้ กับรหัสผ่านที่ถูกต้องของคนอื่น | ได้ประโยคเดียวกัน และไม่มีกล่องเช่นกัน — ครอบคลุมโดย `50a` (row 7) (`credentialsisanexpiry`) · **แยกเป็นคนละแถวโดยตั้งใจ** สองเส้นทางนี้เดินคนละทางใน `resolvePasswordAccount` (ไม่มีแถวผู้ใช้เลย กับมีแถวแต่แฮชไม่ตรง) แล้วมาจบที่คำปฏิเสธเดียวกัน ถ้าวันหนึ่งมีแค่ทางเดียวที่ส่ง `reason` มา จะมีแถวเดียวที่ล้ม | ⚙ |
| 6 | (ครึ่งที่สี่) คำปฏิเสธของ `/api/auth/login` บอกชื่อเหตุผลของตัวเอง | — | 401 ของเส้นทางนี้ส่ง `reason: 'credentials'` มาด้วย เหมือน 401 อื่นทั้งหมดในระบบ — พิสูจน์ที่ seam HTTP (`auth.test.js` *names its reason, the way every other 401 here does*) (`loginhidesitsreason`) · **แถวนี้ไม่ใช่สิ่งที่แก้กล่อง และเขียนแยกไว้เพื่อไม่ให้เข้าใจผิด** สองแถวบนผ่านได้แม้ไม่มี `reason` นี้ เพราะคนแปลกหน้าที่หน้าลงชื่อเข้าใช้ยังไงก็ไม่ได้เข้าระบบอยู่ สิ่งที่แถวนี้ปิดคือข้อ 3 ของ #97 — เส้นทางนี้เคยเป็น 401 เดียวที่ไม่บอกว่าตัวเองคือ 401 แบบไหน | ☑ |
| 6 | (ครึ่งที่ห้า) คำปฏิเสธที่เป็น **403** ก็ไม่ถูกกล่องทับเช่นกัน | — | กล่องผูกกับสถานะ 401 เท่านั้น ไม่มี 403 ชนิดใดยกมันขึ้นได้ — ครอบคลุมโดย `10a` (row 6 *a 403 is not an expiry*) (`lump403`) ซึ่งเป็น ⚙ **ที่ยืมมา** จากใบของ #10 · **สิ่งที่พิสูจน์คือกลไก ไม่ใช่ห้าประโยค** เกณฑ์ข้อ 5 ของ [#97](https://github.com/khthana/Deep-QA/issues/97) ไล่ชื่อไว้ห้าเหตุผล (`inactive` `unverified` `outsideValidity` `noRole` `domain`) และไม่มีแถวไหนในใบนี้ขับ 403 ผ่านฟอร์มจริงสักเหตุผลเดียว — seed ไม่มีบัญชีที่ถูกระงับ หรืออยู่นอกช่วงเวลา จะขับต้องสร้างสถานการณ์แล้วคืนสภาพ ส่วนตัวประโยคเองเป็นเรื่องของแถวที่ 6 (`setErrorMessage(error.message)`) กับแถวที่ 12 ที่เป็น ◐ อยู่แล้ว | ⚙ |
| 6 | (ครึ่งที่หก) **คำปฏิเสธไม่หายไปเอง** | ทำแถวบน แล้วนั่งมองห้าวินาที | ประโยคยังอยู่ครบ ไม่มีนาฬิกาตัวไหนเก็บมันไป — ครอบคลุมโดย `50a` (row 8) (`refusaltimesout`) · เดิมเป็น `setTimeout` สามวินาที ซึ่งสั้นกว่าเวลาที่ใช้ถ่ายภาพหน้าจอ ผ่าน CDP หนึ่งรอบ การเดินที่เจอเรื่องนี้ ([#85](https://github.com/khthana/Deep-QA/issues/85)) ต้องติดตั้ง `MutationObserver` ดักคำไว้ถึงจะเก็บหลักฐานได้ · WCAG 2.2 §2.2.1 | ⚙ |
| 6 | (ครึ่งที่เจ็ด) **แต่ก็ไม่ค้างตลอดไป** — พิมพ์แก้แล้วมันหายไป | ทำแถวบน แล้วพิมพ์ในช่องรหัสผ่าน | ประโยคหายทันทีที่เริ่มแก้ — ครอบคลุมโดย `50a` (row 9) (`typingleavesitup`) · **สองแถวนี้เป็นคู่ อ่านแยกกันไม่ได้** แถวนี้ผ่านมาตั้งแต่ก่อนแก้ เพราะนาฬิกาเก็บประโยคไปก่อน สิ่งที่ตัดนาฬิกาออกจากคำอธิบายคือแถวบน | ⚙ |
| 6 | (ครึ่งที่แปด) **คำปฏิเสธถูก*ประกาศ* ไม่ใช่แค่ถูกวาด** | เปิดโปรแกรมอ่านหน้าจอ แล้วทำแถวที่ 1 | ได้ยินประโยคนั้นตอนมันขึ้น โดยไม่ต้องไล่หาเอง · **ครึ่งที่พิสูจน์แล้ว**: `role="alert"` อยู่บนแถบจริงและไปถึง DOM จริง ซึ่ง `50a` ทั้งไฟล์อาศัยอยู่ — ตั้งแต่ [#85](https://github.com/khthana/Deep-QA/issues/85) `refusalBanner` หาแถบด้วย `getByRole('alert')` ถ้า attribute หาย เก้าแถวแดงทันที **ครึ่งที่ยังไม่ได้เดิน**: หูของคนจริง และคำถามว่า *assertive* เหมาะกับแถบนี้ไหม ซึ่งเป็นของ [#111](https://github.com/khthana/Deep-QA/issues/111) ที่ถือแถบอีกสิบเก้าอันของทั้งระบบอยู่ · อีกครึ่งของคำว่า *ผูกกับฟอร์ม* อยู่ที่แถวถัดไป ซึ่งพิสูจน์ได้ | ◐ |
| 6 | (ครึ่งที่เก้า) **คำปฏิเสธ*ผูกกับฟอร์ม* ไม่ใช่แค่ลอยอยู่เหนือมัน** | ทำแถวที่ 6 แล้วกด Tab กลับเข้าไปในช่องรหัสผ่าน | โปรแกรมอ่านหน้าจออ่านชื่อช่อง **แล้วอ่านเหตุผลที่ครั้งก่อนถูกปฏิเสธต่อท้าย** — ครอบคลุมโดย `50a` (row 10) (`refusaldescribesnothing`) · `role="alert"` ทำให้ประโยค*ถูกประกาศตอนมันมา* แล้วก็จบ ส่วน `aria-describedby` ทำให้มันเป็น*คำอธิบายของช่องที่มันพูดถึง* ซึ่งกลับมาอ่านเมื่อไหร่ก็ได้ #85 ขอทั้งสองอย่าง (*ควรผูกกับฟอร์มด้วย `role="alert"`*) และร่างแรกทำแค่อย่างแรก /code-review ของตั๋วนี้จับได้ · **แถวนี้พิสูจน์ได้ ส่วนครึ่งที่แปดพิสูจน์ไม่ได้ ทั้งที่เป็น attribute เหมือนกัน** ต่างกันตรงที่ locator ไม่ได้ยืนอยู่บน `aria-describedby` | ⚙ |
| 7 | ฟอร์มเปล่าถูกปฏิเสธที่หน้าจอ ไม่ต้องถาม server | กด *Login to your account* โดยไม่กรอกอะไร | *กรุณากรอกอีเมล และ รหัสผ่าน* ขึ้น และ **ไม่มี** request ไปที่ `/api/auth/login` (ดูใน DevTools → Network) — ครอบคลุมโดย `50a` (row 11) (`emptyformgoesthroughanyway`, `emptyformsaysnothing`) | ⚙ |

## สิ่งที่การตรวจของที่ส่งมอบเจอ

**หนึ่ง — `outsideValidity` หายไปจากตารางคำของหน้าจอ** `GOOGLE_REFUSALS` ใน `Login.js` มีหกกุญแจ
ส่วน `admit` ปฏิเสธได้หกเหตุผล และหนึ่งในนั้นไม่ตรงกัน: บัญชีที่อยู่นอกช่วงเวลาใช้งาน
คนเดียวที่มีทางเจอคำปฏิเสธนี้คือผู้ประเมินภายนอกที่รอบการประเมินปิดไปแล้ว และคนคนนั้นจะได้
*เข้าสู่ระบบด้วย Google ไม่สำเร็จ* — ประโยคสำรองที่มีไว้สำหรับเหตุผลที่ยังไม่มีใครเขียนคำไว้
ไม่ใช่สำหรับรูในตารางนี้ แก้แล้ว และรายการกุญแจย้ายไปอยู่ที่ `GOOGLE_REFUSAL_REASONS`
ใน backend ซึ่งมีเทสต์อ่าน `refuse()` ในซอร์สมาเทียบ รายการจึงตามหลังกฎไม่ได้อีก

**สอง — คำปฏิเสธที่เป็นหน้า JSON** `/api/auth/google-login` บนเซิร์ฟเวอร์ที่ไม่ได้ตั้งค่า OAuth
ตอบ `503` พร้อม body ซึ่งอ่านได้ก็ต่อเมื่อมีโค้ดอ่าน — แต่หน้าจอเข้าเส้นทางนี้ด้วย
`window.location` ไม่ใช่ fetch ผลจริงคือเบราว์เซอร์ไปจอดอยู่บน origin ของ API
อ่าน `{"message":"..."}` อยู่นอกแอปพลิเคชัน โดยไม่มีทางกลับนอกจากปุ่ม back
และนี่ไม่ใช่กรณีขอบ: `cp .env.example .env` ทิ้งค่า OAuth ไว้ว่าง นักพัฒนาทุกคนเจอสภาพนี้
ตอนนี้ตอบด้วยการ redirect กลับหน้าลงชื่อเข้าใช้พร้อมเหตุผล ซึ่งเป็นวิธีที่ callback
ของเส้นทางเดียวกันใช้อยู่ก่อนแล้ว

**สาม — ป้ายกำกับที่ไม่ได้เรียกอะไรเลย** `htmlFor` ทั้งสองชี้ไปที่ id ที่ input ไม่ได้ถือไว้
ของช่องรหัสผ่านอ่านว่า `website-admin` ซึ่งเป็น id จาก snippet Flowbite ที่ยกมาและไม่มีอยู่บนหน้านี้
แก้ด้วย `id` สองตัว ไม่มีอะไรขยับและไม่มีอะไรถูกจัดรูปใหม่ — นี่ไม่ใช่การออกแบบใหม่ที่โครงการนี้เลื่อนไว้
มันคือ markup ที่พูดในสิ่งที่มันเขียนไว้อยู่แล้ว

**สี่ — หน้าที่ไม่มีใครพาไปถึง** `/user-not-found` ถูกประกาศไว้ อ่าน `?reason` ได้
และไม่มีที่ใดในระบบพาไปที่นั่น มันเทียบ `?reason` กับ**ประโยคภาษาไทยทั้งประโยค**
การแก้คำใน `backend/auth/refusals.js` จึงเปลี่ยน *บัญชีถูกระงับ* ให้กลายเป็น *ไม่พบผู้ใช้* ได้เงียบ ๆ
ลบทิ้งแล้ว ข้อ 8 ของ *สิ่งที่ยังไม่ปิดใน #10*

**ห้า — ที่อยู่ของ portfolio ฝังในโค้ดสองที่ และ env ตัวหนึ่งที่ไม่มีใครอ่าน**

`REACT_APP_PORTFOLIO_URL` (ข้อ 6) และ **#66 ลบทั้งตัวแปรและทั้งสองปุ่มทิ้งในวันรุ่งขึ้น**

แล้วตรวจได้ว่าไม่มี ⚙ ไหนบนใบนี้ที่ไม่มีการกลายพันธุ์รองรับ:

**ครึ่งที่แปด (การประกาศ) ไม่มีมัตแตนต์ และนั่นเป็นคำตอบ ไม่ใช่ช่องว่าง** [#85](https://github.com/khthana/Deep-QA/issues/85)
เปลี่ยน locator ของแถบจาก class ของ Tailwind มาเป็น `getByRole('alert')` ตั้งแต่นั้น
`role="alert"` กลายเป็น *สิ่งที่แถบเป็น* ในสายตาของชุดทดสอบ เขียนมัตแตนต์ถอด attribute นั้นออก
แล้วเก้าแถวแดงพร้อมกัน — ไม่ใช่เพราะข้ออ้างไหนล้ม แต่เพราะสิ่งที่แถวเหล่านั้นพูดถึงหายไป
**attribute ที่ locator ยืนอยู่บนมัน พิสูจน์ด้วยการกลายพันธุ์ไม่ได้อีกต่อไป มันกลายเป็น*ข้อตั้ง*
ของแถวเหล่านั้น ไม่ใช่ข้ออ้างของแถวไหน** ลองเขียนแล้วสองตัว ฆ่าเก้าแถวเท่ากันทั้งคู่ แยกจากกันไม่ออก
จึงลบทิ้งทั้งสอง เหตุผลเต็มอยู่ในหัวไฟล์ `mutation/85-refusal-that-waits.py`

**และครึ่งที่เก้าคือตัวอย่างแย้งที่ทำให้เส้นแบ่งชัด** `aria-describedby` ก็เป็น attribute
เพื่อการเข้าถึงบนหน้าจอเดียวกัน ตั๋วเดียวกัน แต่ถอดมันออกแล้ว**แถวเดียวแดง** เพราะไม่มี locator
ไหนหาอะไรด้วยมัน **สิ่งที่ตัดสินว่า attribute หนึ่งพิสูจน์ได้หรือไม่ ไม่ใช่ว่ามันสำคัญแค่ไหน
แต่คือชุดทดสอบหาของ*ด้วย*มันหรือเปล่า**

**เลขแถวของ `50a` ขยับเมื่อมีการแทรกเทสต์ และมันเกิดขึ้นสามครั้งในวันเดียว** #97 แทรกสองแถว
ไว้หลังแถวที่ 5 แล้ว #85 แทรกอีกสองแถวไว้หลังแถวที่ 7 แล้ว /code-review ของ #85 ทำให้ต้อง
แทรกอีกหนึ่งแถว **การอ้างอิงชุดเดียวกันสี่จุดเลื่อนทั้งสามรอบ** — จาก 6·7·8·9 เป็น 8·9·10·11
เป็น 10·11·12·13 แล้วเป็น 11·12·13·14

**แต่ละรอบเจอด้วยวิธีที่ต่างกัน และรอบที่สามคือรอบที่บอกอะไรมากที่สุด** รอบแรก /code-review จับได้
รอบสองเจอตอนไล่ตารางเพราะมีสองแถวอ้าง *row 8* พร้อมกัน รอบสาม /code-review จับได้อีก
แต่จับ**คนละที่** — ใบนี้มีตารางสองตาราง และรอบก่อน ๆ แก้แต่ตารางเกณฑ์
**คอลัมน์ *ฆ่าแถว* ของตารางการกลายพันธุ์ไม่เคยถูกแก้เลยตั้งแต่ #97** มันยังเป็นเลขก่อน #97
อยู่ทั้งคอลัมน์ ทั้งที่ร้อยแก้วเหนือมันสองย่อหน้าอธิบายเรื่องการเลื่อนอยู่พอดี

**บทเรียนคือ *ไล่ให้ครบทุกที่ที่อ้างเลข* ไม่ใช่ *ไล่ให้ครบทุกแถว*** หลังแทรกเทสต์ ให้นับเทสต์
ในไฟล์ spec ก่อน แล้ว `grep` หาเลขนั้นทั้งคลัง — ตารางเกณฑ์ ตารางการกลายพันธุ์ และไฟล์
กลายพันธุ์ทุกไฟล์ที่กวาดด้วย `50a` (ตอนนี้มีสามไฟล์) หรือไม่ก็ต่อเทสต์ท้ายไฟล์เสมอ
แล้วเลขจะไม่ขยับเลย ซึ่งเป็นทางที่ถูกกว่ามาก

แถวที่ 4 ไม่ได้ติด ⚙ เพราะมันถามเรื่อง *หน้าตา* — อ่านออกไหม — ซึ่งเป็นครึ่งที่ browser
วัดได้แต่ไม่มีความเห็น เดิมมีอีกสองแถวแบบนั้น (หน้าเลือกแอป และรายการ *ไปที่ Deep Portfolio*
ในเมนูผู้ใช้) ทั้งคู่เดินแล้วในวันเดียวกัน และถูกปลดออกจากตารางในวันรุ่งขึ้นเมื่อ #66 ลบทั้งสอง —
ดู §บันทึกการเดิน 6 กันยายน 2569 แถวที่ 12 เป็น ◐ เพราะเบราว์เซอร์ยิงคำขอนั้นไม่ได้

**ใบนี้ไม่มี ☐ แล้ว** ครึ่งที่สองของแถวที่ 6 เคยเป็น ☐ ที่แปลว่า *เกณฑ์ข้อนี้ยังไม่จริงวันนี้*
พร้อมเลขตั๋วกำกับ — [#97](https://github.com/khthana/Deep-QA/issues/97) ปิดไปเมื่อ 6 ก.ย. 2569 แถวนั้นจึงเป็น ⚙ และแตกออกเป็นสี่ครึ่ง
ตามสิ่งที่แต่ละครึ่งพิสูจน์ได้จริง **☐ ที่บอกเลขตั๋วคือสายที่ต่อระหว่างสองใบ ไม่ใช่รูในใบเดียว**

แถวที่ 1 ถูก**แยกเป็นสองแถว** ด้วยเหตุผลที่ `CLAUDE.md` บอกให้ระวังที่สุด: ⚙ ต้องเป็นแถวที่การยืนยัน
ที่อ้างถึงครอบคลุม**ทั้งแถว** ไม่ใช่ครอบคลุมเกือบหมด ร่างแรกเขียนว่า *ทุกเหตุผลที่เส้นทาง Google
ปฏิเสธได้* แล้วติด ⚙ ทั้งที่ `50a` วนตามรายการ — การลบกุญแจออกจากรายการจึงไม่ทำให้อะไรล้ม
ครึ่ง *ทุกเหตุผล* พิสูจน์ที่ seam HTTP และตอนนี้เป็นแถว ☑ ที่ชี้ไปที่นั่น

**นี่คือใบที่เก้าติดต่อกันที่เจอรูปแบบนี้ และเป็น /code-review ของตั๋วเองที่จับได้อีกครั้ง**
สิ่งที่ต่างจากแปดใบก่อน: รอบนี้ช่องโหว่ถูก*เขียนบอกไว้เป็นร้อยแก้ว*แล้วในไฟล์การกลายพันธุ์
แต่ยังติด ⚙ อยู่ดี — **การอธิบายช่องโหว่ไม่เท่ากับการทำเครื่องหมายให้ตรง**

**ตารางนี้ไม่ครอบคลุมทุกแถวของ `50a` อีกแล้ว และเคยครอบคลุม** ตอนเขียน #50 สเปกมีเก้าแถว
และทั้งเก้าแถวมีตัวฆ่าอยู่ที่นี่ ตอนนี้สเปกมีสิบสี่แถว ห้าแถวที่เพิ่มมา (6·7 ของ #97

## การกลายพันธุ์ที่รอด และสิ่งที่มันเปิดออกมา

รอบแรกของการกวาด **`refusalalwayssomething` ฆ่าอะไรไม่ได้เลย** มันวาดแถบคำปฏิเสธขึ้นบนทุกครั้ง
ที่มาถึงหน้าลงชื่อเข้าใช้ รวมทั้งครั้งที่ไม่มีใครถูกปฏิเสธ และแถวที่ 3 ซึ่งมีหน้าที่จับเรื่องนี้
โดยตรง ผ่านฉลุย

เหตุผลไม่ใช่จังหวะ — probe ยืนยันว่าแถบอยู่บนหน้าจอ นับได้ 1 ตั้งแต่วินาทีที่แถวนั้นเชื่อว่ากำลังตรวจอยู่

เหตุผลคือ **`toHaveCount(0)` เป็น web-first assertion มันลองซ้ำได้ถึงสิบวินาที**
และแถบนี้ลบตัวเองทิ้งใน **สาม** วินาที ([#85](https://github.com/khthana/Deep-QA/issues/85))
การยืนยันว่า *ไม่มี* ด้วยเครื่องมือที่ลองซ้ำจนกว่าจะจริง กับสิ่งที่หายไปเองเสมอ
คือการยืนยันที่ **ไม่มีทางล้มได้** ไม่ว่าหน้าจอจะทำอะไร

**นี่เป็นคนละสายพันธุ์กับ ⚙ ที่ไม่ได้มาจริง** แถวนั้นมีอยู่ มันชี้ถูกที่ ถ้อยคำของมันตรงกับเกณฑ์
และมันก็ยังล้มไม่ได้ — สิ่งที่ผิดคือ *เครื่องมือ* ที่ใช้ยืนยัน ไม่ใช่สิ่งที่ยืนยัน

แก้แล้วสองแห่ง ทั้งสองอ่านจำนวน **ครั้งเดียว** ที่จุดที่นิ่งแล้ว แล้วเทียบเป็นค่าธรรมดา:

- แถวที่ 3 อ่านหลัง `networkidle` ซึ่งเป็นจุดที่เปลือกถามเสร็จแล้วว่าใครเข้าระบบอยู่
  — เป็นสิ่งสุดท้ายที่จะเอาอะไรมาขึ้นบนหน้านี้ได้
- แถวที่ 1 มีด่านเดียวกันซ่อนอยู่ (*ต้องไม่ใช่ประโยคสำรอง*) ซึ่งกลวงด้วยเหตุผลเดียวกัน
  ตอนนี้อ่านทันทีหลังจากที่การยืนยันเชิงบวกเพิ่งพิสูจน์ว่าแถบอยู่บนหน้าจอ

หลังแก้ `refusalalwayssomething` ฆ่าแถวที่ 3 แถวเดียว ตามที่ควรเป็น

**บทเรียนที่ควรพกไป:** การยืนยันเชิงลบด้วย `toHaveCount(0)` หรือ `not.toBeVisible()`
กับสิ่งที่หายไปเองตามเวลา — แถบแจ้งเตือน toast กล่องที่ปิดตัวเอง — เป็นการยืนยันที่ว่างเปล่า

**ตรวจทั่วทั้งคลังแล้ว และผลออกมาแคบกว่าที่กลัว** ชุด browser มีการยืนยันเชิงลบแบบลองซ้ำ
**112 จุดใน 40 ไฟล์** แต่จุดที่เป็นอันตรายคือจุดที่*เป้าหมายลบตัวเองตามเวลา*เท่านั้น
และตอนตรวจ (5 ก.ย. 2569) ในทั้ง `frontend/src` มี `setTimeout` อยู่สี่ที่: สองที่เป็น debounce
ของช่องค้นหา (`TeacherPicker.js`, `ProgramSubjectForm.js`) หนึ่งที่เป็น `revokeObjectURL` ของ #35
และ **`Login.js` ที่เดียวที่ลบสิ่งที่วาดไว้ทิ้ง**

กล่าวคือตอนนั้น **ทั้งระบบมีองค์ประกอบที่หายไปเองอยู่ชิ้นเดียว และมันคือแถบนี้** การยืนยันเชิงลบ
อีก 111 จุดจึงยืนอยู่บนสิ่งที่อยู่นิ่ง — แถวในตาราง รายการในเมนู หัวข้อ — ซึ่งลองซ้ำแล้วก็ยังไม่มี
ไม่ใช่เพราะมันเพิ่งหายไป

**และ [#85](https://github.com/khthana/Deep-QA/issues/85) ลบชิ้นนั้นทิ้งในวันรุ่งขึ้น ย่อหน้าข้างบนจึงเป็นบันทึกของวันที่ตรวจ ไม่ใช่
สภาพวันนี้** ตอนนี้ `frontend/src` มี `setTimeout` สามที่ ทั้งสามไม่ได้ลบอะไรที่วาดไว้
และ**ทั้งระบบไม่มีองค์ประกอบที่หายไปเองเหลืออยู่เลย** การยืนยันเชิงลบทั้ง 112 จุดจึงยืนอยู่บน
