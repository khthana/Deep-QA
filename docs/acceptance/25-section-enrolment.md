# ตรวจรับด้วยมือ — #25 Section enrolment

`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #25

ครึ่งแรกอยู่ที่ `backend/test/enrolment.test.js` (21 subtests) — เกณฑ์ทั้งเก้าข้อที่พิสูจน์ได้ที่ seam
ของ HTTP surface ถูกพิสูจน์ที่นั่นแล้ว

seam ที่สองคือเบราว์เซอร์ — `e2e/tests/25a-section-enrolment.spec.js` (12 แถว) ดูหัวข้อ
*มัตแตนต์ที่พิสูจน์แถว ⚙* ท้ายเอกสาร ซึ่งเป็นเหตุผลว่าทำไมแถวเหล่านั้นถึงถือว่าครอบแล้วจริง

## หน้าจอนี้ต่างจาก #27 ตรงไหน

สองหน้านี้เข้าจากที่เดียวกัน หน้าตาคล้ายกัน และ **grain ไม่เหมือนกันเลย**

**ผลการเรียนรู้รายวิชาเป็นของการเปิดสอน แต่รายชื่อนักศึกษาเป็นของตอนเรียน** ADR-0003 ผูกชุด CLO
ไว้กับ (หลักสูตร, รายวิชา, ปีการศึกษา) `clos.js` จึงแปลง `section_id` เป็น Offering ทุกคำขอ และ
ตอนเรียนสองตอนของรายวิชาเดียวกันเห็นชุดเดียวกัน **การลงทะเบียนไม่ใช่แบบนั้น** ตอนเรียนสองตอนคือ
สองห้องเรียน มีนักศึกษาคนละกลุ่ม ซึ่งเป็นเหตุผลทั้งหมดที่ตอนเรียนมีอยู่ `enrolment.js` จึงหยุดที่
ตอนเรียนและไม่แตะการเปิดสอนเลย — มัตแตนต์ `offeringgrain` คือการเขียนหน้านี้แบบ `clos.js`
และมันทำให้ทั้ง 113 คนไปโผล่บนหน้าจอของทั้งสองตอนเรียน

**ทะเบียนกลางเป็นคนละเรื่องกับรายชื่อของห้อง** #17 สร้างทะเบียน นี่คือการเลือกคนจากทะเบียนนั้น
รหัสที่ทะเบียนไม่มี **ถูกปฏิเสธพร้อมประโยคที่บอกว่าให้ไปเพิ่มที่ไหน** ไม่ใช่ถูกสร้างขึ้นตรงนี้
`student_course.student_id` เป็น foreign key อยู่แล้ว ฐานข้อมูลจึงกันไว้ให้อยู่แล้ว สิ่งที่ route
เพิ่มเข้ามาคือ **ประโยค** — 23503 ที่หลุดไปถึง error handler ตอบว่า *เกิดข้อผิดพลาดในระบบ*

**ไม่มีใครถูกบันทึกว่าเป็นคนเพิ่มใคร** `student_course` มีแค่ `created_at` ไม่มี `created_by`
(ADR-0001 tier 2) และตอนเรียนหนึ่งมีผู้สอนได้สองคน คำถามว่า *ใครเพิ่มนักศึกษาคนนี้* จึงไม่มีคำตอบ
ที่นี่ #25 ไม่ได้ถาม และ #27 มี `updated_by` เพราะตั๋วนั้นถาม

## การนำออกถูกกั้นไว้สองด่าน ซึ่ง #25 ไม่ได้ขอ

**ไม่มีตารางไหนอ้างถึง `student_course` เลย** `DELETE` จึงสำเร็จเสมอ และจะทิ้ง `activity_scores`
กับ `student_group_member` ไว้ชี้ไปที่คนที่ไม่ได้อยู่ในห้องแล้ว นี่คือความล้มเหลวแบบเดียวกับที่
ประโยคของตั๋วเองพูดถึง (*keeps marks from ever attaching to an unknown person*) แค่กลับหัวลูกศร

route จึงตรวจเองก่อน `DELETE` และปฏิเสธด้วยสองประโยคที่บอกทางออกคนละทาง เหมือน `cloHasScores`
กับ `cloInUse` ของ #27 หนึ่งขั้นลงมา

ผลข้างเคียงที่ต้องรู้ก่อนเดิน — **นักศึกษาทุกคนใน seed มีคะแนนแล้ว จึงนำออกไม่ได้สักคน**
แถวที่ต้องเดินการนำออกสำเร็จจึงต้อง **เพิ่มคนเข้ามาก่อนแล้วค่อยนำออก** ใบนี้เขียนไว้อย่างนั้นแล้ว

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

**ต้อง reset + seed ใหม่จริง ๆ ก่อนเดินใบนี้** ด้วยเหตุผลเดียวกับ #24 และ #27 — `db/term.js`
ทำให้ seed เดินตามนาฬิกา ฐานข้อมูลที่ seed ไว้ก่อนหน้าจะไม่ได้อยู่ในเทอมปัจจุบันอีกแล้ว

**ต้อง kill แล้ว start backend ใหม่ก่อนเดิน** — `backend/package.json` คือ `node server.js`
ไม่มี reload process ที่ค้างจากตั๋วก่อนจะตอบ 404 ให้ทุก route ของ #25 ในขณะที่ frontend
(`react-scripts start`) hot-reload ตามปกติ **หน้าจอจึงดูใหม่ทั้งที่ server เป็นของเก่า**
ตรวจด้วยการ login แล้วยิง `GET /api/teaching/sections/1/students` หนึ่งครั้ง ต้องได้ 200
พร้อมรายชื่อ ไม่ใช่ 404 (การยิงแบบไม่ login ตรวจอะไรไม่ได้ — ทุก path ใต้ `/api` ตอบ 401 เหมือนกันหมด)

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือ `deep-core-local` — ค่าของตัวแปร `PASSWORD` ใน `db/seed.js`

ทางเข้าหน้านี้คือ เลือกตอนเรียนจากหน้า *รายวิชา* แล้วกดเมนู **รายชื่อนักศึกษาของรายวิชา** ทางซ้าย
ที่อยู่ที่ได้คือ `/teacher/teacherDashboard/<section_id>/subjectStudents`

seed หลังเดินคำสั่งข้างบนมีรูปร่างที่ใบนี้ต้องใช้พอดี

| `section_id` (ที่อยู่) | ปีการศึกษา | ตอนเรียน | ผู้สอน | นักศึกษา |
|---|---|---|---|---|
| `1` | 2569 (ปัจจุบัน) | 1 | `teacher.one@` | 57 คน รหัส `66010001`, `66010003`, … (เลขคี่) |
| `2` | 2569 (ปัจจุบัน) | 2 | `multi.role@` | 56 คน รหัส `66010002`, `66010004`, … (เลขคู่) |
| `3` | **2568 (ปีก่อน)** | 1 | `teacher.one@` | 60 คน รหัส `65010001` ถึง `65010060` |

สองคอลัมน์แรกไม่ใช่สิ่งเดียวกัน — ตอนเรียนที่ **1** ของปีก่อนมี `section_id` เป็น **3**

- `teacher.one@` — สอนตอนเรียน `1` ทั้งเทอมนี้และปีก่อน
- `multi.role@` — สอนตอนเรียน `2` ของการเปิดสอนเดียวกัน **ต้องสลับเป็น อาจารย์ผู้สอน ก่อน**
- `teacher.two@` — ไม่ได้สอนอะไรเลย ใช้เดินการปฏิเสธข้ามตอนเรียน

**รหัสที่ใช้เดินการเพิ่ม คือ `65010001`** เพราะมันอยู่ในทะเบียนกลางแล้ว (รุ่นปีก่อน) แต่
**ไม่ได้อยู่ในตอนเรียนของปีนี้** นักศึกษาทั้ง 113 คนของปีนี้ถูกลงทะเบียนไปหมดแล้ว จึงไม่มีใครในรุ่นนี้
เหลือให้เพิ่ม — คนที่เรียนซ้ำคือสิ่งที่รหัสนี้แทน และเป็นการลงทะเบียนที่ถูกต้องจริง ไม่ใช่การดัดข้อมูล

**รหัสที่ทะเบียนไม่มีคือ `99019999`** อยู่นอกทั้งสองรุ่นตั้งแต่สองหลักแรก

- **ประโยคไฟล์ผิดหน้าจอไม่ตรงกับที่ใบเดินเขียน** ใบเดินยกร่าง *ไฟล์ที่อัปโหลดไม่ใช่แบบฟอร์มของหน้านี้*

  สาระของแถว — ประโยคเดียว ไม่ใช่รายงานทีละบรรทัด และตัวเลขไม่ขยับ — ผ่านทั้งคู่

  จึงพิสูจน์ด้วยการไล่อ่านทุกหน้าจาก endpoint เดียวกับที่หน้าจอดึง (`/api/students` ครบ 173 ราย
  จาก 18 หน้า) — ไม่มี `99019999` และตัวเลขหน้าจอกับ API ตรงกันที่ 173
- **แถวแบบฟอร์มดาวน์โหลด** ตรวจจาก response ของ endpoint ที่ปุ่มเรียก
  (`Content-Disposition: section-students-template.csv`, บรรทัดสอง `66019999`)

## รายการที่โหลดใหม่ถูกแทนที่ — #140 (17 ก.ย. 2569)

### มัตแตนต์

การแก้คือสองจุด จึงมีมัตแตนต์จุดละตัว (#125) — `programid` ให้จอวาด `program_id` กลับไป
(คือจอก่อนแก้) และ `programidfromroute` ให้ route ส่งรหัสกลับมาในฟิลด์ของชื่อ ซึ่งมัตแตนต์ของจอมองไม่เห็น
สองตัวนี้เปลี่ยนแค่ *ชื่อหรือรหัส* จึงมองไม่เห็นว่าชื่อเป็นของหลักสูตรที่ถูกหรือไม่ (#96) ตัวที่สาม
`oneprogramme` ให้ subquery ตอบชื่อของ 0501 ให้ทุกคน — มีแต่นักศึกษา 0503 ที่เขียนเพิ่มเท่านั้นที่ฆ่ามันได้
กวาดเมื่อ 19 ก.ย. 2569 ด้วย `25a` — baseline **15 ผ่านทั้ง 15** และทั้งสามตัว**ล้ม 1 ผ่าน 14**
ที่แถว #106 ที่ `toEqual` ไม่ใช่ที่ timeout ส่วน `oneprogramme` ทำให้แถวของ backend suite ล้มเพียงแถวเดียว
