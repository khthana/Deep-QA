# ตรวจรับด้วยมือ — #25 Section enrolment

`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #25

ครึ่งแรกอยู่ที่ `backend/test/enrolment.test.js` (21 subtests) — เกณฑ์ทั้งเก้าข้อที่พิสูจน์ได้ที่ seam
ของ HTTP surface ถูกพิสูจน์ที่นั่นแล้ว

seam ที่สองคือเบราว์เซอร์ — `e2e/tests/25a-section-enrolment.spec.js` (12 แถว) ดูหัวข้อ
*มัตแตนต์ที่พิสูจน์แถว ⚙* ท้ายเอกสาร ซึ่งเป็นเหตุผลว่าทำไมแถวเหล่านั้นถึงถือว่าครอบแล้วจริง

## หน้าจอนี้ต่างจาก #27 ตรงไหน

สองหน้านี้เข้าจากที่เดียวกัน หน้าตาคล้ายกัน และ **grain ไม่เหมือนกันเลย**

**ผลการเรียนรู้รายวิชาเป็นของการเปิดสอน แต่รายชื่อนักศึกษาเป็นของตอนเรียน** ADR-0003 ผูกชุด CLO
ไว้กับ (หลักสูตร, รายวิชา, ปีการศึกษา) `clos.js` จึงแปลง `section_id` เป็น Offering ทุกคำขอ และ
ตอนเรียนสองตอนของรายวิชาเดียวกันเห็นชุดเดียวกัน **การลงทะเบียนไม่ใช่แบบนั้น** ตอนเรียนสองตอนคือ
สองห้องเรียน มีนักศึกษาคนละกลุ่ม ซึ่งเป็นเหตุผลทั้งหมดที่ตอนเรียนมีอยู่ `enrolment.js` จึงหยุดที่
ตอนเรียนและไม่แตะการเปิดสอนเลย — มัตแตนต์ `offeringgrain` คือการเขียนหน้านี้แบบ `clos.js`
และมันทำให้ทั้ง 113 คนไปโผล่บนหน้าจอของทั้งสองตอนเรียน

**ทะเบียนกลางเป็นคนละเรื่องกับรายชื่อของห้อง** #17 สร้างทะเบียน นี่คือการเลือกคนจากทะเบียนนั้น
รหัสที่ทะเบียนไม่มี **ถูกปฏิเสธพร้อมประโยคที่บอกว่าให้ไปเพิ่มที่ไหน** ไม่ใช่ถูกสร้างขึ้นตรงนี้
`student_course.student_id` เป็น foreign key อยู่แล้ว ฐานข้อมูลจึงกันไว้ให้อยู่แล้ว สิ่งที่ route
เพิ่มเข้ามาคือ **ประโยค** — 23503 ที่หลุดไปถึง error handler ตอบว่า *เกิดข้อผิดพลาดในระบบ*

**ไม่มีใครถูกบันทึกว่าเป็นคนเพิ่มใคร** `student_course` มีแค่ `created_at` ไม่มี `created_by`
(ADR-0001 tier 2) และตอนเรียนหนึ่งมีผู้สอนได้สองคน คำถามว่า *ใครเพิ่มนักศึกษาคนนี้* จึงไม่มีคำตอบ
ที่นี่ #25 ไม่ได้ถาม และ #27 มี `updated_by` เพราะตั๋วนั้นถาม

## การนำออกถูกกั้นไว้สองด่าน ซึ่ง #25 ไม่ได้ขอ

**ไม่มีตารางไหนอ้างถึง `student_course` เลย** `DELETE` จึงสำเร็จเสมอ และจะทิ้ง `activity_scores`
กับ `student_group_member` ไว้ชี้ไปที่คนที่ไม่ได้อยู่ในห้องแล้ว นี่คือความล้มเหลวแบบเดียวกับที่
ประโยคของตั๋วเองพูดถึง (*keeps marks from ever attaching to an unknown person*) แค่กลับหัวลูกศร

route จึงตรวจเองก่อน `DELETE` และปฏิเสธด้วยสองประโยคที่บอกทางออกคนละทาง เหมือน `cloHasScores`
กับ `cloInUse` ของ #27 หนึ่งขั้นลงมา

ผลข้างเคียงที่ต้องรู้ก่อนเดิน — **นักศึกษาทุกคนใน seed มีคะแนนแล้ว จึงนำออกไม่ได้สักคน**
แถวที่ต้องเดินการนำออกสำเร็จจึงต้อง **เพิ่มคนเข้ามาก่อนแล้วค่อยนำออก** ใบนี้เขียนไว้อย่างนั้นแล้ว

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

**ต้อง reset + seed ใหม่จริง ๆ ก่อนเดินใบนี้** ด้วยเหตุผลเดียวกับ #24 และ #27 — `db/term.js`
ทำให้ seed เดินตามนาฬิกา ฐานข้อมูลที่ seed ไว้ก่อนหน้าจะไม่ได้อยู่ในเทอมปัจจุบันอีกแล้ว

**ต้อง kill แล้ว start backend ใหม่ก่อนเดิน** — `backend/package.json` คือ `node server.js`
ไม่มี reload process ที่ค้างจากตั๋วก่อนจะตอบ 404 ให้ทุก route ของ #25 ในขณะที่ frontend
(`react-scripts start`) hot-reload ตามปกติ **หน้าจอจึงดูใหม่ทั้งที่ server เป็นของเก่า**
ตรวจด้วยการ login แล้วยิง `GET /api/teaching/sections/1/students` หนึ่งครั้ง ต้องได้ 200
พร้อมรายชื่อ ไม่ใช่ 404 (การยิงแบบไม่ login ตรวจอะไรไม่ได้ — ทุก path ใต้ `/api` ตอบ 401 เหมือนกันหมด)

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือ `deep-core-local` — ค่าของตัวแปร `PASSWORD` ใน `db/seed.js`

ทางเข้าหน้านี้คือ เลือกตอนเรียนจากหน้า *รายวิชา* แล้วกดเมนู **รายชื่อนักศึกษาของรายวิชา** ทางซ้าย
ที่อยู่ที่ได้คือ `/teacher/teacherDashboard/<section_id>/subjectStudents`

seed หลังเดินคำสั่งข้างบนมีรูปร่างที่ใบนี้ต้องใช้พอดี

| `section_id` (ที่อยู่) | ปีการศึกษา | ตอนเรียน | ผู้สอน | นักศึกษา |
|---|---|---|---|---|
| `1` | 2569 (ปัจจุบัน) | 1 | `teacher.one@` | 57 คน รหัส `66010001`, `66010003`, … (เลขคี่) |
| `2` | 2569 (ปัจจุบัน) | 2 | `multi.role@` | 56 คน รหัส `66010002`, `66010004`, … (เลขคู่) |
| `3` | **2568 (ปีก่อน)** | 1 | `teacher.one@` | 60 คน รหัส `65010001` ถึง `65010060` |

สองคอลัมน์แรกไม่ใช่สิ่งเดียวกัน — ตอนเรียนที่ **1** ของปีก่อนมี `section_id` เป็น **3**

- `teacher.one@` — สอนตอนเรียน `1` ทั้งเทอมนี้และปีก่อน
- `multi.role@` — สอนตอนเรียน `2` ของการเปิดสอนเดียวกัน **ต้องสลับเป็น อาจารย์ผู้สอน ก่อน**
- `teacher.two@` — ไม่ได้สอนอะไรเลย ใช้เดินการปฏิเสธข้ามตอนเรียน

**รหัสที่ใช้เดินการเพิ่ม คือ `65010001`** เพราะมันอยู่ในทะเบียนกลางแล้ว (รุ่นปีก่อน) แต่
**ไม่ได้อยู่ในตอนเรียนของปีนี้** นักศึกษาทั้ง 113 คนของปีนี้ถูกลงทะเบียนไปหมดแล้ว จึงไม่มีใครในรุ่นนี้
เหลือให้เพิ่ม — คนที่เรียนซ้ำคือสิ่งที่รหัสนี้แทน และเป็นการลงทะเบียนที่ถูกต้องจริง ไม่ใช่การดัดข้อมูล

**รหัสที่ทะเบียนไม่มีคือ `99019999`** อยู่นอกทั้งสองรุ่นตั้งแต่สองหลักแรก

## รายการที่ต้องเดิน

ช่องสุดท้ายมีสี่ค่า

- **☑** เดินด้วยมือจบแล้ว หรือพิสูจน์ที่ seam HTTP แล้ว — **สองอย่างนี้เป็น ☑ เท่ากัน** ⚙ สงวนไว้ให้ browser seam เท่านั้น และแถวบอกเองว่าอะไรพิสูจน์มัน (`CLAUDE.md` §Marks on the sheets · [#194](https://github.com/khthana/Deep-QA/issues/194))
- **◐** เดินไปได้ครึ่งเดียว อีกครึ่งยังไม่ได้เดิน — **แถวนั้นบอกไว้เองว่าครึ่งไหนยังขาด และครึ่งนั้นรออะไร** · ส่วนใหญ่ครึ่งที่เดินแล้วคือครึ่งของ server และครึ่งที่เหลือคือสิ่งที่หน้าจอวาด (แถบสี ตาราง dropdown) ซึ่งยังต้องมีคนดู — **แต่นั่นเป็นกรณีที่พบบ่อย ไม่ใช่นิยาม** ครึ่งที่เหลือรออยู่สามอย่าง คือ **คน** (เช่น attribute ที่ไปถึง DOM แล้ว แต่ยังไม่มีใครเปิดโปรแกรมอ่านหน้าจอฟัง) · **ตั๋ว** ซึ่งแถวจะอ้างเลขไว้ · หรือ **ไม่รออะไรเลย** เพราะไม่มีตัวควบคุมบนจอสร้างคำขอนั้นได้ ซึ่งเป็น ◐ ถาวรโดยโครงสร้าง — **สามอย่างนี้นับแยกกัน** (`CLAUDE.md` §Marks on the sheets · [#157](https://github.com/khthana/Deep-QA/issues/157))
- **☐** ยังไม่ได้เดิน
- **⚙** ครอบคลุมด้วย browser seam แล้ว (#65) ไม่ต้องเดินด้วยมือซ้ำ แถวบอกไฟล์ที่ครอบคลุมไว้ และมาร์กนี้ได้มาเมื่อมัตแตนต์ฆ่า assertion ของแถวนั้นเอง — **ถ้าแถวนั้นพูดถึงสิ่งที่วาดด้วย (เมนู ถ้อยคำ สี) ครึ่งนั้นยังเป็นงานของคนเดิน และแถวจะเขียนกำกับไว้** (`CLAUDE.md` §Two test seams · [#194](https://github.com/khthana/Deep-QA/issues/194))

สิ่งที่พบระหว่างเดินซึ่งใบเดินไม่ได้คาดไว้ สามเรื่อง ไม่มีเรื่องไหนเป็นข้อบกพร่องของหน้าจอ:

- **ประโยคไฟล์ผิดหน้าจอไม่ตรงกับที่ใบเดินเขียน** ใบเดินยกร่าง *ไฟล์ที่อัปโหลดไม่ใช่แบบฟอร์มของหน้านี้*
  แต่ประโยคจริงบนแถบคือ `REFUSALS.importWrongTemplate` ตรงทุกตัวอักษร
  (*หัวคอลัมน์ในไฟล์ไม่ตรงกับแบบฟอร์มของหน้านี้ — ตรวจว่าดาวน์โหลดแบบฟอร์มมาจากหน้าถูกหรือไม่*)
  สาระของแถว — ประโยคเดียว ไม่ใช่รายงานทีละบรรทัด และตัวเลขไม่ขยับ — ผ่านทั้งคู่
- **หน้า *ข้อมูลนักศึกษากลาง* ไม่มีช่องค้นหา** (มีแต่ตัวกรองหลักสูตร) แถว *ไม่มีนักศึกษาครึ่งใบ*
  จึงพิสูจน์ด้วยการไล่อ่านทุกหน้าจาก endpoint เดียวกับที่หน้าจอดึง (`/api/students` ครบ 173 ราย
  จาก 18 หน้า) — ไม่มี `99019999` และตัวเลขหน้าจอกับ API ตรงกันที่ 173
- **แถวแบบฟอร์มดาวน์โหลด** ตรวจจาก response ของ endpoint ที่ปุ่มเรียก
  (`Content-Disposition: section-students-template.csv`, บรรทัดสอง `66019999`)
  แทนการเปิดไฟล์จากดิสก์ — เนื้อไฟล์เดียวกัน

**แถวจอแคบ (#98)** ที่ครึ่งจอจริง (755px) ตารางบีบพอดีจึงยังไม่ต้องมีแถบเลื่อน — คอลัมน์ *จัดการ*

## คำปฏิเสธของการโหลดใหม่ชนะประโยคว่าบันทึกแล้ว — #152 (10 ต.ค. 2569)

#152 เป็นตั๋ว `question` และคำตอบของเจ้าของงานคือ **คำปฏิเสธชนะ** (10 ต.ค. 2569) — บันทึกสำเร็จแต่การอ่านรายการใหม่ถูกปฏิเสธ จอต้องพูดคำปฏิเสธ ไม่ใช่บอกว่าบันทึกแล้ว เพราะ `load` จับความล้มเหลวของตัวเองแล้วคืนค่าปกติ ประโยคสำเร็จที่อยู่หลังมันจึงทับคำปฏิเสธ คนจึงได้ยินว่าบันทึกสำเร็จ และไม่ได้ยินอะไรเลยเกี่ยวกับรายการที่อยู่ตรงหน้า

ที่วัดได้ไม่ใช่เจ็ดจอเจ็ดจุดอย่างที่ตั๋วเขียน แต่เป็น **สิบแฟ้ม สิบแปดจุด** — นับด้วยกลไก (*handler คอยสิ่งที่โยนไม่ได้ แล้วบอกว่าสำเร็จ*) ไม่ใช่ด้วยคำว่าจอของผู้สอน (#174) ตั๋วยังเขียนว่าคำปฏิเสธรอดเมื่อมีฟอร์มอื่นเปิดทีหลัง ซึ่งจริงกับสิบสี่จุด แต่สี่จุด (`GradingWeights.save` `StudentGroups.after` `SubjectStudents.add` `SubjectStudents.remove`) ไม่มี `showing.current` คุมอยู่เลย ข้อยกเว้นนั้นจึงไม่เคยใช้กับมัน และเลขบรรทัดสองคู่ในตารางของตั๋วเลื่อนไปแล้วห้าและหกบรรทัด

ทางแก้ไม่ใช่การสลับลำดับอย่างที่อีกสิบแฟ้มทำ: วัดแล้ว `149a` **ล้ม 14 แถว** เพราะประโยคที่ขึ้นก่อนการโหลดขึ้นก่อนที่ด่านจะเห็นว่าคนย้ายไปไหนแล้ว มันจึงไปนั่งทับฟอร์มที่ดินสออีกอันเพิ่งเปิด `load` ของทั้งสิบแฟ้มจึงคืนค่าว่าวาดสำเร็จหรือไม่ (`return true` ท้าย `try` `return false` ท้าย `catch` — `finally` ไม่คืนค่า จึงไม่ทับคำตอบไหน) และทุก handler ถามสองคำถาม — วาดใหม่สำเร็จไหม และจอยังอยู่ที่เดิมไหม ครึ่งแรกคือใบนี้ ครึ่งหลังคือ #149 ซึ่งยังเขียว

ทุกแถว **เดินด้วยมือไม่ได้** การเขียนถูกตอบด้วย 200 ที่แต่งขึ้น และการโหลดที่ตามมาด้วย 409 ที่แต่งขึ้น (`e2e/support/gate.js`) การบันทึกจึงไม่แตะฐานข้อมูล ไม่มีแถวไหนในใบนี้เขียนอะไรลงฐานข้อมูลเลย เข้าด้วย `teacher.one@kmitl.ac.th` ครอบคลุมโดย describe *SubjectStudents.js* ใน `152a-the-refusal-wins.spec.js` จุดอ่านคือหลังคำปฏิเสธถึงหน้า แล้ว 250 ms อ่านครั้งเดียว (#50 #52) และอ่าน**ทั้งสองครึ่ง** คำปฏิเสธต้องอยู่ 1 ครั้ง ไม่ใช่แค่ประโยคสำเร็จไม่อยู่ เพราะจอที่ไม่พูดอะไรเลยก็ผ่านครึ่งหลัง และตัวอ่านที่เล็งสิ่งที่ไม่เคยถูกวาดก็อ่านว่าว่างทั้งสองทาง (#171)

### มัตแตนต์

- `152:enrolmentaddanyway` **ล้ม 1 ผ่าน 17** (1.1 นาที) ที่แถว *an enrolment whose reload is refused says the refusal and not that it enrolled* แถวเดียว
- `152:enrolmentremovalanyway` **ล้ม 1 ผ่าน 17** (1.1 นาที) ที่แถว *a removal whose reload is refused says the refusal and not that it removed* แถวเดียว

มัตแตนต์แต่ละตัวเอา `reloaded` ออกจากเงื่อนไขของจุดตัวเอง คือโค้ดก่อน #152 เป๊ะ ๆ กวาดทั้งสิบแปดตัวของใบ `152` เมื่อ 10 ต.ค. 2569 ทีละตัวด้วย `152a` ทั้งไฟล์ — baseline **18 ผ่านทั้ง 18** (1.0 นาที) และทุกตัวฆ่าแถวของตัวเองแถวเดียว อ่านจากชื่อแถวในล็อก ไม่ใช่จากจำนวน

#152 ทำให้สามสิบหกตัวในแปดแฟ้มหลุดสมอ เพราะมันยกสองบรรทัดที่สมอเล็งอยู่ — `149` ยี่สิบแปดตัว `140` สองตัวของจอนักศึกษา `25:addstaysonpage` และ `savenoreload` ของ `27` `28` `29` `30` `31` สามสิบเอ็ดตัวเล็งใหม่ด้วยการเติม `reloaded` อย่างเดียวกัน ส่วนห้าตัวที่ *ลบ* การโหลดทิ้งนั้นเติมไม่ได้ เพราะ `reloaded` จะไม่มีตัวตนและแอปหยุดทั้งตัว ห้าตัวนั้นใส่ `const reloaded = true` แทน — ข้ออ้างเดิมในโค้ดที่ยังรันได้

กวาดซ้ำสามสิบสามตัวที่เล็งใหม่ ครบทั้งสามสิบสามเมื่อ 10–11 ต.ค. 2569 — การตรวจสมอบอกว่ามัตแตนต์ยังใช้ได้ มีแต่การกวาดที่บอกว่ามันยังค้ำอะไรอยู่ (#107 #68) `savenoreload` ทั้งห้า (`27a` ล้มแถว 4 กับ 8 · `28a` และ `29a` ล้มแถว 3 · 4 · 5 · `30a` ล้มแถว 3 กับ 5 · `31a` ล้มแถว 2 · 3 · 4) และยี่สิบแปดตัวของ `149` ที่ **ล้ม 1 ผ่าน 28** ตัวละแถวของจอตัวเอง อ่านจากชื่อแถวในล็อก ไม่ใช่จากจำนวน — `27` `28` `29` ตรงกับตารางของใบตัวเองเป๊ะ และ `30` ตรงกับการกวาดซ้ำ 17 ก.ย. 2569 ที่ตารางบันทึกไว้แล้ว ส่วน **`31:savenoreload` ล้มน้อยกว่าที่ตารางบันทึก** — แถว 5 · 6 · 8 ที่เคยตายจากการปนเปื้อนผ่านแล้ว เพราะมัตแตนต์ที่ *แทนค่า* ยังเรียกการโหลดอยู่ การเก็บกวาดของแถว 2–4 จึงขึ้นบนจอและครบ การปนเปื้อนนั้นเป็นผลของการ *ลบ* ไม่ใช่ของข้ออ้าง และข้ออ้างของแถว 3 ยังถูกค้ำเหมือนเดิม

สี่ตัวของ `ContinuousImprovement.js` ตกไปในการกวาดรอบ 10 ต.ค. — ตัวหนึ่งเบราว์เซอร์ล้มกลางรัน (`Target crashed` แล้ว worker ออกเอง) ซึ่งเป็นสีแดงที่ไม่ใช่การวัด และอีกสามตัวถูกตัดกลางคันตอนหยุดการกวาด จึงทิ้งทั้งสี่ (#146) และกวาดใหม่ทั้งชุดจาก baseline ใหม่เมื่อ 11 ต.ค. 2569 — baseline **29 ผ่านทั้ง 29** (2.7 นาที) และทั้งสี่ตัว **ล้ม 1 ผ่าน 28** ที่แถวของตัวเอง

### ครึ่งหลัง — ทางที่ย้ายหน้าแทนที่จะอ่าน (11 ต.ค. 2569)

จอนี้มีสองทางที่ `load` ไม่ได้ถูกเรียก: `reload` ของการเพิ่ม ซึ่งขอหน้าแรกด้วยการ `setPage(1)` และการนำออกคนสุดท้ายของหน้า ซึ่งถอยไปหน้าก่อนด้วย `setPage(page - 1)` การอ่านที่ตามมาเป็นของ effect ไม่ใช่ของ handler จึงไม่มีอะไรให้ `await` และรอบแรกของ #152 เขียนว่า `return true` พร้อมคอมเมนต์ว่า *ไม่มีอะไรถูกปฏิเสธในทางนั้น* — **คอมเมนต์นั้นเป็นข้ออ้าง ไม่ใช่การวัด** สิ่งที่ถูกปฏิเสธคือการอ่านที่ทางนั้นเพิ่งขอมาเอง

วัดทีละเฟรม (#164) เมื่อ 11 ต.ค. 2569 บนทางของการเพิ่มจากหน้า 2: ประโยค *…เข้าตอนเรียนแล้ว* ขึ้นบนจอ **1 เฟรมจาก 30** เมื่อคำปฏิเสธถูกตอบทันที และ **19 จาก 47** เมื่อถือคำปฏิเสธไว้ 300 ms — คือประโยคเดียวที่คำตอบของเจ้าของงานบอกว่าต้องไม่พูด

ทางแก้: handler ฝากประโยคไว้ที่ ref ชื่อ `waiting` แล้วบอกผู้เรียกว่าอย่าพูด `load` พูดประโยคนั้นเมื่อมันวาดสำเร็จ และ `finally` ทิ้งมันทุกครั้ง — การอ่านที่ถูกปฏิเสธ หรือที่จอย้ายไปแล้ว จึงไม่มีประโยคค้าง

แถวของการนำออกต้องมีหน้าที่ 2 ที่เหลือนักศึกษาคนเดียว ซึ่งรายการที่ seed มีห้าสิบกว่าคนสร้างไม่ได้ และเงื่อนไขอยู่ใน handler ไม่ใช่ในข้อมูล **ของจริงที่ถูกตัด** จึงเป็นสิ่งที่ทำให้ข้ออ้างนั้นเอื้อมถึง (#96) — `total` `page` และ `section` ยังเป็นของ server และคำตอบของหน้าอื่นผ่านไปตามเดิม

**สองแถวนี้อ่านที่จุดสงบไม่ได้** รอบแรกเขียนอย่างนั้น และ `152:enrolmentmovedanyway` กับ `152:enrolmentmovedremovalanyway` **รอดทั้งคู่ (21 ผ่านทั้ง 21)** เพราะคำปฏิเสธที่มาทีหลัง *ทับ* ประโยคสำเร็จ จุดสงบจึงเห็นแต่คำปฏิเสธ และแถวก็ผ่านบนโค้ดที่มันถูกเขียนขึ้นมาจับ — ผู้รอดชีวิตบอกว่าแถวอ่านผิดเวลา ไม่ได้บอกว่าข้ออ้างไม่เคยถูกเสี่ยง

### มัตแตนต์ของครึ่งหลัง

- `152:enrolmentmovedanyway` **ล้ม 1 ผ่าน 20** ที่แถว *an enrolment from another page says the refusal of the first page and not that it enrolled* แถวเดียว — ตายที่ `expect(seen.saying)` ด้วย **19 เฟรม** ไม่ใช่ที่จุดสงบ
- `152:enrolmentmovedremovalanyway` **ล้ม 1 ผ่าน 20** ที่แถว *a removal that empties a page says the refusal of the page behind it and not that it removed* แถวเดียว — ตายด้วย **18 เฟรม**
- `152:enrolmentdrewunsaid` **ล้ม 1 ผ่าน 20** ที่แถว *an enrolment from another page says it enrolled once the first page is drawn* แถวเดียว

สองตัวแรกคือโค้ดก่อนครึ่งหลังเป๊ะ ๆ (`setPage` แล้ว `return true` · `setPage(page - 1)` แล้วพูดเอง) ตัวที่สามลบบรรทัดที่ `load` พูดประโยคที่ฝากไว้ กวาด 11 ต.ค. 2569 ทีละตัวด้วย `152a` ทั้งไฟล์ — baseline **21 ผ่านทั้ง 21**

ครึ่งหลังยังทำให้สี่ตัวหลุดสมอ เพราะมันยกบรรทัดที่สมอเล็งอยู่ — `140:enrolmentreloadstalewins` `140:enrolmentremovestalewins` `25:addstaysonpage` และ `25:importstaysonpage` (ย่อหน้าของ 10 ต.ค. นับไว้สามตัว ไม่มี `importstaysonpage` เพราะวันนั้น `onImported={reload}` ยังไม่ถูกแตะ) ทั้งสี่เล็งใหม่และกวาดซ้ำวันเดียวกัน: `140:enrolmentreloadstalewins` **ล้ม 2 ผ่าน 30** (แถวของการเพิ่มและของการนำเข้า) `140:enrolmentremovestalewins` **ล้ม 1 ผ่าน 31** `25:addstaysonpage` และ `25:importstaysonpage` **ล้ม 1 ผ่าน 14** ตัวละแถวของตัวเอง — ตรงกับตัวเลขที่ตารางของทั้งสองใบบันทึกไว้ (17 ก.ย. 2569) ทุกตัว

### แถวของหน้า 2 ถูกเล็งใหม่ เพราะ #209 ย้ายคนตัดสินเรื่องหน้า (20 ต.ค. 2569)

แถว *a removal that empties a page says the refusal of the page behind it and not that it removed*
ยืนยันไว้ว่า **การอ่านที่ถูกปฏิเสธถาม `page=1`** และเขียนเหตุผลไว้ว่านั่นคือคำยืนยันว่า handler
เดินทางที่ย้ายหน้า — ซึ่งเป็นข้ออ้างเกี่ยวกับ**กลไก** ไม่ใช่เกี่ยวกับสิ่งที่ #152 จับ คำตอบข้อ ก ของ
เจ้าของงานเมื่อ 19 ต.ค. 2569 เอากลไกนั้นออก: การลบอ่าน**หน้าที่คนยืนอยู่**ใหม่ และ `load` ส่งหน้าต่อ
เมื่อคำตอบบอกว่าหน้านั้นไม่มีแล้ว การอ่านที่ถูกปฏิเสธไม่มีคำตอบ จึงไม่มีการส่งต่อ แถวจึงแดงที่ `page=1`

แถวถูกเล็งใหม่ที่หน้า 2 และข้อความของ assertion บอกว่าเป็นข้ออ้างไหน เพราะในแฟ้มนี้มีสองแถวที่กัก
การอ่านที่ถูกปฏิเสธแล้วอ่านหน้าที่มันถาม (#173) ข้ออ้างของ #152 ที่แถวนี้มีอยู่ไม่แตะเลย — ไม่มีเฟรม

### สิ่งที่ยังไม่ถูกค้ำ — คำตอบของ `load` คือ *ไม่ถูกปฏิเสธ* ไม่ใช่ *วาดแล้ว* (11 ต.ค. 2569)

`load` คืน `true` ท้าย `try` แม้ `isCurrent()` จะเป็นเท็จ คือคำตอบมาถึงแต่ไม่มีอะไรถูกวาด ประโยคที่ *ฝากไว้* ไม่ถูกพูดในกรณีนั้น เพราะ `finally` ล้าง `waiting` ทุกครั้ง แต่ผู้เรียกที่พูดประโยค *เอง* ยังพูด — บนจอนี้คือ `add` ที่หน้าแรกและ `remove` ที่ไม่ใช่คนสุดท้ายของหน้า ซึ่งไม่มี `showing.current === sent` คุมอย่างเจ็ดจอการ์ด

**ทางเข้ามีจริง:** `Pager` ที่บรรทัด 380 ส่ง `onPage={setPage}` และ**ไม่ได้ปิดตอน `busy`** (ที่ปิดคือปุ่มส่งฟอร์ม บรรทัด 281 และปุ่มในกล่องยืนยัน) กด *ถัดไป* ระหว่างที่การเขียนยังค้างอยู่จึงเปลี่ยน `page` → `load` เป็นตัวใหม่ → `isCurrent()` เท็จ → ไม่มีอะไรวาด แต่ประโยคว่าเพิ่มแล้วขึ้นบนหน้าใหม่

## ประโยคที่ฝากไว้บอกว่ามันเป็นของการอ่านไหน — #205 (13 ต.ค. 2569)

#152 ฝากประโยคไว้ที่ ref `waiting` เพราะ handler ที่ย้ายหน้าไม่มีอะไรให้ `await` และ #203 พารูปนั้น
ไปถึงจออีกสิบจอ สิ่งที่ตั๋วนี้วัดคือสองครึ่งของรูปนั้นผิดทั้งคู่ และ **ทางเข้าไม่ต้องมีข้อบกพร่องที่สอง**:
ไม่มี `Pager` บนแปดจอที่ถือ ref นี้ที่รับ `busy` ซึ่ง `add` ของจอนี้วัดไว้เองเมื่อ 11 ต.ค. 2569 (#199)

> **บันทึกลงวันที่ 15 ต.ค. 2569** — ประโยคข้างบนเป็นการวัดของ 13 ต.ค. 2569 วันนี้ `Pager` ของ
> จอนี้รับ `busy` แล้ว (#199 ทางที่หนึ่ง) อีกเจ็ดจอไม่เปลี่ยน (หกจอในนั้นรับเมื่อ 19 ต.ค. 2569
> ด้วยคำตอบของ #210 — ประโยคนี้เป็นการวัดของ 15 ต.ค. 2569) แถวแรกของตารางข้างล่างยังเป็นข้ออ้าง
> โดยย้ายการกด *ถัดไป* ไปอยู่ก่อนการเขียน และแถวที่สองกลายเป็น net — รายละเอียดอยู่บนแถวนั้น

* `finally` ล้าง `waiting.current` **นอก** `isCurrent()` — การอ่านที่ถูกแทนไปแล้วจึงทิ้งประโยคที่ถูกฝาก
  *หลัง* มันออกจากบ้านไป คนที่เพิ่มนักศึกษาสำเร็จไม่ได้ยินอะไรเลย
* `reload` ถูกสร้างบน `page` ของ render ที่มันปิดทับ — handler ที่ออกจากหน้า 2 แล้วพบว่าคนกลับมา
  หน้า 1 สั่ง `setPage(1)` ซึ่งไม่ทำให้เกิดการอ่านใด ประโยคจึงค้างใน ref และ **ถูกพูดโดยการเดิน
  ครั้งถัดไปของคน บนรายการที่ไม่ใช่ของมัน** (คำทำนายของแถวที่เขียนไว้ว่า *ไม่ถูกพูด* ได้ 1 ไม่ใช่ 0)

ทางแก้ที่เจ้าของเลือกคือสองข้อรวมกัน: ref ถือ `{ of, said }` โดย `of` เขียนจาก `readOf` ซึ่งเป็น
รายการ dependency ของ loader เองในค่าเดียว `load` พูดเฉพาะเมื่อกุญแจของการอ่านตัวเองตรง และล้าง
เฉพาะเมื่อการอ่านที่จอยังต้องการลงถึงแล้ว ส่วน `reload` ถามหน้าที่ pager อยู่ **ตอนนี้** จาก ref
`onPage` และอ่านผ่าน `onScreen.current`

**สิ่งที่การวัดเปลี่ยนไปจากที่ตั๋วเขียน**: รอบแรกให้กิ่งที่อ่านเองพูดประโยคเอง แถวที่ 2 ยังแดง เพราะ
`onScreen.current === sent` ของ #202 ปฏิเสธ — `sent` คือ loader ของหน้าที่ handler ออกมา และคน
ย้ายหน้าไปแล้ว ฉะนั้นกิ่งที่อ่านเองต้องฝากประโยคเหมือนอีกกิ่ง แล้วให้กุญแจเป็นคนตัดสิน ซึ่งทำให้

### มัตแตนต์

กวาดเมื่อ 13 ต.ค. 2569 ด้วย `205a` ทั้งไฟล์ ทีละตัว — baseline **4 ผ่านทั้ง 4** (21.6 วินาที) สามตัวข้างล่างอยู่ใน
`mutation/205-the-sentence-names-its-read.py` ตัวที่สี่ของแฟ้มนั้นอยู่บนใบ `17-students.md`

- `205:clearsoutside` **ล้ม 1 ผ่าน 3** (21.7 วินาที) ที่แถวที่ 1 ตายที่
  `the banner of the enrolment, said by the read that drew`
- `205:alwaysmoves` **ล้ม 1 ผ่าน 3** (22.3 วินาที) ที่แถวที่ 2 ตายที่
  `the banner of the enrolment, on the page the person came back to`
- `205:saysanyread` **ล้ม 1 ผ่าน 3** (22.6 วินาที) ที่แถวที่ 3 ตายที่
  `the banner of the enrolment, over a list it is not about`

**สามตัวนี้ถูกกวาดสองครั้ง เพราะสเปกโตขึ้นหนึ่งแถวในวันเดียวกัน** ตัวเลขข้างบนเป็นของรอบที่สอง หลัง code review
เพิ่มแถวที่สี่เข้ามา รอบแรกตอน baseline เป็น **3 ผ่านทั้ง 3** ทั้งสามตัวล้ม **1 ผ่าน 2** ที่แถวเดิมของมันเอง
ที่เปลี่ยนคือจำนวนแถวที่ยืนอยู่ ไม่ใช่แถวที่ตาย — แถวที่สี่อยู่บนจอทะเบียน (`Students.js`)
ส่วนสามตัวนี้อยู่ใน `SubjectStudents.js` จึงเอื้อมไปถึงมันไม่ได้

**แต่ละตัวฆ่าแถวเดียว และคนละแถวกัน** และทุกตัวตายที่ assertion ของแถวนั้นเอง ไม่ใช่ที่ precondition
และไม่ใช่ที่ timeout ซึ่งเป็นสิ่งที่บอกว่ามัตแตนต์ไม่ได้หยุดแอป แต่เอาเฉพาะข้ออ้างออก (#97)

**แถวทั้งสามถูกรันกับโค้ดที่ยังไม่แก้ก่อนเขียนมัตแตนต์** (#203) แถวที่ 1 และ 2 แดงบนโค้ดวันนั้น

### มัตแตนต์

อยู่ใน `mutation/199-the-pager-while-a-write-is-out.py` สามตัว: `nextstayslive` กับ `prevstayslive`
เอา `busy` ออกจากปุ่มของตัวเองใน `Pager.js` — คือโค้ดก่อนตั๋วนี้เป๊ะ ๆ — และ `screenkeepsitquiet`
ให้จอนี้ไม่ส่ง `busy` ลงไปเลย ซึ่งเป็นตัวที่แยก *คอมโพเนนต์รู้กฎ* ออกจาก *จอนี้บอกมัน* ที่สองตัวแรก
แยกไม่ได้ สองตัวแรกอยู่ในโค้ดร่วมของสิบเอ็ดผู้เรียก ใบนี้จึงเป็น*ที่หนึ่ง*ที่มันฆ่า ไม่ใช่รายการทั้งหมด (#123)
และทั้งคู่ค้ำแถว net ของ `205a` ด้วย

ทั้งสามวัด**ทีละแถว**ด้วย `<file>:<line>` ไม่ใช่อ่านจากการรันทั้งแฟ้ม เพราะ `mode: 'serial'` รายงาน
แถวแรกที่ตายแล้วข้ามที่เหลือ (#67): `nextstayslive` ฆ่าแถว 1 กับ 3 และปล่อยแถว 2 ผ่าน ·
`prevstayslive` ฆ่าแถว 2 และปล่อยแถว 1 กับ 3 ผ่าน · `screenkeepsitquiet` ฆ่าทั้งสาม ·
`202:enrolmentaddsaysanyway` กับ `202:enrolmentremovesaysanyway` ยังฆ่าแถวที่เล็งใหม่ของตัวเอง
ตัวละ **ล้ม 1 ผ่าน 9** (ตัวนำออกถอนเป็นบันทึกเมื่อ 19 ต.ค. 2569 ดูหัวข้อ *ถอนเป็นบันทึก* ข้างบน) · `205:clearsoutside` `205:saysanyread` `205:keyforgetsthefilter` ตัวละ
**ล้ม 1 ผ่าน 3** ที่แถวของตัวเอง · `141b` ทั้งแฟ้ม **11 ผ่านทั้ง 11** หลังย้ายทางเดินออกไปเป็นของร่วม

`57:prevalive` กับ `57:nextalive` ถูกเล็งใหม่วันเดียวกัน: ความผิดที่ทั้งสองถืออยู่คือ**กฎปลาย**พูดไม่เป็น
จึงทิ้งครึ่งของตัวเองและปล่อยให้ `busy` ยืนอยู่ แทนที่จะแทนด้วย `false` ซึ่งจะเป็นมัตแตนต์ที่ไม่มีกฎอะไรเลย
และ `199a` จะฆ่ามันด้วย — การเล็งใหม่ที่ซื่อสัตย์คือตัวที่รักษา*ความผิด*ไว้ ไม่ใช่ตัวที่หาบรรทัดถูก (#203)

### สิ่งที่ยังเปิดอยู่

`busy` มีค่าตั้งต้นเป็น `false` ผู้เรียกอีกสิบรายจึงไม่เปลี่ยนเลย — จอที่ยังไม่ถูกวัดไม่ได้อ้างว่าตัวแบ่งหน้า
ของมันปลอดภัย คำถามเดียวกันที่อีกสิบรายนั้นเป็นตั๋วของตัวเอง ไม่ใช่ย่อหน้าในไฟล์นี้ (#119 — การเลื่อน
ที่เขียนไว้ในร้อยแก้วแต่ไม่ได้เขียนลงกระดานคือการตัดสินที่ไม่มีใครหาเจอ)

> **บันทึกลงวันที่ 19 ต.ค. 2569** — **หกจอจากสิบตอบแล้ว** [#210](https://github.com/khthana/Deep-QA/issues/210)
> คือตั๋วที่ย่อหน้านี้เรียกว่า *ตั๋วของตัวเอง* และเจ้าของงานตอบว่าให้ส่ง `busy` ไปที่ตัวแบ่งหน้าของจอ

> และอีกหกจุดตั้งแต่ #210) · **สองจุดถือธง `busy` ของตัวเองอยู่แล้วและไม่ส่งลงไป** คือ
> `Students.js` กับ `Users.js` ซึ่งเป็นรูปเดียวกับที่ #210 ถาม และ **ยังไม่ถูกวัดบนจอ** ·
> อีกสองจุดคือ `components/groups/GroupHistory.js` กับ `components/users/HistoryPanel.js`
> ซึ่งเป็นแผงประวัติที่ไม่เขียนอะไรเลย จึงไม่มีอะไรให้ `busy` เป็น — ปลอดภัยด้วยโครงสร้าง
> ไม่ใช่ด้วยการวัด · สองจุดที่เหลือยังเป็น **ตั๋วของตัวเอง** ไม่ใช่ย่อหน้าในไฟล์นี้ (#119)
