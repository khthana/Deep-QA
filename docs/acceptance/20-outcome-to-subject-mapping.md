# ตรวจรับด้วยมือ — #20 การเชื่อมโยงผลการเรียนรู้กับรายวิชา

`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #20

ครึ่งแรกอยู่ที่ `backend/test/plo-mapping.test.js` (14 subtests) — ทุกเกณฑ์ที่พิสูจน์ได้ที่ seam ของ
HTTP surface ถูกพิสูจน์ที่นั่นแล้ว รวมทั้ง **เกณฑ์ข้อ 7 ทั้งข้อ** ซึ่งเป็นข้อความเกี่ยวกับเทสต์เอง คือ
ระดับทั้งห้าเขียนได้ครบทุกตัว ค่าที่ไม่ใช่หนึ่งในห้า (`'X'`, `'e'`, `''`, `null`, `'Introduced'`) ถูกปฏิเสธ 400
และการบันทึกซ้ำที่ช่องเดิม *แก้ของเดิม* จนเหลือแถวเดียว ไม่ใช่เพิ่มแถวที่สอง

ตั้งแต่ #65 มี seam ที่สองคือเบราว์เซอร์ — `e2e/tests/20a-plo-mapping.spec.js` 8 ข้อทดสอบ
ดูหัวข้อ *มัตแตนต์* ท้ายเอกสารว่าแต่ละแถว ⚙ ถูกพิสูจน์ด้วยการทำอะไรพัง

## สิ่งที่ตั๋วเขียนไว้แล้วโค้ดตีความต่างไป และทำไม

**เกณฑ์ข้อ 3 ไม่ใช่การปฏิเสธ แต่เป็นการแก้ทับ** ตั๋วเขียนว่า *"Saving an already-set cell updates it
rather than creating a second mapping"* — primary key ของ `subject_plo_mapping` คือ
`(program_id, subject_id, outcome_id)` (ADR-0001 ชั้นสอง) แถวที่สองจึงเกิดไม่ได้อยู่แล้วโดยตัวฐานข้อมูล
สิ่งที่เกณฑ์ข้อนี้ *เลือก* จริง ๆ คือระหว่าง **ปฏิเสธ 409** กับ **แก้ทับ** และมันขอแบบหลัง
route จึงเป็น `ON CONFLICT ... DO UPDATE` ไม่ใช่ guard ที่ตอบ 409

**เกณฑ์ข้อ 4 คือ *ไม่มีแถว* ไม่ใช่แถวที่ว่าง** `db/migrations/0002_offerings_and_learning_outcomes.sql`
เขียนไว้สองประโยคที่ตัดสินเรื่องนี้ คือ `createEmptyMapping` เป็นโค้ดที่ไม่มีใครเรียก
รายวิชาที่ยังไม่ระบุจึงคือรายวิชาที่ *ไม่มีแถวเลย* และ `'E'` แปลว่าผลการเรียนรู้ข้อที่ระบุชื่อไว้ข้อนั้น
**ไม่ได้** ถูกสอนในรายวิชานี้ ซึ่งแคบกว่าความเงียบ ระบบที่นักศึกษาส่งมอบทำกลับกันทั้งสองข้อ
— มันเขียนแถว placeholder ที่แปลว่าสิ่งเดียวกับความเงียบ และทิ้งความต่างนั้นไป
หน้าจอกับ PDF ในตั๋วนี้จึงต้องวาด *ช่องว่าง* กับ *`–`* ให้ต่างกัน และนั่นเป็นแถวหนึ่งใน checklist นี้

**`FACULTY_ADMIN` ไม่เข้าหน้านี้** — [#79](https://github.com/khthana/Deep-QA/issues/79) ระบุ **A10 ซึ่งคือหน้านี้**
ไว้ตรง ๆ `MAINTAINERS` ของ route จึงมีแค่ `PROG_MANAGER` กับ `DEPT_ADMIN`
และ `FacultyAdmin.js` ไม่มีรายการเมนูนี้

**หน้านี้ไม่สร้าง PLO ให้เอง** ตัวตั๋วเขียนไว้เองว่า *"A PLO must already exist before it can be mapped"*
หลักสูตรที่ยังไม่มี PLO จึงได้ประโยคที่บอกให้ไปกำหนด PLO ก่อน ไม่ใช่ตารางว่าง ๆ ที่ไม่บอกอะไร

**ไม่มีปุ่มบันทึก** เลือกแล้วเขียนทันทีทีละช่อง ตารางกว้าง ๆ ที่ต้องกดบันทึกทีเดียวตอนจบ
คือตารางที่คนทำงานครึ่งชั่วโมงแล้วปิดหน้าต่างทิ้ง

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js:58`
อีเมลต้องพิมพ์เต็มรวมโดเมน `@kmitl.ac.th`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ผลการเรียนรู้ → การเชื่อมโยงผลการเรียนรู้กับรายวิชา* (`/main/mapping-plo`)

**ต้อง restart backend ก่อนเดิน** — process ที่ค้างจากตั๋วก่อนยังไม่รู้จัก `/api/plo-mapping`
และจะตอบ *ไม่พบเส้นทางที่เรียกบนเซิร์ฟเวอร์นี้* ให้ทุกแถวในใบนี้ (#95)

**สิ่งที่ seed ให้มา และข้อจำกัดที่ตามมา**

- หลักสูตร `0501` มีรายวิชาอยู่ใน `program_subjects` **รายวิชาเดียว** คือ `01076105`
  ตารางตอนเริ่มเดินจึงมี **หนึ่งแถว** คูณด้วยต้นไม้ PLO ของ `0501` (`PLO-1`..`PLO-13` พร้อมข้อย่อย)
- `01076105` ถูก map ไว้แล้วแปดข้อ — `PLO-1` = `I`, `PLO-2` = `P`, `PLO-3` = `D`, `PLO-5` = `D`,
  `PLO-6` = `P`, `PLO-7` = `I`, `PLO-8` = `D`, `PLO-12` = `A` (`db/seed.js:414`)
  ข้อหลักอื่น ๆ ยังว่าง (ข้อย่อยไม่เป็นคอลัมน์แล้วตั้งแต่ #100)
- **หลักสูตร `0503` มี PLO แต่ยังไม่มีรายวิชาเลย** สลับไปดูจะได้ประโยค *หลักสูตรนี้ยังไม่มีรายวิชา*
  ซึ่งถูกต้อง ไม่ใช่ความผิดพลาด
- **`01076105` เป็นรายวิชาเดียวใน seed ทั้งระบบ** ไม่ใช่แค่ในหลักสูตรนี้ แถวที่ต้องการรายวิชาที่สอง
  จึงต้อง *สร้างรายวิชาใหม่* ที่หน้า #16 ก่อน แล้วค่อยใส่เข้าหลักสูตรที่หน้า #18 — ใบนี้เขียนขั้นตอนไว้ตรงแถวนั้น

หลายแถวข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`npm run seed` ใหม่หลังเดินจบ** ก่อนเริ่มตั๋วถัดไป

## รายการที่ต้องเดิน

ช่องสุดท้ายมีสี่ค่า

- **☑** เดินจบแล้ว
- **◐** ครึ่งของ server เดินแล้วและผ่าน ส่วนที่เหลือคือสิ่งที่หน้าจอวาด ยังต้องมีคนดู
- **☐** ยังไม่ได้เดิน
- **⚙** ครอบคลุมด้วย browser seam แล้ว ไม่ต้องเดินด้วยมือซ้ำ ถ้าแถวนั้นพูดถึงสิ่งที่วาดด้วย ครึ่งนั้นยังเป็นงานของคนเดิน และแถวจะเขียนกำกับไว้

## บันทึกการเดินด้วยมือ

**เดินจบรอบแรก** 2026-08-25 — **8 ⚙ · 12 ☑ · 1 แถวเดินแล้วและตก (→ #100)**
แถว ⚙ ทั้งแปดถูกครอบด้วย `20a-plo-mapping.spec.js` และมัตแตนต์ของมันแล้ว (ดูหัวข้อถัดไป)
แถวที่เหลือติ๊กได้จากสิ่งที่ผู้เดินเห็นและรายงานกลับมาเท่านั้น

**#100 เปิดสองแถวขึ้นมาใหม่** — **8 ⚙ · 11 ☑ · 2 ☐** ตอนนี้
เมื่อ grain เปลี่ยนเป็นข้อหลักอย่างเดียว แถวหัวคอลัมน์ที่เดินผ่านมาแล้วพิสูจน์ความต่าง
ระหว่างข้อหลักกับข้อย่อย ซึ่งไม่มีอะไรให้แยกอีกต่อไป และแถวหน้ากระดาษ PDF ที่ตกไป
ก็เป็นคนละคำถามเมื่อคอลัมน์เหลือสิบสาม **แถวที่เดินภายใต้เงื่อนไขที่เปลี่ยนไปแล้ว
ไม่ยกยอดมา** ทั้งสองแถวจึงเขียนใหม่และกลับไปเป็น ☐ รอคนเดิน

**สามแถว ☐ ในนี้เกิดจากการรีวิว ไม่ใช่จากการเขียนครั้งแรก** ฉบับแรกมีแถว ⚙ สามแถวที่เขียนข้อความอ้าง
ถึงสิ่งที่ *มองเห็น* ปนอยู่ในแถวที่บอกว่าเครื่องรับไปแล้ว — สีพื้นช่องที่ระบุแล้ว, การไม่มี dropdown
ให้กรรมการหลักสูตรเลือกหลักสูตรอื่น, และปุ่ม *ส่งออก PDF* ที่ต้องกดไม่ได้บนหน้าที่ถูกปฏิเสธ
ทั้งสามอย่างไม่มี assertion ไหนใน `20a-plo-mapping.spec.js` แตะเลย จึงถูกแยกออกมาเป็นแถวของคนเดิน
`docs/06` §Acceptance เขียนว่าแถวหนึ่ง *"either walked by a person or covered here, never counted twice"*
— แถวที่นับสองครั้งคือแถวที่ไม่มีใครตรวจ

แถวที่คุ้มที่สุดในใบนี้คือ **สระและวรรณยุกต์ใน PDF** — `20a-plo-mapping.spec.js` ยืนยันได้แค่ว่าไฟล์
*พก* ฟอนต์ไทยไปด้วย คำถามว่าฟอนต์นั้นวาง `เ` `ื่` `อ` ถูกตำแหน่งไหม ไม่มีอะไรในเบราว์เซอร์ตอบได้
และเป็นความพังที่ไฟล์ยังดาวน์โหลดได้ ยังเปิดได้ ยังพิมพ์ได้

### สิ่งที่การเดินเจอ

**แถวหัวคอลัมน์ (ข้อ 1)** ตกรอบแรก ข้อย่อเป็น `text-slate-400` ซึ่งผู้เดินบอกว่า
*จางมากไปหน่อย* แก้โดยขยับสองแกน — ข้อย่อเป็น `text-slate-500` และข้อหลักเป็น
`font-semibold text-gray-800` เพราะการทำให้ข้อย่ออ่านง่ายขึ้นอย่างเดียวจะกลืนความต่างกับข้อหลักไป

**คำตอบตอนบันทึก** ผู้เดินสังเกตว่าสีที่เปลี่ยนแยกออกชัด *แต่เงียบไปเฉยๆ*
คำถามที่ตามมาคือ ควรมีข้อความตอนบันทึกสำเร็จหรือไม่ คำตอบคือ **พอ** สีที่เปลี่ยน
คือคำตอบทั้งหมด ไม่เปิดตั๋วใหม่ — และนั่นเป็นการตัดสินใจ ไม่ใช่การมองข้าม

**หน้ากระดาษ PDF (ข้อ 5) ไม่ผ่าน** อักขระไทยถูกหมด ไม่มีกล่องสี่เหลี่ยม
แต่ห้าสิบสองคอลัมน์บนหน้าเดียวแคบจน คำตัดสินของผู้เดินคือ
*"หน้ากระดาษแบบนี้ ไม่มีใครอ่านออกแน่"* แถวนี้จึงเป็น ☐ ที่เดินแล้วและตก
ไม่ใช่แถวที่ยังไม่ได้ไปดู — และสิ่งที่ผู้เดินเสนอต่อจากนั้นคือให้เชื่อมโยงเฉพาะ
PLO ข้อหลัก ไม่ลงไปถึงข้อย่อย ซึ่งเป็นคนละเรื่องกับความกว้างหน้ากระดาษ และขัดกับเกณฑ์ข้อที่หนึ่ง
ของตั๋ว (*every PLO of the Program*) ตรงๆ จึงตัดสินกันนอกใบนี้ — และ #100 ตัดสินให้เชื่อมโยงที่ข้อหลัก โดยแก้เกณฑ์ข้อที่หนึ่ง
ของ #20 เป็น *every main PLO* แทนที่จะฝืนเกณฑ์เดิม

ข้อเท็จจริงที่การอ่านโค้ดที่ส่งมอบพบ: `MappingPLO.js` มี `flattenPlo()` ที่เอาข้อย่อยมาแสดง
เป็นตัวเลือก แต่ใส่ `outcome_id: main.outcome_id` คือ **ไอดีของพ่อ** ลงไป และ
`subjectPloMappingController` ยัง dedupe ด้วย `outcome_id` อีกชั้น แปลว่าระบบที่ส่งมอบ
**เก็บการเชื่อมโยงที่ระดับ PLO ข้อหลักอยู่แล้ว** ข้อย่อยเป็นป้ายชื่อที่กดได้
แต่กดแล้วเขียนทับข้อหลัก การเปลี่ยนมาเป็นข้อหลักอย่างเดียวจึงเป็นการ *คืน* ไม่ใช่การคิดใหม่

เรื่อนี้เปิดเป็น **#100** แล้ว โดยผูก blocked-by ไว้กับ #20 — เดิน #20 ให้จบก่อน
เพราะการเปลี่ยนเกรนกลางคันต้องรื้อ route หน้าจอ e2e มัตแตนต์ และเกณฑ์ข้อ 1 บน GitHub
พร้อมกัน แถวหัวคอลัมน์ที่เพิ่งติ๊กไปจะหมดความหมายเมื่อ #100 ลง และนั่นอยู่ในเกณฑ์ของ #100 แล้ว

อีกสองตั๋วเกิดจากการเดินครั้งนี้ ทั้งคู่เป็นของหน้าอื่น ไม่ใช่ของใบนี้ แต่เจอเพราะตั้งค่า
ข้อมูลให้แถวหลักสูตรที่ไม่มี PLO ต้องเดินผ่านหน้า #19:

- **#101** — หน้า #19 มีตัวเลือก *ทุกหลักสูตร* ซึ่งทำให้ลิสต์ผลการเรียนรู้ของสองหลักสูตรปนกัน
  บนหน้าที่ลบข้อมูลได้ และรหัส PLO ซ้ำกันข้ามหลักสูตร — หน้า #20 ตัดสินใจเรื่องนี้ถูกไว้แล้ว
  ด้วยเหตุผลที่เขียนไว้ใน `PloMapping.js:197`
- **#102** — หลักสูตรใน seed อยู่ภาค `05` ทั้งหมด `reachablePrograms` จึงถูกลบทิ้งได้
  โดยไม่มีเทสต์ไหนล้ม แถว *ผู้ดูแลภาควิชาเข้าถึงทั้งสองหลักสูตร* ในใบนี้จึงผ่านได้บนข้อมูลชุดนี้
  โดยที่ขอบเขตภาควิชาเองยังพิสูจน์ไม่ได้

สองแถวที่ต้องถามซ้ำเพราะคำตอบแรกตอบมาครึ่งเดียว: ปุ่ม *ส่งออก PDF* บนหน้าที่ถูกปฏิเสธ
(*กดไม่ได้* กับ *ดูออกว่ากดไม่ได้* เป็นคนละเรื่อง) และกลุ่มเมนู *ผลการเรียนรู้* ของผู้ดูแลคณะ
(#79 ตัดทั้งกลุ่ม ไม่ใช่ตัดเฉพาะหน้านี้) — การถามรวมหนึ่งคำตอบมาครึ่งเดียวแล้วติ๊ก คือแถวที่ครึ่งหนึ่งไม่มีใครตรวจ

แถวของ `faculty.admin` ผ่านโดยมีข้อสังเกตหนึ่ง: ใต้แถบแดงมี *โครง* ตารางอยู่
แต่ไม่มีแถวรายวิชาสักแถว เกณฑ์ของแถวนี้คือ *ไม่มีตารางที่มีแถวข้อมูล* ซึ่งผ่าน
โครงเปล่าไม่ใช่ตัวควบคุมที่ค้างอยู่ จึงไม่ใช่สิ่งที่แถวนี้ห้าม แต่บันทึกไว้เพราะมันคือสิ่งที่เห็นจริง

| `emptyise` | ช่องที่ยังไม่มีใครเขียน วาดเป็น `E` แทนที่จะว่าง | รายวิชาที่เพิ่งถูกใส่ มีทุกช่องว่าง — ตายพร้อมแถวแรกด้วย ดูย่อหน้าใต้ตาราง |
| `onelevel` | ทุกการเขียนเก็บเป็น `I` ไม่ว่าเลือกอะไร | ค่าที่ตั้งอยู่ต่อ (**ตัวเดียวที่ค้ำแถวนี้**) — ตายพร้อมกันสามแถว ดูย่อหน้าใต้ตาราง |
| `noupsert` | `ON CONFLICT` เป็น `DO NOTHING` — การบันทึกครั้งที่สองหายไปเงียบ ๆ แต่ route ยังตอบ 200 | บันทึกซ้ำที่ช่องเดิม แก้ของเดิม |
| `nofont` | ทิ้ง `addFont` ทั้งสองบรรทัด — ไม่มีฟอนต์ไทยฝังในไฟล์เลย | ส่งออก PDF ได้ และเป็นไฟล์ของหลักสูตรนั้น (ครึ่งที่เป็นฟอนต์) |
| `nosticky` | คอลัมน์ *รายวิชา* เลื่อนหายไปพร้อมแถว (รันซ้ำตอน #100 ที่หน้าต่าง 800px) | ตารางเลื่อนในกรอบ และคอลัมน์รายวิชาไม่หาย (ครึ่งหลัง) |
| `openreach` | ทิ้งการตรวจ reach ตอนอ่าน — ยื่นตารางของหลักสูตรอื่นให้ | กรรมการหลักสูตรของอีกหลักสูตรถูกปฏิเสธ (ครึ่ง 403) |
| `letfaculty` | ใส่ `FACULTY_ADMIN` กลับเข้า `MAINTAINERS` ขัดกับ #79 | บัญชีที่ไม่ควรเข้าถึงเลย — ครึ่งที่เป็นกฎ |

**แถวที่เงื่อนไขการรันเปลี่ยนไป ต้องรันมัตแตนต์ของมันใหม่** หลัง #100 สิบสามคอลัมน์ไม่ล้นหน้าต่างเต็มอีกต่อไป
แถวเรื่องการเลื่อนจึงรันที่ viewport 800px ซึ่งตรงกับขั้นเดินของมันเอง (*ย่อหน้าต่างให้แคบกว่าตาราง*) เครื่องหมาย ⚙
ติดได้ก็ต่อเมื่อมัตแตนต์ฆ่า assertion ตามที่มันเขียนอยู่จริง ไม่ใช่ตามที่เคยเขียน `nosticky` จึงถูกรันซ้ำ
ที่ความกว้างใหม่ — 1 failed / 7 passed ตายที่แถวเดิมตามที่ควร

**`emptyise` ฆ่าสองแถว และแถวที่สองคือคู่ assertion ที่ทำงาน** แถวแรกของ spec ยืนยันสองอย่างคู่กัน
คือช่องที่ seed เขียนไว้ต้องมีค่า **และ** ช่องที่ seed ไม่ได้แตะต้องว่าง เพราะตารางที่วาดทุกช่องเต็ม
กับตารางที่วาดทุกช่องว่าง จะผ่านอย่างละครึ่ง มัตแตนต์นี้ทำลายครึ่งหลังพอดี การที่มันตายจึงคือคู่นั้นทำงาน
ไม่ใช่ความเสียหายข้างเคียง

**`onelevel` ฆ่าสามแถว และนั่นคือจำนวนจริง** มันเป็นตัวเดียวที่แตะเส้นทางการเขียน แถวเรื่อง
*เลือกซ้ำแล้วเปลี่ยน* กับแถวเรื่อง *`E` ไม่ใช่ช่องว่าง* ก็อ่านระดับกลับมาเหมือนกัน ทั้งคู่จึงตายไปด้วย
ที่ยังคุ้มเก็บไว้เพราะสองแถวนั้นมีตัวที่ฆ่ามันเดี่ยว ๆ อยู่แล้ว (`noupsert`, `emptyise`)
ส่วนแถว *ค่าที่ตั้งอยู่ต่อ* ไม่มีตัวอื่นแตะเลย

**`letfaculty` ฆ่าครั้งเดียว ไม่ใช่สองครั้ง** ฉบับแรกของไฟล์มัตแตนต์อ้างว่ามันทำให้หน้าจอวาดตาราง
ออกมาด้วย ซึ่งไม่จริง — ตัวเลือกหลักสูตรบนหน้านี้ถาม `/api/plos/programs` ซึ่ง `MAINTAINERS` ของมัน
อยู่ที่ `backend/routes/plos.js` และมัตแตนต์ตัวนี้ไม่ได้แตะ คนที่ถูกปฏิเสธจึงยังเห็นแถบแดงเหมือนเดิม
สิ่งที่ตายคือ assertion บนสถานะของคำขอ ซึ่งเป็นครึ่งที่เกี่ยวกับ route นี้จริง ๆ

**มัตแตนต์ตัวแรกที่เขียนไว้ฆ่าอะไรไม่ได้ และเป็นบทเรียนของตั๋วนี้**

ตัวแรกชื่อ `latinfont` เปลี่ยน `FAMILY = 'THSarabun'` เป็น `'helvetica'` — ผ่านครบทั้งแปดข้อ
สาเหตุมีสองชั้น ชั้นแรก `addFont(..., FAMILY, ...)` ลงทะเบียนไบต์ของ TH Sarabun ไว้ *ใต้ชื่อ*
ที่ `FAMILY` บอก การเปลี่ยนชื่อจึงเปลี่ยนแค่ชื่อ ไม่ได้เปลี่ยนตัวอักษรสักตัว ชั้นที่สองหนักกว่า
ไฟล์ฟอนต์ที่คัดลอกมามีบรรทัด `jsPDF.API.events.push(['addFonts', ...])` ปิดท้าย
แค่ *import* ก็ฝัง TH Sarabun ลงทุกเอกสารที่แอปสร้างแล้ว
PDF สองไฟล์จึงยาวเท่ากันเป๊ะ มี `/FontFile2` สี่ก้อนเท่ากัน และ content stream ก้อนแรกเหมือนกันทุกไบต์

สิ่งที่แก้จึงเป็น *โค้ด* ไม่ใช่มัตแตนต์ — ตัดบรรทัดลงทะเบียนตัวเองออกจากไฟล์ฟอนต์ทั้งสอง
(ดู `frontend/src/assets/fonts/README.md`) การลงทะเบียนใน `exportPdf.js` จึงกลายเป็นการลงทะเบียนเดียวที่มี
แล้ว `nofont` ถึงฆ่าแถวนั้นได้จริง — และฆ่าแถวนั้นแถวเดียว อีกเจ็ดข้อยังผ่าน

> assertion ที่ฆ่าไม่ได้ ไม่ใช่ assertion ที่อ่อน แต่คือ assertion ที่ไม่มีทางไปถึง
> และวิธีเดียวที่จะรู้คือลองทำให้พังดู
