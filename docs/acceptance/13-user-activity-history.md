## แถวที่ตั้งใจปล่อยไว้ให้คนเดิน

สามแถวที่เหลือเป็น ☐ โดยตั้งใจ ไม่ใช่เพราะยังเขียนไม่ถึง

- **มีเมนูของตัวเอง** (เกณฑ์ข้อ 3) — สิ่งที่แถวขอให้ดูคือรายการในเมนูด้านซ้ายกับถ้อยคำของ breadcrumb
  ซึ่งเป็นสิ่งที่วาด ไม่ใช่พฤติกรรมที่เซิร์ฟเวอร์บังคับ #65 ให้ครึ่งนี้เป็นงานของคนเดิน
  (ครึ่งที่ว่า "ยังไม่มีตารางจนกว่าจะเลือกคน" ถูกเดินโดยปริยายทุกครั้งที่ spec เลือกคน เพราะ
  `pick` รอคำตอบของ `/api/users/:userId/history` ที่เกิดขึ้น *หลัง* การเลือกเท่านั้น)
- **สองแถวที่ยิง `fetch` จาก DevTools** (เกณฑ์ข้อ 4) — ทั้งสองถูกพิสูจน์ครบแล้วที่ seam ของ backend
  ใน `backend/test/history.test.js` เขียน spec ที่ยิง API ตรง ๆ จาก Playwright จะเป็นสำเนาของการทดสอบ
  ที่มีอยู่ ไม่ใช่การพิสูจน์สิ่งใหม่ และตัวแถวเองก็เขียนไว้ว่าซ้ำโดยเจตนา *เพื่อให้เห็นด้วยตา*

ทุกข้ออ้างใหม่ในไฟล์ spec ถูกพิสูจน์ด้วย mutation test ก่อนติด ⚙ แปดตัวกลายพันธุ์ แปดตัวถูกฆ่า
ตรงจุดที่ตั้งใจ — เรียงจากเก่าไปใหม่, บันทึกการเปลี่ยนสถานะไว้กับผู้ถูกกระทำ, พิมพ์ id โดยไม่บอกชนิดระเบียน,
เติมอะไรบางอย่างแทน `—` เมื่อไม่มีเป้าหมาย, ถอด `timeZone: 'Asia/Bangkok'`, ถอด `setPage(1)` ตอนเปลี่ยนคน,
ไม่บันทึก `LOGOUT`, และรายชื่อผู้ใช้ที่ไม่ได้ถูกจำกัดขอบเขต

## สิ่งที่เปิดเผยไว้ว่าเบี่ยงจากตั๋ว

1. **ไม่บันทึกการอ่าน — เป็นการตัดสินใจ ไม่ใช่การค้าง** ตั๋วเขียนว่า "sign-ins, sign-outs and record views"
   แต่เกณฑ์ทั้งหกไม่มีข้อใดขอให้บันทึกการ *อ่าน* และอาจารย์ที่ปรึกษาตัดสินแล้วว่า **ไม่บันทึก** (18 ส.ค. 2569)
   เหตุผลคือปริมาณ: การบันทึกทุกครั้งที่มีคนเปิดหน้าจอจะทำให้ `user_log` โตจากหลักสิบเป็นหลักพันแถวต่อคนต่อเดือน
   บนตารางที่ยังไม่มีนโยบายเก็บ/ตัดรอบ และจะกลบประวัติการ *เปลี่ยนแปลง* ซึ่งเป็นสิ่งที่จอนี้มีไว้ตอบ
   คำถาม "ใครเปิดดูข้อมูลนี้" จึงตอบไม่ได้ทั้งระบบโดยเจตนา ถ้าวันหนึ่งต้องตอบ ให้เป็น `access_log` ตารางของตัวเอง
   พร้อมนโยบาย retention ไม่ใช่การเติมแถวลงตารางนี้

2. **จอเลือกคนไม่ได้ลิสต์กิจกรรมของทุกคนรวมกัน** เกณฑ์ข้อ 3 ขอ "filterable by user" จอ
   `/main/users/user-history` (docs/05 A13) จึงให้เลือกคนก่อนแล้วค่อยแสดงประวัติ ไม่ใช่แสดงกิจกรรมของทุกคน
   ปนกันแล้วค่อยกรอง — จอรวมแบบนั้นผู้ดูแลระดับภาควิชาก็เห็นได้แค่คนในภาควิชาตัวเองอยู่ดี และ dropdown
   ก็ถูกจำกัดขอบเขตมาจากเซิร์ฟเวอร์แล้ว (`GET /api/users`) ส่วน dropdown แสดงได้สูงสุด 100 บัญชีต่อคำค้น
   ถ้าเกินจะบอกจำนวนที่พบทั้งหมดและให้พิมพ์คำค้นให้แคบลง
3. **ไม่มีตัวกรองตามชนิดกิจกรรม** ตั๋วไม่ได้ขอ ถ้าประวัติยาวจนต้องกรอง ให้เปิดตั๋วใหม่
4. **เรียกว่า history ไม่ใช่ activity** CONTEXT.md ผูกคำว่า **Activity** ไว้กับกิจกรรมการเรียนรู้ในหมู่เรียนแล้ว
   route/โมดูล/แผงของตั๋วนี้จึงใช้คำว่า history ทั้งหมด (`GET /api/users/:userId/history`) คอลัมน์ `user_log.activity`
   คงชื่อเดิมไว้เพราะการเปลี่ยนชื่อคอลัมน์คือ migration ไม่ใช่งานของตั๋วนี้ — เพิ่มคำ **Activity log entry**
   ลง CONTEXT.md แล้ว

1. **`user_log` ไม่มีใครลบ** เป็นตารางเดียวในระบบที่โตทางเดียว ยังไม่มีนโยบายเก็บ/ตัดรอบ (retention)
   วันนี้ไม่กระทบเพราะแบ่งหน้าที่ฝั่งเซิร์ฟเวอร์และมี index `(user_id, time_stamp DESC)` อยู่แล้ว
2. **ประวัติบอกว่า "ทำอะไร กับข้อมูลไหน" แล้ว แต่ยังตอบ "ใครมาแก้ระเบียนนี้" ไม่ได้** migration `0006` เพิ่ม
   `target_kind` / `target_id` ลง `user_log` และทุกจุดที่แก้บัญชีหรือบทบาทส่งระเบียนที่ถูกกระทำเข้าไปแล้ว
   ประวัติของ `admin01` จึงอ่านว่า *แก้ไขข้อมูลผู้ใช้ · บัญชีผู้ใช้ teach01* แทนที่จะเป็น *แก้ไขข้อมูลผู้ใช้* เก้าบรรทัดติดกัน
   สิ่งที่ **ไม่** เปลี่ยนคือเจ้าของบรรทัด — บรรทัดยังอยู่กับ *ผู้ลงมือ* ตามที่อาจารย์ยืนยัน (18 ส.ค. 2569)
   เปิดประวัติของ `teach01` จึงยังไม่พบว่าใครมาแก้ข้อมูลของ `teach01` คำถามนั้นคือการ *ค้นข้ามประวัติของทุกคน
   ด้วยระเบียนเป้าหมาย* ซึ่งยังไม่มีจอไหนถาม — สองคอลัมน์นี้เป็นเงื่อนไขที่ทำให้ถามได้ในวันหน้า ไม่ใช่คำตอบวันนี้
   ข้อจำกัดที่เหลืออีกสองข้อ: `IMPORT_USERS` เขียนบรรทัดเดียวต่อการอัปโหลด ไม่ได้เขียนต่อบัญชีที่ถูกสร้าง
   จึงไม่มีเป้าหมาย และ `GRANT_ROLE` / `REVOKE_ROLE` ชี้ที่ *ผู้ได้รับบทบาท* — ว่าเป็นบทบาทใดในขอบเขตใดไม่ได้อยู่ในบรรทัด
   เพราะสองคอลัมน์ชี้ระเบียนเดียว ส่วน `user_roles` ไม่มี surrogate key ให้ชี้
3. **`PAGE_SIZE = 10` ประกาศไว้สามที่** (`backend/routes/history.js`, `frontend/src/pages/Users.js`,
   `frontend/src/components/users/HistoryPanel.js`) ~~และแถบแบ่งหน้าเขียนซ้ำกันสองที่~~
   ครึ่งหลังปิดแล้วใน **#57** (โค้ดรวมแล้ว และ `docs/acceptance/57-pager.md` เดินจบแล้ว ทั้งด้วยมือเมื่อ 19 ส.ค. และที่ browser seam เมื่อ 20 ส.ค. (`e2e/tests/57a-pager.spec.js`)) — แถบแบ่งหน้าเป็น `frontend/src/components/Pager.js` ตัวเดียว
   ที่ทุกหน้าจอเรียก ส่วน `PAGE_SIZE` ยังแยกกันอยู่ตามเหตุผลใน `docs/acceptance/57-pager.md` ข้อ 1
4. **`assigned_at` ในแผง *บทบาทที่ได้รับ* ยังใช้เวลาตามเครื่องผู้ใช้** (`madeOn` ใน `GrantsPanel.js`)
   เป็นวันที่ล้วนจึงเพี้ยนได้อย่างมากหนึ่งวัน แผงประวัติของ #13 ระบุ `Asia/Bangkok` ไว้แล้ว
   ถ้าจะให้ทั้งจอใช้ตัวจัดรูปแบบเดียวกัน ควรเป็นตั๋วเล็ก ๆ ของตัวเอง
5. **สลับคนขณะอยู่หน้าสอง เคยยิง request ที่เสียเปล่าหนึ่งครั้ง — แก้แล้วใน commit เดียวกับที่พบ**
   browser seam พบว่า `HistoryPanel` คืนเลขหน้าเป็น 1 ด้วย `useEffect` ที่ผูกกับ `user.user_id`
   ซึ่งทำงาน *หลัง* การ render ครั้งแรกของคนใหม่ ลำดับจริงจึงเป็น ขอหน้า 2 ของคนใหม่ → คืนเป็นหน้า 1 → ขอหน้า 1
   จอมาหยุดที่หน้าหนึ่งเสมอ จึงมองไม่เห็นด้วยการเดินมือ แต่คำตอบสองใบวิ่งพร้อมกัน ถ้าใบของหน้า 2 มาถึงทีหลัง
   จอจะวาดหน้า 2 ของคนใหม่ค้างไว้

   แก้ด้วยการให้เลขหน้าเป็น state *ของประวัติคนนั้น* ไม่ใช่ของแผง — ผู้เรียกทั้งสองใส่ `key={user.user_id}`
   และ effect ที่ตามมาแก้ถูกลบทิ้ง React ทิ้ง instance เก่าทั้งใบ `page` จึงเริ่มที่ 1 ตั้งแต่ render แรก
   ไม่มี request ของหน้าสองเกิดขึ้นเลย และคำตอบใบเก่าที่ค้างอยู่ก็ตกไปกับ instance ที่ถูกทิ้ง — race หายทั้งคู่
   ไม่ใช่ถูกกลบ

   spec ของแถวนี้ assert ว่า *ทุก* request ของคนใหม่เป็นหน้าหนึ่ง เพราะสภาพที่จอมาหยุดอย่างเดียว
   แยกโค้ดเก่ากับโค้ดใหม่ไม่ออก พิสูจน์ด้วย mutant N9 (เอา `key` ออกและใส่ effect กลับ) ซึ่งฆ่าแถวนี้แถวเดียว

   สิ่งที่ยังเหลือ แยกเป็น [#68](https://github.com/khthana/Deep-QA/issues/68) แล้ว คือ `load` ยังไม่มีตัวกันคำตอบเก่ามาทับโดยทั่วไป — กด *ถัดไป* รัว ๆ
   ในประวัติของคนเดิม ก็มีสองใบวิ่งพร้อมกันเหมือนกัน ซึ่ง `key` ช่วยไม่ได้เพราะเป็น instance เดิม
   และรูปแบบเดียวกันนี้น่าจะซ้ำอยู่ในทุกแผงที่ paging ฝั่งเซิร์ฟเวอร์
