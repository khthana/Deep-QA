`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #13

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ผู้ใช้งานระบบ* (`/main/users`) → กด *แก้ไข* ที่แถวของใครสักคน
แผง *ประวัติการใช้งาน* จะอยู่ใต้แผง *บทบาทที่ได้รับ*

## สิ่งที่เปิดเผยไว้ว่าเบี่ยงจากตั๋ว

1. **"record views" ในคำบรรยายของตั๋วยังไม่มีจริง** ตั๋วเขียนว่า "sign-ins, sign-outs and record views"
   แต่เกณฑ์ทั้งหกไม่มีข้อใดขอให้บันทึกการ *อ่าน* และวันนี้ `recordActivity` ถูกเรียกเฉพาะตอนเข้า/ออกจากระบบ
   และตอน *เปลี่ยนแปลง* ข้อมูล (สิบเอ็ดรหัสกิจกรรม) จอนี้จึงอ่านสิ่งที่ log มีจริง ไม่ได้เติมการบันทึกการอ่านเข้าไปเอง
   — การบันทึกทุกครั้งที่มีคนเปิดหน้าจอเป็นการตัดสินใจเรื่องนโยบาย audit (ปริมาณแถวจะโตอีกคนละหลักพันต่อเดือน)
   ซึ่งเป็นเรื่องของอาจารย์ ไม่ใช่ของตั๋วนี้ ถ้าต้องการให้เปิดตั๋วใหม่
2. **"filterable by user" ตีความว่าการเลือกคนคือตัวกรอง** เกณฑ์ข้อ 1 เขียนว่า "activity for a selected user"
   จอนี้จึงเป็นแผงต่อหนึ่งบัญชีที่เปิดอยู่ ไม่ใช่จอรวมที่ลิสต์กิจกรรมของทุกคนแล้วมี dropdown เลือกชื่อ
   — ซึ่งจะเป็นจอที่ผู้ดูแลระดับภาควิชาเห็นข้ามภาควิชาไม่ได้อยู่ดี และ sidebar ก็ไม่มีเมนูแยกสำหรับมัน (docs/05 A13)
3. **ไม่มีตัวกรองตามชนิดกิจกรรม** ตั๋วไม่ได้ขอ ถ้าประวัติยาวจนต้องกรอง ให้เปิดตั๋วใหม่
4. **เรียกว่า history ไม่ใช่ activity** CONTEXT.md ผูกคำว่า **Activity** ไว้กับกิจกรรมการเรียนรู้ในหมู่เรียนแล้ว
   route/โมดูล/แผงของตั๋วนี้จึงใช้คำว่า history ทั้งหมด (`GET /api/users/:userId/history`) คอลัมน์ `user_log.activity`
   คงชื่อเดิมไว้เพราะการเปลี่ยนชื่อคอลัมน์คือ migration ไม่ใช่งานของตั๋วนี้ — เพิ่มคำ **Activity log entry**
   ลง CONTEXT.md แล้ว

## ข้อค้างจาก #13

1. **`user_log` ไม่มีใครลบ** เป็นตารางเดียวในระบบที่โตทางเดียว ยังไม่มีนโยบายเก็บ/ตัดรอบ (retention)
   วันนี้ไม่กระทบเพราะแบ่งหน้าที่ฝั่งเซิร์ฟเวอร์และมี index `(user_id, time_stamp DESC)` อยู่แล้ว
2. **ประวัติบอกว่า "ทำอะไร" แต่ไม่บอกว่า "กับใคร"** `user_log` มีแค่ `activity` กับเวลา และทุกจุดที่เรียก
   `recordActivity` ส่ง `req.auth.userId` คือ *ผู้ลงมือ* ไม่ใช่ *ผู้ถูกกระทำ* ดังนั้นการเปิดประวัติของ `teach01`
   จะไม่พบว่าใครมาแก้ข้อมูลของ `teach01` — บรรทัด *แก้ไขข้อมูลผู้ใช้* ไปตกอยู่ในประวัติของผู้ดูแลคนที่กด
   คำถาม "ใครแก้ระเบียนนี้" จึงยังตอบได้เฉพาะเมื่อรู้ตัวผู้ต้องสงสัยอยู่ก่อน นี่เป็นข้อจำกัดของ schema
   ที่ ADR-0001 ยกเว้นไว้ตั้งแต่ต้น (log line ไม่มี natural key) การเพิ่มคอลัมน์เป้าหมายเป็นการแก้ schema
   ซึ่งควรเป็นตั๋วของตัวเอง
3. **`assigned_at` ในแผง *บทบาทที่ได้รับ* ยังใช้เวลาตามเครื่องผู้ใช้** (`madeOn` ใน `GrantsPanel.js`)
   เป็นวันที่ล้วนจึงเพี้ยนได้อย่างมากหนึ่งวัน แผงประวัติของ #13 ระบุ `Asia/Bangkok` ไว้แล้ว
   ถ้าจะให้ทั้งจอใช้ตัวจัดรูปแบบเดียวกัน ควรเป็นตั๋วเล็ก ๆ ของตัวเอง
