## กติกาสองข้อนี้ฐานข้อมูลถือไว้ไม่ได้

migration 0003 เขียนไว้ตรงที่ประกาศ `student_group_member` ว่า **BR-06** (กลุ่มละไม่เกิน 10 คน)
กับ **BR-07** (หนึ่งคนหนึ่งกลุ่มต่อหนึ่งตอนเรียน) ไม่ใช่เงื่อนไขที่แถวเดียวตรวจตัวเองได้ — ข้อแรกต้องนับ
พี่น้องของแถว ข้อที่สองต้องไล่ผ่านสองตารางไปถึงตอนเรียน ทั้งคู่จึงเป็นของ service layer และของตั๋วนี้

ผลที่ตามมาคือคำถามที่กติกาแบบนี้ติดหนี้อยู่เสมอ — **ถ้าสองคำขอมาพร้อมกันล่ะ** `workGroups.js` ตอบด้วย
ล็อกตัวเดียว: ทุกเส้นทางที่เขียนล็อกแถวของ **ตอนเรียน** เองเป็นคำสั่งแรกหลัง BEGIN แล้วจึงทำงานต่อ

คำตอบแรกคือล็อกสองตัวที่ละเอียดกว่าตามลำดับคงที่ (แถว `student_course` ของนักศึกษาก่อน แล้วจึงแถว
`student_group` ของกลุ่มปลายทาง) ซึ่งถูกสำหรับเส้นทางที่แตะคนเดียวกลุ่มเดียว และผิดสำหรับการนำเข้า
ซึ่งถือกลุ่มของบรรทัดแรกไว้ขณะเอื้อมไปหานักศึกษาของบรรทัดที่สอง — การเพิ่มด้วยมือที่ถือคู่นั้นสลับข้าง
กันปิดวงพอดี ล็อกตัวเดียวปิดวงไม่ได้

## เพิ่ม ไม่ใช่ ย้าย

หน้าจอมีปุ่มสองปุ่มติดกัน **เพิ่มเข้ากลุ่ม** กับ **ย้ายมากลุ่มนี้** และไม่มีปุ่มไหนถอยไปเป็นอีกปุ่ม

คนที่อยู่ในกลุ่มอื่นแล้วถูก *เพิ่ม* จะถูกปฏิเสธพร้อมชื่อกลุ่มเดิม (เกณฑ์ข้อ 4) และคนที่ยังไม่มีกลุ่มถูก
*ย้าย* ก็ถูกปฏิเสธเช่นกัน เหตุผลอยู่ที่เกณฑ์ข้อ 5 — *ย้ายต้องถูกบันทึกเป็นการย้าย ไม่ใช่ลบแล้วเพิ่มใหม่*
หน้าจอที่เดาแทนคนใช้จะทิ้งประวัติที่ไม่มีใครถูกย้ายเลย มีแต่คนหายจากที่หนึ่งไปโผล่อีกที่หนึ่ง ซึ่งเป็นคำถาม
เดียวที่หน้านี้มีไว้ตอบตอนนักศึกษามาบอกว่าถูกย้ายกลุ่ม

## การเปลี่ยนชื่อกลุ่มไม่มีบรรทัดในประวัติ

`action_type` มี CHECK ห้าค่าและไม่มีการเปลี่ยนชื่ออยู่ในนั้น — ซึ่งเป็น schema ที่ถูก ไม่ใช่ schema
ที่ขาด ทุกบรรทัดของประวัติ **คัดลอก** `group_name` ณ เวลาที่เขียนไว้ในตัวมันเอง สิ่งที่การเปลี่ยนชื่อ
จะบันทึกจึงถูกบันทึกไปแล้วบรรทัดละครั้ง และเกณฑ์ข้อ 6 ก็ระบุห้าอย่างพอดี — สร้าง ลบ เพิ่ม นำออก ย้าย

migration **0007** เพิ่ม partial unique index บน `(section_id, group_name) WHERE group_name <> ''`
ด้วยเหตุผลเดียวกัน: ถ้าสองกลุ่มที่ยังอยู่ใช้ชื่อเดียวกัน สำเนาชื่อในประวัติทุกบรรทัดจะกำกวมตลอดไป
0003 ไม่ใส่ unique ไว้เพราะค่า default เป็นสตริงว่าง — index แบบมีเงื่อนไขพูดทั้งสองเรื่องพร้อมกัน

## การลบกลุ่มพากันออกจากกลุ่ม ไม่ใช่ปฏิเสธ

`student_group_member` เป็น CASCADE อยู่แล้ว แถวสมาชิกจะหายไปไม่ว่าทางไหน สิ่งที่ CASCADE ทำไม่ได้
คือ *บอกว่ามันหายไป* route จึงเขียน `REMOVE_STUDENT` ให้สมาชิกทุกคนก่อน แล้วจึง `DELETE_GROUP`
แล้วจึงลบกลุ่ม ทั้งหมดในทรานแซกชันเดียว

ทางเลือกที่ไม่ได้เลือกคือ *ปฏิเสธการลบกลุ่มที่ยังมีคนอยู่* — การลบไม่ได้ทำให้อะไรหาย (นักศึกษายังอยู่
ในตอนเรียน และคะแนนไม่เคยเป็นของกลุ่ม) และผู้สอนที่จะยุบกลุ่มสิบคนจะต้องกดนำออกสิบครั้งก่อนถึงจะกดลบ
ได้หนึ่งครั้ง

## seed ทิ้งคนไว้ไม่มีกลุ่มโดยตั้งใจ

`UNGROUPED_TAIL` ใน `db/seed.js` เท่ากับ `MAX_GROUP_SIZE + 1` = **11 คนท้ายของแต่ละตอนเรียนปีนี้**
ไม่ถูกจัดกลุ่ม ตัวเลขนี้เป็นของ BR-06 ไม่ใช่รสนิยม — วิธีเดียวที่คนหรือเบราว์เซอร์จะพิสูจน์เพดานได้คือ
ตั้งกลุ่มให้ครบสิบแล้วโดนปฏิเสธคนที่สิบเอ็ด และคนที่หยิบมาใช้ได้มีแต่คนที่ยังไม่มีกลุ่ม

ห้องที่ทุกคนมีกลุ่มแล้วคือ fixture ที่หน้าจอนี้ทำอะไรไม่ได้เลย ทุกคำสั่งของมันเริ่มด้วยการเลือกคนที่ยัง
ไม่มีกลุ่ม — และคนที่มาลงทะเบียนหลังจากแบ่งกลุ่มไปแล้วก็เป็นเรื่องปกติของห้องเรียนจริง ไม่ใช่การดัดข้อมูล

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

**ต้อง reset + migrate + seed ใหม่ก่อนเดินใบนี้** — migration 0007 เป็นของใหม่ และ `UNGROUPED_TAIL`
เปลี่ยนรูปของ seed ฐานข้อมูลที่ seed ไว้ก่อนหน้าจะไม่มีคนที่ยังไม่มีกลุ่มเหลือให้เพิ่มเลยสักคน

**ต้อง kill แล้ว start backend ใหม่ก่อนเดิน** — `node server.js` ไม่มี reload กระบวนการที่ค้างจาก
ตั๋วก่อนจะตอบ 404 ให้ทุก route ของ #26 ในขณะที่หน้าจอ hot-reload ตามปกติ **จอจึงดูใหม่ทั้งที่
server เป็นของเก่า** ตรวจด้วยการ login แล้วเปิด `GET /api/teaching/sections/1/groups` หนึ่งครั้ง
ต้องได้ 200 พร้อมรายการกลุ่ม

ทุกบัญชีใน seed ใช้รหัสผ่าน `deep-core-local` — ค่าของตัวแปร `PASSWORD` ใน `db/seed.js`

ทางเข้าคือ เลือกตอนเรียนจากหน้า *รายวิชา* แล้วกดเมนู **กลุ่มงานนักศึกษา** ทางซ้าย
ที่อยู่คือ `/teacher/teacherDashboard/<section_id>/studentGroups`

seed หลังเดินคำสั่งข้างบนมีรูปร่างที่ใบนี้ต้องใช้พอดี

| `section_id` | ปีการศึกษา | ตอนเรียน | ผู้สอน | นักศึกษา | กลุ่ม | ยังไม่มีกลุ่ม |
|---|---|---|---|---|---|---|
| `1` | 2569 (ปัจจุบัน) | 1 | `teacher.one@` | 57 (รหัสคี่) | 6 กลุ่ม กลุ่มละ 7–8 คน | **11 คน** |
| `2` | 2569 (ปัจจุบัน) | 2 | `multi.role@` | 56 (รหัสคู่) | 6 กลุ่ม กลุ่มละ 7–8 คน | **11 คน** |
| `3` | 2568 (ปีก่อน) | 1 | `teacher.one@` | 60 | **ไม่มีเลย** | 60 คน |

ตอนเรียนของปีก่อนไม่มีกลุ่มเลยโดยตั้งใจ (seed จัดกลุ่มเฉพาะปีปัจจุบัน) เป็นห้องว่างที่ใช้ทดลอง
สร้าง–เติม–ย้าย–ลบ ได้โดยไม่แตะของปีนี้ **แต่แถวส่วนใหญ่ของใบนี้เดินที่ตอนเรียน `1`** เพราะเป็นห้อง
ที่มีกลุ่มอยู่แล้วให้อ่าน

**กลุ่มที่ใหญ่ที่สุดของตอนเรียน 1 มี 8 คน** เติมอีกสองคนจากรายชื่อ *ยังไม่มีกลุ่ม* จะครบสิบ แล้วคนที่สาม
คือคนที่ต้องถูกปฏิเสธ — สามคลิก ไม่ใช่สิบเอ็ดคลิก

ช่องสุดท้ายมีสี่ค่า

- **☑** เดินจบแล้ว
- **◐** ครึ่งของ server เดินแล้วและผ่าน ส่วนที่เหลือคือสิ่งที่หน้าจอวาด (เมนู ถ้อยคำ) ยังต้องมีคนดู

ที่หาไม่เจอก็ยังไม่ใช่ทางออก แก้ประโยคให้ตรงกับปุ่ม

### แถวหน้าต่างแคบ และกับดักของมัน

ผู้ใช้ย่อหน้าต่างให้เอง เพราะ `resize_window` ของส่วนขยายรายงานสำเร็จโดยที่ viewport ไม่ขยับ
(`innerWidth` ค้างที่ 1150 แล้ว 1316) **และหลังผู้ใช้ย่อแล้วหน้าก็ยังไม่ reflow** — หน้ายังวาดที่ความกว้าง
เดิมโดยมีขอบหน้าต่างบังส่วนที่เกิน ซึ่งอ่านผ่าน ๆ เหมือนหน้าจอที่ไม่ตอบสนองความกว้าง ทั้งที่เป็นแค่
metrics ของแท็บที่ยังตามไม่ทัน โหลดหน้าใหม่หนึ่งครั้งแล้ว `innerWidth` เป็น **607** ตามจริง

ที่ 607px: กรอบ `overflow-x-auto` กว้าง 510 หุ้มตารางที่กว้าง 576 (`min-w-[36rem]`) เลื่อนได้จริง
จาก `scrollLeft` 0 ไป 65.6 จากสูงสุด 66 คอลัมน์ **โดย** โผล่เข้ามา และแถบเลื่อนอยู่ในการ์ดไม่ใช่ใต้หน้า
ส่วนหน้าเองไม่เลื่อนข้างเลย — `scrollWidth` เท่ากับ `clientWidth` ที่ 607 ทั้งก่อนและหลังเลื่อนตาราง
