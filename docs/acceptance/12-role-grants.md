`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #12

ตรวจว่า dropdown ไม่ได้แสดงตัวเลือกนั้น ซึ่งเป็นถ้อยคำของเกณฑ์ข้อ 8 ตรงตัว

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ข้อมูลผู้ใช้งาน* (`/main/users`) → กด *แก้ไข* ที่แถวของใครสักคน
แผง *บทบาทที่ได้รับ* จะอยู่ใต้ฟอร์มข้อมูลส่วนตัว

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`npm run seed` ใหม่หลังเดินจบ** ก่อนเริ่มตั๋วถัดไป

## หกแถวที่เก็บไว้ให้คนเดิน — เดินแล้วเมื่อ 21 ส.ค. 2569

หกแถวนี้เป็น ☐ มาโดยตั้งใจ ไม่ใช่เพราะยังเขียนไม่ถึง ทั้งหกแถวถูกเดินด้วยมือจนครบเมื่อ 21 ส.ค. 2569 และอาจารย์ที่ปรึกษาเป็นคนติ๊กจากหลักฐานที่เสนอ เหตุผลที่เขียนไว้ข้างล่างยังใช้ได้ — มันคือเหตุผลที่ seam รับแถวเหล่านี้ไปไม่ได้

- **สลับหมวกแล้วเมนูเปลี่ยน** (เกณฑ์ข้อ 4) และ **ตัวเลือกจำกัดตามขอบเขต** ทั้งสองแถว (เกณฑ์ข้อ 5) —
  สิ่งที่แถวขอให้ดูคือ *เนื้อในของ dropdown* กับ *รายการเมนูด้านซ้าย* ซึ่งเป็นถ้อยคำและสิ่งที่วาด
  ไม่ใช่พฤติกรรมที่เซิร์ฟเวอร์บังคับ #65 ให้ครึ่งนี้เป็นงานของคนเดิน
  ผลคือ **เกณฑ์ข้อ 4 และข้อ 5 ไม่มีแถว ⚙ เลย** — ตั้งใจ ไม่ใช่ตกหล่น
- **สามแถวที่ยิง `fetch` จาก DevTools** (เกณฑ์ข้อ 6 สองแถว และข้อ 2 หนึ่งแถว) —
  ทั้งสามถูกพิสูจน์ครบแล้วที่ seam ของ backend ใน `backend/test/grants.test.js`
  (`a role more senior than the granter holds`, `a scope the granter does not reach`,
  และ `a scope identifier that names nothing, from the Central Admin`)
  เขียน spec ที่ยิง API ตรง ๆ จาก Playwright จะเป็นสำเนาของการทดสอบที่มีอยู่ ไม่ใช่การพิสูจน์สิ่งใหม่
  และตัวแถวเองก็เขียนไว้ว่าซ้ำโดยเจตนา *เพื่อให้เห็นด้วยตา*

| 5 · ผู้ดูแลระบบกลางเห็นทั้งมหาวิทยาลัย | `admin@` → แผงเดียวกัน | ขอบเขตมีครบทุกชั้น: `FULL_ADMIN` *ทั้งมหาวิทยาลัย* · `ENG` *คณะวิศวกรรมศาสตร์* · `01` *วิศวกรรมโยธา* · `05` · `0501` · `0503` และบทบาทครบหกตัว |

| 6 · ข้ามภาควิชาไม่ได้ | คำสั่งเดิม → `{role_id:'TEACHER', scope_id:'01'}` | `403` *ไม่สามารถจัดการบัญชีนอกขอบเขตที่รับผิดชอบได้* |

สองแถวของเกณฑ์ข้อ 5 อ่านจาก DOM ตรง ๆ ไม่ได้ดูด้วยตา เพราะสิ่งที่แถวอ้างคือ
*สิ่งที่ไม่มีในรายการ* ซึ่งภาพหน้าจอพิสูจน์ไม่ได้

**สิ่งที่เห็นระหว่างเดินแต่ไม่ใช่ข้ออ้างของแถว** — สลับบทบาทแล้ว route เดิมค้างอยู่
ทำให้ breadcrumb อ่านว่า *ข้อมูลหลัก / รายวิชาที่รับผิดชอบ* ยังไม่เจ็บเพราะหน้าปลายทางทั้งสองเป็น
`NotBuiltYet` ยื่นไว้ที่ [#81](https://github.com/khthana/Deep-QA/issues/81)

ทุกข้ออ้างใหม่ในไฟล์ spec ถูกพิสูจน์ด้วย mutation test ก่อนติด ⚙ เจ็ดตัวกลายพันธุ์ เจ็ดตัวถูกฆ่า
ตรงจุดที่ตั้งใจ — ไม่บันทึกนามสกุล, ล้าง `user_roles` ตอนแก้ข้อมูล, เขียน `assigned_by` เป็นคนอื่น,
ยกเลิกแล้วไม่ได้ปิดจริง, `allRoles` ไม่กรอง `is_active`, ถอดด่านห้ามยกเลิกบทบาทตัวเอง,
และ revival ที่ไม่ประทับชื่อผู้ให้คนใหม่

## สิ่งที่เปิดเผยไว้ว่าเบี่ยงจากตั๋ว

1. **ยกเลิกบทบาทของตัวเองไม่ได้** ตั๋วไม่ได้ขอ แต่เป็นกฎเดียวกับที่ #11 ใช้กับการระงับบัญชีตัวเอง
   ผู้ดูแลที่ถอดบทบาทสุดท้ายของตัวเองจะถูกล็อกออกใน request ถัดไป และคนที่ใส่กลับให้ได้ต้องอาวุโสกว่าเสมอ
2. **ยกเลิกบทบาทที่มีขอบเขตนอกเขตรับผิดชอบไม่ได้** ถึงแม้เจ้าของบัญชีจะอยู่ในเขตก็ตาม —
   สมมาตรกับกฎตอนให้ ตอบ `403 scopeNotYours` — ยังมีคนถอนให้ได้เสมอ เพราะ
   `coveredScopes` ของผู้ดูแลระดับคณะครอบทุกภาควิชาและทุกหลักสูตร กรณีนี้จึงแค่ต้องขึ้นไปหนึ่งชั้น

## ข้อค้างจาก #12

1. **ยกเลิกบทบาทสุดท้ายได้** ตั๋วข้อ 3 เขียนว่า "revoke a grant, and the grantee loses that access" ไม่มีข้อยกเว้น
   จึงไม่ได้ห้าม บัญชีที่ไม่เหลือบทบาทจะเข้าระบบไม่ได้ (`REFUSALS.noRole`) และผู้ดูแลต้องใส่กลับให้ —
   ถ้าอาจารย์เห็นว่าควรเตือนก่อน ให้เปิดตั๋วใหม่
2. **แผง *บทบาทที่ได้รับ* ยังไม่บอกชื่อคนที่กำหนด** แสดงเป็นรหัสผู้ใช้ (`deptadm05`) เพราะ route
   ตอบเฉพาะ `assigned_by` การ join ชื่อกลับมาต้องอ่านบัญชีคนอื่นเพิ่มอีกหนึ่งครั้ง
3. **`GET /api/users/grantable` อ่านชื่อคณะ/ภาควิชา/หลักสูตรตรงจากตาราง** ซึ่งเป็นงานของ #14/#15
   ที่นี่อ่านเฉพาะ id ที่อยู่ใน `coveredScopes` อยู่แล้วกับชื่อไทยสำหรับแสดงผล ไม่ได้เปิดรายการทั้งมหาวิทยาลัย
4. **ข้อค้างเดิมจาก #11 ที่ #12 ปิดไปหนึ่งข้อ** ข้อ 7 (รายชื่อบทบาทอยู่สามที่) ปิดแล้ว —
   `ROLES` ใน `UserForm.js` ถูกถอดออกและถามเซิร์ฟเวอร์แทน ส่วนข้อ 6 (`coveredScopes` คำนวณซ้ำ)
   ปิดด้วย memoisation ต่อ request ใน `auth/administration.js` ข้อ 1 (ผู้ดูแลรีเซ็ตรหัสผ่านไม่ได้) ยังค้าง
5. **การจับคู่บทบาทที่เข้าด้วยรหัสผ่านกับบทบาทที่เข้าด้วย Google ยังไม่ถูกกั้น** เคยเขียนไว้ที่ route ตอนให้บทบาท
   แล้วถอดออก เพราะกฎแบบนั้นเท่ากับห้าม `FULL_ADMIN` ถือบทบาทที่สองเลย ซึ่งขัดตั๋วข้อ 4 โดยตรง
   ด่านที่ถูกต้องคือ `PUT /api/me/acting-role` (session ที่เข้าด้วยรหัสผ่านห้ามสลับไปบทบาทที่ต้องเข้าด้วย Google)
   เปิดเป็นตั๋ว #53
6. **เปลือกหน้าจออ่าน `/api/me` ตอน mount เท่านั้น** `AuthContext` เรียก `load()` ใน `useEffect` ครั้งเดียว
   การกดเมนูด้านซ้ายเป็นการเปลี่ยน route ฝั่ง client จึงไม่ได้อ่านใหม่ ตัวเลือกบทบาทบนหัวจอ
   จะเห็นบทบาทที่เพิ่งได้รับก็ต่อเมื่อโหลดหน้าใหม่ browser seam จึง reload ก่อน
   สิทธิ์ *ที่เซิร์ฟเวอร์บังคับ* เปลี่ยนใน request ถัดไปเสมอ (`attachRoles` อ่านใหม่ทุก request)
   ที่ตามไม่ทันคือรายการใน picker เท่านั้น แถวข้อ 2 ที่เขียนว่า "กดเมนูใด ๆ" จึงเดินตามตัวอักษรไม่ผ่าน
