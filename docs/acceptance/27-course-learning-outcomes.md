## หน้าจอนี้ต่างจากทุกหน้าก่อนหน้าอย่างไร

**สิ่งที่แสดงไม่ได้เป็นของตอนเรียนที่ใช้เปิดมัน** ADR-0004 บอกว่าบริบทของผู้สอนคือ `section_id`
ในที่อยู่และไม่มีที่อื่น ส่วน ADR-0003 บอกว่าชุด CLO เป็นของ (หลักสูตร, รายวิชา, ปีการศึกษา)
ไม่ใช่ของตอนเรียน หน้านี้คือที่แรกที่ข้อกำหนดสองข้อนั้นมาเจอกัน — ที่อยู่คือตอนเรียน ระเบียนคือ
การเปิดสอน และ **เซิร์ฟเวอร์เป็นฝ่ายแปลงอันแรกเป็นอันหลังทุกครั้งที่มีคำขอ**

ผลที่ตามมาซึ่งพลาดได้ง่ายที่สุดคือ *สามค่านั้นอยู่ใน body ของคำขออยู่แล้ว* หน้าจอแสดงปีการศึกษา
จึงมีมันในมือ และการอ่านจาก body สั้นกว่าการ resolve หนึ่งบรรทัด — มันคือ ADR-0002 ที่ถูกละเมิด
โดยที่ **ไม่มีอะไรบนหน้าจอเปลี่ยนเลย** เพราะหน้าจอส่งกลับสิ่งที่เซิร์ฟเวอร์เพิ่งให้มันมา
มัตแตนต์ชื่อ `bodygrain` คือตัวนั้น และมีแถวเดียวในระบบที่ฆ่ามันได้

**ผู้สอนสองคนแก้รายการเดียวกัน** นั่นคือสิ่งที่ grain นี้ซื้อมา และเป็นเหตุผลที่ `updated_by`
เป็นคอลัมน์ที่ต้องทำงาน ไม่ใช่คอลัมน์ตรวจสอบย้อนหลัง — ADR-0003 เลือก *เขียนทีหลังชนะ*
ไว้อย่างตั้งใจแทนการล็อก และชื่อกับเวลาบนแถวคือวิธีเดียวที่คนแพ้จะรู้ตัว

**ตัวเลือก PLO ถูกจำกัดด้วยตารางความครอบคลุม ไม่ใช่ด้วย foreign key** `subject_clo.plo_id`
อ้างถึง `learning_outcomes` ผ่าน `(program_id, plo_id)` ฐานข้อมูลจึงยอมรับ PLO ทุกข้อของหลักสูตร
รวมทั้งข้อย่อย และรวมทั้งข้อที่รายวิชานี้ไม่เคยถูก map ถึง `subject_plo_mapping` คือตารางนั้น
และเป็นสิ่งที่ route ถาม

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

**ต้อง reset + seed ใหม่จริง ๆ ก่อนเดินใบนี้** ด้วยเหตุผลเดียวกับ #24 — `db/term.js` ทำให้ seed
เดินตามนาฬิกา ฐานข้อมูลที่ seed ไว้ก่อนหน้าจะไม่ได้อยู่ในเทอมปัจจุบันอีกแล้ว

**ต้อง restart backend ก่อนเดิน** — process ที่ค้างจากตั๋วก่อนจะตอบ 404 ให้ทุก route ของ #27
และหน้าจอแปลผลเป็น *เกิดข้อผิดพลาดในการเชื่อมต่อเซิร์ฟเวอร์* (#95) การเดิน #24 เสียเวลาไปกับ
เรื่องนี้หนึ่งชั่วโมง **ยิง `curl http://localhost:3000/api/teaching/sections/1/clos` หนึ่งครั้งก่อนเริ่ม**

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือ `deep-core-local` — ค่าของตัวแปร `PASSWORD` ใน `db/seed.js`

ทางเข้าหน้านี้คือ เลือกตอนเรียนจากหน้า *รายวิชา* แล้วกดเมนู **ผลการเรียนรู้รายวิชา** ทางซ้าย
ที่อยู่ที่ได้คือ `/teacher/teacherDashboard/<section_id>/courseOutcomes`

seed หลังเดินคำสั่งข้างบนมีรูปร่างที่ใบนี้ต้องใช้พอดี

| `section_id` (ที่อยู่) | ปีการศึกษา | ตอนเรียน | ผู้สอน | ชุด CLO |
|---|---|---|---|---|
| `1` | 2569 (ปัจจุบัน) | 1 | `teacher.one@` | CLO-1..CLO-9 ของปีปัจจุบัน |
| `2` | 2569 (ปัจจุบัน) | 2 | `multi.role@` | **ชุดเดียวกัน** (การเปิดสอนเดียวกัน) |
| `3` | **2568 (ปีก่อน)** | 1 | `teacher.one@` | CLO-1..CLO-9 **คนละเก้าแถว** |

สองคอลัมน์แรกไม่ใช่สิ่งเดียวกัน และเป็นที่ที่เสียเวลาได้ง่ายที่สุด — ตอนเรียนที่ **1** ของปีก่อน
มี `section_id` เป็น **3** ที่อยู่ใช้เลขในคอลัมน์แรกเสมอ ตรวจกับฐานข้อมูลจริงแล้วเมื่อ 23 ส.ค. 2569

- `teacher.one@` — สอนตอนเรียน `1` ทั้งเทอมนี้และปีก่อน จึงเป็นบัญชีเดียวที่เดินเกณฑ์ข้อ 5 ได้
- `multi.role@` — สอนตอนเรียน `2` ของการเปิดสอนเดียวกัน **ต้องสลับเป็น อาจารย์ผู้สอน ก่อน**
  จึงจะเข้าถึงหน้านี้ได้ เป็นบัญชีเดียวที่เดินเกณฑ์ข้อ 3 กับ 4 ได้
- `teacher.two@` — ไม่ได้สอนอะไรเลย ใช้เดินการปฏิเสธข้ามตอนเรียน

**PLO-1, 2, 3, 5, 6, 7, 8 และ 12 ถูก map เข้ารายวิชานี้ ส่วน PLO-4, 9, 10, 11, 13 ไม่ได้ถูก map**
ห้าข้อหลังคือสิ่งที่เกณฑ์ข้อ 2 พูดถึงจริง ๆ picker ที่สร้างจาก `learning_outcomes` เฉย ๆ
จะดูถูกต้องทุกอย่างจนกว่าจะมีคนเลือกหนึ่งในห้าข้อนั้น

**CLO ทั้ง 18 แถวใน seed มีคะแนนบันทึกไว้แล้วทุกแถว** จึงลบไม่ได้สักแถวเดียว แถวที่ต้องเดินการลบ
สำเร็จจึงต้อง **สร้าง CLO ใหม่ขึ้นมาลบ** ไม่ใช่ลบของที่มีอยู่ ใบนี้เขียนไว้อย่างนั้นแล้ว

### สามอย่างที่การเดินจับได้ และเทสต์จับไม่ได้

**ช่องว่างกลางคำไทยในประโยคที่บอกเรื่อง grain** `CourseOutcomes.js` ขึ้นบรรทัดใหม่กลางประโยคพอดี
ที่คำว่า `ในปีการศึกษา` และ JSX ต่อสองบรรทัดของข้อความด้วย **ช่องว่างหนึ่งตัวเสมอ** บนจอจึงอ่านว่า
*ทุกตอนเรียนของรายวิชานี้ใน ปีการศึกษาเดียวกัน* ซึ่งภาษาไทยไม่เว้นวรรคตรงนั้น ทั้งสอง seam
มองไม่เห็นเพราะทุก assertion จับข้อความแบบบางส่วน ไม่ได้เทียบทั้งประโยค **แก้แล้ว** โดยย้ายจุด
ขึ้นบรรทัดใหม่ไปอยู่หน้าคำว่า *และ* ซึ่งเป็นที่ที่ควรมีช่องว่างจริง และเขียนคอมเมนต์กำกับไว้
อาจารย์อ่านซ้ำหลังแก้แล้วว่าหายไปจริง

**การเรียงรายการเป็นแบบพจนานุกรม ไม่ใช่แบบตัวเลข** ตอนสร้าง CLO เพิ่มระหว่างเดิน รหัสที่พิมพ์คือ
`CLO-10` และมันไปแทรกอยู่ระหว่าง `CLO-1` กับ `CLO-2` `ORDER BY c.clo_number ASC` เรียงคอลัมน์
ข้อความ **seed มีแค่ `CLO-1` ถึง `CLO-9` ซึ่งเป็นเลขหลักเดียวทั้งหมด การเรียงสองแบบจึงให้ผล
เหมือนกันเป๊ะบนข้อมูลชุดนั้น** ไม่มี assertion ไหนมีทางเห็นความต่างได้เลย เปิดเป็น
[#96](https://github.com/khthana/Deep-QA/issues/96) **แก้แล้วเมื่อ 7 ก.ย. 2569** กฎการเรียงย้ายไปอยู่ที่
`backend/lib/cloOrder.js` ที่เดียว และ route สิบแห่งในแปดไฟล์เรียกมัน

**คำถามที่ตั๋วนี้ค้างอยู่ มีคำตอบอยู่ก่อนแล้ว และไม่มีใครเคยถาม** ย่อหน้านี้เคยเขียนว่า
ไม่แก้ในตั๋ว #27 เพราะรหัสเป็นข้อความอิสระโดยตั้งใจ *(ต้องรองรับ `CLO-3ก`)* การเรียงที่ถูกจึง
ต้องตัดสินก่อนว่า `CLO-3ก` อยู่ตรงไหน — อาจารย์เจ้าของงานตอบเมื่อ 7 ก.ย. 2569 ว่า
**รหัส CLO ไม่มีตัวหนังสือ เป็นตัวเลขอย่างเดียว** คำถามนั้นตอบได้ในประโยคเดียว แต่ตั๋วค้างอยู่
**สิบห้าวัน** เพราะไม่มีใครเอ่ยปากถาม **ตั๋วที่ติดอยู่กับการตัดสินที่ไม่ใช่ของเรา
คือตั๋วที่ต้องถาม ไม่ใช่ตั๋วที่ต้องคิด** — ดู `docs/06` §Out of Scope ซึ่งบอกว่าข้อเสนอใดๆ
ที่จะเปลี่ยนของเดิม ให้**ถาม** ไม่ใช่ตัดสินเอง

**`0.5` ของใบเดินงานเป็นการตรวจที่ไม่ตรวจอะไรเลย** มันบอกให้ `curl` route ของ #27 แบบไม่เข้าระบบ
แล้วดูว่าได้ 401 ซึ่งเป็นสิ่งที่ **ทุก path ใต้ `/api` ตอบเหมือนกันหมด** เพราะด่าน session อยู่ก่อน
การ routing backend ที่ค้างอยู่จึงผ่านการตรวจนั้นทั้งที่ไม่มี route ของ #27 อยู่ในตัวเลย และ

## มัตแตนต์ที่พิสูจน์แถว ⚙

`mutation/27-course-outcomes.py` ยี่สิบสามตัว อ่านวิธีใช้ที่ `mutation/README.md` ก่อน

ทุกแถวที่ติด ⚙ มีมัตแตนต์ของตัวเอง และมัตแตนต์นั้นตายที่ assertion ของแถวนั้นจริง ๆ ไม่ใช่แค่ที่
spec ไฟล์เดียวกันตาย เดินจริงเมื่อ 23 สิงหาคม 2569 บน `backend/test/clos.test.js` (20 subtests)
และบน `npx playwright test 27a` (9 tests) ตัวเลขข้างล่างนี้คือสิ่งที่มัตแตนต์ฆ่าได้จริง ไม่ใช่สิ่งที่
ควรจะฆ่าได้ ตารางฝั่งเบราว์เซอร์บอก **บรรทัดที่ตาย** ไว้ด้วย เพราะบรรทัดคือสิ่งเดียวที่แยก
*แถวนี้พิสูจน์เรื่องนี้* ออกจาก *แถวนี้ตายทีหลังเพราะหน้าจอเพี้ยนไปก่อนแล้ว*

### สี่อย่างที่รอบนี้จับได้ และควรอ่านก่อนเชื่อตัวเลขรอบก่อน ๆ

**มัตแตนต์ที่ทำให้ query พัง ไม่ได้พิสูจน์อะไร** `nodetail` กับ `noeditor` รอบแรกเขียนเป็น
`clo_detail = clo_detail` และ `updated_by = updated_by` ซึ่งทำให้ `$3` กับ `$7` ไม่ถูกอ้างถึง
PostgreSQL จึงปฏิเสธทั้ง statement และ route ตอบ **500** แถวเบราว์เซอร์ที่ตายจึงตายที่บรรทัด
`toBe(200)` ไม่ใช่ที่บรรทัดซึ่ง assert ว่าการแก้ไปถึงอีกตอนเรียน — คนละเรื่องกันคนละอย่าง
ทั้งสองตัวถูกเขียนใหม่เป็น `COALESCE(clo_detail, $3)` กับ `CASE WHEN TRUE THEN updated_by ELSE $7 END`
ซึ่งยังผูก parameter ไว้ครบและเปลี่ยนแค่ *พฤติกรรม* ตอนนี้ทั้งคู่ตายที่บรรทัดของมันเอง

**subtest ที่ผูกกับเลขเก้า ทำให้มัตแตนต์ดูเก่งเกินจริง** ข้อ 14 เคย assert ว่ารายการยาวเก้าแถว
หลังคำขอที่ถูกปฏิเสธ ซึ่งพังทุกครั้งที่เทสต์ก่อนหน้าทิ้งแถวไว้ หรือทุกครั้งที่มัตแตนต์เปลี่ยนความยาว
ของรายการ — `noploguard` `mappedasmarked` และ `anyyear` จึงเคยนับข้อ 14 เป็นเหยื่อทั้งที่
ไม่ได้แตะสิ่งที่ข้อ 14 อ้าง ตอนนี้มันอ่านความยาวไว้ก่อนแล้วเทียบกับตัวเอง

**เทสต์ที่ใช้รหัสร่วมกัน ส่งต่อความพังให้กัน** ข้อ 6 เคยเขียนด้วยรหัสของ `DRAFT` พอ `noploguard`
ทำให้การเขียนผ่าน แถวที่มันทิ้งไว้ก็ไปชนกับรหัสที่ข้อ 7 กำลังจะอ้าง ข้อ 7 จึงตายตาม ตอนนี้ข้อ 6
ใช้ `CLO-96` ของตัวเอง และ `noploguard` ฆ่าได้ subtest เดียวคือของมันเอง ข้อ 7 ก็เป็นแบบเดียวกัน
และเพิ่งแก้รอบนี้ — มันใช้ `CLO-90` ซึ่งเป็นรหัสของ `DRAFT` พอ `swallowdelete` ทำให้การลบไม่เกิดขึ้นจริง
แถวที่ข้อ 5 เก็บกวาดไม่สำเร็จก็ค้างอยู่ และข้อ 7 ตายเพราะรหัสชน ตอนนี้ข้อ 7 ใช้ `CLO-97`
และ `swallowdelete` ฆ่าได้ข้อ 13 ข้อเดียว

**สองแถวที่ติด ⚙ มานาน โดยยังไม่มีมัตแตนต์ของตัวเอง** *เพิ่ม CLO ใหม่ได้* กับ
*ลบ CLO ที่ไม่มีอะไรอ้างถึงได้* ทั้งคู่ชี้ไปที่ `27a` แถว 8 แต่มัตแตนต์ตัวเดียวที่ฆ่าแถว 8 ได้คือ
`cancelremoves` ซึ่งตายที่บรรทัด 227 อันเป็นบรรทัดของ *การยกเลิก* ไม่ใช่ของการเพิ่มหรือการลบ
สองแถวนั้นจึงอยู่ในสภาพเดียวกับที่รอบนี้ตามแก้มาตลอด คือ assertion มีอยู่ แต่ไม่มีอะไรพิสูจน์ว่ามันจะเห็น
`savenoreload` กับ `swallowdelete` เพิ่งเขียนขึ้นเพื่อปิดช่องนี้

พอเจอสองแถวนั้นแล้วจึงไล่ **ทั้งสิบสามแถว ⚙** ใหม่ทีละแถว โดยถามคำถามเดียวกัน คือ
*ข้ออ้างของแถวนี้วางอยู่บนบรรทัดไหน* และ *มัตแตนต์ตัวไหนตายที่บรรทัดนั้น* การไล่แบบนี้เจอช่องที่สาม
คือ **การปฏิเสธรหัสซ้ำ** ซึ่งวางอยู่บนบรรทัด 196 และไม่มีมัตแตนต์ตัวใดตายที่นั่นเลย — `swallowsave`
ตายที่ 197 ซึ่งเป็นเรื่อง *แถบไม่ขึ้น* ไม่ใช่ *ไม่มีการปฏิเสธ* และฝั่งเซิร์ฟเวอร์ก็ไม่มีอะไรฆ่าข้อ 7 เช่นกัน
`dupnotseen` ปิดช่องนั้น ตอนนี้ทั้งสิบสามแถวจับคู่กับบรรทัดที่ตายจริงได้ครบ และไม่มีบรรทัดไหนถูกใช้
ต่างแถวกันโดยที่ข้ออ้างไม่ตรงกัน

## คำตอบของการบันทึก ปิดฟอร์มที่ส่งมันไป ไม่ใช่ฟอร์มที่มันเจอ — #146 (20 ก.ย. 2569)

`save` ของ `frontend/src/pages/CourseOutcomes.js` เคยจบด้วย `setEditing(null)` กับประโยคสำเร็จ
โดยไม่ถามอะไรเลย
การเขียนไม่มีอะไรมารื้อทิ้ง คำตอบของมันจึงมาถึงหน้าจอที่ขยับไปแล้วได้ —
รายการใต้ฟอร์มถูกวาดอยู่เสมอและไม่ปิดปุ่มไหนเลย ดินสอของการ์ดอื่นจึงมาแทนฟอร์ม ได้ทันทีโดยไม่ต้องมี
*ยกเลิก* ด้วยซ้ำ
ฟอร์มที่สองจึงถูกปิดไปพร้อมสิ่งที่พิมพ์ค้างไว้

เป็นเรื่องของรายการที่คนกำลังมองอยู่ ตอนนี้ `showing` จำ **สิ่งล่าสุดที่เปิดขึ้นบนจอนี้**
ทุกตัวควบคุมที่เปิดอะไรขึ้นมาเขียนมัน และคำตอบที่เจอการเปิดอื่นไม่ปิดอะไรและไม่พูดอะไร ทั้งประโยคสำเร็จ
และคำปฏิเสธ — คำถามเดียวกับที่ #139 ให้การอ่านถาม ที่ปลายของการเขียน (#133) เหตุผลทั้งหมดอยู่บน
`frontend/src/pages/Departments.js`

สิ่งที่ไม่ได้เปลี่ยนคือสิ่งที่หน้าจอปิดการใช้งาน ทั้งรายการและดินสอทุกตัวยังกดได้ระหว่างการบันทึก

- **`removalsentatthelanding` คือการถอดเงื่อนไขทิ้งในผล** `sent` ที่จับข้างการเปรียบเทียบเท่ากับ ref ตัวเอง ใบมัตแตนต์เคยเขียนว่าไม่ใช่ แก้คำบรรยายแล้ว การฆ่ายังเป็นการฆ่า
- **คำตอบนี้แยกประโยคของการบันทึกออกจาก `mine`** ก่อนหน้านั้น `146:closclosewins` ฆ่าทั้งการปิดและประโยคด้วยตัวเดียว ตอนนี้มันเห็นแค่การปิด ครึ่ง *ไม่มีประโยคสำเร็จ* ของแถว [#146](https://github.com/khthana/Deep-QA/issues/146) จึงได้ `clossavebannerunguarded` (`true ||` หน้าเงื่อนไข) — การกวาดซ้ำของ `146` เป็นที่ที่เห็นมัน *สมอที่ยังอยู่ไม่ได้แปลว่ายังพิสูจน์อะไรได้* (#107)

กวาดทีละตัว — baseline ของ `149a` **29 ผ่านทั้ง 29** (1.6 นาที) และของ `146a` **49 ผ่านทั้ง 49** (2.5–2.6 นาที) ทุกรันเวลาเท่า baseline ล้ม + ผ่าน = จำนวนแถวพอดี อ่านจากชื่อ describe *ผลการเรียนรู้รายวิชา (CourseOutcomes.js)*:

- `149:closremovalbannerunsaid` กับ `149a` **ล้ม 1 ผ่าน 28** ที่ *the banner of the removal* ของแถวใหม่ แถวเดียว
- `149:clossavebannerunguarded` กับ `149a` **ล้ม 1 ผ่าน 28** ที่ *the banner of the save before* และกับ `146a` **ล้ม 1 ผ่าน 48** ที่ *the first save's banner* ของแถวที่ `closewins` ฆ่าที่ฟอร์ม
- `146:closclosewins` **ล้ม 1 ผ่าน 48** ที่ assertion ของฟอร์ม
- `146:closcancelclears` **ล้ม 2 ผ่าน 47** — เหมือน 20 ก.ย.

หกตัวของจอนี้ใน `149` ตอนนี้ และ baseline ของ `149a` คือ 29 ไม่ใช่ 22 ที่ตัวเลขข้างบนอ่าน

## การโหลดใหม่ที่ล้มเหลวเก็บสิ่งที่วาดไว้ — #151 (22 ก.ย. 2569)

ตั้งแต่ #149 จอเก็บรายการและฟอร์มไว้ระหว่างการโหลดใหม่ แต่การโหลดที่**ล้มเหลว**ยังล้างทั้งคู่: `catch` ของ `load` ตั้ง `data` เป็น `null` ฟอร์มจึงถูกถอดพร้อมสิ่งที่พิมพ์ไว้ คำตอบ (22 ก.ย. 2569) คือคำตอบของ #149 ต่อไปอีกขั้น — **การโหลดที่ล้มเหลวเก็บสิ่งที่จอวาดไว้ล่าสุด** และคำปฏิเสธขึ้นเหนือมัน การโหลดครั้งแรกที่ล้มไม่มีอะไรให้เก็บ `loading && !data` วาดเหมือนเดิม ซึ่งตั๋วนี้ไม่เปลี่ยน

ทุกแถว **เดินด้วยมือไม่ได้** การเขียนถูกตอบด้วย 200 ที่แต่งขึ้น และการโหลดที่ตามมาด้วย 409 ที่แต่งขึ้น (`e2e/support/gate.js`) จึงไม่มีแถวไหนเขียนฐานข้อมูลผ่านการบันทึก เข้าด้วย `teacher.one@kmitl.ac.th` ครอบคลุมโดย describe *ผลการเรียนรู้รายวิชา (CourseOutcomes.js)* ใน `151a-failed-reload-keeps-the-list.spec.js` จุดอ่านคือหลังคำปฏิเสธถึงหน้า แล้ว 250 ms อ่านครั้งเดียว (#52) สิ่งที่ค้ำมันคือการกวาดข้างล่าง

### มัตแตนต์

`151:closblanks` ใส่ `setData(null)` กลับเข้า `catch` ของจอนี้ — โค้ดก่อน #151 — และ `151:closblinks` ล้าง `data` แล้วคืนมันในจังหวะถัดไป ฟอร์มจึงถูกถอดแล้ววาดใหม่ เปิดอยู่แต่สิ่งที่พิมพ์หายไป `blinks` เพิ่มหลังการตรวจ: `blanks` ฆ่าแถวฟอร์มที่ *the second card's form* ซึ่งอ่านก่อน *what was typed* ครึ่งหลังนั้นจึงไม่มีมัตแตนต์ไปถึง กวาดทั้งสิบสี่ตัวของใบ `151` เมื่อ 22 ก.ย. 2569 ด้วย `151a` ทั้งไฟล์บนข้อความสุดท้ายของมัน — baseline **14 ผ่านทั้ง 14** (0.8 นาที) `closblanks` **ล้ม 2 ผ่าน 12** (0.9 นาที) ที่ *the second card's form* และที่ *the cards drawn before the reload* `closblinks` **ล้ม 1 ผ่าน 13** (0.9 นาที) ที่ *what was typed* แถวเดียว ไม่ใช่ที่ timeout และไม่มีแถวของจออื่นตาย อ่านจากชื่อ describe ไม่ใช่จากจำนวน

### สิ่งที่วัดได้แต่ไม่ใช่ของตั๋วนี้

ตั๋วเขียนว่า *แบนเนอร์คำปฏิเสธบอกว่าการโหลดล้มเหลว* วัดแล้วจริงแค่เมื่อมีฟอร์มอื่นเปิดทีหลัง: ถ้าไม่มีอะไรเปิด `save` ตั้งประโยคสำเร็จ*หลัง*การโหลด ประโยคนั้นจึงทับคำปฏิเสธ (วัดด้วย probe ที่ลบทิ้งแล้ว: บนจอ ผลการเรียนรู้รายวิชา คำปฏิเสธ 0 ประโยคสำเร็จ 1 และบนแถวรายการของ `151a` ทั้งเจ็ดจอ คำปฏิเสธ 0 ทุกจอ) — ตอนนี้คือ *บันทึก…แล้ว* เหนือรายการ ที่ยังไม่มีสิ่งที่บันทึก ซึ่งเป็นคำถามของเจ้าของ ไม่ได้แก้ในตั๋วนี้
