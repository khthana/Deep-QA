## หน้าจอนี้ต่างจากทุกหน้าก่อนหน้าอย่างไร

**สิ่งที่แสดงไม่ได้เป็นของตอนเรียนที่ใช้เปิดมัน** ADR-0004 บอกว่าบริบทของผู้สอนคือ `section_id`
ในที่อยู่และไม่มีที่อื่น ส่วน ADR-0003 บอกว่าชุด CLO เป็นของ (หลักสูตร, รายวิชา, ปีการศึกษา)
ไม่ใช่ของตอนเรียน หน้านี้คือที่แรกที่ข้อกำหนดสองข้อนั้นมาเจอกัน — ที่อยู่คือตอนเรียน ระเบียนคือ
การเปิดสอน และ **เซิร์ฟเวอร์เป็นฝ่ายแปลงอันแรกเป็นอันหลังทุกครั้งที่มีคำขอ**

ผลที่ตามมาซึ่งพลาดได้ง่ายที่สุดคือ *สามค่านั้นอยู่ใน body ของคำขออยู่แล้ว* หน้าจอแสดงปีการศึกษา
จึงมีมันในมือ และการอ่านจาก body สั้นกว่าการ resolve หนึ่งบรรทัด — มันคือ ADR-0002 ที่ถูกละเมิด
โดยที่ **ไม่มีอะไรบนหน้าจอเปลี่ยนเลย** เพราะหน้าจอส่งกลับสิ่งที่เซิร์ฟเวอร์เพิ่งให้มันมา
มัตแตนต์ชื่อ `bodygrain` คือตัวนั้น และมีแถวเดียวในระบบที่ฆ่ามันได้

**ผู้สอนสองคนแก้รายการเดียวกัน** นั่นคือสิ่งที่ grain นี้ซื้อมา และเป็นเหตุผลที่ `updated_by`
เป็นคอลัมน์ที่ต้องทำงาน ไม่ใช่คอลัมน์ตรวจสอบย้อนหลัง — ADR-0003 เลือก *เขียนทีหลังชนะ*
ไว้อย่างตั้งใจแทนการล็อก และชื่อกับเวลาบนแถวคือวิธีเดียวที่คนแพ้จะรู้ตัว

**ตัวเลือก PLO ถูกจำกัดด้วยตารางความครอบคลุม ไม่ใช่ด้วย foreign key** `subject_clo.plo_id`
อ้างถึง `learning_outcomes` ผ่าน `(program_id, plo_id)` ฐานข้อมูลจึงยอมรับ PLO ทุกข้อของหลักสูตร
รวมทั้งข้อย่อย และรวมทั้งข้อที่รายวิชานี้ไม่เคยถูก map ถึง `subject_plo_mapping` คือตารางนั้น
และเป็นสิ่งที่ route ถาม

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

**ต้อง reset + seed ใหม่จริง ๆ ก่อนเดินใบนี้** ด้วยเหตุผลเดียวกับ #24 — `db/term.js` ทำให้ seed
เดินตามนาฬิกา ฐานข้อมูลที่ seed ไว้ก่อนหน้าจะไม่ได้อยู่ในเทอมปัจจุบันอีกแล้ว

**ต้อง restart backend ก่อนเดิน** — process ที่ค้างจากตั๋วก่อนจะตอบ 404 ให้ทุก route ของ #27
และหน้าจอแปลผลเป็น *เกิดข้อผิดพลาดในการเชื่อมต่อเซิร์ฟเวอร์* (#95) การเดิน #24 เสียเวลาไปกับ
เรื่องนี้หนึ่งชั่วโมง **ยิง `curl http://localhost:3000/api/teaching/sections/1/clos` หนึ่งครั้งก่อนเริ่ม**

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือ `deep-core-local` — ค่าของตัวแปร `PASSWORD` ใน `db/seed.js`

ทางเข้าหน้านี้คือ เลือกตอนเรียนจากหน้า *รายวิชา* แล้วกดเมนู **ผลการเรียนรู้รายวิชา** ทางซ้าย
ที่อยู่ที่ได้คือ `/teacher/teacherDashboard/<section_id>/courseOutcomes`

seed หลังเดินคำสั่งข้างบนมีรูปร่างที่ใบนี้ต้องใช้พอดี

| ปีการศึกษา | ตอนเรียน | ผู้สอน | ชุด CLO |
|---|---|---|---|
| เทอมปัจจุบัน | `1` | `teacher.one@` | CLO-1..CLO-9 ของปีปัจจุบัน |
| เทอมปัจจุบัน | `2` | `multi.role@` | **ชุดเดียวกัน** (การเปิดสอนเดียวกัน) |
| ปีก่อนหน้า | `1` | `teacher.one@` | CLO-1..CLO-9 **คนละเก้าแถว** |

- `teacher.one@` — สอนตอนเรียน `1` ทั้งเทอมนี้และปีก่อน จึงเป็นบัญชีเดียวที่เดินเกณฑ์ข้อ 5 ได้
- `multi.role@` — สอนตอนเรียน `2` ของการเปิดสอนเดียวกัน **ต้องสลับเป็น อาจารย์ผู้สอน ก่อน**
  จึงจะเข้าถึงหน้านี้ได้ เป็นบัญชีเดียวที่เดินเกณฑ์ข้อ 3 กับ 4 ได้
- `teacher.two@` — ไม่ได้สอนอะไรเลย ใช้เดินการปฏิเสธข้ามตอนเรียน

**PLO-1, 2, 3, 5, 6, 7, 8 และ 12 ถูก map เข้ารายวิชานี้ ส่วน PLO-4, 9, 10, 11, 13 ไม่ได้ถูก map**
ห้าข้อหลังคือสิ่งที่เกณฑ์ข้อ 2 พูดถึงจริง ๆ picker ที่สร้างจาก `learning_outcomes` เฉย ๆ
จะดูถูกต้องทุกอย่างจนกว่าจะมีคนเลือกหนึ่งในห้าข้อนั้น

**CLO ทั้ง 18 แถวใน seed มีคะแนนบันทึกไว้แล้วทุกแถว** จึงลบไม่ได้สักแถวเดียว แถวที่ต้องเดินการลบ
สำเร็จจึงต้อง **สร้าง CLO ใหม่ขึ้นมาลบ** ไม่ใช่ลบของที่มีอยู่ ใบนี้เขียนไว้อย่างนั้นแล้ว

## มัตแตนต์ที่พิสูจน์แถว ⚙

`mutation/27-course-outcomes.py` ยี่สิบสองตัว อ่านวิธีใช้ที่ `mutation/README.md` ก่อน

ทุกแถวที่ติด ⚙ มีมัตแตนต์ของตัวเอง และมัตแตนต์นั้นตายที่ assertion ของแถวนั้นจริง ๆ ไม่ใช่แค่ที่
spec ไฟล์เดียวกันตาย เดินจริงเมื่อ 23 สิงหาคม 2569 บน `backend/test/clos.test.js` (20 subtests)
และบน `npx playwright test 27a` (9 tests) ตัวเลขข้างล่างนี้คือสิ่งที่มัตแตนต์ฆ่าได้จริง ไม่ใช่สิ่งที่
ควรจะฆ่าได้ ตารางฝั่งเบราว์เซอร์บอก **บรรทัดที่ตาย** ไว้ด้วย เพราะบรรทัดคือสิ่งเดียวที่แยก
*แถวนี้พิสูจน์เรื่องนี้* ออกจาก *แถวนี้ตายทีหลังเพราะหน้าจอเพี้ยนไปก่อนแล้ว*

### สี่อย่างที่รอบนี้จับได้ และควรอ่านก่อนเชื่อตัวเลขรอบก่อน ๆ

**มัตแตนต์ที่ทำให้ query พัง ไม่ได้พิสูจน์อะไร** `nodetail` กับ `noeditor` รอบแรกเขียนเป็น
`clo_detail = clo_detail` และ `updated_by = updated_by` ซึ่งทำให้ `$3` กับ `$7` ไม่ถูกอ้างถึง
PostgreSQL จึงปฏิเสธทั้ง statement และ route ตอบ **500** แถวเบราว์เซอร์ที่ตายจึงตายที่บรรทัด
`toBe(200)` ไม่ใช่ที่บรรทัดซึ่ง assert ว่าการแก้ไปถึงอีกตอนเรียน — คนละเรื่องกันคนละอย่าง
ทั้งสองตัวถูกเขียนใหม่เป็น `COALESCE(clo_detail, $3)` กับ `CASE WHEN TRUE THEN updated_by ELSE $7 END`
ซึ่งยังผูก parameter ไว้ครบและเปลี่ยนแค่ *พฤติกรรม* ตอนนี้ทั้งคู่ตายที่บรรทัดของมันเอง

**subtest ที่ผูกกับเลขเก้า ทำให้มัตแตนต์ดูเก่งเกินจริง** ข้อ 14 เคย assert ว่ารายการยาวเก้าแถว
หลังคำขอที่ถูกปฏิเสธ ซึ่งพังทุกครั้งที่เทสต์ก่อนหน้าทิ้งแถวไว้ หรือทุกครั้งที่มัตแตนต์เปลี่ยนความยาว
ของรายการ — `noploguard` `mappedasmarked` และ `anyyear` จึงเคยนับข้อ 14 เป็นเหยื่อทั้งที่
ไม่ได้แตะสิ่งที่ข้อ 14 อ้าง ตอนนี้มันอ่านความยาวไว้ก่อนแล้วเทียบกับตัวเอง

**เทสต์ที่ใช้รหัสร่วมกัน ส่งต่อความพังให้กัน** ข้อ 6 เคยเขียนด้วยรหัสของ `DRAFT` พอ `noploguard`
ทำให้การเขียนผ่าน แถวที่มันทิ้งไว้ก็ไปชนกับรหัสที่ข้อ 7 กำลังจะอ้าง ข้อ 7 จึงตายตาม ตอนนี้ข้อ 6
ใช้ `CLO-96` ของตัวเอง และ `noploguard` ฆ่าได้ subtest เดียวคือของมันเอง ข้อ 7 ก็เป็นแบบเดียวกัน
และเพิ่งแก้รอบนี้ — มันใช้ `CLO-90` ซึ่งเป็นรหัสของ `DRAFT` พอ `swallowdelete` ทำให้การลบไม่เกิดขึ้นจริง
แถวที่ข้อ 5 เก็บกวาดไม่สำเร็จก็ค้างอยู่ และข้อ 7 ตายเพราะรหัสชน ตอนนี้ข้อ 7 ใช้ `CLO-97`
และ `swallowdelete` ฆ่าได้ข้อ 13 ข้อเดียว

**สองแถวที่ติด ⚙ มานาน โดยยังไม่มีมัตแตนต์ของตัวเอง** *เพิ่ม CLO ใหม่ได้* กับ
*ลบ CLO ที่ไม่มีอะไรอ้างถึงได้* ทั้งคู่ชี้ไปที่ `27a` แถว 8 แต่มัตแตนต์ตัวเดียวที่ฆ่าแถว 8 ได้คือ
`cancelremoves` ซึ่งตายที่บรรทัด 227 อันเป็นบรรทัดของ *การยกเลิก* ไม่ใช่ของการเพิ่มหรือการลบ
สองแถวนั้นจึงอยู่ในสภาพเดียวกับที่รอบนี้ตามแก้มาตลอด คือ assertion มีอยู่ แต่ไม่มีอะไรพิสูจน์ว่ามันจะเห็น
`savenoreload` กับ `swallowdelete` เพิ่งเขียนขึ้นเพื่อปิดช่องนี้

แถว 6 จึงทิ้งแถวไว้ และแถว 8 ไปตายที่บรรทัด 224 `toBe(201)` แทนที่จะเป็นบรรทัดเรื่องรายการ
เป็นการฆ่าด้วยการปนเปื้อน ซึ่งไม่พิสูจน์อะไร

**สองอย่างที่ตารางนี้ไม่ได้ครอบ และเขียนไว้ให้เห็น**

`allplos` ตายที่บรรทัด 182 ซึ่งอ่าน `plos` จาก **คำตอบของเซิร์ฟเวอร์** ไม่ใช่จากหน้าจอ ส่วนบรรทัด 175
ที่นับตัวเลือกนั้นเอาจำนวนมาจากคำตอบเดียวกัน มันจึงจับได้แค่ *หน้าจอกรองไม่ตรงกับที่เซิร์ฟเวอร์ให้มา*
ไม่ใช่ *เซิร์ฟเวอร์ให้มากเกินไป* ครึ่งหลังเป็นของบรรทัด 182 ครึ่งแรกเป็นของ `emptypicker` — สองตัวรวมกัน
ครอบเกณฑ์ข้อ 2 ครบ แต่ไม่มีตัวไหนครอบได้คนเดียว

`bodygrain` กับ `putnoploguard` ไม่มีแถวเบราว์เซอร์ตัวไหนฆ่าได้ ทั้งคู่เป็นการละเมิดที่หน้าจอ
มองไม่เห็นตามนิยาม — หน้าจอส่งกลับสิ่งที่เพิ่งได้รับมา และเลือกได้เฉพาะจากรายการที่ให้มา
seam ของ HTTP เป็นที่เดียวที่ทั้งสองข้อพิสูจน์ได้ และเป็นเหตุผลที่ #27 ยังมีเทสต์ฝั่ง server อยู่ยี่สิบตัว

## สิ่งที่ตัดสินใจไว้และควรรู้ก่อนแก้

**เกณฑ์ข้อ 8 มีสามสถานะ ไม่ใช่หนึ่ง และตั๋วกับ schema ไม่ตรงกัน** ตั๋วเขียนว่า *CLO ที่มีคะแนน
บันทึกไว้ ลบไม่ได้* แต่สิ่งที่ฐานข้อมูลห้ามจริง ๆ มีสามอย่างและมันไม่ตรงกัน

- `activity_scores.clo_id` เป็น `ON DELETE RESTRICT` — นี่คือสถานะที่ตั๋วพูดถึง
- `activity_clo_mapping.clo_id` เป็น `ON DELETE RESTRICT` เหมือนกัน แต่มันห้ามตั้งแต่มีกิจกรรม
  ชี้มา **ไม่ว่าจะเคยมีคะแนนหรือไม่** ทางออกของสถานะนี้คนละทางกับข้างบน คือไปยกเลิกการผูกที่กิจกรรม
- `clo_course_cycle_detail_cloplan.clo_id` เป็น **`ON DELETE CASCADE`** ฐานข้อมูลจะไม่ห้ามอะไรเลย
  และบันทึกทบทวนของรอบการสอนจะหายไปพร้อมกันโดยไม่มีใครรู้

route จึงตรวจทั้งสามเองก่อน `DELETE` และปฏิเสธด้วยประโยคของตัวเองสามประโยค แต่ละประโยคบอกทางออก
คนละทาง สองในสามฐานข้อมูลจะจับได้อยู่แล้ว และการจับเองก็ยังไม่ซ้ำซ้อน — 23503 ที่ไปถึง handler
ใน `app.js` ตอบว่า *เกิดข้อผิดพลาดในระบบ* ซึ่งเป็นประโยคผิดสำหรับสิ่งที่คนไปแก้เองได้ นี่คือบทเรียน
เดียวกับ `24:nonumericguard` จาก #23 ส่วนอย่างที่สามฐานข้อมูลไม่จับให้เลย

**`is_active` ของ PLO อยู่ในเงื่อนไขของ picker แล้ว แต่ยังพิสูจน์ด้วยข้อมูลไม่ได้** เกณฑ์ข้อ 6
ของ **#19** บอกว่า PLO ที่ถูก CLO อ้างถึงต้องถูกปิดการใช้งานแทนการลบ คอลัมน์ `is_active` จึงจะ
เป็น false ได้จริงในอนาคต ตอนนี้ทุกแถวใน seed เป็น true เงื่อนไขนั้นจึงถูกเขียนไว้ล่วงหน้าเพื่อไม่ให้
#19 ต้องย้อนกลับมาแก้ route ของ #27 — แต่ **ไม่มีเทสต์ไหนพิสูจน์มันได้จนกว่า #19 จะมาปิด PLO สักข้อ**
บันทึกไว้ตรง ๆ แทนที่จะปล่อยให้ดูเหมือนถูกครอบแล้ว

**#19 ยังเปิดอยู่ตอนที่ #27 ถูกทำ** ตั๋ว #27 เขียนไว้ในหัวข้อ *Blocked by* ว่าติด #19 ซึ่งเป็น
ข้อความใน body ไม่ใช่ native dependency ของ GitHub (`blockedByIssues` ไม่มีบน schema ของ repo นี้)
ที่ทำได้เพราะข้อมูลที่ #27 ต้องใช้มีครบแล้ว — 52 `learning_outcomes` และ 8 `subject_plo_mapping`
**#19 เพิ่มความสามารถในการ *จัดการ* PLO ไม่ใช่ตัวข้อมูล** สิ่งที่ #19 ยังขาดคือทั้งหมดที่เป็นโค้ด
ไม่มี route ไม่มีหน้าจอ ไม่มีเทสต์

**ฟอร์มเดียวใช้ทั้งเพิ่มและแก้** ไม่ใช่สองฟอร์ม เพราะช่องเป็นห้าช่องเดียวกันและต่างกันแค่ค่าตั้งต้น
สองฟอร์มคือสองที่ที่ต้องเพิ่มช่องที่หก และหนึ่งในนั้นจะถูกลืม

**รหัส CLO ไม่ได้ถูกสร้างให้อัตโนมัติ** `CLO-1..CLO-9` ดูเหมือนลำดับแต่ไม่ใช่ — เกณฑ์ข้อ 6 ทำให้
รหัสไม่ซ้ำ *ภายในปีการศึกษา* และหลักสูตรที่แยกหรือเลิกใช้ผลการเรียนรู้ข้อหนึ่งกลางปีต้องเขียน
`CLO-3ก` ได้ ช่องจึงเป็น text คนพิมพ์เอง และเซิร์ฟเวอร์เป็นฝ่ายปฏิเสธเมื่อชน

**ปุ่มยืนยันการลบปิดกล่องเสมอ ไม่ว่าคำตอบจะเป็นอะไร** กล่องที่ค้างอยู่เหนือแถบปฏิเสธจะบังมัน และ
เสนอปุ่มเดิมให้กดซ้ำ ซึ่งกดอีกกี่ครั้งก็ได้ผลเดิม
