# ตรวจรับด้วยมือ — #57 แยกตัวควบคุมการแบ่งหน้า

ตั๋วนี้ไม่มีพฤติกรรมใหม่เลย ทุกอย่างที่หน้าจอทำได้ก่อนหน้านี้ต้องทำได้เหมือนเดิมทุกประการ —
นั่นคือทั้งหมดที่ต้องพิสูจน์ และเป็นเหตุผลที่ checklist ใบนี้สั้น

`frontend/src/components/Pager.js` คือของใหม่หนึ่งไฟล์ และหน้าจอทั้งหกที่เคยเขียนแถบแบ่งหน้าเอง
ถูกย้ายมาเรียกมันแทน — ผู้ใช้งานระบบ, แผงประวัติการใช้งาน, ข้อมูลภาควิชา, ข้อมูลหลักสูตร
และข้อมูลรายวิชา (ห้าแฟ้ม หกจุดเรียกถ้านับ #16 ที่เพิ่งเพิ่ม)

**ทำไมต้องเดินด้วยมือทั้งที่เป็น refactor** — `docs/06 §Testing Decisions` ระบุว่า frontend
components ไม่มี unit test ชุดทดสอบ backend 243 ตัวไม่แตะโค้ดส่วนนี้เลย แถบแบ่งหน้าจึงไม่มีอะไร
คุ้มกันนอกจากสายตา และตั๋ว #57 เองเขียนไว้ว่า "the paging rows in the five existing acceptance
checklists re-walked, since the control beneath them is new"

**ตั้งแต่ #65 มี seam ที่สอง** คือเบราว์เซอร์ — `e2e/tests/57a-pager.spec.js` (เก้าข้อทดสอบ)
รับแถวข้างล่างไปเกือบทั้งใบ นี่คือใบที่ได้ประโยชน์จาก seam มากที่สุดในบรรดาที่มี เพราะข้ออ้างของ
ตั๋วนี้คือ *ไม่มีอะไรเปลี่ยน* ซึ่งเป็นข้ออ้างที่การเดินด้วยมือพิสูจน์ได้ครั้งเดียวและพิสูจน์ซ้ำเองไม่ได้เลย
ดูหัวข้อ *แถวที่ browser seam รับไป* ท้ายเอกสาร

## ตั้งต้น

```
docker start deep-core-postgres
cd db       && npm run reset && npm run migrate && npm run seed
cd backend  && npm start          # :3000
cd frontend && npm start          # :5000
```

seed มีบัญชีเกินสิบบัญชีอยู่แล้ว หน้า *ผู้ใช้งานระบบ* จึงแบ่งหน้าได้ทันทีโดยไม่ต้องสร้างข้อมูล
ส่วนหน้าอื่นต้องทำให้มีเกินสิบแถวก่อน ซึ่งวิธีที่เร็วที่สุดคือใช้กล่องนำเข้าไฟล์ของหน้านั้น ๆ

ช่องสุดท้ายมีสี่ค่า

- **☑** เดินด้วยมือจบแล้ว
- **◐** เดินไปครึ่งเดียว
- **☐** ยังไม่ได้เดิน
- **⚙** ครอบคลุมด้วย browser seam แล้ว (#65) ไม่ต้องเดินด้วยมือซ้ำ แถวบอกไฟล์ที่ครอบคลุมไว้
  ถ้าแถวนั้นพูดถึงสิ่งที่วาดด้วย (สีของปุ่ม ระยะห่าง ถ้อยคำ) ครึ่งนั้นยังเป็นงานของคนเดิน
  และแถวจะเขียนกำกับไว้

## แถวที่ browser seam รับไป

`e2e/tests/57a-pager.spec.js` — เก้าข้อทดสอบ รับแปดในเก้าแถวของตารางข้างบน เหลือแถว 2
(ระยะห่างของแผงประวัติ) เป็นแถวที่คนเดิน

ไฟล์นี้ต่างจากไฟล์ spec ใบอื่นสองเรื่อง และทั้งสองเรื่องเป็นเรื่องเดียวกับที่ทำให้ #57 มีอยู่

1. **มันแตะสี่หน้าจอในไฟล์เดียว** เพราะสิ่งที่พิสูจน์คือ *คอมโพเนนต์ตัวเดียวกัน* ที่ทั้งสี่หน้าวาด
   ถ้าแยกไปอยู่ไฟล์ของแต่ละหน้าจอ ก็จะกลายเป็นการเขียน helper เดียวกันสี่รอบ ซึ่งเป็นสิ่งที่
   ตั๋วนี้เพิ่งเลิกทำในโค้ด `e2e/support/pager.js` คือส่วนที่ใช้ร่วมกัน และแต่ละหน้าจอส่ง
   *ตารางของตัวเอง* เข้ามา เพราะนั่นคือส่วนที่ต่างกันจริง ๆ
2. **มันเป็นเจ้าของข้อมูลของตัวเองทั้งหมด** `57a` เรียงหลัง `16x` และ `18x` ทุกไฟล์ภายใต้
   worker เดียว แถวที่อ่านว่า "สิบแถวต่อหน้า" จากของที่ไฟล์อื่นทิ้งไว้ จะเป็นแถวที่ความหมาย
   ขึ้นกับไฟล์ที่มันไม่เคยเอ่ยถึง ทุกจำนวนจึงวัดจากสิ่งที่ตารางมีจริงขณะนั้น และรหัสทุกตัว
   อยู่ในช่วงที่ไม่มีไฟล์อื่นใช้ — `Z…` สำหรับภาควิชา `ZP…` สำหรับหลักสูตร `010797…` สำหรับรายวิชา

**รอบกวาดแรกจับข้อบกพร่องของ spec เองได้หนึ่งข้อ** `nofloor` ควรไม่มีผลกับรายการที่ไม่ว่างเลย
แต่กลับฆ่าแถว *ถัดไป/ก่อนหน้า* ทิ้ง สาเหตุคือแถวนั้นอ่านตารางในช่องระหว่างที่ server ตอบแล้ว
กับตอนที่หน้าจอวาดเสร็จ จึงได้แถว *กำลังโหลด…* มาเป็นคำตอบ ซึ่งไม่ซ้ำกับหน้าไหนเลย
ข้ออ้าง "หน้าถัดไปคือคนละชุด" จึงเป็นจริงโดยบังเอิญ แก้ที่ `settled()` ใน `e2e/support/pager.js`
ด้วยการรอให้ตารางวาดเสร็จก่อนอ่านเสมอ แล้วกวาดใหม่ทั้งหมด — ตัวเลขในตารางข้างล่างคือรอบหลังแก้

**ลำดับภายในแถวสำคัญ** ข้ออ้าง "หน้าถัดไปคือคนละชุด" ถูก assert *ก่อน* บรรทัดที่อ่านว่า *หน้า 2*
เสมอ เพราะหน้าจอที่เลิกส่ง `page` จะได้หน้าหนึ่งกลับมา และ `shown` จะอ่านว่า 1 — บรรทัดจะตายก่อน
และข้ออ้างที่แถวนั้นพูดถึงจริง ๆ จะไม่มีหลักฐานรองรับเลย นี่คือความผิดพลาดแบบเดียวกับ
`alwaysfilter` ของ #18 และ #69

## สิ่งที่ยังไม่ปิดใน #57

1. **`PAGE_SIZE = 10` ยังประกาศแยกกันในแต่ละหน้าจอ** — ตกทอดมาจาก `13-user-activity-history.md`
   ข้อ 3 ตั้งใจไม่รวมในตั๋วนี้ เพราะค่านี้ไม่ได้ใช้แค่วาดแถบ แต่ถูกส่งไปกับ `per_page` ของคำขอด้วย
   การรวมเป็นค่าเดียวจึงเป็นการตัดสินใจเรื่องสัญญาระหว่างหน้าจอกับ API ไม่ใช่เรื่องของคอมโพเนนต์
   ฝั่ง backend มี `lib/paging` ถือค่านี้อยู่แล้วหนึ่งที่ — ตัวกลายพันธุ์ `perpage` เปลี่ยนของ
   หน้าผู้ใช้งานระบบจาก 10 เป็น 5 และฆ่าได้ ซึ่งพิสูจน์ว่าหน้านั้นถือค่านี้เอง
2. **`<Pager>` ยังไม่มีปุ่มกระโดดไปหน้าที่ต้องการ** — มีแค่ *ก่อนหน้า* / *ถัดไป* ซึ่งเป็นสิ่งที่
   ตั๋วหน้าจอทุกใบขอไว้ ถ้าแคตตาล็อกรายวิชาโตถึงหลายสิบหน้า การกดทีละหน้าจะเริ่มไม่ไหว
   และตอนนั้นเปลี่ยนที่เดียวจบ — ซึ่งเป็นเหตุผลของตั๋วนี้ทั้งใบ
3. **ยังไม่มีที่ไหนบอกจำนวนแถวต่อหน้าให้ผู้ใช้เลือก** — สิบแถวเป็นค่าที่ตั๋วกำหนด ไม่ใช่ค่าที่
   ผู้ใช้ตั้งได้ `lib/paging` เปิดเพดานไว้ที่ 100 แล้วถ้าวันหนึ่งจะให้เลือก
4. **หน้าจอ *รายวิชาในหลักสูตร* (#18) ก็มีสำเนาของกฎ *ถอยกลับหนึ่งหน้า* เป็นของตัวเอง** —
   `ProgramSubjects.js` เขียนไว้เป็นครั้งที่สี่ ใบนี้พิสูจน์ของหน้าภาควิชากับหน้าหลักสูตรแล้ว
   ส่วนของ #16 และ #18 ยังไม่มีตัวกลายพันธุ์ของตัวเอง กฎสามบรรทัดนี้เป็นสิ่งที่ควรย้ายเข้าไป
   อยู่ในที่เดียวกันต่อจาก `<Pager>` แต่มันอยู่ในตัวจัดการการลบ ไม่ได้อยู่ในตัวแถบ
   จึงไม่ใช่เรื่องที่ตั๋วนี้ทำได้
