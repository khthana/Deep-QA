# ตรวจรับด้วยมือ — #57 แยกตัวควบคุมการแบ่งหน้า

ตั๋วนี้ไม่มีพฤติกรรมใหม่เลย ทุกอย่างที่หน้าจอทำได้ก่อนหน้านี้ต้องทำได้เหมือนเดิมทุกประการ —
นั่นคือทั้งหมดที่ต้องพิสูจน์ และเป็นเหตุผลที่ checklist ใบนี้สั้น

`frontend/src/components/Pager.js` คือของใหม่หนึ่งไฟล์ และหน้าจอทั้งหกที่เคยเขียนแถบแบ่งหน้าเอง
ถูกย้ายมาเรียกมันแทน — ผู้ใช้งานระบบ, แผงประวัติการใช้งาน, ข้อมูลภาควิชา, ข้อมูลหลักสูตร
และข้อมูลรายวิชา (ห้าแฟ้ม หกจุดเรียกถ้านับ #16 ที่เพิ่งเพิ่ม)

**ทำไมต้องเดินด้วยมือทั้งที่เป็น refactor** — `docs/06 §Testing Decisions` ระบุว่า frontend
components ไม่มี unit test ชุดทดสอบ backend 243 ตัวไม่แตะโค้ดส่วนนี้เลย แถบแบ่งหน้าจึงไม่มีอะไร
คุ้มกันนอกจากสายตา และตั๋ว #57 เองเขียนไว้ว่า "the paging rows in the five existing acceptance
checklists re-walked, since the control beneath them is new"

## ตั้งต้น

```
docker start deep-core-postgres
cd db       && npm run reset && npm run migrate && npm run seed
cd backend  && npm start          # :3000
cd frontend && npm start          # :5000
```

seed มีบัญชีเกินสิบบัญชีอยู่แล้ว หน้า *ผู้ใช้งานระบบ* จึงแบ่งหน้าได้ทันทีโดยไม่ต้องสร้างข้อมูล
ส่วนหน้าอื่นต้องทำให้มีเกินสิบแถวก่อน ซึ่งวิธีที่เร็วที่สุดคือใช้กล่องนำเข้าไฟล์ของหน้านั้น ๆ

## สิ่งที่ยังไม่ปิดใน #57

1. **`PAGE_SIZE = 10` ยังประกาศแยกกันในแต่ละหน้าจอ** — ตกทอดมาจาก `13-user-activity-history.md`
   ข้อ 3 ตั้งใจไม่รวมในตั๋วนี้ เพราะค่านี้ไม่ได้ใช้แค่วาดแถบ แต่ถูกส่งไปกับ `per_page` ของคำขอด้วย
   การรวมเป็นค่าเดียวจึงเป็นการตัดสินใจเรื่องสัญญาระหว่างหน้าจอกับ API ไม่ใช่เรื่องของคอมโพเนนต์
   ฝั่ง backend มี `lib/paging` ถือค่านี้อยู่แล้วหนึ่งที่
2. **`<Pager>` ยังไม่มีปุ่มกระโดดไปหน้าที่ต้องการ** — มีแค่ *ก่อนหน้า* / *ถัดไป* ซึ่งเป็นสิ่งที่
   ตั๋วหน้าจอทุกใบขอไว้ ถ้าแคตตาล็อกรายวิชาโตถึงหลายสิบหน้า การกดทีละหน้าจะเริ่มไม่ไหว
   และตอนนั้นเปลี่ยนที่เดียวจบ — ซึ่งเป็นเหตุผลของตั๋วนี้ทั้งใบ
3. **ยังไม่มีที่ไหนบอกจำนวนแถวต่อหน้าให้ผู้ใช้เลือก** — สิบแถวเป็นค่าที่ตั๋วกำหนด ไม่ใช่ค่าที่
   ผู้ใช้ตั้งได้ `lib/paging` เปิดเพดานไว้ที่ 100 แล้วถ้าวันหนึ่งจะให้เลือก
