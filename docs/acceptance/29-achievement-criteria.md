## สิ่งที่ต้องเข้าใจก่อนเดิน — เกณฑ์การบรรลุผลเป็นของ CLO และของอย่างอื่นไม่มีเลย

`subject_clo_achievement_criteria` มีแค่ `clo_id` — ไม่มีตอนเรียน ไม่มีปี ไม่มีหลักสูตร ไม่มีเจ้าของ
ทั้ง ADR-0003 จึงมาถึงหน้านี้โดยการสืบทอดแบบเดียวกับ #28 ทุกประการ: เข้าผ่านตอนเรียนไหนของ
การเปิดสอนก็เห็นชุดเดียวกัน และ CLO รหัสเดียวกันของคนละปีถือคนละชุด `achievementCriteria.js`
ไม่ได้ถามคำถามสิทธิ์เอง — มัน import `offeringOf` กับ `cloOf` จาก `clos.js` และทุกการอ่านแถวเป็น
`WHERE id = $1 AND clo_id = $2` เสมอ

**สี่ระดับเป็น CHECK ไม่ใช่ enum และค่าที่เก็บคือคำไทยเอง** ดีเยี่ยม · ดี · พอใช้ · ต้องปรับปรุง —
คำเดียวกับที่ rubric ใช้ (ดูโน้ตใน migration 0002 ว่าทำไมถึงเป็น CHECK ที่ขยายได้ในตารางเดียว)
จอจึง**ไม่มีตารางป้าย** แบบ `labels.js` ของ #28: ค่าบนสายกับคำบนจอคือตัวเดียวกัน route
ยังตรวจในโค้ดก่อนถึงฐานข้อมูลเพราะ 23514 ที่ไปถึง error handler จะกลายเป็น
*เกิดข้อผิดพลาดในระบบ* — ประโยคผิดสำหรับค่าที่คนเลือกจากรายการ

**ระดับไม่ unique ต่อ CLO** ตั๋วบอกว่า CLO *สามารถ*ถือเกณฑ์ครบทั้งสี่ระดับ — เป็นความสามารถ
ไม่ใช่ข้อบังคับ — และ CLO หนึ่งถือหลายเกณฑ์ระดับเดียวกันได้ (เทสต์จัดเลขใหม่เขียนสามข้อ
ระดับเดียวกันเพื่อพิสูจน์ว่าไม่มีอะไรห้าม) constraint ที่บอกว่า *ต้อง* จะเป็นของที่ประดิษฐ์ขึ้นเอง
ไม่ใช่ของที่หามาได้จากที่ไหน

**คำอธิบาย (`criteria_description`) เป็นช่องเดียวที่ไม่บังคับ** คอลัมน์ nullable ช่องเว้นว่าง
ขาวล้วน หรือไม่ส่งมา ล้วนเก็บเป็น NULL — การแก้ที่ลบข้อความออกจนหมดจึงล้างคอลัมน์จริง
ไม่ใช่เก็บ `''` และจอวาดย่อหน้าคำอธิบายเฉพาะเมื่อมี (ขีดกลางจะสื่อว่าเป็นช่องที่ลืมกรอก
ซึ่งไม่ใช่)

**เลขลำดับเป็นของเซิร์ฟเวอร์ ไม่ใช่ของฟอร์ม** เพิ่มแล้วได้เลขถัดไป (ล็อกแถว CLO ก่อนนับ)
ลบแล้วที่เหลือถูกจัดใหม่เป็น 1..N ไม่มีช่องว่าง — `UNIQUE (clo_id, criteria_no)` ยึดตาม
ความเข้าใจนี้ไว้แล้วใน migration 0002 เลขใน body ถูกเมินแบบเดียวกับปีที่ส่งมาหา #27

**ไม่มีใครถูกบันทึกว่าเป็นคนแก้ และการลบไม่มีด่านกั้น** — คำตอบของ schema ทั้งคู่ แบบเดียวกับ
#28: ไม่มี `updated_by` และไม่มีตารางไหนอ้างถึงเกณฑ์การบรรลุผล กล่องยืนยันของหน้าจอ
คือด่านเดียว และประโยคในกล่องต้องบอกว่ากำลังจะลบข้อไหน

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

**ต้อง reset + seed ใหม่จริง ๆ ก่อนเดินใบนี้** — `db/term.js` ทำให้ seed เดินตามนาฬิกา

**ต้อง kill แล้ว start backend ใหม่ก่อนเดิน** — `node server.js` ไม่มี reload ตรวจด้วยการ login
แล้วยิง `GET /api/teaching/sections/1/clos/<clo_id>/criteria` หนึ่งครั้ง ต้องได้ 200 พร้อมรายการ

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือ `deep-core-local`

ทางเข้า: เลือกตอนเรียนจากหน้า *รายวิชา* → เมนู **ผลการเรียนรู้รายวิชา** → กดลิงก์
**เกณฑ์การบรรลุผล** บนการ์ดของ CLO ที่ต้องการ (อยู่ข้างลิงก์ *พฤติกรรมบ่งชี้* ของ #28)
ที่อยู่ที่ได้คือ `/teacher/teacherDashboard/<section_id>/courseOutcomes/<clo_id>/criteria`

seed ให้ **CLO ทุกตัวของทั้งสองปีมีเกณฑ์ครบสี่ข้อ ข้อละหนึ่งระดับ เรียงจากดีสุด**:
ข้อ 1 ดีเยี่ยม · ข้อ 2 ดี · ข้อ 3 พอใช้ · ข้อ 4 ต้องปรับปรุง — ทุกข้อมีทั้งเกณฑ์การประเมิน
และคำอธิบาย (`เกณฑ์ระดับ…ของ CLO-…`)

| `section_id` (ที่อยู่) | ปีการศึกษา | ผู้สอน | ใช้เดินอะไร |
|---|---|---|---|
| `1` | 2569 (ปัจจุบัน) | `teacher.one@` | เกือบทุกข้อ |
| `2` | 2569 (ปัจจุบัน) | `multi.role@` (สลับเป็น *อาจารย์ผู้สอน* ก่อน) | ข้อชุดเดียวกันข้ามตอนเรียน |
| `3` | **2568 (ปีก่อน)** | `teacher.one@` | ข้อปีอื่นมีชุดของตัวเอง |

## คำตอบของการบันทึก ปิดฟอร์มที่ส่งมันไป ไม่ใช่ฟอร์มที่มันเจอ — #146 (20 ก.ย. 2569)

`save` ของ `frontend/src/pages/AchievementCriteria.js` เคยจบด้วย `setEditing(null)` กับประโยคสำเร็จ
โดยไม่ถามอะไรเลย
การเขียนไม่มีอะไรมารื้อทิ้ง คำตอบของมันจึงมาถึงหน้าจอที่ขยับไปแล้วได้ —
รายการใต้ฟอร์มถูกวาดอยู่เสมอและไม่ปิดปุ่มไหนเลย ดินสอของการ์ดอื่นจึงมาแทนฟอร์ม ได้ทันทีโดยไม่ต้องมี
*ยกเลิก* ด้วยซ้ำ
ฟอร์มที่สองจึงถูกปิดไปพร้อมสิ่งที่พิมพ์ค้างไว้
และประโยคของการบันทึกครั้งก่อนมาขึ้นในที่ที่อ่านได้ว่า
เป็นเรื่องของรายการที่คนกำลังมองอยู่ ตอนนี้ `showing` จำ **สิ่งล่าสุดที่เปิดขึ้นบนจอนี้**
ทุกตัวควบคุมที่เปิดอะไรขึ้นมาเขียนมัน และคำตอบที่เจอการเปิดอื่นไม่ปิดอะไรและไม่พูดอะไร ทั้งประโยคสำเร็จ
และคำปฏิเสธ — คำถามเดียวกับที่ #139 ให้การอ่านถาม ที่ปลายของการเขียน (#133) เหตุผลทั้งหมดอยู่บน
`frontend/src/pages/Departments.js`

สิ่งที่ไม่ได้เปลี่ยนคือสิ่งที่หน้าจอปิดการใช้งาน ทั้งรายการและดินสอทุกตัวยังกดได้ระหว่างการบันทึก
เพราะนั่นเป็นการเปลี่ยน UI ซึ่งเป็นคำถาม
ไม่ใช่การแก้ (`docs/06` §Out of Scope) และการโหลดรายการใหม่ทำเสมอ ไม่ว่าการเทียบจะออกทางไหน (#131)

**ฟอร์มอยู่ต่อ แต่สิ่งที่พิมพ์ในนั้นไม่อยู่**
([#149](https://github.com/khthana/Deep-QA/issues/149)) จอนี้วาดทั้งรายการและฟอร์มไว้ใน
`{!loading && data && (` อันเดียวกัน และการโหลดทุกครั้งขึ้นต้นด้วย `setLoading(true)`
การโหลดที่ตามหลังการบันทึกจึง **ถอดฟอร์มทิ้ง** ตลอดช่วงที่คำขอยังไม่กลับ แล้วสร้างใหม่โดยอ่านค่า
จากระเบียน #146 กันไม่ให้คำตอบที่มาช้า *ปิด* ฟอร์มที่คนย้ายไปแล้ว แต่ไม่ได้กันสิ่งที่พิมพ์ค้างไว้
ในฟอร์มนั้น แถวข้างล่างไม่ได้อ้างถึงเนื้อในฟอร์ม (มันอ่านว่าฟอร์มไหนเปิดอยู่ กับการมีหรือไม่มีประโยค)
จึงไม่มีการอ้างเกิน แต่ก็ยังไม่มีแถวไหนถือเรื่องนี้ไว้ หกจอที่เป็นรายการไม่มีรูปนี้ — `!loading`
ของมันครอบแค่แถวในตาราง ฟอร์มอยู่นอกนั้นและรอดการโหลด ซึ่งเป็นเหตุผลที่แถวของจอเหล่านั้น
อ่านค่าที่พิมพ์ไว้ในช่องได้หลังการโหลด (`inputValue()`) และแถวของจอนี้อ่านไม่ได้

**ย่อหน้านี้คือสภาพของวันที่ 20 ก.ย. 2569** — แก้แล้วเมื่อ 21 ก.ย. 2569 ตามคำตอบของเจ้าของ
จอนี้เก็บสิ่งที่วาดไว้ระหว่างการโหลด ฟอร์มจึงรอด และแถวของ `149a` อ่าน `inputValue()` ได้แล้ว
ดูหัวข้อ #149 ท้ายใบนี้

ทุกแถวข้างล่าง **เดินด้วยมือไม่ได้** มันต้องการคำขอที่ถูกกักไว้จนกว่าแถวจะปล่อย ซึ่ง
`e2e/support/gate.js` ทำให้

`teacher.one@kmitl.ac.th`
ครอบคลุมโดย describe *เกณฑ์การบรรลุผล (AchievementCriteria.js)* ใน

ที่ตามมา — การปิดฟอร์มที่ข้อบกพร่องจะวาด commit ไปก่อนคำขอนั้นถูกส่ง — แล้วอ่านครั้งเดียวหลังจากนั้น
250 ms ส่วนแถวคำปฏิเสธไม่มีจุดแบบนั้น (คำปฏิเสธไม่โหลดอะไรใหม่
และประโยคที่ถูกต้องคือประโยคที่ไม่ถูกวาด)
จึงนับจากตอนที่คำตอบถึงหน้า ตัวเลขนั้นตัดสินผลได้ (#52) สิ่งที่ค้ำมันคือการกวาดข้างล่าง

**คำถามที่ตั๋วฝากไว้ ถูกตอบแล้ว (20 ก.ย. 2569)** ร่างแรกให้ *ยกเลิก* เขียน `null` ลง `showing`
การบันทึกที่ถูก *ยกเลิก* แซงโดยไม่มีฟอร์มที่สองมาแทน จึงเงียบทั้งประโยคสำเร็จและคำปฏิเสธ —
คนที่กด *บันทึก* ไม่ได้ยินอะไรเลยเกี่ยวกับการเขียนที่ตัวเองสั่ง ตั๋วฝากเรื่องนี้ไว้เองว่าเป็น
*คำถามเรื่องสิ่งที่คนเห็น แบบเดียวกับ #143* ซึ่ง `docs/06` §Out of Scope บอกว่าเป็นคำถาม

`showing` จึงไม่ได้แปลว่า *ฟอร์มไหนเปิดอยู่* อีกต่อไป แต่แปลว่า **สิ่งล่าสุดที่เปิดขึ้นบนจอนี้**
— *ยกเลิก* ไม่เขียนมัน และการบันทึกที่ปิดฟอร์มของตัวเองก็ไม่เขียน `null` จึงเหลือความหมายเดียว
คือ *ยังไม่มีอะไรเปิดขึ้นเลย* บรรทัดที่เทียบ (`showing.current === sent`) ไม่ถูกแตะเลย

— `{data && (` แทน `{!loading && data && (` และบรรทัด *กำลังโหลดข้อมูล…* ขึ้นเฉพาะตอนที่ยังไม่มีอะไร
ให้วาด (`{loading && !data && …}`) ฟอร์มจึงรอดการโหลด และสิ่งที่พิมพ์ค้างไว้อยู่ต่อ

การแก้นั้นเปิดประตูที่ #146 นับไว้ว่าปิด: ระหว่างการโหลดมีดินสอให้กดแล้ว และทั้ง `save` กับ `remove`
ตั้งประโยคของตัวเอง*หลัง*การโหลด ประโยคของการบันทึกจึงถาม `showing.current === sent` ตอนที่มันตัดสิน
แทนที่จะถือคำตอบเก่าไว้ใน `mine` และ `remove` จับ `sent` ไว้ตอนถูกกด แล้วถามคำถามเดียวกันก่อน
ประโยค *ลบเกณฑ์การบรรลุผลแล้ว*

ทุกแถวข้างล่าง **เดินด้วยมือไม่ได้** มันต้องการคำขอที่ถูกกักไว้ที่ route จนกว่าแถวจะปล่อย
(`e2e/support/gate.js`) การเขียนที่ถูกกักถูกตอบด้วย 200 ที่แต่งขึ้น จึงไม่มีแถวไหนเขียนฐานข้อมูล
เข้าด้วย `teacher.one@kmitl.ac.th` ครอบคลุมโดย describe *เกณฑ์การบรรลุผล (AchievementCriteria.js)* ใน
`149a-reload-keeps-the-open-form.spec.js` จุดอ่านคือหลังคำตอบที่ถูกกักถึงหน้า แล้ว 250 ms อ่านครั้งเดียว

### มัตแตนต์

สี่ตัวของจอนี้อยู่ใน `mutation/149-reload-keeps-the-open-form.py` กวาดเมื่อ 21 ก.ย. 2569 ด้วย `149a`
ทั้งไฟล์ ทีละตัว — baseline **22 ผ่านทั้ง 22** (1.2 นาที)

- `149:criteriagateback` **ล้ม 3 ผ่าน 19** (1.5 นาที) — ที่ assertion ของค่าในกล่องของแถวสิ่งที่พิมพ์ (ได้ค่าของระเบียนแทน) และที่ timeout ของการกดในอีกสองแถว
- `149:criterialoadingline` **ล้ม 1 ผ่าน 21** (1.3 นาที) — ที่ assertion *the loading line over a list already drawn* ของแถวประโยคการบันทึก แถวเดียว
- `149:criteriasavebannerunasked` **ล้ม 1 ผ่าน 21** (1.3 นาที) — ที่ assertion *the banner of the save before* แถวเดียว
- `149:criteriaremovalsentatthelanding` **ล้ม 1 ผ่าน 21** (1.3 นาที) — ที่ assertion *the banner of the removal* แถวเดียว

`criteriagateback` ฆ่าแถวของประโยคสองแถวด้วย **แต่ที่การรอ ไม่ใช่ที่ assertion** — ดินสอที่แถวกดไม่ถูกวาด
ระหว่างการโหลด และการกดมี timeout ห้าวินาที *การอ่านสิ่งที่มัตแตนต์ทำให้ไม่มีอยู่คือการรอ* (#139)
สองแถวนั้นจึงไม่ถูกอ้างด้วยตัวนี้ ตัวที่ค้ำมันคือตัวของมันเอง

### สิ่งที่การตรวจเจอ และการกวาดที่มันขอ (21 ก.ย. 2569)

การตรวจโค้ดอ่านสามข้อที่การกวาดครั้งแรกไม่เห็น

- **ไม่มีแถวไหนถามว่าประโยคของการลบยังขึ้น** ทุกแถวถามแค่ให้มันเงียบ ตัวที่ทำให้มันไม่พูดอีกเลยจะรอด ทุกไฟล์ แถว *a removal nothing took the place of says what it did* กับ `criteriaremovalbannerunsaid` (`false &&` หน้าเงื่อนไข) เพิ่มเข้ามา — *สองตัวที่แปรคุณสมบัติเดียวกันไม่เห็นอันที่สาม* (#96)
- **`removalsentatthelanding` คือการถอดเงื่อนไขทิ้งในผล** `sent` ที่จับข้างการเปรียบเทียบเท่ากับ ref ตัวเอง ใบมัตแตนต์เคยเขียนว่าไม่ใช่ แก้คำบรรยายแล้ว การฆ่ายังเป็นการฆ่า
- **คำตอบนี้แยกประโยคของการบันทึกออกจาก `mine`** ก่อนหน้านั้น `146:criteriaclosewins` ฆ่าทั้งการปิดและประโยคด้วยตัวเดียว ตอนนี้มันเห็นแค่การปิด ครึ่ง *ไม่มีประโยคสำเร็จ* ของแถว [#146](https://github.com/khthana/Deep-QA/issues/146) จึงได้ `criteriasavebannerunguarded` (`true ||` หน้าเงื่อนไข) — การกวาดซ้ำของ `146` เป็นที่ที่เห็นมัน *สมอที่ยังอยู่ไม่ได้แปลว่ายังพิสูจน์อะไรได้* (#107)

กวาดทีละตัว — baseline ของ `149a` **29 ผ่านทั้ง 29** (1.6 นาที) และของ `146a` **49 ผ่านทั้ง 49** (2.5–2.6 นาที) ทุกรันเวลาเท่า baseline ล้ม + ผ่าน = จำนวนแถวพอดี อ่านจากชื่อ describe *เกณฑ์การบรรลุผล (AchievementCriteria.js)*:

- `149:criteriaremovalbannerunsaid` กับ `149a` **ล้ม 1 ผ่าน 28** ที่ *the banner of the removal* ของแถวใหม่ แถวเดียว
- `149:criteriasavebannerunguarded` กับ `149a` **ล้ม 1 ผ่าน 28** ที่ *the banner of the save before* และกับ `146a` **ล้ม 1 ผ่าน 48** ที่ *the first save's banner* ของแถวที่ `closewins` ฆ่าที่ฟอร์ม
- `146:criteriaclosewins` **ล้ม 1 ผ่าน 48** ที่ assertion ของฟอร์ม
- `146:criteriacancelclears` **ล้ม 1 ผ่าน 48** — เหมือน 20 ก.ย.

หกตัวของจอนี้ใน `149` ตอนนี้ และ baseline ของ `149a` คือ 29 ไม่ใช่ 22 ที่ตัวเลขข้างบนอ่าน
