# ใบตรวจรับ #47 — รูปโปรไฟล์

[#47](https://github.com/khthana/Deep-QA/issues/47) · **ไม่มีหน้าจอเป็นของตัวเอง** — กล่องที่เปิดจาก
เมนูผู้ใช้บนแถบด้านบน (`frontend/src/components/ProfilePhotoDialog.js`) กับรูปในปุ่มอวาตาร์เอง

## สิ่งที่ต้องเข้าใจก่อนเดิน

**ตั๋วนี้เป็นข้อบกพร่องด้านความปลอดภัยสองข้อ พอ ๆ กับเป็นฟีเจอร์** #46 สร้างตาราง `user_image` แล้ว
**จงใจไม่แตะทางเดินของมัน** และเขียนไว้ว่าใครก็ตามที่รับทางเดินนี้ต้องรับข้อบกพร่องสามข้อที่ติดมาด้วย
ใบนี้คือตั๋วนั้น รูปร่างของโค้ดชุดนี้จึงเหมือน #35 หนึ่งตารางถัดไป เพราะเป็นข้อบกพร่องชุดเดียวกัน

**ข้อแรก — ไม่มีการตรวจชนิดไฟล์เลยแม้แต่นามสกุล** `uploads.single('image')` ที่ส่งมอบมาเขียนสิ่งที่มา
ลงดิสก์ตามที่มา การตรวจจึงอยู่ที่ **ไบต์** (`backend/lib/userPhoto.js` อ่านลายเซ็นของ PNG กับ JPEG)
และแถวที่มีความหมายคือแถวที่อัปโหลด**ไบต์ของ PDF ที่ชื่อ `photo.png` และประกาศตัวว่า `image/png`**
เพราะชื่อกับ Content-Type ผู้อัปโหลดเขียนเองได้ ส่วนไบต์แปดตัวแรกเขียนไม่ได้

**ข้อสอง — ไดเรกทอรีตอบทุกคน** `app.use('/static', express.static('/data/evidence'))` ไม่มีด่าน
และที่อยู่ของรูปคือ `/static/user_image/<user_id>_<timestamp>.png` ซึ่งประกอบจากสองสิ่งที่คนเดาได้
ที่นี่ **ไม่มี static mount** — `GET /api/me/photo` ไม่มีตัวระบุตัวตนอยู่ใน path เลย มันตอบรูปของ
บัญชีที่อยู่ในคุกกี้เท่านั้น เกณฑ์ข้อ 6 กับ 7 จึงเป็นเรื่องเชิงโครงสร้าง ไม่ใช่กิ่งเงื่อนไขที่เขียนผิดได้

**ข้อสาม — ลบบัญชีแล้วไฟล์ยังอยู่ ยังไม่มีผู้เรียก** `0004` ให้ `ON DELETE CASCADE` กับแถว แต่ไฟล์
ไม่ได้ถูก unlink — และ**ระบบที่สร้างใหม่ไม่มี route ลบบัญชีเลย** (`backend/routes/users.js` มีแค่
อ่าน/สร้าง/แก้/เปลี่ยนสถานะ/นำเข้า ซึ่ง `docs/acceptance/11-user-accounts.md` เขียนไว้ตรง ๆ) เกณฑ์ข้อ 5
จึงไม่มีที่ให้เรียก `removePhoto` ฟังก์ชันนั้นมีอยู่และถูกใช้จริงโดยการเปลี่ยนรูป ส่วนวันที่มี route ลบบัญชี
มันคือสิ่งที่ route นั้นต้องเรียก — เขียนไว้ในหัวไฟล์ของ `userPhoto.js` แล้ว **นี่เป็นคำถาม ไม่ใช่งาน**

**ไม่มีหน้าจอเดิมให้ลอก** วัดแล้ว: navbar ที่ส่งมอบมาวาด `profile_picture` ของ Google ซึ่งเป็นที่อยู่
ของบริษัทอื่นและว่างเปล่าสำหรับทุกคนที่เข้าระบบด้วยรหัสผ่าน และไม่มีที่ไหนใน `DEEP-QA-FRONTEND`
เรียก `upload-profile-image` เลย — ฟีเจอร์นี้เป็นโค้ดที่ไม่มีผู้เรียกในระบบที่ส่งมอบมา `docs/06` §Out of
Scope บอกว่า UI ทำซ้ำตามของเดิม แต่ **ของเดิมไม่มี** รูปร่างของกล่องจึงเลือกให้น้อยที่สุดโดยอิงกล่อง
เปลี่ยนรหัสผ่านที่อยู่ในเมนูเดียวกัน

**ขนาดจำกัด 5 MB เป็นการตัดสินใจ ไม่ใช่มรดก** ของเดิมได้ 50 MB มาจาก middleware ที่ใช้ร่วมกับหลักฐาน
การประเมิน ซึ่งเป็น PDF ของงานนักศึกษา รูปโปรไฟล์ไม่ใช่สิ่งเดียวกัน (#45: ตัวเลขที่ลอกมาจากหน้าจอ
ข้างเคียงคือการตัดสินใจ ไม่ใช่การสืบทอด) ตัวเลขเดินทางมากับ `/api/me` เพื่อให้ประโยคใต้ช่องเลือกไฟล์
กับสิ่งที่ multer บังคับขัดกันไม่ได้

## ข้อมูลที่ใช้เดิน

`user_image` ใน seed **ว่างเปล่า** การเดินทุกแถวจึงต้องอัปโหลดรูปของตัวเองก่อน แล้วเก็บกวาดเอง
ชุดทดสอบทั้งสองฝั่งชี้ `EVIDENCE_DIR` ไปที่ไดเรกทอรีของตัวเองใต้ temp ของระบบ การรันจึงไม่แตะ
`_local/evidence` — ส่วนการเดินด้วยมือแตะของจริง **ให้นับแถว `user_image` ก่อนและหลังเดิน**

### มัตแตนต์ของตั๋วอื่นที่ตั๋วนี้อาจทำให้หมดอายุ

`FILES` ของตั๋วนี้ถือ `frontend/src/components/Navbar.js` ร่วมกับแฟ้มกลายพันธุ์ 10, 66
และ 111 จึง**ห้ามกวาดพร้อมกัน** และตั๋วนี้เกิดขึ้นโดยแก้ไฟล์ที่มัตแตนต์ของคนอื่นอาศัยอยู่
— จำนวนที่มันฆ่าได้เป็นข้ออ้างที่มีวันหมดอายุ จึงกวาดซ้ำสามตัวที่ผูกจุดยึดอยู่ในไฟล์นี้ ทีละตัว
กวาดเมื่อ 27 กันยายน 2569 ทั้งสามตัวฆ่าเท่าเดิม แถวเดิม และแถวเดียว:

| มัตแตนต์ | ชุดที่รัน | ผล |
|---|---|---|
| `10/ejectonrefusal` | `10a-shell.spec.js` | 1 ล้ม / 10 ผ่าน — แถวของเกณฑ์ข้อ 7 เดิม (เลขบรรทัดขยับไป 358 ตามแถวที่แทรกอยู่เหนือ) |
| `111/dialogstayssilent` | `111a` | 1 ล้ม / 4 ผ่าน — แถวกล่องเปลี่ยนรหัสผ่านเดิม |
| `66/portfoliodoorreturns` | `66a` | 1 ล้ม / 7 ผ่าน — แถวเมนูผู้ใช้เดิม รายการ *เปลี่ยนรูปโปรไฟล์* ที่เพิ่มเข้ามาไม่ทำให้แถวนี้หลง |

อีก 18 ตัวที่ผูกอยู่ในไฟล์ที่ตั๋วนี้แก้ (`routes/me.js`, `auth/accounts.js`, `auth/refusals.js`, `lib/evidence.js`,
`context/AuthContext.js`) **ไม่ได้กวาดซ้ำ และนี่คือสิ่งที่เครื่องมือวัดไม่ได้** — เหตุผลที่ไม่กวาดคือ สิ่งที่ตั๋วนี้
เติมลงในห้าไฟล์นั้นเป็นการ**เติม**ทั้งหมด — คอลัมน์ใน `SELECT`, คู่ใน `REFUSALS`, การ export อีกหนึ่งตัว,
ฟีลด์อีกหนึ่งฟีลด์ใน context — ไม่มีกิ่งไหนเปลี่ยน และจุดยึดของมัตแตนต์เหล่านั้นทุกตัวยังอยู่ครบ
(`python mutation/anchors.py` — 819 ตัว 838 จุดยึด 0 ปัญหา) และชุดทดสอบทั้งสองสแกนเขียวหลังการแก้ สิ่งที่
เหลืออยู่จึงเป็นข้ออ้างเชิงเหตุผล ไม่ใช่การวัด ใครอ่านแล้วไม่เชื่อ กวาดซ้ำได้ด้วยตารางข้างต้นนี้

## สิ่งที่ชุดทดสอบจับได้ระหว่างเขียน

**แถวที่หา *ไฟล์ของตัวเอง* ด้วยไบต์ที่แถวอื่นก็อัปโหลด** สองแถวในชุดหลังบ้านรู้จักไฟล์ของตัวเองบนดิสก์
ด้วยการอ่านไบต์เทียบ เพราะชื่อบนดิสก์เป็นชื่อสุ่ม แต่ไบต์ที่ใช้เทียบเป็นค่าที่แถวอื่นก็ส่ง แถวหนึ่งจึงลบ
ไฟล์ของบัญชีอื่นแล้วสรุปผิด (#129: แถวที่จับได้บางรอบไม่ใช่แถวที่ถือข้ออ้างนั้นไว้) แก้ด้วยการให้แต่ละแถว
ใช้ไบต์ที่ไม่มีใครใช้ และเขียนเหตุผลไว้บนแถว

**`getByRole('img')` ตอบทั้งรูปจริงและไอคอนรูปแทน** Playwright ให้ `<svg>` ถือ role `img` ด้วย
แถวที่ถามด้วย role จึงได้คำตอบว่า *มีรูป* ในทั้งสองสถานะ — ซึ่งคือคำถามที่แถวนั้นพยายามถามพอดี
`avatarImage` ใน `e2e/support/shell.js` จึงถามด้วย element ไม่ใช่ด้วย role

**การนับศูนย์ผ่านได้บนหน้าที่ยังไม่ได้วาด** (#164) เงื่อนไขก่อนเดินของแถว 1 คือ *ยังไม่มีรูป* ซึ่ง
`toHaveCount(0)` ตอบว่าจริงทันทีบน navbar ที่ยังไม่มีอยู่ ตอนนี้แถวยืนยันว่าเห็นปุ่มอวาตาร์ก่อน
แล้วจึงนับสิ่งที่อยู่ในปุ่ม

## คำถามที่ยังไม่ได้ตอบ

**เกณฑ์ข้อ 5 ไม่มีผู้เรียก** ตามที่เขียนไว้ข้างบน ระบบที่สร้างใหม่ไม่ลบบัญชี วันที่มีตั๋วสำหรับ route
ลบบัญชี ตั๋วนั้นต้องเรียก `removePhoto` และต้องมีแถวที่ยืนยันว่าไฟล์หายจากดิสก์ — ถ้ายืนยันว่าระบบ
จะไม่ลบบัญชีเลย เกณฑ์ข้อ 5 กับครึ่งหนึ่งของข้อ 8 ควรถูกขีดออกจากตั๋วอย่างเป็นทางการ

**ประโยคแจ้งความสำเร็จหายไปพร้อมกับ `reload()`** `AppRoutes` ตอบ shell ที่กำลังโหลดด้วย
`LoadingScreen` ต้นไม้ทั้งต้นจึงถูกถอดและสร้างใหม่ — รวมถึง `Mainpage` ที่ถือ state ของ snackbar
ประโยค *บันทึกแล้ว* ที่ยกขึ้นคร่อมการเรียกนั้นจึงถูกลบทิ้งเสมอ (วัดแล้วตอนเขียน `47a`) ที่นี่ใช้รูปที่
โผล่ขึ้นมาเป็นคำยืนยันแทน แต่ **การเปลี่ยนรหัสผ่านไม่ได้เรียก `reload()`** ประโยคของมันจึงรอด —
ถ้าวันหนึ่งมันต้องเรียก ประโยคนั้นจะหายไปเงียบ ๆ เหมือนกัน
