## สิ่งที่ต้องเข้าใจก่อนเดิน

**บันทึกเป็นของรายวิชาที่เปิดสอน ไม่ใช่ของตอนเรียน** ADR-0003 และตารางที่รับมาก็อยู่ที่ grain นี้
มาก่อนการรื้อสร้างแล้ว (`clo_course_cycle_cloplan` มี key เป็น subject + program + ปีการศึกษา)
ผู้สอนสองคนของสองตอนเรียนจึงเขียนบันทึกชุดเดียวกัน คนหนึ่งบันทึกอีกคนเห็น และแก้ของกันได้
เป็นสิ่งที่ต่างจาก **แผนการสอน** ของ #31 ซึ่งเป็นของตอนเรียน — หัวจอจึงเขียนบอกไว้

**บันทึกของปีก่อนจับคู่ด้วย *เลขข้อ* ไม่ใช่ `clo_id`** เรื่องนี้ผิดได้ง่ายและมองไม่เห็นเมื่อผิด
ADR-0003 ให้ CLO ของแต่ละปีเป็นแถวของตัวเอง CLO-4 ของปีที่แล้วกับของปีนี้จึงเป็นคนละ `clo_id`
ถ้า join ด้วย id แผงอ้างอิงจะว่างเปล่าทุกรายวิชาตลอดไป — และแผงว่างหน้าตาเหมือนปีที่ไม่มีใครเขียนอะไร

**ปีที่ถูกหยิบมาอ้างอิงคือปีล่าสุดที่มีใครเขียนไว้ ไม่ใช่ปีนี้ลบหนึ่ง** รายวิชาไม่ได้เปิดสอนทุกปี
และรอบปีที่ถูกเปิดแล้วปล่อยว่างก็มีได้ ทั้งสองกรณีจะทำให้แผงว่างถ้ากติกาคือ "ปีก่อนหน้า"

**`reference_academic_year` เซิร์ฟเวอร์เขียนเอง และเขียนเฉพาะ `IMPROVEMENT`** docs/02 นิยาม
หัวข้อนี้ว่า *การปรับปรุงจากรอบก่อนหน้า* จึงเป็นหัวข้อเดียวในสี่ที่ชี้ไปปีอื่น ปีที่ชี้คือปีที่แผงอ้างอิง
กำลังแสดงอยู่ การอ่านค่านี้จาก body คือ ADR-0002 ในหน่วยที่เล็กที่สุดที่มันปรากฏในระบบ
**เกณฑ์ทั้งหกข้อไม่ได้เอ่ยถึงคอลัมน์นี้ตรง ๆ** — ที่เก็บไว้เพราะ *what was changed following last
year's reflection* ในหัวตั๋วต้องการบอกได้ว่า *ตามการสะท้อนคิดของปีไหน* และคอลัมน์มีอยู่แล้วในตาราง
ถ้าจะตัดออก ให้ตัดทั้งคอลัมน์ ไม่ใช่ปล่อยให้ว่างไว้เฉย ๆ

**แผงอ้างอิงมีสถานะว่างสองแบบ และจงใจทำไม่เหมือนกัน** ไม่มีปีก่อนที่เขียนไว้เลย → **ไม่วาดแผง**
มีปีก่อนแต่ข้อที่เลือกไม่ได้ถูกเขียนถึง → **วาด และบอกว่าไม่มี** ข้อบกพร่องของ #40 คือ *ตัวควบคุม*
ที่กดแล้วเปิดออกมาว่าง ส่วนอันนี้เป็น *ประโยคบอกข่าว* และเป็นครึ่งที่มีประโยชน์ของคำตอบ —
*ปีที่แล้วไม่มีใครเขียนถึงข้อนี้* กับ *ไม่มีปีที่แล้ว* เป็นคนละข่าว แผงที่หายไปจะรายงานทั้งสองเหมือนกัน
และจะกะพริบเข้าออกทุกครั้งที่เลื่อน dropdown

**รอบปีถูกสร้างตอนบันทึกครั้งแรก ไม่ใช่ตอนเปิดหน้าจอ** เกณฑ์ข้อ 3 ขอแบบนั้นตรง ๆ และเหตุผลที่ต้อง
อยู่ฝั่งเขียนคือ ผู้สอนที่เปิดดูแล้วปิดไปยังไม่ได้เริ่มรอบ แถวที่บอกว่าเริ่มแล้วคือปีที่อยู่ในระเบียน
โดยไม่มีอะไรอยู่ในนั้น ซึ่งคณะกรรมการประเมินอ่านว่าเป็นรอบที่ถูกทิ้งกลางคัน

**ตารางนี้ไม่มีคอลัมน์บอกว่าใครเขียน** `clo_course_cycle_detail_cloplan` มีแต่ `created_at`
ไม่มี `created_by` และไม่มี `updated_at` ต่างจาก `subject_clo` ของ #27 ที่มี `updated_by`
เกณฑ์ของ #41 ไม่ได้ขอ จึงไม่ได้เพิ่ม migration ให้ — และหน้าจอก็**ไม่แสดงเวลา**เลย เพราะ
`created_at` ของแถวที่ถูกแก้แล้วยังเป็นเวลาที่เขียนครั้งแรก การพิมพ์มันข้างข้อความที่เพิ่งแก้
คือการบอกเวลาที่ผิด ถ้าอยากได้ว่าใครแก้ล่าสุด ต้องเปิดตั๋วใหม่พร้อม migration

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

**ต้อง reset + seed ใหม่ก่อนเดินใบนี้ และต้อง kill แล้ว start backend ใหม่** — `node server.js`
ไม่มี reload ทุกบัญชีใน seed ใช้รหัสผ่าน `deep-core-local`

ทางเข้า: เลือกตอนเรียนจากหน้า *รายวิชา* → เมนู **การปรับปรุงอย่างต่อเนื่อง** ที่อยู่คือ
`/teacher/teacherDashboard/<section_id>/ContinuousImprove`

**seed ไม่มีรอบปีเลย** — `db/seed.js` เขียนไว้ตรง ๆ ว่าเว้นไว้ให้ตั๋วที่สร้างหน้าจอนี้ ดังนั้นหน้าจอ
ที่เปิดครั้งแรกจะไม่มีบันทึกและไม่มีแผงอ้างอิง ซึ่งเป็นสถานะตั้งต้นที่ถูกต้อง

| `section_id` | ปีการศึกษา | ผู้สอน | ใช้เดินอะไร |
|---|---|---|---|
| `1` | 2569 (ปัจจุบัน) | `teacher.one@` | เกือบทุกข้อ |
| `2` | 2569 (ปัจจุบัน) | `multi.role@` | ข้อ 5 — สองตอนเรียนของรายวิชาที่เปิดสอนเดียวกัน |
| `3` | **2568 (ปีก่อน)** | `teacher.one@` | ข้อ 4 — เขียนของปีก่อนไว้แล้วกลับมาดูที่ปีนี้ |

## สี่อย่างที่การเดินหาเจอ และแก้ในตั๋วนี้

ทั้งสี่ข้อไม่มี assertion ไหนพูดได้ ล้วนเป็นการตัดสินว่า *สิ่งที่วาดออกมามันใช้งานได้จริงไหม*

**หนึ่ง — การ์ดกินความกว้างแค่สองในสาม ทั้งที่ไม่มีแผงอ้างอิง** `lg:grid-cols-3` ถูกประกาศไว้เสมอ
ไม่ว่าจะมีแผงหรือไม่ พอไม่มีแผง ที่ว่างหนึ่งส่วนทางขวาอ่านเหมือนแผงที่โหลดไม่ขึ้น ไม่ใช่แผงที่ไม่มี
แก้ด้วยการผูกทั้ง `lg:grid-cols-3` และ `lg:col-span-2` เข้ากับ `data.previous`
**นี่คือบทเรียนของ #40 ในรูปที่ไม่คาดคิด** — ตัวควบคุมไม่ได้ถูกวาดผิด แต่ *ที่ว่างที่มันเคยอยู่* ยังอยู่

**สอง — ช่องเลือก CLO แคบเกินไป** `sm:max-w-md` (448px) ตัด CLO-3 ที่ *…ในการเขียนโปรแกร*
และ native `<select>` ตัดโดยไม่มีจุดไข่ปลา ตัวเลือกที่ถูกตัดจึงอ่านเหมือนพิมพ์ตกมากกว่าล้นกรอบ
ขยายเป็น `sm:max-w-3xl`

**สาม — การ์ดทั้งสี่ไม่เอ่ยชื่อ CLO เลย** ช่องเลือกอยู่บนสุดและเลื่อนพ้นจอ พอเลื่อนลงมาเขียนหัวข้อ
ท้าย ๆ ก็ไม่มีอะไรบนจอบอกว่ากำลังเขียนถึงข้อไหน เติม `CLO-n` เป็นบรรทัดเล็กเหนือหัวข้อของทุกการ์ด
วางไว้นอก `aria-label` เพื่อไม่ให้ชื่อที่เข้าถึงได้ของ section เปลี่ยน

**สี่ — บรรทัดอ้างปีเล็กและจางเกินไป** *ต่อเนื่องจากการสะท้อนคิดของปีการศึกษา 2568* เป็น
`text-xs text-slate-400` อ่านเหมือนคำบรรยายภาพ ทั้งที่มันคือ**หลักฐานที่คณะกรรมการประเมินอ่าน** —
สิ่งที่ทำให้การเปลี่ยนแปลงเป็นการตอบรอบก่อน ไม่ใช่เรื่องบังเอิญ เปลี่ยนเป็น `text-sm text-slate-600`
บนแถบพื้น `bg-slate-50`

ทั้งสี่แก้แล้วและตรวจซ้ำบนจอในการเดินรอบเดียวกัน — **รับได้ทั้งสาม** และ **เด่นพอแล้ว**

## หนึ่งอย่างที่เจอ และไม่ได้แก้ที่นี่

กล่องยืนยันตัดคำว่า **ปีการศึกษา** เป็น *ในปีการ / ศึกษา* ซึ่งไม่ใช่ขอบคำ `ConfirmDialog`
เป็นกล่องเดียวที่ทุกการลบในระบบใช้ตั้งแต่ #14 ประโยคของมันเป็นภาษาไทยที่เอ่ยชื่อสิ่งที่กำลังจะหาย
ทุกใบ เรื่องนี้จึงเป็นของทั้งระบบ ไม่ใช่ของหน้าเดียว เปิดเป็น
[#118](https://github.com/khthana/Deep-QA/issues/118) ชนิดเดียวกับ #117 คนละตัวเรนเดอร์

### แก้แล้ว 24 ก.ย. 2569 — และไม่ใช่เพราะสิ่งที่ตั๋วสงสัย

ตั๋วสงสัยสองอย่าง `break-words` กับความกว้าง `max-w-sm` **วัดแล้วไม่ใช่ทั้งคู่** และวัดเพิ่ม
อีกสองอย่างที่ไม่มีใครเอ่ย — `lang="th"` กับ `word-break: keep-all` — ก็ไม่ขยับรอยตัดแม้แต่
ตัวอักษรเดียว ย่อหน้านั้น**ไม่เคยล้นกรอบ** `break-words` จึงไม่เคยทำงานเลยสักครั้ง

รอยตัดที่ `ปีการ|ศึกษา` เป็นโอกาสตัดบรรทัดที่ Chromium **เลือกเอง** `Intl.Segmenter('th')`
ตอบว่า `ใน|ปี|การ|ศึกษา` การตัดหลัง `การ` จึงถูกต้องในสายตาของ ICU ไม่มี CSS ตัวไหนลดโอกาส
ตัดพวกนั้นได้ ตัวข้อความจึงต้องเป็นคนบอกเอง — U+2060 WORD JOINER ระหว่างตัวอักษรไทยทุกคู่
ที่ติดกัน เหลือไว้เฉพาะช่องว่างที่คนเขียนประโยคใส่ไว้ `break-words` **คงไว้** และคราวนี้มีอะไร
ค้ำมันเป็นครั้งแรก

เกณฑ์ของตั๋วมีสี่ข้อ **สามข้อเป็นแถว หนึ่งข้อไม่ใช่**

| เกณฑ์ | ผล | พิสูจน์ที่ |
|---|---|---|
| ประโยคที่มี `ปีการศึกษา` ไม่ตัดกลางคำที่ความกว้างของกล่องเอง | ⚙ | `118a-thai-line-breaks.spec.js` แถว 1 — ประโยคของหน้านี้เอง |
| ตรวจกับประโยคยืนยันที่ยาวที่สุดในระบบ ไม่ใช่แค่ของ #41 | ⚙ | แถว 2 — *ยกเลิกการเปิดรายวิชา* ของ `Offerings.js` ซึ่งมี `ภาคการศึกษา` กับ `ผู้สอน` ที่ประโยคของหน้านี้ไม่มี |
| ชื่อที่ไม่มีที่ให้ตัดยังต้องไม่ล้นกล่อง ซึ่งคือสิ่งที่ `break-words` มีไว้ | ⚙ | แถว 3 (ชื่ออังกฤษ) และแถว 4 (ชื่อไทย 78 ตัวอักษร) |

**ข้อที่สอง — *หาสาเหตุให้เจอและเขียนไว้ ไม่ใช่เลี่ยงมัน* — ไม่มีมาร์ก และนี่คือคำตอบที่ถูกต้อง
ของมัน** มันเป็นข้อกล่าวถึง**บันทึก** ไม่ใช่ข้อกล่าวถึงหน้าจอ ไม่มีแถวไหนยืนยันมันได้ และร่างแรก
ของหัวข้อนี้ให้ ⚙ กับมันโดยอ้าง `nobreakwords` ว่า *ปล่อยแถว 1 กับ 2 ยืนอยู่* — ซึ่งเป็นมัตแตนต์
ที่**รอด**ตรงนั้น ไม่ใช่มัตแตนต์ที่ฆ่าอะไร ⚙ แปลว่ามัตแตนต์ฆ่า**ข้อความยืนยันของแถวนั้นเอง**
(`CLAUDE.md` §Marks on the sheets) นี่คือ ⚙ ที่ไม่เคยได้มา ซึ่งเป็นมาร์กที่ต้องระแวงที่สุด

สิ่งที่ค้ำข้อสองจริง ๆ คือ**การวัดครั้งเดียวก่อนแก้** — ถอด `break-words` ออกแล้วรอยตัดอยู่ที่เดิม,
ขยายกล่องแล้วอยู่ที่เดิม, `lang` กับ `word-break: keep-all` แล้วอยู่ที่เดิม, และ `scrollWidth`
เท่ากับ `clientWidth` ทุกครั้ง — บันทึกไว้บนหัว `ConfirmDialog.js` **การวัดไม่ใช่แถว** ชุดทดสอบ
ไม่ได้วัดซ้ำให้ทุกครั้งที่รัน และเอกสารนี้ไม่ควรทำเป็นว่ามันวัด

แถวอยู่ที่ `e2e/tests/118a-thai-line-breaks.spec.js` มัตแตนต์อยู่ที่
`mutation/118-thai-line-breaks.py` สามตัว กวาดเมื่อ 24 ก.ย. 2569 บนห้าแถว — `notglued`
ฆ่าแถว 1 กับ 2, `nobreakwords` ฆ่าแถว 3 กับ 4, `nowrapinstead` ฆ่าแถว 4 แถวเดียว
ทุกแถวที่เป็นเกณฑ์มีตัวที่ฆ่ามัน และไม่มีสองตัวที่ฆ่าชุดเดียวกัน ตัวเลขเต็มอยู่บนหัวไฟล์มัตแตนต์

**แถวที่ห้าของไฟล์นั้นไม่ได้อยู่ในตารางข้างบน** มันไม่ใช่เกณฑ์ข้อไหน แต่เป็นข้อตั้งที่ข้อ 2 พูดถึง —
`Intl.Segmenter('th')` ตอบ `ใน|ปี|การ|ศึกษา` ในเบราว์เซอร์ที่รันจริงหรือไม่ ไม่มีมัตแตนต์ฆ่ามันได้
และวันที่คำตอบนั้นเปลี่ยน กาวทั้งหมดก็เลิกจำเป็น ซึ่งเป็นสิ่งเดียวในบันทึกของข้อ 2 ที่ชุดทดสอบ
ถามซ้ำให้ได้ทุกครั้งที่รัน

**ใบนี้เป็นหนึ่งในที่ที่มัตแตนต์ฆ่า ไม่ใช่รายการทั้งหมด** (#123) `ConfirmDialog` ถูกใช้โดย

## คำตอบที่ถูกแทนที่ — #133 (16 ก.ย. 2569)

`load` ของหน้าจอนี้รับธง `isCurrent` แล้ว และวาดคำตอบก็ต่อเมื่อคำขอที่ทำให้มันเกิด ยังเป็นคำขอ
ที่หน้าจอต้องการอยู่ — กฎเดียวกับ #68 ตัวอักษรต่อตัวอักษร ซึ่งเขียนไว้บน `frontend/src/pages/Students.js`

**และหน้านี้ไม่ได้อยู่ในรายการของตั๋วด้วยซ้ำ** grep ที่ #133 เผยแพร่ไว้มองหารูป
`set…(await …)` ส่วนหน้านี้รับคำตอบลง `const` ก่อนแล้วค่อยวาด มันจึงไม่เคยถูกจับได้ —
*grep เป็นหลักฐานของแพตเทิร์นที่พิมพ์ ไม่ใช่ของข้ออ้างที่ต้องการ* (#111) และการตรวจของ #133
คืนคำตอบว่ายี่สิบสองจุด ไม่ใช่สิบหก

**แต่ตรงนี้ยังไม่ได้ทดสอบ ไม่ใช่ไม่ต้องมี** `sectionId` เป็นพารามิเตอร์ตัวเดียวของหน้านี้
และมาจาก `useParams` (ADR-0004) สิ่งเดียวที่แทนคำขอได้คือการเดินจากตอนเรียนหนึ่ง
ไปอีกตอนบนเส้นทางเดิม โดยคอมโพเนนต์ไม่ถูกถอด ซึ่งทุกลิงก์บนจอนี้เดิน*ขึ้น*ไปหารายการ
ที่ถอดหน้านี้ทิ้ง — วัดเมื่อ 16 ก.ย. 2569 และเป็นคำกล่าว**ที่มีวันหมดอายุ** ตั๋วที่
เพิ่มทางเดินระหว่างพี่น้องบนเส้นทางนี้ ทำให้มันเข้าถึงได้ทันที และต้องมีแถวของตัวเองในวันนั้น
รายการทั้งยี่สิบสองจุดพร้อมสถานะอยู่ที่ `docs/acceptance/57-pager.md` §ครึ่งหลังปิดแล้ว — #133
และตัวติดตามของสิบหกจุดที่ยังไม่มีแถวของตัวเองคือ #141

## รายการที่โหลดใหม่ถูกแทนที่ — #140 (17 ก.ย. 2569)

`frontend/src/pages/ContinuousImprovement.js` โหลดใหม่หลังการบันทึกและการลบ ก่อนตั๋วนี้ทุกจุดเรียก `load()` เฉย ๆ แล้วรับค่าตั้งต้นที่ตอบว่า

ทุกจอ — รูปเดียวกับอีกเก้าจอที่มีแถวของตัวเอง เหตุผลอยู่บน `frontend/src/pages/Students.js`

วันเดียวกัน**: ทางเดินระหว่างพี่น้องบนเส้นทางนี้ หรือตัวควบคุมบนจอที่ป้อนเข้า `load` ทำให้จุดเหล่านี้
ต้องมีแถวของตัวเองทันที ตัวติดตามคือ #141

## คำตอบของการบันทึก ปิดฟอร์มที่ส่งมันไป ไม่ใช่ฟอร์มที่มันเจอ — #146 (20 ก.ย. 2569)

`save` ของ `frontend/src/pages/ContinuousImprovement.js` เคยจบด้วย `setEditing(null)`
กับประโยคสำเร็จ โดยไม่ถามอะไรเลย
การเขียนไม่มีอะไรมารื้อทิ้ง คำตอบของมันจึงมาถึงหน้าจอที่ขยับไปแล้วได้ —
สี่หัวข้อคือสี่การเปิดของฟอร์มเดียว *เขียน…* ของหัวข้ออื่นมาแทนได้ทันที
และจอนี้ยังมีตัวควบคุมที่อีกสิบสองจอไม่มี คือตัวเลือกผลการเรียนรู้
ซึ่งปิดฟอร์มโดยไม่ได้เป็นตัวควบคุมของฟอร์มเลย
ฟอร์มที่สองจึงถูกปิดไปพร้อมสิ่งที่พิมพ์ค้างไว้
และประโยคของการบันทึกครั้งก่อนมาขึ้นในที่ที่อ่านได้ว่า
เป็นเรื่องของรายการที่คนกำลังมองอยู่ ตอนนี้ `showing` จำ **สิ่งล่าสุดที่เปิดขึ้นบนจอนี้**
ทุกตัวควบคุมที่เปิดอะไรขึ้นมาเขียนมัน และคำตอบที่เจอการเปิดอื่นไม่ปิดอะไรและไม่พูดอะไร ทั้งประโยคสำเร็จ
และคำปฏิเสธ — คำถามเดียวกับที่ #139 ให้การอ่านถาม ที่ปลายของการเขียน (#133) เหตุผลทั้งหมดอยู่บน
`frontend/src/pages/Departments.js`

สิ่งที่ไม่ได้เปลี่ยนคือสิ่งที่หน้าจอปิดการใช้งาน ทั้ง *เขียน…*
ของทุกหัวข้อและตัวเลือกผลการเรียนรู้ยังกดได้ระหว่างการบันทึก เพราะนั่นเป็นการเปลี่ยน UI
ซึ่งเป็นคำถาม
ไม่ใช่การแก้ (`docs/06` §Out of Scope) และการโหลดรายการใหม่ทำเสมอ ไม่ว่าการเทียบจะออกทางไหน (#131)

**ฟอร์มอยู่ต่อ แต่สิ่งที่พิมพ์ในนั้นไม่อยู่**
([#149](https://github.com/khthana/Deep-QA/issues/149)) จอนี้วาดทั้งรายการและฟอร์มไว้ใน
`{!loading && data && (` อันเดียวกัน และการโหลดทุกครั้งขึ้นต้นด้วย `setLoading(true)`
การโหลดที่ตามหลังการบันทึกจึง **ถอดฟอร์มทิ้ง** ตลอดช่วงที่คำขอยังไม่กลับ แล้วสร้างใหม่โดยอ่านค่า
จากระเบียน #146 กันไม่ให้คำตอบที่มาช้า *ปิด* ฟอร์มที่คนย้ายไปแล้ว แต่ไม่ได้กันสิ่งที่พิมพ์ค้างไว้
ในฟอร์มนั้น แถวข้างล่างไม่ได้อ้างถึงเนื้อในฟอร์ม (มันอ่านว่าฟอร์มไหนเปิดอยู่ กับการมีหรือไม่มีประโยค)
จึงไม่มีการอ้างเกิน แต่ก็ยังไม่มีแถวไหนถือเรื่องนี้ไว้ หกจอที่เป็นรายการไม่มีรูปนี้ — `!loading`
ของมันครอบแค่แถวในตาราง ฟอร์มอยู่นอกนั้นและรอดการโหลด ซึ่งเป็นเหตุผลที่แถวของจอเหล่านั้น
อ่านค่าที่พิมพ์ไว้ในช่องได้หลังการโหลด (`inputValue()`) และแถวของจอนี้อ่านไม่ได้

**ย่อหน้านี้คือสภาพของวันที่ 20 ก.ย. 2569** — แก้แล้วเมื่อ 21 ก.ย. 2569 ตามคำตอบของเจ้าของ
จอนี้เก็บสิ่งที่วาดไว้ระหว่างการโหลด ฟอร์มจึงรอด และแถวของ `149a` อ่าน `inputValue()` ได้แล้ว
ดูหัวข้อ #149 ท้ายใบนี้

#148 อธิบายอาการเดียวกันบนจอนี้ด้วยกลไกอื่น (effect ที่ผูกกับ object `entry`)

`showing` จึงไม่ได้แปลว่า *ฟอร์มไหนเปิดอยู่* อีกต่อไป แต่แปลว่า **สิ่งล่าสุดที่เปิดขึ้นบนจอนี้**

## การโหลดใหม่ไม่ถอดช่องเขียนที่คนกำลังพิมพ์ — #149 และ #148 (21 ก.ย. 2569)

การวัดเมื่อ 21 ก.ย. 2569 (คอมเมนต์บน [#148](https://github.com/khthana/Deep-QA/issues/148)) เจอว่า
อาการของจอนี้มีสองกลไก ซ้อนกันเป็นสองชั้น ไม่ใช่ทางเลือกของกันและกัน:

| | effect ผูกกับ object `entry` | effect ผูกกับ `entry?.entry_id` |
|---|---|---|
| **ประตู `!loading && data`** | ยังไม่เขียน: หาย · เขียนแล้ว: หาย — สร้างใหม่ทั้งคู่ | เหมือนช่องซ้าย ทุกอย่าง |
| **ยกประตูออก (`data &&`)** | ยังไม่เขียน: อยู่ · เขียนแล้ว: **หาย บน node เดิม** | **อยู่ทั้งคู่** |

ประตูบังกลไกที่สองไว้ — ช่องเขียนไม่ถูก mount อยู่เลยตอนการโหลดยังไม่กลับ effect จึงไม่มีโอกาส
ทำงาน พอยกประตูออก หัวข้อที่*เขียนแล้ว*ยังถูกตั้งค่าใหม่ เพราะ `entries` ถูกสร้างใหม่จาก `data`
ที่โหลดมา และส่ง object ใหม่ที่ `entry_id` เดิมให้ `EntrySection` หัวข้อที่ยังไม่เขียนรอดเพราะ
`entry` เป็น `undefined` ทั้งก่อนและหลัง

คำตอบของเจ้าของคือ **ทั้งสองชั้น** — จอเก็บสิ่งที่วาดไว้ระหว่างการโหลด บรรทัด *กำลังโหลดข้อมูล…*
ขึ้นเฉพาะตอนที่ยังไม่มีอะไรให้วาด (#149) และ `EntrySection` ตั้ง draft ตาม `entry_id` (#148)
จอนี้เป็นจอเดียวในเจ็ดที่ต้องมีชั้นที่สอง อีกหกจอส่งแถวที่ถืออยู่ใน `editing` ให้ฟอร์ม ซึ่งไม่มีการโหลด
ไหนแตะตัวตนของมัน **แถวที่แยกสองชั้นออกจากกันได้มีแถวเดียว คือหัวข้อที่เขียนแล้ว**

การยกประตูเปิดประตูที่ #146 นับไว้ว่าปิด: ระหว่างการโหลด *เขียน…* ของหัวข้ออื่นกดได้แล้ว และทั้ง `save`
กับ `remove` ตั้งประโยคของตัวเอง*หลัง*การโหลด ประโยคของการบันทึกจึงถาม `showing.current === sent`
ตอนที่มันตัดสิน แทนที่จะถือคำตอบเก่าไว้ใน `mine` และ `remove` จับ `sent` ไว้ตอนถูกกด

### สิ่งที่การตรวจเจอ และการกวาดที่มันขอ (21 ก.ย. 2569)

การตรวจโค้ดอ่านสามข้อที่การกวาดครั้งแรกไม่เห็น

- **ไม่มีแถวไหนถามว่าประโยคของการลบยังขึ้น** ทุกแถวถามแค่ให้มันเงียบ ตัวที่ทำให้มันไม่พูดอีกเลยจะรอด ทุกไฟล์ แถว *a removal nothing took the place of says what it did* กับ `improvementremovalbannerunsaid` (`false &&` หน้าเงื่อนไข) เพิ่มเข้ามา — *สองตัวที่แปรคุณสมบัติเดียวกันไม่เห็นอันที่สาม* (#96)
- **`removalsentatthelanding` คือการถอดเงื่อนไขทิ้งในผล** `sent` ที่จับข้างการเปรียบเทียบเท่ากับ ref ตัวเอง ใบมัตแตนต์เคยเขียนว่าไม่ใช่ แก้คำบรรยายแล้ว การฆ่ายังเป็นการฆ่า
- **คำตอบนี้แยกประโยคของการบันทึกออกจาก `mine`** ก่อนหน้านั้น `146:improvementclosewins` ฆ่าทั้งการปิดและประโยคด้วยตัวเดียว ตอนนี้มันเห็นแค่การปิด ครึ่ง *ไม่มีประโยคสำเร็จ* ของแถว [#146](https://github.com/khthana/Deep-QA/issues/146) จึงได้ `improvementsavebannerunguarded` (`true ||` หน้าเงื่อนไข) — การกวาดซ้ำของ `146` เป็นที่ที่เห็นมัน *สมอที่ยังอยู่ไม่ได้แปลว่ายังพิสูจน์อะไรได้* (#107)

## การโหลดใหม่ที่ล้มเหลวเก็บสิ่งที่วาดไว้ — #151 (22 ก.ย. 2569)

ตั้งแต่ #149 จอเก็บรายการและฟอร์มไว้ระหว่างการโหลดใหม่ แต่การโหลดที่**ล้มเหลว**ยังล้างทั้งคู่: `catch` ของ `load` ตั้ง `data` เป็น `null` ฟอร์มจึงถูกถอดพร้อมสิ่งที่พิมพ์ไว้ คำตอบ (22 ก.ย. 2569) คือคำตอบของ #149 ต่อไปอีกขั้น — **การโหลดที่ล้มเหลวเก็บสิ่งที่จอวาดไว้ล่าสุด** และคำปฏิเสธขึ้นเหนือมัน การโหลดครั้งแรกที่ล้มไม่มีอะไรให้เก็บ `loading && !data` วาดเหมือนเดิม ซึ่งตั๋วนี้ไม่เปลี่ยน

ทุกแถว **เดินด้วยมือไม่ได้** การเขียนถูกตอบด้วย 200 ที่แต่งขึ้น และการโหลดที่ตามมาด้วย 409 ที่แต่งขึ้น (`e2e/support/gate.js`) จึงไม่มีแถวไหนเขียนฐานข้อมูลผ่านการบันทึก เข้าด้วย `teacher.one@kmitl.ac.th` ครอบคลุมโดย describe *แผนพัฒนาต่อเนื่อง (ContinuousImprovement.js)* ใน `151a-failed-reload-keeps-the-list.spec.js` จุดอ่านคือหลังคำปฏิเสธถึงหน้า แล้ว 250 ms อ่านครั้งเดียว (#52) สิ่งที่ค้ำมันคือการกวาดข้างล่าง

### สิ่งที่วัดได้แต่ไม่ใช่ของตั๋วนี้

ตั๋วเขียนว่า *แบนเนอร์คำปฏิเสธบอกว่าการโหลดล้มเหลว* วัดแล้วจริงแค่เมื่อมีฟอร์มอื่นเปิดทีหลัง: ถ้าไม่มีอะไรเปิด `save` ตั้งประโยคสำเร็จ*หลัง*การโหลด ประโยคนั้นจึงทับคำปฏิเสธ (วัดด้วย probe ที่ลบทิ้งแล้ว: บนจอ ผลการเรียนรู้รายวิชา คำปฏิเสธ 0 ประโยคสำเร็จ 1 และบนแถวรายการของ `151a` ทั้งเจ็ดจอ คำปฏิเสธ 0 ทุกจอ) — ตอนนี้คือ *บันทึก…แล้ว* เหนือรายการ ที่ยังไม่มีสิ่งที่บันทึก ซึ่งเป็นคำถามของเจ้าของ ไม่ได้แก้ในตั๋วนี้ — เปิดเป็น [#152](https://github.com/khthana/Deep-QA/issues/152)

## รายการที่มาถึงใต้ช่องที่เปิดอยู่ — #150 (23 ก.ย. 2569)

#148 ผูกการ seed ของ `EntrySection` ไว้กับ `entry_id` แทน object การโหลดใหม่ที่สร้างรายการ**เดิม**ขึ้นมาใหม่จึงไม่ทับสิ่งที่พิมพ์อยู่อีก สิ่งที่การตัดสินนั้นไม่ได้มอง คือ id ที่เปลี่ยนจาก **ไม่มี เป็น มี** ขณะช่องเปิดอยู่ ซึ่งคือหน้าตาของ save ของตัวเองที่เดินทางกลับมา: กด *เขียน* ในหัวข้อที่ยังไม่มีอะไร พิมพ์ กด *บันทึก* → ฟอร์มปิด แต่การโหลดใหม่ยังไม่กลับ หัวข้อนั้นจึงยังไม่มีรายการและยังเสนอ *เขียน* อยู่ → กดอีกครั้ง ช่องเปิดบน `undefined` → พิมพ์ → การโหลดใหม่ลง `entry_id` เปลี่ยนจาก `undefined` เป็น id → effect seed ช่องจาก `detail_text` **สิ่งที่พิมพ์หายไป กลายเป็นสิ่งที่บันทึกไว้เมื่อครู่**

คำตอบ (23 ก.ย. 2569) แยกสองการเปลี่ยนออกจากกันด้วย ref ที่จำ id ที่ draft ถูก seed มา: *มาถึง* (`undefined` → id) ไม่ seed · *ถูกแทนที่* (id → id อื่น) ยัง seed เหมือนเดิม ค่า `CLOSED` เป็น `Symbol` เพราะ `undefined` เป็นสถานะจริงที่ ref ต้องถืออยู่แล้ว — หัวข้อที่ยังไม่เคยเขียนไม่มี id — `null` จึงชนกัน **ครึ่งที่สองไม่ถูกแตะเลย** ดูหัวข้อ *คำถามที่ยังเปิดอยู่* ท้ายส่วนนี้

แถวแรก **เดินด้วยมือไม่ได้** ต้องกักการโหลดไว้ที่ route (`e2e/support/gate.js`) ถึงจะสร้างจังหวะนั้นได้ และต่างจากแถวอื่นของจอนี้ตรงที่ **การเขียนไม่ถูกกัก** — กลไกทั้งหมดคือการโหลดที่พารายการซึ่ง*มีอยู่จริง*กลับมา การบันทึกที่ถูกหยุดไว้ที่ route ไม่สร้างรายการอะไรเลย ไฟล์นี้จึงเขียนฐานข้อมูลผ่านหน้าจอจริงและใช้ `hold()` คืนให้ ส่วนแถวที่สอง **เดินด้วยมือได้** (พิมพ์ ยกเลิก เปิดใหม่) แต่ถูกค้ำด้วยเบราว์เซอร์แล้วจึงเป็น ⚙ เข้าด้วย `teacher.one@kmitl.ac.th` อยู่ใน `e2e/tests/150a-an-entry-arriving-under-an-open-editor.spec.js` สองแถวใช้คนละหัวข้อกัน เพื่อให้แถวที่สองเจอหัวข้อที่ยังไม่มีอะไรไม่ว่าจะรันลำดับไหน

### มัตแตนต์

สามตัวใน `mutation/150-entry-arriving-under-an-open-editor.py` กวาดเมื่อ 23 ก.ย. 2569 — baseline `150a` **2 ผ่านทั้ง 2** (15.6 วินาที)

- `arrivalreseeds` คือ**พฤติกรรมก่อน #150** (`replaced` ไม่ดู id เดิม) **ล้ม 1 ผ่าน 1** ที่แถวแรกเท่านั้น และในรอบแรกที่กวาดคู่กับ `149a` ทั้งไฟล์ **ล้ม 1 ผ่าน 29** — สามสิบแถวของ `149a` ยืนหมด ซึ่งถูก: ไม่มีแถวไหนในนั้นที่ id เปลี่ยนเลย
- `closekeepstheid` ปิดช่องแล้วไม่คืน ref เป็น `CLOSED` **ล้ม 1 ผ่าน 10** ที่แถวที่สองเท่านั้น เก้าแถวของ `41a` ยืนหมด — กวาดซ้ำ 25 ก.ย. 2569 หลัง #164 ได้ **ล้ม 2 ผ่าน 39** (`41a` `149a` `150a` `164a`) แถวที่เพิ่มมาคือแถวของ `164a` ซึ่งยังไม่มีอยู่ตอนวัดครั้งแรก มัตแตนต์ตัวนี้ทำให้ช่องค้างข้อความเก่า**ทุกเฟรม** จึงตายทั้งสองที่
- `neverreseeds` มีไว้ให้รอด ดูหัวข้อถัดไป

**ใบนี้เคยเขียนไว้ว่า `closekeepstheid` ฆ่าแถวที่ 3 ของ `41a` ซึ่งผิด และการกวาดเป็นผู้บอก ไม่ใช่การอ่านโค้ด** แถวนั้นเปิดช่องซ้ำบนรายการที่ตัวเองเพิ่งบันทึก draft ที่ค้างอยู่จึงเท่ากับ `detail_text` ที่ควรถูก seed ลงไปพอดี สองค่าตรงกัน มัตแตนต์จึงมองไม่เห็น — [#154](https://github.com/khthana/Deep-QA/issues/154) เขียนรูปนี้ไว้แล้ว: *มัตแตนต์ที่แทนค่าด้วยค่าปริยาย มองไม่เห็นทุกที่ที่สองค่าเท่ากัน* **แถวที่สองจึงถูกเขียนขึ้นที่จุดเดียวที่สองค่าต่างกัน** คือหัวข้อที่ยังไม่มีอะไร ซึ่งค่าที่ควร seed คือว่าง ส่วนค่าที่ค้างคือสิ่งที่พิมพ์แล้วกดยกเลิก

`41:editorstartsempty` เกาะบรรทัด `if (editing) setDraft(...)` ที่ตั๋วนี้เขียนใหม่ จึงถูกเล็งใหม่ไปที่ `if (opening || replaced) setDraft(...)` ซึ่งมีความหมายเดิม และ**กวาดซ้ำในวันเดียวกัน**: `41a` **ล้ม 1 ผ่าน 8** ที่แถวที่ 3 เหมือนเดิม — การตรวจจุดยึดบอกได้แค่ว่ามัตแตนต์ยังใช้ได้ มีแต่การกวาดที่บอกว่ามันยังพิสูจน์อะไรอยู่

### คำถามที่ยังเปิดอยู่ — และการวัดที่มันต้องการ

ครึ่งที่สองคือคนอื่นลบหรือแทนรายการขณะช่องเปิดอยู่ ตั๋ว #150 เขียนเองว่าการ seed ตรงนั้น**อาจจะถูกแล้ว** `docs/06` §Out of Scope จึงบอกว่านั่นเป็นคำถามของเจ้าของ ไม่ใช่งาน — การแก้นี้ไม่แตะการเปลี่ยนแบบนั้นเลย

`150:neverreseeds` คือเครื่องมือวัดคำถามนั้น ไม่ใช่มัตแตนต์ธรรมดา: มันคือ**ทางเลือกอีกทาง** (ผูกกับ `editing` อย่างเดียว ไม่ seed ซ้ำเลยไม่ว่าอะไรมาถึง) กวาดผ่านทุกใบที่วาด `EntrySection` ขึ้นจอ — `133a` `146a` `149a` `150a` `151a` `41a` รวม **109 แถว ไม่ตายสักแถว** (5.7 นาที) และกวาดซ้ำกับแถวที่สองหลังจากมันถูกเขียนเพิ่ม ก็ยัง **2 ผ่านทั้ง 2** และกวาดซ้ำอีกครั้ง 25 ก.ย. 2569 กับ `164a` ที่เพิ่งเกิด — `41a` `149a` `150a` `164a` **41 แถว ไม่ตายสักแถว** คำถามจึงยังไม่มีแถวไหนแยกคำตอบได้เหมือนเดิม

**แปลว่าวันนี้ไม่มีแถวไหนแยกสองคำตอบออกจากกันได้** ซึ่งเป็นการวัดที่คำถามต้องการ ไม่ใช่ความบกพร่องของแถว ถ้าเจ้าของงานเลือกทางนั้น การแก้คือลบ `replaced` ทิ้ง และแถวที่ต้องเขียนเพิ่มคือแถวของการถูกแทนที่

## เฟรมที่ถือสิ่งที่ทิ้งไปแล้ว — #164 (25 ก.ย. 2569)

`draft` ของ `EntrySection` อยู่ยืนกว่าตัวช่อง การปิดคืน `seededFrom` เป็น `CLOSED` แต่ไม่แตะสิ่งที่พิมพ์ไว้ ช่องที่ *เขียน* ครั้งที่สองเปิดขึ้นมาจึง **mount พร้อมข้อความที่กดยกเลิกไปแล้ว** แล้วถูกล้างโดย effect อีกหนึ่ง commit ถัดมา — และ `useEffect` ทำงาน**หลัง** paint เบราว์เซอร์จึงได้รับ commit แรกนั้นไปวาด และมันวาดจริง

### การวัดที่ค้านตั๋วของตัวเอง

ตั๋วเขียนไว้ว่าให้**หน่วง renderer** ตาม [#136](https://github.com/khthana/Deep-QA/issues/136) วัดแล้วได้ตรงข้าม: อ่านครั้งเดียวได้ข้อความค้าง **1 ใน 5** รอบตอนไม่หน่วง และ **0 ใน 5 ทั้งที่ x4 x10 และ x20** การหน่วงบีบให้การอ่านไปต่อคิวหลังงานที่ React ค้างอยู่ มันจึง**ปิด**การแข่งนี้ ไม่ใช่เปิด — #136 เขียนขึ้นจากการแข่งระหว่างคำตอบกับการวาดของมัน ส่วนตัวนี้คือการอ่านที่แข่งกับ effect คนละรูป

คำถามที่ถูกคือคำถามที่คนใช้ถาม — *ข้อความนั้นเคยขึ้นจอไหม* สุ่มตัวอย่างค่าของช่องทุก animation frame ตลอดการเปิดใหม่ **แปดรอบจากแปดรอบ ได้หนึ่งเฟรมที่ถือข้อความนั้นพอดี** (ช่องโผล่ที่เฟรมที่ 3–4 จากราว 28–30 เฟรม) ส่วนการอ่านครั้งเดียวได้ค่าค้าง **6 จาก 8** — **ตัวข้อบกพร่องไม่ได้สุ่ม มีแต่การอ่านที่สุ่ม**

ทางแก้คือ `useLayoutEffect` ซึ่ง**ตัดสินใจเหมือนเดิมทุกอย่างจากค่าเดิมทุกตัว** สิ่งที่ย้ายคือ React flush มันก่อนเบราว์เซอร์ paint เฟรมที่ถูกวาดจึงเป็นเฟรมที่ effect นี้แก้ไปแล้ว **ไม่ใช่การเปลี่ยน UI** — เกณฑ์ *ช่องว่าง ไม่ใช่สิ่งที่พิมพ์ทิ้งไว้รอบก่อน* ของ #150 เขียนไว้อยู่แล้ว ตั๋วนี้แค่ทำให้มันเป็นจริงในเฟรมแรกที่ช่องปรากฏ ไม่ใช่ในเฟรมที่สอง

### แถวนี้เดินด้วยมือไม่ได้ และนั่นเป็นคำตอบ ไม่ใช่ช่องว่าง

หนึ่งเฟรมคือราว 16 มิลลิวินาที ขอให้คนมองแล้วตอบว่าเห็นหรือไม่เห็นไม่ได้ และคำตอบที่ได้จะไม่ใช่การวัด เครื่องมือของแถวนี้จึงเป็นตัวสุ่มตัวอย่างรายเฟรม ไม่ใช่สายตา สิ่งที่คนยืนยันได้คือ *เปิดช่องแล้วเห็นช่องว่าง* ซึ่งคือแถวของ #150 ที่เดินด้วยมือได้อยู่แล้ว

**ตัวนับช่อง ไม่ใช่ตัวอ่านค่า** ร่างแรกของแถวนี้ถือว่า *เฟรมที่ค่าไม่ว่าง* คือ *เฟรมที่ช่องเปิดอยู่* ซึ่งใช้ได้ตอนจอยังพัง และ**ล้มทันทีที่จอถูก** — ช่องที่เปิดมาว่างกับไม่มีช่องเลย อ่านได้เหมือนกันทั้งคู่ เงื่อนไขนำจึงแดงบนจอที่ทำงานถูก ตัวสุ่มตัวอย่างวันนี้เก็บ *จำนวนช่อง* มาด้วย นี่เป็นสิ่งที่**การวัดบอก ไม่ใช่การคาดไว้ก่อน**

### มัตแตนต์

สองตัวใน `mutation/164-a-reopened-editor-painted-stale.py` กวาดเมื่อ 25 ก.ย. 2569

- `paintedafter` คือ**พฤติกรรมก่อน #164** ทุกตัวอักษร (`useLayoutEffect` กลับเป็น `useEffect` ทั้ง import และจุดเรียก — สองแก้เพราะเป็นการตัดสินใจอันเดียว ย้อนอันเดียวได้โค้ดที่พังตอนโหลด ซึ่งคือมัตแตนต์ที่ฆ่ามากเกินไป) กวาดผ่านทุกใบที่วาด `EntrySection` ขึ้นจอ — `41a` `133a` `146a` `149a` `150a` `151a` `164a` — **ล้ม 1 ผ่าน 110** (5.9 นาที) ที่แถวของ `164a` แถวเดียว **และ `150a` แถวที่สองรอดในรอบนั้น** ซึ่งคือคำอธิบายของตั๋วนี้ทั้งใบ: ยามที่อ่อนไม่ได้จับทุกครั้ง
- `clearondraftclose` **มีไว้ให้รอด และรอดจริง** — กวาดกว้างเท่ากับตัวบน คือทั้งเจ็ดใบ **111 แถว ไม่ตายสักแถว** (5.8 นาที) มันคือ**ทางแก้อีกทาง**: คง `useEffect` ไว้หลัง paint แล้วล้าง `draft` ตอนปิดแทน ช่องจึง mount ว่างตั้งแต่แรกและ `164a` เขียว — ผู้รอดที่กวาดแคบกว่าผู้ฆ่าคือผู้รอดที่ยังไม่ได้ถูกถามให้ครบ ([#51](https://github.com/khthana/Deep-QA/issues/51))

**แถวเดิมของ #150 ยังอ่านครั้งเดียว และวัดแล้วว่าเลิกแดง** เกณฑ์ของตั๋วข้อ 2 ขอว่าแถวต้องไม่แพ้หรือชนะด้วยจังหวะอีก หลังแก้ รัน `150a` กับ `164a` อย่างละหกรอบติดกันได้ **18 ผ่านทั้ง 18** และชุดเต็มรอบเดียวกันนี้ **637 ผ่าน 0 ล้ม** เทียบกับที่ตั๋วเขียนไว้ว่าเคยแดงสองในหกครั้งที่สังเกต — ส่วนคำถามว่า*มันยังล้มได้เมื่อจอพัง*ไหม ตอบด้วย `164:paintedafter` ซึ่งฆ่าแถวใหม่ทุกครั้ง ไม่ใช่ด้วยการนับรอบ

**ผู้รอดตัวหลังบอกขอบเขตของแถว** `164a` ถือข้ออ้างว่า *กรณีหัวข้อว่างไม่แฟลช* ไม่ได้ถือข้ออ้างว่า *การ seed ถูก flush ก่อน paint* ทางแก้สองทางต่างกันที่กรณี**ถูกแทนที่** — เปิดช่องบนรายการ A ปิด มีคนเปลี่ยนเป็น B แล้วเปิดใหม่ — ที่ `clearondraftclose` ยังแฟลช A อยู่หนึ่งเฟรม แถวของกรณีนั้น**เขียนวันนี้ไม่ได้** ไม่ใช่เพราะสร้างสถานการณ์ไม่ได้ แต่เพราะมันจะผูกตัวเองเข้ากับ**คำถามที่ #150 เปิดค้างไว้** (การถูกแทนที่ควร seed ทับสิ่งที่พิมพ์หรือไม่) ถ้าเจ้าของงานตอบว่าไม่ควร แถวนั้นจะแดงทั้งที่จอถูก สิ่งที่ยึดข้ออ้างระดับชั้นไว้วันนี้จึงเป็นมัตแตนต์ตัวนี้กับคำอธิบายข้างโค้ด ไม่ใช่แถว — เขียนไว้ให้หาเจอ ไม่ใช่ปล่อยเป็นร้อยแก้วที่ไม่มีใครหา
