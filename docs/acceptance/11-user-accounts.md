# ตรวจรับด้วยมือ — #11 User accounts

`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #11

ครึ่งแรกอยู่ที่ `backend/test/users.test.js` (42 subtests) — ทุกเกณฑ์ที่พิสูจน์ได้ที่ seam เดียวของเรา
คือ HTTP surface ของ backend ถูกพิสูจน์ที่นั่นแล้ว รวมทั้งข้อ 9 ที่เรียกร้องเทสต์ของขอบเขตและของการ
ปฏิเสธไฟล์นำเข้าทั้งไฟล์โดยตรง ที่เหลือลงมาอยู่ในตารางข้างล่างเพราะ docs/06 §Testing Decisions
ระบุว่า **"Frontend components are not unit-tested"** — สิ่งที่คนเห็นบนหน้าจอจึงพิสูจน์ด้วยมือ
โดยการออกแบบ ไม่ใช่โดยการละเลย

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ข้อมูลผู้ใช้งาน* (`/main/users`)

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`cd db && npm run reset && npm run migrate && npm run seed` หลังเดินจบ** (`seed` เพียงอย่างเดียวเป็น upsert ไม่ลบแถวที่เกินมา) ก่อนเริ่มตั๋วถัดไป

ถ้า `withinValidity()` ตีความ `NULL` ว่าอยู่นอกช่วง ผลไม่ใช่ผู้ประเมินภายนอกคนหนึ่งเข้าไม่ได้
แต่คือทุกบัญชีในระบบเข้าไม่ได้พร้อมกัน และไม่มีเทสต์ที่เขียนโดยคิดถึงผู้ประเมินภายนอกจะจับได้

แถว *ให้บทบาทสูงกว่าตัวเองไม่ได้* ถูกแก้ถ้อยคำไปพร้อมกับการเดิน คำสั่งเดิมให้เลือกบทบาท
*ผู้ดูแลระบบระดับคณะ* ในฟอร์ม ซึ่งเลือกไม่ได้เพราะตัวเลือกนั้นไม่มีอยู่ — สิ่งที่เดินได้จริงแข็งกว่า
ที่เอกสารเขียน คือฟอร์มไม่เสนอให้เลย **และ** server ปฏิเสธถ้าข้ามฟอร์มไป ป้ายของช่องขอบเขต
แยกภาควิชาจากหลักสูตรด้วยจำนวนหลักของรหัสอย่างเดียว เปิดเป็น
[#90](https://github.com/khthana/Deep-QA/issues/90) ไว้

**ตัดสินแล้วเมื่อ 21 ส.ค. 2569 ว่าไม่แก้** — ผู้ดูแลสร้างผู้ดูแล **ระดับเดียวกัน** ในขอบเขตตัวเองได้
(`dept.admin.05@` สร้าง `DEPT_ADMIN` ขอบเขต `05` ได้ `201` และยังมองเห็นคนที่ตัวเองสร้าง)
กฎใน `backend/auth/administration.js` ปฏิเสธเฉพาะบทบาทที่ *สูงกว่า* และเหตุผลที่คอมเมนต์ให้ไว้ —
ผู้ตั้งจะกลายเป็นผู้น้อยแล้วมองไม่เห็นสิ่งที่ตัวเองเพิ่งทำ — ใช้กับระดับเท่ากันไม่ได้ เพราะยังเห็นกันอยู่


สองอย่างที่ตั้งใจปล่อยไว้เป็นแถวเดินด้วยมือ

- แถวข้อ 8 ที่ให้เปิด `http://localhost:3000/api/users/<รหัสของคนภาควิชาอื่น>` ตรง ๆ **เดินด้วยมือแล้ว
  แต่จะไม่ยกไปเป็น ⚙** โดยตั้งใจ — `backend/test/users.test.js` พิสูจน์ route นั้นไว้แล้วที่ seam ของ
  HTTP สำเนาบนเบราว์เซอร์จะเป็นการทดสอบตัวทดสอบ ไม่ได้เพิ่มอะไรที่ seam ใหม่มีให้
- แถวข้อ 8 *ให้บทบาทสูงกว่าตัวเองไม่ได้* **เดินด้วยมือทั้งสองครึ่งแล้ว แต่จะไม่ยกไปเป็น ⚙**
  โดยตั้งใจ — ครึ่งของ server (`403` เมื่อข้ามฟอร์มไปยิงตรง ๆ) `backend/test/users.test.js`
  พิสูจน์ไว้แล้วที่ seam ของ HTTP ส่วนครึ่งของฟอร์มคือ *รายการตัวเลือกที่หน้าจอวาด* ซึ่งเป็น
  เรื่องของหน้าตา จึงอยู่นอกขอบเขตที่ #65 กำหนดไว้ ไม่มีครึ่งไหนที่ browser seam จะเพิ่มอะไรให้

ครึ่งที่ browser seam รับไปของแถวข้อ 8 สองแถวแรก คือ *บัญชีไหนปรากฏในตาราง* ซึ่งเป็นการปฏิเสธ
ที่ไม่ทิ้งแถบแดงไว้ให้เห็นเลย มีแต่แถวที่หายไป — เป็นแถวที่คนเดินด้วยมือจับได้ยากที่สุด สเปกจึงค้น
ด้วยช่องค้นหาของหน้าจอเอง เพราะสิบบัญชีใน seed กับหน้าละสิบแถวแปลว่าอ่านจากหน้าแรกหน้าเดียวไม่ได้

สองข้อที่ mutation test เปิดออกมา และควรอ่านคู่กับแถวข้างบน

- **ช่วงเวลาที่กลับด้านถูกกันสองชั้น** — กลับเครื่องหมายเปรียบเทียบ `from.value > until.value` ใน `backend/routes/users.js` แล้วแถวนั้นยังถูกปฏิเสธอยู่ดี เพราะ CHECK constraint ของตารางรับต่อผ่าน `23514` → `invalidValidity` ต้องทำลายทั้งสองที่เดียวแถวจึงจะหลุด — แปลว่าข้อห้ามนี้มีของจริงสองชั้น ไม่ใช่ข้อความที่เขียนทิ้งไว้เฉย ๆ
- **รายงานทุกบรรทัดพร้อมกัน** — เปลี่ยน `continue` เป็น `break` ใน `backend/lib/importer.js` ทำให้แถวที่รายงานเหลือแค่บรรทัดแรก และ spec จับได้ทันที

อีกข้อหนึ่งที่คนอ่านภายหลังควรรู้ แถว *ไม่เห็นคนของภาควิชาอื่น* ใช้ `dept.admin.01@` เป็นตัวแทน ซึ่งทำหน้าที่สองอย่างพร้อมกัน คือทั้ง *คนของภาควิชาอื่น* และ *ผู้ดูแลระดับเดียวกัน* เพราะ seed ไม่มีคนธรรมดาของภาควิชา 01 อยู่เลย แถวนี้จึงผ่านด้วยบัญชีที่แข็งที่สุดเท่าที่มี ไม่ใช่ด้วยคนธรรมดาของภาควิชานั้น

## สิ่งที่ยังไม่ปิดใน #11

1. **นำเข้าเป็น CSV ไม่ใช่ `.xlsx`** — ตั๋วเขียนว่า "spreadsheet" ระบบเดิมใช้ `xlsx@0.18.5` ซึ่งยังมี
   ช่องโหว่ prototype-pollution และ ReDoS ที่ไม่มี patch ตัวอ่าน CSV ที่เขียนเองตอบเกณฑ์ได้ครบทุกข้อ
   โดยไม่ต้องเพิ่ม dependency และรูปของ endpoint ไม่เปลี่ยนถ้าภายหลังต้องรับ `.xlsx` จริง
   แบบฟอร์มมี BOM เพื่อให้ Excel เปิดภาษาไทยได้ตรง
2. **การให้/ถอนบทบาทหลังสร้างบัญชีเป็นของ #12** — หน้าจอนี้ให้บทบาทแรกพร้อมบัญชี เพราะเกณฑ์ข้อ 2
   เรียกร้องว่าเข้าใช้ได้ทันที การแก้ไขจึงส่งเฉพาะข้อมูลส่วนตัว ไม่ส่งบทบาท
3. **ยังไม่มีการรีเซ็ตรหัสผ่านโดยผู้ดูแล** — ตั๋วนี้ไม่ได้ขอ และ #10 ให้เจ้าของบัญชีเปลี่ยนเองได้แล้ว
   ถ้าต้องการให้ผู้ดูแลตั้งใหม่ให้คนที่ลืมรหัส ต้องเปิดตั๋ว
4. **ช่องขอบเขตของบทบาทเป็นการพิมพ์รหัสเอง** — ฟอร์มยังไม่มี dropdown ของภาควิชา/หลักสูตร
   เพราะหน้าจอที่จัดการสองสิ่งนั้นคือ #14 และ #15 ซึ่งยังไม่ถึง server ปฏิเสธรหัสที่ไม่มีจริงอยู่แล้ว —
   **ปิดแล้วใน #12** ทั้งสองช่องเป็น dropdown ที่ `GET /api/users/grantable` เป็นคนตอบ
5. **บัญชีที่ถูกระงับกลางทางเห็นแถบแดงแทนกล่องเข้าสู่ระบบใหม่** — `sessionAdmission` ตรวจสถานะและ
   ช่วงเวลาทุก request จึงตัดสิทธิ์ทันทีไม่ต้องรอ cookie หมดอายุ แต่ตอบ 403 ซึ่ง
   `frontend/src/api/client.js` ส่งต่อให้กล่อง *Session หมดอายุ* เฉพาะ 401 คนที่ถูกระงับระหว่างใช้งาน
   จึงเห็นข้อความปฏิเสธในหน้าเดิมแทนที่จะถูกพากลับไปหน้าเข้าสู่ระบบ — เปิดเป็น #52 แล้ว
6. **`coveredScopes` ถูกคำนวณซ้ำหลายครั้งต่อหนึ่ง request** — `placeAllowed` และ `assignable`
   ต่างเรียก `reachOf` เอง การนำเข้าจึงยิงสองคิวรีต่อหนึ่งแถว ไฟล์ร้อยแถวคือสองร้อยคิวรีที่ตอบเหมือนกันทุกครั้ง
   ควรคำนวณครั้งเดียวต่อ request — **ปิดแล้วใน #12** โดย memoise ต่อ request ใน `backend/auth/administration.js`
7. **รายชื่อบทบาทถูกเขียนไว้สามที่** — ตาราง `roles.priority` ในฐานข้อมูล, `ADMIN_ROLES` ใน
   `backend/routes/users.js` และ `ROLES` ใน `frontend/src/components/users/UserForm.js`
   ถ้าเพิ่มบทบาทใหม่แล้วแก้ไม่ครบทั้งสามที่ จะไม่มีอะไรฟ้อง — **ปิดแล้วใน #12** `ROLES` ถูกถอดออก
   และฟอร์มถาม `GET /api/users/grantable` แทน เหลือสองที่คือฐานข้อมูลกับ `ADMIN_ROLES`
