## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ข้อมูลผู้ใช้งาน* (`/main/users`)

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`cd db && npm run reset && npm run migrate && npm run seed` หลังเดินจบ** (`seed` เพียงอย่างเดียวเป็น upsert ไม่ลบแถวที่เกินมา) ก่อนเริ่มตั๋วถัดไป

แถว *ซ่อนไม่ใช่สิ่งเดียวที่กันไว้* มีหัวใจอยู่ที่คำว่า **เหมือนกัน** ไม่ใช่คำว่าถูกปฏิเสธ ถ้าคนนอกขอบเขต

แถว *บัญชีปกติไม่ต้องมีช่วงเวลา* คือด้านกลับของเกณฑ์ข้อ 4 ทั้งหมด และเป็นด้านที่พังแล้วเจ็บกว่า —

แถว *ให้บทบาทสูงกว่าตัวเองไม่ได้* ถูกแก้ถ้อยคำไปพร้อมกับการเดิน คำสั่งเดิมให้เลือกบทบาท
*ผู้ดูแลระบบระดับคณะ* ในฟอร์ม ซึ่งเลือกไม่ได้เพราะตัวเลือกนั้นไม่มีอยู่ — สิ่งที่เดินได้จริงแข็งกว่า
ที่เอกสารเขียน คือฟอร์มไม่เสนอให้เลย **และ** server ปฏิเสธถ้าข้ามฟอร์มไป ป้ายของช่องขอบเขต
แยกภาควิชาจากหลักสูตรด้วยจำนวนหลักของรหัสอย่างเดียว เปิดเป็น
[#90](https://github.com/khthana/Deep-QA/issues/90) ไว้

**ตัดสินแล้วเมื่อ 21 ส.ค. 2569 ว่าไม่แก้** — ผู้ดูแลสร้างผู้ดูแล **ระดับเดียวกัน** ในขอบเขตตัวเองได้
(`dept.admin.05@` สร้าง `DEPT_ADMIN` ขอบเขต `05` ได้ `201` และยังมองเห็นคนที่ตัวเองสร้าง)
กฎใน `backend/auth/administration.js` ปฏิเสธเฉพาะบทบาทที่ *สูงกว่า* และเหตุผลที่คอมเมนต์ให้ไว้ —
ผู้ตั้งจะกลายเป็นผู้น้อยแล้วมองไม่เห็นสิ่งที่ตัวเองเพิ่งทำ — ใช้กับระดับเท่ากันไม่ได้ เพราะยังเห็นกันอยู่


สองอย่างที่ตั้งใจปล่อยไว้เป็นแถวเดินด้วยมือ

- แถวข้อ 8 ที่ให้เปิด `http://localhost:3000/api/users/<รหัสของคนภาควิชาอื่น>` ตรง ๆ **เดินด้วยมือแล้ว
  แต่จะไม่ยกไปเป็น ⚙** โดยตั้งใจ — `backend/test/users.test.js` พิสูจน์ route นั้นไว้แล้วที่ seam ของ
  HTTP สำเนาบนเบราว์เซอร์จะเป็นการทดสอบตัวทดสอบ ไม่ได้เพิ่มอะไรที่ seam ใหม่มีให้
- แถวข้อ 8 *ให้บทบาทสูงกว่าตัวเองไม่ได้* **เดินด้วยมือทั้งสองครึ่งแล้ว แต่จะไม่ยกไปเป็น ⚙**
  โดยตั้งใจ — ครึ่งของ server (`403` เมื่อข้ามฟอร์มไปยิงตรง ๆ) `backend/test/users.test.js`
  พิสูจน์ไว้แล้วที่ seam ของ HTTP ส่วนครึ่งของฟอร์มคือ *รายการตัวเลือกที่หน้าจอวาด* ซึ่งเป็น
  เรื่องของหน้าตา จึงอยู่นอกขอบเขตที่ #65 กำหนดไว้ ไม่มีครึ่งไหนที่ browser seam จะเพิ่มอะไรให้

ครึ่งที่ browser seam รับไปของแถวข้อ 8 สองแถวแรก คือ *บัญชีไหนปรากฏในตาราง* ซึ่งเป็นการปฏิเสธ
ที่ไม่ทิ้งแถบแดงไว้ให้เห็นเลย มีแต่แถวที่หายไป — เป็นแถวที่คนเดินด้วยมือจับได้ยากที่สุด สเปกจึงค้น
ด้วยช่องค้นหาของหน้าจอเอง เพราะสิบบัญชีใน seed กับหน้าละสิบแถวแปลว่าอ่านจากหน้าแรกหน้าเดียวไม่ได้

สี่ข้อที่ mutation test เปิดออกมา และควรอ่านคู่กับแถวข้างบน

- **ช่วงเวลาที่กลับด้านถูกกันสองชั้น** — กลับเครื่องหมายเปรียบเทียบ `from.value > until.value` ใน `backend/routes/users.js` แล้วแถวนั้นยังถูกปฏิเสธอยู่ดี เพราะ CHECK constraint ของตารางรับต่อผ่าน `23514` → `invalidValidity` ต้องทำลายทั้งสองที่เดียวแถวจึงจะหลุด — แปลว่าข้อห้ามนี้มีของจริงสองชั้น ไม่ใช่ข้อความที่เขียนทิ้งไว้เฉย ๆ
- **รายงานทุกบรรทัดพร้อมกัน** — เปลี่ยน `continue` เป็น `break` ใน `backend/lib/importer.js` ทำให้แถวที่รายงานเหลือแค่บรรทัดแรก และ spec จับได้ทันที
- **ด่านของ session ที่ค้างอยู่เป็นคนละตัวกับด่านตอนลงชื่อเข้าใช้** — `11-12:M8` ตัดบรรทัด `if (user.status !== 'active')` ออกจาก `sessionAdmission` เท่านั้น (ผูกกับบรรทัด `unknown` ที่อยู่เหนือมัน เพราะสำเนาทั้งสองเขียนเหมือนกันทุกตัวอักษร) แล้ว `11c` ตายที่บรรทัด 109 คือ `/api/me` ตอบ `200` ทั้งที่บัญชีถูกระงับไปแล้ว ส่วนด่านตอนลงชื่อเข้าใช้ยังปฏิเสธตามปกติ — ซึ่งเป็นเหตุผลทั้งหมดที่แถวนี้ต้องมีสเปกของตัวเอง

- **ตัวเลขที่ฆ่าไม่ได้ไม่ใช่หลักฐาน** — `11b` กับ `14b` เคยอ่านจำนวนแถวหลังการนำเข้าที่ถูกปฏิเสธไว้สี่จุด `ImportPanel` เรียก `onImported` เฉพาะตอนสำเร็จ รายการจึงไม่ถูกดึงใหม่หลังการปฏิเสธ ตัวเลขบนหน้าจอคือตัวเลขก่อนอัปโหลด ไม่ว่า server จะทำอะไรกับไฟล์ สองในสี่จุดยิ่งกว่านั้น คืออ่านหลังไฟล์เปล่าซึ่งไม่มีแถวให้เขียนอยู่แล้ว ทั้งสี่จุดถูก**ลบทิ้ง**พร้อมคอมเมนต์ว่าข้ออ้างนั้นพิสูจน์อยู่ที่ไหน (#64) ที่พิสูจน์จริงคือแถวก่อนหน้าในไฟล์เดียวกัน — `11b` บรรทัด 131 และ `14b` บรรทัด 124 — ซึ่ง `reload` แล้วเปิดรายการใหม่แล้วจึง poll ตัวเลขที่มาจาก server หลังอัปโหลด `11-12:M9` เปลี่ยน `ROLLBACK` เป็น `COMMIT` ใน `backend/lib/importer.js` แล้วสองแถวนั้นตายทั้งคู่ (ได้ 7 ที่ควรเป็น 6) และเป็นแถวที่ล้ม*ก่อน*แถวอื่นในไฟล์ของตัวเอง ซึ่งคือสิ่งที่กติกาต้องการ คือ assertion ใหม่ล้ม ไม่ใช่ assertion ที่อยู่ก่อนหน้า สองไฟล์นี้เป็น `mode: 'serial'` แถวที่อยู่หลังแถวที่ล้มจึงถูกข้าม ไม่ได้รัน รอบนี้จึงไม่ได้บอกอะไรเกี่ยวกับแถวเหล่านั้น มัตแตนต์ตัวเดียวคุมการนำเข้าของทุกหน้าจอ เพราะ `importer.js` ตัดสินใจ rollback ที่ `errors.length > 0` ที่เดียว — และนั่นคือเหตุผลที่จุดที่ห้า คือไฟล์ที่แถวชนกันเอง ถ้าใส่ assertion ใหม่เข้าไปก็จะพิสูจน์ของเดิมซ้ำ ไม่ได้อะไรเพิ่ม

อีกข้อหนึ่งที่คนอ่านภายหลังควรรู้ แถว *ไม่เห็นคนของภาควิชาอื่น* ใช้ `dept.admin.01@` เป็นตัวแทน ซึ่งทำหน้าที่สองอย่างพร้อมกัน คือทั้ง *คนของภาควิชาอื่น* และ *ผู้ดูแลระดับเดียวกัน* เพราะ seed ไม่มีคนธรรมดาของภาควิชา 01 อยู่เลย แถวนี้จึงผ่านด้วยบัญชีที่แข็งที่สุดเท่าที่มี ไม่ใช่ด้วยคนธรรมดาของภาควิชานั้น

## ปีในช่วงเวลาใช้งานอยู่คนละศักราช — #125 (9 ก.ย. 2569)

`2569-09-30` เป็นวันที่ ISO ที่ถูกรูปแบบ `Date` รับ และถูกเก็บเป็นปี 2569 **ค.ศ.**
`readDate` ตรวจ**รูปร่าง**ของวันที่ และเขียน docstring ไว้เองว่าทำไมถึงปฏิเสธ `01/03/2026`
แต่ความผิดพลาดนี้อยู่ที่**ความหมาย** ไม่ใช่รูปร่าง — **ด่านที่ตรวจรูปแบบมองไม่เห็นความผิดพลาดเรื่องศักราช**

เจ้าของข้อกำหนดเลือกข้อสองจากสามข้อที่ตั๋วเสนอเมื่อ 9 ก.ย. 2569 — **ปฏิเสธ แล้วทดเลขให้ในประโยค**
ช่วงที่รับคือ ค.ศ. 1900–2200 ซึ่งกว้างจนไม่มีช่วงเวลาจริงเข้าใกล้ปลายทั้งสองข้าง
มันไม่ได้มีไว้เดาว่าระบบนี้จะอยู่ถึงเมื่อไร แต่มีไว้ให้ปีพุทธศักราชตกออกไป

### สองประโยค ไม่ใช่ประโยคเดียวที่มีรู

`validityEra` ทดเลขให้ (`ปี 2569 … ให้ใช้ ค.ศ. 2026 แทน`) ส่วน `validityYearRange` บอกช่วง
ปีจะได้ประโยคแรกก็ต่อเมื่ออ่านแบบ พ.ศ. แล้วตกลงมาอยู่ในช่วงพอดี เพราะการบอกคนที่พิมพ์ `1500`
ว่าให้กรอก `957` แย่กว่าการไม่บอกอะไรเลย มัตแตนต์ `alwaysoffersconversion` คือการรวมสองประโยคเป็นหนึ่ง
ซึ่งเป็นความผิดพลาดที่น่าทำกว่า เพราะโค้ดน้อยกว่าและอ่านแล้วเป็นมิตรกว่า

### ประโยคที่เป็นฟังก์ชัน กับสองจุดที่เคยอ่านมันเป็นคีย์

ประโยคที่เอ่ยถึงปีที่คนพิมพ์มา เป็นค่าคงที่ไม่ได้ มันจึงเป็น**ฟังก์ชัน**ใน `REFUSALS`
เหมือนอีกยี่สิบตัวที่มีอยู่ก่อนแล้ว (นับเมื่อ 9 ก.ย. 2569 — หลังตั๋วนี้เป็นยี่สิบสอง) แต่ route ทั้งสองเส้นเขียนว่า `REFUSALS[draft.reason]` —
ซึ่งยื่น**ฟังก์ชัน**ให้ `res.json` แล้ว `JSON.stringify` ทิ้งมันไปเงียบ ๆ **คนกรอกฟอร์มจะถูกปฏิเสธ
โดยไม่มีข้อความอะไรเลย** `sentenceOf` ของ `lib/importer.js` (มีมาตั้งแต่ #26 เพราะการนำเข้ามีคำปฏิเสธ
ชนิดนี้ก่อนใคร) จึงย้ายไปอยู่ใน `auth/refusals.js` และทั้งสองเส้นอ่านมันแทน

**เส้นแก้ไขไม่เคยมีแถวของตัวเอง** ทั้งที่การต่อรอบให้ผู้ประเมินคือสิ่งที่เกิดขึ้นจริงกับช่วงเวลาหนึ่ง ๆ
`editsentenceisakey` มีไว้เพราะเรื่องนี้ ถ้าไม่มีแถวนั้น มันจะฆ่าอะไรไม่ได้เลย

### สิ่งที่มัตแตนต์ในใบนี้พูดไม่ได้

**ไม่มีอะไรพิสูจน์ `valid_until` แยกจาก `valid_from`** เพราะปลายทั้งสองข้างอ่านด้วยการเรียกฟังก์ชัน
เดียวกันสองครั้ง มัตแตนต์ที่กันข้างเดียวจึงเขียนไม่ได้ — เป็นคำตอบข้อสองในสามข้อของ #101
(*เอื้อมไม่ถึงโดยโครงสร้าง*) ไม่ใช่ช่องโหว่ แถวที่ยืนยันศักราชใน `valid_until` ยังคุ้มที่จะมี
เพราะมันเป็นคำกล่าวว่า `readAccount` เรียก `readDate` สองครั้ง ซึ่งการแก้ครั้งหลังเอาออกได้

## ปลายสองข้างของช่วงเวลา ต้องการคนละการกระทำ — #89 (9 ก.ย. 2569)

บัญชีที่**ยังไม่ถึง**วันเริ่มใช้งาน กับบัญชีที่**หมด**ช่วงเวลาไปแล้ว เคยได้ประโยคปฏิเสธเดียวกัน
ทุกตัวอักษร คือ *บัญชีนี้อยู่นอกช่วงเวลาที่กำหนดให้ใช้งาน* ตั๋วนี้เปิดไว้เป็น**เรื่องที่ควรตัดสิน
ไม่ใช่ข้อบกพร่อง** ด้วยเหตุผลที่ตรวจสอบได้ และเหตุผลนั้นอยู่ในใบนี้เอง: แถว *ยังไม่ถึงวันเริ่ม
ก็เข้าไม่ได้* ในตารางการเดินข้างบนเขียนสั่งไว้ด้วยลายมือตัวเองว่า **"ข้อความเดียวกับแถวบน"**
ระบบทำถูกตามที่ถูกสั่งทุกตัวอักษร — **ข้อบกพร่องอยู่ในใบตรวจรับ ไม่ได้อยู่ในโค้ด** ใบจึงถูกแก้ก่อน
แล้วโค้ดจึงตามไป ซึ่งเป็นลำดับที่ตั๋วขอไว้เอง

แกนที่แยกสองประโยคออกจากกันคือ **สิ่งที่คนที่เจอต้องทำต่อ**

| สถานะ | สิ่งที่ต้องทำ | ประโยค |
|---|---|---|
| ยังไม่ถึงวันเริ่ม | รอ แล้วเข้าใหม่เมื่อถึงกำหนด | *บัญชีนี้ยังไม่ถึงวันเริ่มใช้งาน กรุณาเข้าใช้งานอีกครั้งเมื่อถึงวันที่กำหนด* |
| หมดช่วงเวลาแล้ว | ติดต่อผู้ดูแลเพื่อขอต่ออายุ รอไปก็ไม่มีอะไรเปลี่ยน | *บัญชีนี้พ้นช่วงเวลาที่กำหนดให้ใช้งานแล้ว กรุณาติดต่อเจ้าหน้าที่เพื่อขอต่ออายุ* |

ผู้ประเมินภายนอกเป็นคนนอกสถาบัน เดาเองไม่ได้ และไม่รู้ว่าควรถามใคร ประโยคเดียวที่ครอบคลุม
ทั้งสองสถานะ จึงไม่ได้บอกอะไรเขาสักอย่าง ที่ค้านคือการบอกรายละเอียดของบัญชีก่อนพิสูจน์ตัวตน
สำเร็จเป็นการรั่วข้อมูล — แต่ประโยคเดิมก็ยืนยันอยู่แล้วว่าบัญชีนี้มีอยู่จริง**และรหัสผ่านถูกต้อง**
การบอกเพิ่มว่าอยู่ก่อนหรือหลังหน้าต่าง ไม่ได้เปิดเผยอะไรที่ยังไม่ถูกเปิดเผย

### ทำไมประโยคไม่บอกวันที่ — วัดแล้ว ไม่ได้เถียงเอา

ตั๋วเสนอไว้ว่า *"พิจารณาให้ข้อความฝั่งยังไม่ถึงวันเริ่ม บอกวันที่เริ่มไปเลย เพราะเป็นวันที่คนคนนั้นรออยู่"*
ซึ่งฟังดูถูก และทำไม่ได้ให้เหมือนกันทุกประตู

กุญแจทั้งสอง (และ `outsideValidity` ก่อนหน้านี้) อยู่ใน `GOOGLE_REFUSAL_REASONS` ซึ่งเดินทางเป็น `/login?error=<reason>`
**ไม่มี body** และ `frontend/src/pages/Login.js` เก็บสำเนาถ้อยคำของตัวเองไว้โดยมี reason เป็นกุญแจ
ยิ่งกว่านั้น `refuse()` ใน `backend/auth/accounts.js` เขียนว่า `message: REFUSALS[reason]` —
เป็น `REFUSALS[` แบบเดียวกับที่ #125 เพิ่งแก้ที่ route สองเส้นเมื่อวันเดียวกัน คือยื่นฟังก์ชันให้
`JSON.stringify` ทิ้ง

ทางเลือกที่เหลือคือให้ประตูที่มี body บอกวันที่ ส่วนประตูที่เป็น redirect ไม่บอก — ซึ่ง**แย่กว่า
การไม่บอกทั้งคู่** สถานะเดียวของบัญชีเดียว ตอบคนละอย่างตามประตูที่เข้ามา คือรูปของ #66
(*แถวที่บอกทางเข้าสองทาง คือสองแถว*) ในรูปของคำปฏิเสธ ถ้าเจ้าของข้อกำหนดยังอยากได้วันที่
**นั่นเป็นตั๋วของตัวเอง — [#128](https://github.com/khthana/Deep-QA/issues/128)** เพราะ redirect ต้องแบกวันที่เป็นพารามิเตอร์ที่สอง ซึ่งคือข้อมูลของบัญชีใน URL

### สามประตู สองจุดอ่าน กฎเดียว

คนเข้าได้สามทาง — รหัสผ่าน, cookie ที่ถืออยู่ และ Google — แต่จุดที่อ่าน `validityRefusal`

ไม่ได้อ่านเอง ร่างแรกของหัวข้อนี้นับเป็นสาม และ `/code-review` จับได้ โดยที่

สามจุดเรียก** มัตแตนต์ที่ทำให้สองเส้นนี้ตอบต่างกันจึงเขียนไม่ได้ —

### เทสต์ที่อ่านตัวโค้ดเอง หยุดที่ขอบของฟังก์ชันที่มันอ่าน

`backend/test/auth.test.js` มีข้อ *the list of reasons is the list the rules can actually produce*
ซึ่งอ่าน**ตัวข้อความของ source เอง** ของฟังก์ชันที่เส้นทาง Google ประกอบขึ้น หา `refuse(<status>, '<reason>')`
แล้วเทียบกับ `GOOGLE_REFUSAL_REASONS` — มีไว้เพื่อไม่ให้รายการนั้นเป็นรายการที่ต้องจำเอง
การย้ายการตัดสินใจเรื่องหน้าต่างออกไปเป็น `validityRefusal` ทำให้เหตุผลสองตัวหลุดออกจากข้อความ
ที่มันอ่าน และมันฟ้องทันทีหลัง run ที่เขียว — **ซึ่งคือระบบทำงาน ไม่ใช่เทสต์ขวางทาง**

ทางออกสองทาง และความต่างสำคัญ: เขียนชื่อเหตุผลทั้งสองที่จุดเรียกทั้งสองจุด แปลว่าชื่อเหตุผลถูกเขียนซ้ำสี่จุด
ในสองฟังก์ชัน และการตัดสินใจอยู่สองที่ — รูปที่ #97 มีย่อหน้าของตัวเองว่าด้วยเรื่องนี้ ส่วนการให้
`validityRefusal` **คืนคำปฏิเสธทั้งก้อน** เก็บการตัดสินใจไว้ที่เดียว และเก็บเหตุผลทุกตัวไว้ใน
รูปที่ scan นั้นหาเจออยู่แล้ว สิ่งที่ต้องบอกเทสต์คือกฎย้ายขึ้นไปอีกฟังก์ชันหนึ่งเท่านั้น
**การขยาย regexp แทน คือการเอารายการที่ต้องจำเองกลับมาในหมวกอีกใบ**

### สองประโยค ไม่ใช่ประโยคเดียว

แต่ละประโยคเอ่ยการกระทำที่คนเพิ่งกด — *ระงับ* บนหน้าจอหนึ่ง *ยกเลิกบทบาท* บนอีกหน้าจอ

สามประโยคที่อยู่ใต้มันในไฟล์เดียวกัน

**และร่างแรกเขียนประโยคแรกไว้กว้างกว่าย่อหน้าที่อธิบายมันเอง** คือ *เปลี่ยนสถานะบัญชีของ
ตัวเองไม่ได้* ซึ่งเอ่ยชื่อ *route* ไม่ใช่ปุ่ม ทั้งที่ย่อหน้าข้างบนนี้ — และคอมเมนต์ใน `refusals.js`
และใบมัตแตนต์ — อ้างเหตุผลว่าแต่ละประโยคเอ่ยปุ่มที่เพิ่งถูกกด `/code-review` จับได้ ตอนนี้เป็น
*ระงับบัญชีของตัวเองไม่ได้* ตามที่ตั๋วขอไว้ตรงตัว **และเหตุที่ประโยคแคบกว่าด่านได้โดยไม่มีรู**
คือทิศอีกทางของ route นี้ไปไม่ถึงแถวของตัวเอง: บัญชีที่ไม่ได้อยู่สถานะ *ใช้งานอยู่* ถูกปฏิเสธ
ทุก request ด้วย `inactive` ซึ่งเป็นสิ่งที่ `11c` แถว 3 วัดไว้ มันจึงไม่มีวันถือ session ที่จะไปกด
*เปิดใช้งาน* ให้ตัวเอง **ประโยคที่แคบกว่าด่าน แต่กว้างเท่าสิ่งที่คนทำได้จริง คือคู่ที่ไม่มีรู**

ไปทำอะไรพังบ้าง — อันหลังต้องรันชุดสะอาด** ทั้งสามแถวแก้แล้ว อ่าน `REFUSALS` ตัวจริงจาก

(ตัวเลขนี้เขียนเป็น *เก้า* ก่อน แล้วนับจริงได้สิบสี่ — `grep -c` ตอบ 15 ครั้ง โดยหนึ่งในนั้น

### สิ่งที่การแก้เปิดออกมา และมันไม่ใช่เรื่องเอกสาร

ตั๋วทำนายไว้ว่า *"ถ้ามีที่ใดผูกกับกฎอีเมลต้องเป็น `@kmitl.ac.th` การแก้นี้จะเปิดออกมาเอง"*
มันเปิดออกมาจริง และเป็นข้อที่ดีที่สุดของรอบนี้

`backend/test/auth.test.js` มีสองข้อที่ยิง `resolveGoogleAccount` — **ทาง Google** — ด้วยบัญชี
ผู้ประเมินคนนั้น แล้ววัดว่าได้ `validityEnded` กับ `validityNotStarted` ย้ายโดเมนออกไปแล้วรัน
ผลคือ `expected: 'validityEnded'` · `actual: 'domain'`

`resolveGoogleAccount` ตรวจโดเมนเป็นบรรทัดแรก และตรวจช่วงเวลาอีกสามบรรทัดถัดมา
**ผู้ประเมินภายนอกจึงไม่มีวันไปถึงช่วงเวลาของตัวเองทางประตูนั้นเลย** เขาถูกปฏิเสธด้วย `domain`
ก่อน สองข้อนั้นไปถึงกฎช่วงเวลาได้ก็เพราะ seed ขัดกับบทบาทอยู่พอดี **กฎถูก แต่ตัวประธาน
เป็นคนที่มีอยู่จริงไม่ได้**

สองเหตุผลนั้นยังไปถึงได้อยู่ และเป็นของคนละคนกับที่เทสต์บอกเป็นนัย — `backend/routes/users.js`
ไม่ได้กั้น `valid_from`/`valid_until` ไว้ที่บทบาทใด ผู้ดูแลจึงกำหนดช่วงเวลาให้บัญชีไหนก็ได้ และ
คนที่เจอกฎนี้ที่ประตู Google คือ**อาจารย์ที่ถูกกำหนดช่วงเวลาแล้วช่วงนั้นปิดไป** สองข้อนั้นย้ายไปอยู่บน
`U_TEACH` ซึ่ง seed ไม่ได้ให้ช่วงเวลาไว้ `resetValidity` จึงคืนค่า `NULL` เดิมได้พอดี

ส่วนช่วงเวลาของตัวผู้ประเมินเองถูกตัดสินที่**ประตูรหัสผ่าน** ซึ่งเป็นประตูเดียวที่บทบาทนี้มี และ
`backend/test/users.test.js` พิสูจน์ไว้ตรงนั้นแล้ว **การแบ่งแบบนี้ตรงกับความจริงมากกว่าที่เคยเขียนไว้**
