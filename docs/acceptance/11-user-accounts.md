# ตรวจรับด้วยมือ — #11 User accounts

`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #11

ครึ่งแรกอยู่ที่ `backend/test/users.test.js` (39 subtests) — ทุกเกณฑ์ที่พิสูจน์ได้ที่ seam เดียวของเรา
คือ HTTP surface ของ backend ถูกพิสูจน์ที่นั่นแล้ว รวมทั้งข้อ 9 ที่เรียกร้องเทสต์ของขอบเขตและของการ
ปฏิเสธไฟล์นำเข้าทั้งไฟล์โดยตรง ที่เหลือลงมาอยู่ในตารางข้างล่างเพราะ docs/06 §Testing Decisions
ระบุว่า **"Frontend components are not unit-tested"** — สิ่งที่คนเห็นบนหน้าจอจึงพิสูจน์ด้วยมือ
โดยการออกแบบ ไม่ใช่โดยการละเลย

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ผู้ใช้งานระบบ* (`/main/users`)

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`npm run seed` ใหม่หลังเดินจบ** ก่อนเริ่มตั๋วถัดไป

## สิ่งที่ปิดไปจากตั๋วอื่น

- **#10 ข้อ 2 ของ "สิ่งที่ยังไม่ปิด"** — `/main/users` เคยกันไว้ที่ `FULL_ADMIN` อย่างเดียวทั้งที่
  sidebar ของ FACULTY_ADMIN และ DEPT_ADMIN มีรายการนี้ (docs/05 A11) ตอนนี้
  `backend/routes/users.js` รับทั้งสามบทบาทแล้วกรองด้วยขอบเขตแทน เมนูกับสิทธิ์จึงตรงกัน

## สิ่งที่ยังไม่ปิดใน #11

1. **นำเข้าเป็น CSV ไม่ใช่ `.xlsx`** — ตั๋วเขียนว่า "spreadsheet" ระบบเดิมใช้ `xlsx@0.18.5` ซึ่งยังมี
   ช่องโหว่ prototype-pollution และ ReDoS ที่ไม่มี patch ตัวอ่าน CSV ที่เขียนเองตอบเกณฑ์ได้ครบทุกข้อ
   โดยไม่ต้องเพิ่ม dependency และรูปของ endpoint ไม่เปลี่ยนถ้าภายหลังต้องรับ `.xlsx` จริง
   แบบฟอร์มมี BOM เพื่อให้ Excel เปิดภาษาไทยได้ตรง
2. **การให้/ถอนบทบาทหลังสร้างบัญชีเป็นของ #12** — หน้าจอนี้ให้บทบาทแรกพร้อมบัญชี เพราะเกณฑ์ข้อ 2
   เรียกร้องว่าเข้าใช้ได้ทันที การแก้ไขจึงส่งเฉพาะข้อมูลส่วนตัว ไม่ส่งบทบาท
3. **ยังไม่มีการรีเซ็ตรหัสผ่านโดยผู้ดูแล** — ตั๋วนี้ไม่ได้ขอ และ #10 ให้เจ้าของบัญชีเปลี่ยนเองได้แล้ว
   ถ้าต้องการให้ผู้ดูแลตั้งใหม่ให้คนที่ลืมรหัส ต้องเปิดตั๋ว
4. **ช่องขอบเขตของบทบาทเป็นการพิมพ์รหัสเอง** — ฟอร์มยังไม่มี dropdown ของภาควิชา/หลักสูตร
   เพราะหน้าจอที่จัดการสองสิ่งนั้นคือ #14 และ #15 ซึ่งยังไม่ถึง server ปฏิเสธรหัสที่ไม่มีจริงอยู่แล้ว —
   **ปิดแล้วใน #12** ทั้งสองช่องเป็น dropdown ที่ `GET /api/users/grantable` เป็นคนตอบ
5. **บัญชีที่ถูกระงับกลางทางเห็นแถบแดงแทนกล่องเข้าสู่ระบบใหม่** — `sessionAdmission` ตรวจสถานะและ
   ช่วงเวลาทุก request จึงตัดสิทธิ์ทันทีไม่ต้องรอ cookie หมดอายุ แต่ตอบ 403 ซึ่ง
   `frontend/src/api/client.js` ส่งต่อให้กล่อง *Session หมดอายุ* เฉพาะ 401 คนที่ถูกระงับระหว่างใช้งาน
   จึงเห็นข้อความปฏิเสธในหน้าเดิมแทนที่จะถูกพากลับไปหน้าเข้าสู่ระบบ — เปิดเป็น #52 แล้ว
6. **`coveredScopes` ถูกคำนวณซ้ำหลายครั้งต่อหนึ่ง request** — `placeAllowed` และ `assignable`
   ต่างเรียก `reachOf` เอง การนำเข้าจึงยิงสองคิวรีต่อหนึ่งแถว ไฟล์ร้อยแถวคือสองร้อยคิวรีที่ตอบเหมือนกันทุกครั้ง
   ควรคำนวณครั้งเดียวต่อ request — **ปิดแล้วใน #12** โดย memoise ต่อ request ใน `backend/auth/administration.js`
7. **รายชื่อบทบาทถูกเขียนไว้สามที่** — ตาราง `roles.priority` ในฐานข้อมูล, `ADMIN_ROLES` ใน
   `backend/routes/users.js` และ `ROLES` ใน `frontend/src/components/users/UserForm.js`
   ถ้าเพิ่มบทบาทใหม่แล้วแก้ไม่ครบทั้งสามที่ จะไม่มีอะไรฟ้อง — **ปิดแล้วใน #12** `ROLES` ถูกถอดออก
   และฟอร์มถาม `GET /api/users/grantable` แทน เหลือสองที่คือฐานข้อมูลกับ `ADMIN_ROLES`
