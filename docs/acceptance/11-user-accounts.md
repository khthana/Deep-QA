## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`
เมนูที่ใช้ตลอดเอกสารนี้คือ *ข้อมูลผู้ใช้งาน* (`/main/users`)

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`cd db && npm run reset && npm run migrate && npm run seed` หลังเดินจบ** (`seed` เพียงอย่างเดียวเป็น upsert ไม่ลบแถวที่เกินมา) ก่อนเริ่มตั๋วถัดไป

แถว *มีผลกับ session ที่ค้างอยู่* เคยเป็น **◐** อยู่นาน และเหตุผลเป็นเรื่องของเบราว์เซอร์ ไม่ใช่ของกฎ —
สองแท็บใน Chrome โปรไฟล์เดียวใช้ cookie ก้อนเดียวกัน การลงชื่อเข้าใช้เป็น `admin@` ในแท็บที่สอง
จึงทับ session ที่กำลังจะทดสอบทิ้ง คนที่นั่งอยู่หน้าคีย์บอร์ดเดียวไม่มีทางถือสอง session พร้อมกันได้

`e2e/tests/11c-suspension-and-a-live-session.spec.js` ซึ่งเป็นของที่คนไม่มีแต่ Playwright มี
— cookie jar สองใบที่ไม่รู้จักกัน คือสิ่งที่แถวนี้เรียกว่า "แท็บ A" กับ "แท็บ B" จริง ๆ

สิ่งที่แถวนี้แยกออกจากกันคือ session ที่ถูกตรวจ **ครั้งเดียวตอนลงชื่อเข้าใช้** กับ session ที่ถูกตรวจ
**ทุก request** สองอย่างนี้หน้าตาเหมือนกันสนิทจนกว่าจะมีใครถูกระงับกลางคัน แล้วอย่างแรกจะปล่อยให้
cookie ใบนั้นทำงานต่อจนหมดอายุ — ครึ่งชั่วโมงที่บัญชีถูกระงับแล้วยังอ่านทะเบียนได้ ตัวที่ปิดช่องนั้นคือ
`sessionAdmission` ใน `backend/auth/accounts.js` ซึ่งเป็นสำเนา**คนละตัว**กับด่านที่ `admit` ตรวจ
ตอนลงชื่อเข้าใช้ แถวที่ว่าบัญชีถูกระงับเข้าระบบไม่ได้จึงไม่ได้พูดถึงแถวนี้เลยแม้แต่น้อย

การสั่งระงับในสเปกทำผ่านปุ่มของหน้าจอเอง ไม่ใช่ `PUT` ที่ตัวทดสอบยิงเอง — แถวนี้เป็นเรื่องของผู้ดูแล
ที่ระงับใครสักคน และการระงับที่ตัวทดสอบทำเองจะทิ้งปุ่มบนหน้าจอไว้โดยไม่มีใครพิสูจน์ ส่วนหน้าจอฝั่ง
ผู้ถูกระงับยังเป็นอย่างที่ [#52](https://github.com/khthana/Deep-QA/issues/52) เขียนไว้ คืออยู่กับ
หน้าเดิมพร้อมแถบแดง ไม่ถูกพากลับไปหน้าเข้าสู่ระบบ — ข้อ 5 ของ *สิ่งที่ยังไม่ปิดใน #11* ข้างล่างว่าไว้แล้ว
ว่าทำไม และสเปกนี้ไม่ได้ผูกกับพฤติกรรมนั้น จึงไม่ต้องแก้เมื่อ #52 ถูกปิด

  เรื่องของหน้าตา จึงอยู่นอกขอบเขตที่ #65 กำหนดไว้ ไม่มีครึ่งไหนที่ browser seam จะเพิ่มอะไรให้

ครึ่งที่ browser seam รับไปของแถวข้อ 8 สองแถวแรก คือ *บัญชีไหนปรากฏในตาราง* ซึ่งเป็นการปฏิเสธ
ที่ไม่ทิ้งแถบแดงไว้ให้เห็นเลย มีแต่แถวที่หายไป — เป็นแถวที่คนเดินด้วยมือจับได้ยากที่สุด สเปกจึงค้น
ด้วยช่องค้นหาของหน้าจอเอง เพราะสิบบัญชีใน seed กับหน้าละสิบแถวแปลว่าอ่านจากหน้าแรกหน้าเดียวไม่ได้

สี่ข้อที่ mutation test เปิดออกมา และควรอ่านคู่กับแถวข้างบน

- **ช่วงเวลาที่กลับด้านถูกกันสองชั้น** — กลับเครื่องหมายเปรียบเทียบ `from.value > until.value` ใน `backend/routes/users.js` แล้วแถวนั้นยังถูกปฏิเสธอยู่ดี เพราะ CHECK constraint ของตารางรับต่อผ่าน `23514` → `invalidValidity` ต้องทำลายทั้งสองที่เดียวแถวจึงจะหลุด — แปลว่าข้อห้ามนี้มีของจริงสองชั้น ไม่ใช่ข้อความที่เขียนทิ้งไว้เฉย ๆ
- **รายงานทุกบรรทัดพร้อมกัน** — เปลี่ยน `continue` เป็น `break` ใน `backend/lib/importer.js` ทำให้แถวที่รายงานเหลือแค่บรรทัดแรก และ spec จับได้ทันที
- **ด่านของ session ที่ค้างอยู่เป็นคนละตัวกับด่านตอนลงชื่อเข้าใช้** — `11-12:M8` ตัดบรรทัด `if (user.status !== 'active')` ออกจาก `sessionAdmission` เท่านั้น (ผูกกับบรรทัด `unknown` ที่อยู่เหนือมัน เพราะสำเนาทั้งสองเขียนเหมือนกันทุกตัวอักษร) แล้ว `11c` ตายที่บรรทัด 109 คือ `/api/me` ตอบ `200` ทั้งที่บัญชีถูกระงับไปแล้ว ส่วนด่านตอนลงชื่อเข้าใช้ยังปฏิเสธตามปกติ — ซึ่งเป็นเหตุผลทั้งหมดที่แถวนี้ต้องมีสเปกของตัวเอง

- **ตัวเลขที่ฆ่าไม่ได้ไม่ใช่หลักฐาน** — `11b` กับ `14b` เคยอ่านจำนวนแถวหลังการนำเข้าที่ถูกปฏิเสธไว้สี่จุด `ImportPanel` เรียก `onImported` เฉพาะตอนสำเร็จ รายการจึงไม่ถูกดึงใหม่หลังการปฏิเสธ ตัวเลขบนหน้าจอคือตัวเลขก่อนอัปโหลด ไม่ว่า server จะทำอะไรกับไฟล์ สองในสี่จุดยิ่งกว่านั้น คืออ่านหลังไฟล์เปล่าซึ่งไม่มีแถวให้เขียนอยู่แล้ว ทั้งสี่จุดถูก**ลบทิ้ง**พร้อมคอมเมนต์ว่าข้ออ้างนั้นพิสูจน์อยู่ที่ไหน (#64) ที่พิสูจน์จริงคือแถวก่อนหน้าในไฟล์เดียวกัน — `11b` บรรทัด 131 และ `14b` บรรทัด 124 — ซึ่ง `reload` แล้วเปิดรายการใหม่แล้วจึง poll ตัวเลขที่มาจาก server หลังอัปโหลด `11-12:M9` เปลี่ยน `ROLLBACK` เป็น `COMMIT` ใน `backend/lib/importer.js` แล้วสองแถวนั้นตายทั้งคู่ (ได้ 7 ที่ควรเป็น 6) และเป็นแถวที่ล้ม*ก่อน*แถวอื่นในไฟล์ของตัวเอง ซึ่งคือสิ่งที่กติกาต้องการ คือ assertion ใหม่ล้ม ไม่ใช่ assertion ที่อยู่ก่อนหน้า สองไฟล์นี้เป็น `mode: 'serial'` แถวที่อยู่หลังแถวที่ล้มจึงถูกข้าม ไม่ได้รัน รอบนี้จึงไม่ได้บอกอะไรเกี่ยวกับแถวเหล่านั้น มัตแตนต์ตัวเดียวคุมการนำเข้าของทุกหน้าจอ เพราะ `importer.js` ตัดสินใจ rollback ที่ `errors.length > 0` ที่เดียว — และนั่นคือเหตุผลที่จุดที่ห้า คือไฟล์ที่แถวชนกันเอง ถ้าใส่ assertion ใหม่เข้าไปก็จะพิสูจน์ของเดิมซ้ำ ไม่ได้อะไรเพิ่ม

อีกข้อหนึ่งที่คนอ่านภายหลังควรรู้ แถว *ไม่เห็นคนของภาควิชาอื่น* ใช้ `dept.admin.01@` เป็นตัวแทน ซึ่งทำหน้าที่สองอย่างพร้อมกัน คือทั้ง *คนของภาควิชาอื่น* และ *ผู้ดูแลระดับเดียวกัน* เพราะ seed ไม่มีคนธรรมดาของภาควิชา 01 อยู่เลย แถวนี้จึงผ่านด้วยบัญชีที่แข็งที่สุดเท่าที่มี ไม่ใช่ด้วยคนธรรมดาของภาควิชานั้น

ไม่ใช่ช่องโหว่ เพราะบรรทัดที่ผลิตมันมีอยู่บรรทัดเดียว แต่เป็นตัวเลขที่ควรรู้ก่อนแก้บรรทัดนั้น

## ปีในช่วงเวลาใช้งานอยู่คนละศักราช — #125 (9 ก.ย. 2569)

`2569-09-30` เป็นวันที่ ISO ที่ถูกรูปแบบ `Date` รับ และถูกเก็บเป็นปี 2569 **ค.ศ.**
`readDate` ตรวจ**รูปร่าง**ของวันที่ และเขียน docstring ไว้เองว่าทำไมถึงปฏิเสธ `01/03/2026`
แต่ความผิดพลาดนี้อยู่ที่**ความหมาย** ไม่ใช่รูปร่าง — **ด่านที่ตรวจรูปแบบมองไม่เห็นความผิดพลาดเรื่องศักราช**

เจ้าของข้อกำหนดเลือกข้อสองจากสามข้อที่ตั๋วเสนอเมื่อ 9 ก.ย. 2569 — **ปฏิเสธ แล้วทดเลขให้ในประโยค**
ช่วงที่รับคือ ค.ศ. 1900–2200 ซึ่งกว้างจนไม่มีช่วงเวลาจริงเข้าใกล้ปลายทั้งสองข้าง
มันไม่ได้มีไว้เดาว่าระบบนี้จะอยู่ถึงเมื่อไร แต่มีไว้ให้ปีพุทธศักราชตกออกไป

### สองประโยค ไม่ใช่ประโยคเดียวที่มีรู

`validityEra` ทดเลขให้ (`ปี 2569 … ให้ใช้ ค.ศ. 2026 แทน`) ส่วน `validityYearRange` บอกช่วง
ปีจะได้ประโยคแรกก็ต่อเมื่ออ่านแบบ พ.ศ. แล้วตกลงมาอยู่ในช่วงพอดี เพราะการบอกคนที่พิมพ์ `1500`
ว่าให้กรอก `957` แย่กว่าการไม่บอกอะไรเลย มัตแตนต์ `alwaysoffersconversion` คือการรวมสองประโยคเป็นหนึ่ง
ซึ่งเป็นความผิดพลาดที่น่าทำกว่า เพราะโค้ดน้อยกว่าและอ่านแล้วเป็นมิตรกว่า

### ประโยคที่เป็นฟังก์ชัน กับสองจุดที่เคยอ่านมันเป็นคีย์

ประโยคที่เอ่ยถึงปีที่คนพิมพ์มา เป็นค่าคงที่ไม่ได้ มันจึงเป็น**ฟังก์ชัน**ใน `REFUSALS`
เหมือนอีกยี่สิบตัวที่มีอยู่ก่อนแล้ว (นับเมื่อ 9 ก.ย. 2569 — หลังตั๋วนี้เป็นยี่สิบสอง) แต่ route ทั้งสองเส้นเขียนว่า `REFUSALS[draft.reason]` —
ซึ่งยื่น**ฟังก์ชัน**ให้ `res.json` แล้ว `JSON.stringify` ทิ้งมันไปเงียบ ๆ **คนกรอกฟอร์มจะถูกปฏิเสธ
โดยไม่มีข้อความอะไรเลย** `sentenceOf` ของ `lib/importer.js` (มีมาตั้งแต่ #26 เพราะการนำเข้ามีคำปฏิเสธ
ชนิดนี้ก่อนใคร) จึงย้ายไปอยู่ใน `auth/refusals.js` และทั้งสองเส้นอ่านมันแทน

**เส้นแก้ไขไม่เคยมีแถวของตัวเอง** ทั้งที่การต่อรอบให้ผู้ประเมินคือสิ่งที่เกิดขึ้นจริงกับช่วงเวลาหนึ่ง ๆ
`editsentenceisakey` มีไว้เพราะเรื่องนี้ ถ้าไม่มีแถวนั้น มันจะฆ่าอะไรไม่ได้เลย

### สิ่งที่มัตแตนต์ในใบนี้พูดไม่ได้

**ไม่มีอะไรพิสูจน์ `valid_until` แยกจาก `valid_from`** เพราะปลายทั้งสองข้างอ่านด้วยการเรียกฟังก์ชัน
เดียวกันสองครั้ง มัตแตนต์ที่กันข้างเดียวจึงเขียนไม่ได้ — เป็นคำตอบข้อสองในสามข้อของ #101
(*เอื้อมไม่ถึงโดยโครงสร้าง*) ไม่ใช่ช่องโหว่ แถวที่ยืนยันศักราชใน `valid_until` ยังคุ้มที่จะมี
เพราะมันเป็นคำกล่าวว่า `readAccount` เรียก `readDate` สองครั้ง ซึ่งการแก้ครั้งหลังเอาออกได้

## สิ่งที่ยังไม่ปิดใน #11

1. **นำเข้าเป็น CSV ไม่ใช่ `.xlsx`** — ตั๋วเขียนว่า "spreadsheet" ระบบเดิมใช้ `xlsx@0.18.5` ซึ่งยังมี
   ช่องโหว่ prototype-pollution และ ReDoS ที่ไม่มี patch ตัวอ่าน CSV ที่เขียนเองตอบเกณฑ์ได้ครบทุกข้อ
   โดยไม่ต้องเพิ่ม dependency และรูปของ endpoint ไม่เปลี่ยนถ้าภายหลังต้องรับ `.xlsx` จริง
   แบบฟอร์มมี BOM เพื่อให้ Excel เปิดภาษาไทยได้ตรง
2. **การให้/ถอนบทบาทหลังสร้างบัญชีเป็นของ #12** — หน้าจอนี้ให้บทบาทแรกพร้อมบัญชี เพราะเกณฑ์ข้อ 2
   เรียกร้องว่าเข้าใช้ได้ทันที การแก้ไขจึงส่งเฉพาะข้อมูลส่วนตัว ไม่ส่งบทบาท
3. **ยังไม่มีการรีเซ็ตรหัสผ่านโดยผู้ดูแล** — ตั๋วนี้ไม่ได้ขอ และ #10 ให้เจ้าของบัญชีเปลี่ยนเองได้แล้ว
   ถ้าต้องการให้ผู้ดูแลตั้งใหม่ให้คนที่ลืมรหัส ต้องเปิดตั๋ว
4. **ช่องขอบเขตของบทบาทเป็นการพิมพ์รหัสเอง** — ฟอร์มยังไม่มี dropdown ของภาควิชา/หลักสูตร
   เพราะหน้าจอที่จัดการสองสิ่งนั้นคือ #14 และ #15 ซึ่งยังไม่ถึง server ปฏิเสธรหัสที่ไม่มีจริงอยู่แล้ว —
   **ปิดแล้วใน #12** ทั้งสองช่องเป็น dropdown ที่ `GET /api/users/grantable` เป็นคนตอบ
5. **บัญชีที่ถูกระงับกลางทางเห็นแถบแดงแทนกล่องเข้าสู่ระบบใหม่** — `sessionAdmission` ตรวจสถานะและ
   ช่วงเวลาทุก request จึงตัดสิทธิ์ทันทีไม่ต้องรอ cookie หมดอายุ แต่ตอบ 403 ซึ่ง
   `frontend/src/api/client.js` ส่งต่อให้กล่อง *Session หมดอายุ* เฉพาะ 401 คนที่ถูกระงับระหว่างใช้งาน
   จึงเห็นข้อความปฏิเสธในหน้าเดิมแทนที่จะถูกพากลับไปหน้าเข้าสู่ระบบ — เปิดเป็น #52 แล้ว
6. **`coveredScopes` ถูกคำนวณซ้ำหลายครั้งต่อหนึ่ง request** — `placeAllowed` และ `assignable`
   ต่างเรียก `reachOf` เอง การนำเข้าจึงยิงสองคิวรีต่อหนึ่งแถว ไฟล์ร้อยแถวคือสองร้อยคิวรีที่ตอบเหมือนกันทุกครั้ง
   ควรคำนวณครั้งเดียวต่อ request — **ปิดแล้วใน #12** โดย memoise ต่อ request ใน `backend/auth/administration.js`
7. **รายชื่อบทบาทถูกเขียนไว้สามที่** — ตาราง `roles.priority` ในฐานข้อมูล, `ADMIN_ROLES` ใน
   `backend/routes/users.js` และ `ROLES` ใน `frontend/src/components/users/UserForm.js`
   ถ้าเพิ่มบทบาทใหม่แล้วแก้ไม่ครบทั้งสามที่ จะไม่มีอะไรฟ้อง — **ปิดแล้วใน #12** `ROLES` ถูกถอดออก
   และฟอร์มถาม `GET /api/users/grantable` แทน เหลือสองที่คือฐานข้อมูลกับ `ADMIN_ROLES`
