## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`

## รายการที่ต้องเดิน

ช่องสุดท้ายมีสี่ค่า

- **☑** เดินจบแล้ว
- **◐** เดินไปได้ครึ่งเดียว อีกครึ่งยังไม่ได้เดิน — **แถวนั้นบอกไว้เองว่าครึ่งไหนยังขาด และครึ่งนั้นรออะไร** · ส่วนใหญ่ครึ่งที่เดินแล้วคือครึ่งของ server และครึ่งที่เหลือคือสิ่งที่หน้าจอวาด (แถบสี ตาราง dropdown) ซึ่งยังต้องมีคนดู — **แต่นั่นเป็นกรณีที่พบบ่อย ไม่ใช่นิยาม** ครึ่งที่เหลือรออยู่สามอย่าง คือ **คน** (เช่น attribute ที่ไปถึง DOM แล้ว แต่ยังไม่มีใครเปิดโปรแกรมอ่านหน้าจอฟัง) · **ตั๋ว** ซึ่งแถวจะอ้างเลขไว้ · หรือ **ไม่รออะไรเลย** เพราะไม่มีตัวควบคุมบนจอสร้างคำขอนั้นได้ ซึ่งเป็น ◐ ถาวรโดยโครงสร้าง — **สามอย่างนี้นับแยกกัน** (`CLAUDE.md` §Marks on the sheets · [#157](https://github.com/khthana/Deep-QA/issues/157))
- **☐** ยังไม่ได้เดิน
- **⚙** ครอบคลุมด้วย browser seam แล้ว (#65) ไม่ต้องเดินด้วยมือซ้ำ แถวบอกไฟล์ที่ครอบคลุมไว้ ถ้าแถวนั้นพูดถึงสิ่งที่วาดด้วย (เมนู ถ้อยคำ สี) ครึ่งนั้นยังเป็นงานของคนเดิน และแถวจะเขียนกำกับไว้

## สิ่งที่ #94 แลกมา และคนเดินควรรู้ก่อน

เดินด้วยมือแล้วเมื่อ **23 ส.ค. 2569** ด้วย `dept.admin.05@` บนแท็บที่ทิ้งไว้ **31 นาทีจริง** ไม่ใช่
cookie ปลอม สิ่งที่การเดินนั้นยืนยัน และไม่มีชุดทดสอบใดยืนยันแทนได้ คือลำดับสามขั้นของคนที่กลับมา
หลังลุกไปครึ่งชั่วโมง — กล่องขึ้น, F5 แล้วได้กล่อง*อีกครั้ง*ซึ่งถูกแล้ว, F5 อีกทีกล่องหายและกรอกอีเมล
ได้จริง — บวกกับการที่ `user_log` มีแต่บรรทัด `LOGIN` และไม่มี `LOGOUT` เลย ตรงกับที่หัวข้อข้างล่าง
อธิบายไว้ ข้อที่เดินไม่สำเร็จคือข้อสองหน้าต่าง ซึ่งอธิบายไว้ด้านล่างว่าทำไมและไปอยู่ที่ไหนแทน

**กล่องยังขึ้นหนึ่งครั้งเสมอ และนั่นถูกแล้ว** เกณฑ์ข้อ 6 คือ session ที่จบต้อง *บอก* ไม่ใช่เงียบ
สิ่งที่ #94 เปลี่ยนคือครั้งที่ *สอง* ไม่ใช่ครั้งแรก คนที่กลับมาแล้วกดเมนูก่อน จะเห็นกล่องจากคำขอของ
หน้าจอนั้น (401 จาก `/api/programs` ไม่ใช่จาก `/api/me`) แล้วกด F5 จะเห็นกล่องอีกครั้งหนึ่ง —
เพราะ F5 ครั้งนั้นเป็นครั้งแรกที่ `/api/me` ถูกถาม — แล้วครั้งถัดไปจึงถึงหน้าลงชื่อเข้าใช้ เห็นสองครั้ง
คือพฤติกรรมที่ถูก ไม่ใช่การแก้ที่ล้มเหลว

**สองหน้าต่าง — และคำว่า "แท็บ" ในเอกสารฉบับก่อนทำให้เดินผิด** ถ้าเปิดค้างไว้สองหน้าต่าง
หน้าต่างที่โหลดก่อนคือหน้าต่างที่ได้ยินข่าว และเป็นหน้าต่างที่ทำให้ cookie หายไป อีกหน้าต่างที่โหลด
ตามมาจะได้ `anonymous` แล้วลงเอยที่หน้าลงชื่อเข้าใช้โดยไม่มีกล่อง นี่คือราคาที่จ่ายและจ่ายโดยตั้งใจ —
ของเดิมคือทั้งสองหน้าต่างติดอยู่ในกล่องเดียวกันครึ่งชั่วโมงโดยไม่มีทางออก การถูกพาไปหน้าลงชื่อเข้าใช้
ที่กรอกได้จริงนั้นแย่กว่าน้อยกว่ามาก

**เงื่อนไขจริงคือ cookie jar ใบเดียวกัน ไม่ใช่จำนวนหน้าต่าง** ข้อนี้ทำให้การเดินด้วยมือเมื่อ
23 ส.ค. 2569 พลาดไปหนึ่งข้อ คนเดินเปิด browser คนละตัวแทนที่จะเปิดหน้าต่างที่สองของตัวเดิม
(เพราะไม่ชอบเปิดแท็บ กลัวปิดพร้อมกันหมด) browser ตัวที่สองจึงมี cookie ของตัวเอง ไม่มีอะไรที่
ตัวแรกทำจะแตะมันได้ และมันทำงานต่อได้อย่างถูกต้องทุกประการ — ซึ่ง *ไม่ใช่* การพิสูจน์แถวนี้ และก็
ไม่ใช่การล้มด้วย แถวนี้จึงถูกย้ายไปอยู่กับ seam แทน เพราะข้ออ้างของมันเป็นพฤติกรรมล้วน ๆ ไม่มี

**บรรทัด `LOGOUT` ในประวัติ** คนที่กด *เข้าสู่ระบบใหม่* **หลังจาก**โหลดหน้าไปแล้วหนึ่งครั้ง จะยิง

## heartbeat ของคนที่กำลังทำงาน — #99 (22 ก.ย. 2569)

ตั๋วเขียนว่า token *ไม่ต่ออายุเมื่อมีการใช้งาน* ซึ่ง**ไม่เคยจริง** การต่ออายุอยู่มาตั้งแต่ `d368652`
ก่อนตั๋วเปิดแปดวัน สิ่งที่จริงคือมันต่อเฉพาะเมื่อมี**คำขอ**เข้ามาในสิบนาทีสุดท้ายของ token คำขอที่นาทีที่
สิบเก้าจึงไม่ต่ออะไรและเหลือสิบเอ็ดนาที และ**การพิมพ์ไม่ใช่คำขอ** — ฟอร์มเกณฑ์สี่ระดับที่เขียนในสิบเอ็ด
นาทีนั้นถูกบันทึกลง session ที่หมดแล้ว ซึ่งคืออาการที่ตั๋วรายงานไว้ คอมเมนต์ที่ `session.js` กับแถวที่
`auth.test.js` เขียนว่า *คนที่ลุกไปหมดอายุสามสิบนาทีหลังคำขอสุดท้าย* ก็ไม่จริงเช่นกัน ของจริงคือสิบถึง
สามสิบนาที แก้ทั้งสองที่แล้ว

คำตอบ (22 ก.ย. 2569) บันทึกไว้ที่ [ADR-0005](../adr/0005-session-renews-on-work-not-on-requests.md):
**การกดปุ่มหรือคลิกนับเป็นการทำงาน** shell ส่ง `POST /api/me/activity` เมื่อมีการกด ห่างกันอย่างน้อย
ห้านาที route ไม่ทำอะไร การต่ออายุเป็นของ `requireSession` ที่เกณฑ์เดิม **สิบลบห้าคือช่วงที่คนทำงาน
หยุดกดได้โดยไม่ถูกเด้งออก** — ไม่หยุดนานถึงห้านาที heartbeat ก็ห่างกันไม่ถึงสิบ และมีอันหนึ่งตกในสิบนาที
สุดท้ายของ token เสมอ **ไม่มีเพดานอายุ** และไม่มีอะไรส่งตามนาฬิกา คนที่ไม่กดอะไรจึงหมดอายุเหมือนเดิม

ผู้รีวิวเจอทางเข้าใหม่สู่ #51 ที่ heartbeat เปิดไว้: **การคลิกที่ส่ง heartbeat อาจเป็นการคลิกออกจากระบบ
หรือสลับบทบาทเอง** คำตอบของมันอาจมีคุกกี้ที่ต่ออายุแล้ว มาถึงหลังการออกจากระบบก็พาเบราว์เซอร์กลับเข้า
มาถึงหลังการสลับก็เอาบทบาทเก่ากลับ `logout` กับ `switchRole` จึงรอ heartbeat ที่ยังค้างอยู่ก่อนส่งอะไร
รีวิวรอบสองเจอทางที่สาม: การออกจากระบบของ listener เมื่อบัญชีถูกจบ (#52) — `requireSession` ต่ออายุก่อน
`attachRoles` ปฏิเสธ heartbeat ที่**ถูกปฏิเสธ**จึงยังพาคุกกี้กลับมาได้ listener จึงรอด้วย สามทางนี้คือทุกที่
ในเบราว์เซอร์ที่เขียนหรือลบคุกกี้ระหว่างที่มีคนลงชื่อเข้าอยู่ (หาด้วย grep `issueSession` `clearSession`
แล้วตามผู้เรียก route ของมัน) แถวห้าถึงเจ็ดกั้น heartbeat ไว้ที่ route แล้วถามว่ายังไม่มีอะไรออกไป

แถวเหล่านั้น**วัดลำดับ** ส่วน *คุกกี้ที่ต่ออายุมาถึงทีหลังจะพากลับเข้า* เป็น**เหตุผล ไม่ใช่การวัด**
heartbeat ที่ถูกกั้นถูกตอบที่ route โดยไม่มีคุกกี้ และสิ่งที่ปิดคือ*การคลิกเดียวกัน* ไม่ใช่ heartbeat จาก
ปุ่มที่กด*ระหว่าง*ที่การออกหรือการสลับยังไม่กลับ ซึ่งคือ race ของ #51 แบบเดียวกับการบันทึก ปล่อยไว้กับ #51

ทุกแถว **เดินด้วยมือไม่ได้** ไม่มีใครรอสามสิบนาทีจริงได้ แถว browser ขยับนาฬิกาของหน้าด้วย
`page.clock` ส่วนนาฬิกาของ server ไม่ขยับ token จึงสดอยู่ และทุก heartbeat ในแถวเหล่านั้นถูกตอบ 204
โดยไม่ต่ออายุ นาฬิกาห้านาทีเริ่มตอน session เริ่ม ไม่ใช่ตอน heartbeat ล่าสุด เพราะการเข้าระบบกับการอ่าน
ที่ตามมาเป็นคำขออยู่แล้ว แถว HTTP เซ็น token ที่อายุเหลือตามที่ต้องการ แบบเดียวกับแถวเดิมของ #8 และ #10
จุดอ่านของแถว browser คือหลังการกด 250 ms อ่านจำนวนครั้งเดียว (#50) สิ่งที่เขียนลงฐานข้อมูลมีแค่
`user_log` เหมือนทุกไฟล์ที่ลงชื่อเข้า: `LOGIN` ทุกแถว และ `SWITCH_ROLE` ที่แถวหก ไม่มีใครล้างตารางนั้น

## การต่ออายุที่ข้ามการสลับบทบาท — #51 (23 ก.ย. 2569)

ข้อ 3 ของ *สิ่งที่ยังไม่ปิดใน #10* ข้างบน `requireSession` ต่ออายุ token ที่เหลือไม่ถึงสิบนาที และ
พา*การเลือก*ในนั้นไปด้วย ซึ่งจำเป็น ไม่งั้นคนที่ทำงานยาวข้ามนาทีที่ยี่สิบจะถูกดีดกลับไปบทบาทอาวุโสสุด
เงียบ ๆ แต่การเลือกที่มันพาไปคือการเลือกใน token *ของคำขอนั้น* คือการเลือก ณ ตอนที่คำขอออกจาก
เบราว์เซอร์ คำขอที่ยังค้างตอนคนสลับบทบาทจึงเขียนคุกกี้ทีหลังคุกกี้ของการสลับ คนเขียนทีหลังชนะ และ
เบราว์เซอร์กลับไปสวมหมวกที่ตัวเลือกบนจอไม่แสดงแล้ว — ความไม่ตรงกันที่เกณฑ์ข้อสี่มีไว้กัน มาจากด้าน
ที่ลำดับใน `PUT /api/me/acting-role` เอื้อมไม่ถึง #99 ทำให้ช่องนี้กว้างขึ้น เพราะ heartbeat คือคำขอ
ที่คนไม่รู้ตัวว่าส่ง

คำตอบบันทึกไว้ที่ [ADR-0006](../adr/0006-a-renewal-cannot-carry-a-superseded-grant.md):
**บัญชีนับการสลับของตัวเอง และการต่ออายุต้องนับตรงกัน** `users.acting_epoch` (migration 0008)
การสลับบวกหนึ่ง**ก่อน**ออกคุกกี้ของตัวเอง แล้วประทับเลขใหม่ลง token ทุก token พาเลขนี้ไปด้วย
การต่ออายุอ่านเลขของบัญชีมาเทียบ ตรงก็ออกคุกกี้เหมือนเดิม ไม่ตรงก็**ไม่เขียนคุกกี้เลย** — ไม่ใช่เขียน
คุกกี้ที่ไม่มี `acting` ซึ่งจะเป็นความไม่ตรงกันอันเดิมจากอีกด้าน คำขอนั้นยังถูกตอบตามหมวกที่มันถือมา

**ราคาที่ ADR-0006 เขียนไว้:** ตัวนับอยู่บนบัญชี ไม่ใช่บนคุกกี้ เครื่องที่สองของคนเดียวกันจึงหยุด
ต่ออายุหลังการสลับที่เครื่องแรก และหมดอายุเมื่อครบครึ่งชั่วโมงของมัน การแยกคุกกี้สองใบของบัญชีเดียว
ต้องมีตัวระบุราย session ซึ่งเป็นสิ่งที่ JWT ตั้งใจมาแทน — ใหญ่กว่าที่ #51 เปิดไว้ จึงเขียนไว้ให้หา
เจอแทนที่จะแก้เงียบ ๆ

**ข้อ 5 ของรายการข้างบนยังเปิดอยู่** สองแท็บที่ไม่ตรงกันเป็นอาการเดียวกันคนละเหตุ: อันนั้นคือ
*การวาดที่เก่า* อันนี้คือ*คุกกี้ที่เก่า* ตัวนับไม่ได้แตะการวาด

### สิ่งที่แต่ละ seam พูดได้

แถว browser เป็นเรื่องของ**ถังคุกกี้** ซึ่งเป็นที่ที่ *คนเขียนทีหลังชนะ* เกิดขึ้นจริง และเป็นครึ่งที่
seam HTTP ได้แต่ให้เหตุผล และมันสร้าง**คำขอที่เก่าเอง**ได้ด้วย: คำขอที่ `gate` กั้นไว้ที่ route ถือ
header ชุดที่มันถูกส่งออกไป — token ใบก่อนการสลับรวมอยู่ในนั้น — และตอนปล่อย มันเล่นซ้ำ header ชุดนั้น
แถวแรกจึงเป็นการสลับซ้อนการอ่านแบบที่คนทำได้จริง ตั้งแต่ต้นจนจบ

สิ่งที่แถวนั้นต้องระวังคือ**จังหวะที่ย่นอายุ session**: คำขออะไรก็ได้ที่ออกไปหลังจากนั้นจะต่ออายุให้
แล้วคำขอที่ถูกกั้นก็จะถือ token ใบสด ซึ่งไม่เก่าและไม่พิสูจน์อะไร — ฉบับแรกของแถวนี้เป็นแบบนั้น
และผ่าน `51:noguard` ไปได้ แถวจึงรอให้หน้าแรกวาดเสร็จก่อน แล้วย่นอายุ แล้วให้การอ่านที่มันกั้นเป็น
สิ่งถัดไปที่ออกจากเบราว์เซอร์ — และ **assert เงื่อนไขนั้นไว้เอง** ว่า token ที่คำขอถือออกไปเหลือ
ไม่ถึงสิบนาทีจริง และตัวนับยังเป็นของก่อนการสลับ

**สิ่งที่ทำให้คำขอหนึ่งเก่าคือ token ที่มันถือ ไม่ใช่จังหวะที่มันมาถึง** ในเบราว์เซอร์สถานะนั้นต้อง
จัดฉากขึ้นมา ที่ seam HTTP มันคือการเซ็น token ขึ้นมาใหม่สองบรรทัด ซึ่งคือแถว HTTP ทั้งห้า

อายุของ session ถูกย่อด้วยการเซ็นคุกกี้จริงใหม่ (`shortenSession`) แบบเดียวกับแถวหมดอายุของ `10a`
และด้วยเหตุผลเดียวกัน — `LIFETIME_SECONDS` ไม่มีที่ให้ย่อ และไม่มีอะไรอื่นพาเบราว์เซอร์ไปถึงเกณฑ์
ต่ออายุได้โดยไม่รอยี่สิบนาทีจริง ไฟล์ spec เขียนลงฐานข้อมูลแค่ `user_log` กับ `users.acting_epoch`

นี่คือแถวที่ต้องบอกว่าให้เดินอะไร**

### มัตแตนต์

`mutation/51-renewal-across-a-switch.py` **หกตัว** กวาดครั้งแรกเมื่อ 23 ก.ย. 2569 ทีละตัว —
baseline `51a-renewal-across-a-switch` **2 ผ่านทั้ง 2** `shell.test.js` **33 ผ่าน** · **หลัง #154 baseline เป็น 35 ผ่าน**
เพราะตั๋วนั้นเติมแถว HTTP มาสองแถว — ตัวเลขของสี่ตัวแรกข้างล่างวัดไว้ตอน baseline ยังเป็น 33
และไม่ได้วัดใหม่ เพราะแถวใหม่ทั้งสองไม่อยู่ในรายการที่มันฆ่า ส่วน `noguard` เปลี่ยน จึงกวาดซ้ำ
สิ่งที่ไม่หมดอายุคือ*ชื่อแถว* ข้างหลังตัวเลข

ชื่อ spec เขียนเต็มเมื่อ 24 ก.ย. 2569 — `51a` เฉย ๆ จับ `151a-failed-reload-keeps-the-list`
(6 แถว) ด้วยตั้งแต่ 22 ก.ย. ซึ่ง #154 เห็นแล้วแต่ไม่ได้แก้ **สองแถวข้างบนเป็นแถวของ `51a` เอง
ทั้งคู่** ไม่ได้รวมหกแถวนั้น ตรวจเมื่อ 24 ก.ย. 2569 ด้วยจำนวนแถว ไม่ได้กวาดใหม่ (#158)

* `nobump` (การสลับไม่ขยับตัวนับ) — browser **ล้ม 1 ผ่าน 1** ที่ *the hat in the browser after
  the read landed* · HTTP **ล้ม 2** ที่แถวหนึ่งกับแถวสี่
* `bumpafterissue` (ขยับหลังออกคุกกี้) — browser **ล้ม 2** ที่ *the switch counter the browser is
  carrying* และที่ *the token the browser holds after the request* เพราะคุกกี้ของการสลับเกิดมาพร้อม
  เลขเก่า · HTTP **ล้ม 2** ที่แถวสามกับสี่
* `switchkeepsold` (คุกกี้ของการสลับพาหมวกเดิม) — browser **ล้ม 2** ที่ `acting` ทั้งสองแถว ·
  HTTP **ล้ม 4** รวมสองแถวของ *switching role* ใน #10 ซึ่งเป็นข้ออ้างของมันจริง ๆ
* `neverrenew` (เทียบเป็นเท็จเสมอ) — browser **ล้ม 1 ผ่าน 1** ที่อายุของ token · HTTP **ล้ม 5**:
  แถวสามกับห้าของใบนี้ แถวของ #99 แถวของ #8 **นี่คือตัวควบคุมของทั้งใบ** การแก้ที่ทำให้ไม่มีใคร
  ต่ออายุเลยก็ผ่านทุกแถวที่เหลือ
* `noguard` (ลบการเทียบ คือโค้ดก่อน #51) — browser **ล้ม 1 ผ่าน 1** ที่ *the hat in the browser
  after the read landed*: คุกกี้ที่คำขอค้างเขียนทีหลังไม่มี `acting` เลย เบราว์เซอร์จึงกลับไปสวมหมวก
  อาวุโสสุดขณะที่ปุ่มบอก อาจารย์ผู้สอน — ความไม่ตรงกันของ #51 เห็นกับตาในถังคุกกี้ · HTTP **ล้ม 2**
  ที่แถวหนึ่งกับ**แถวเจ็ด** (กวาดซ้ำ 23 ก.ย. 2569 หลัง #154 เดิม **ล้ม 1** ตอนยังไม่มีแถวเจ็ด) ·
  แถว browser ที่สองไม่ตาย ซึ่งถูก มันเป็นแถวของการต่ออายุที่*ควร*เกิด
* `missingiszero` (อ่าน claim ที่ไม่มีว่าเป็นศูนย์ — #154) — HTTP **ล้ม 1** ที่แถวเจ็ดแถวเดียว ·
  browser **ไม่ฆ่าอะไรเลย** ซึ่งถูก: token ที่ไม่มีตัวนับไม่มีทางเกิดในเบราว์เซอร์ได้ server ตัวนี้
  ประทับตัวนับลงทุกใบที่มันเซ็น ทางเดียวที่จะได้มันคือเซ็นเอง ซึ่งมีแต่ seam HTTP ทำได้ · แถวหกไม่ตาย
  ก็ถูกเช่นกัน มันถามว่าคำขอ*ถูกตอบ* ไม่ใช่ว่าคุกกี้ถูกเขียน

อ่านจากชื่อ ไม่ใช่จากจำนวน · `10:guardedlogout` เขียนคำแทนที่ที่ mount `requireSession` ซึ่ง #51
ทำให้เป็น factory จึงถูกแก้และกวาดซ้ำบน `10a` (ล้มแถวเดิม *the box gets the person back in*
ที่ assertion ไม่ใช่ที่ timeout) และ `99:alwaysrenew` เรียก `issueSession` จึงถูกแก้และกวาดซ้ำ
บน `shell.test.js` (ล้ม *leaves a session with more than that alone* แถวเดิม)

**กวาดรอบสอง (23 ก.ย. 2569 เย็นวันเดียวกัน) หลังรีวิว** `renew()` เคยคืน `true`/`false` ที่ไม่มีใคร
อ่าน จึงถูกตัดทิ้ง ค่าคงที่ `COMPARE` ของใบนี้เปลี่ยนตาม และ `noguard` กับ `neverrenew` ถูกกวาดซ้ำ
ทั้งสอง seam — ฆ่าแถวเดิมที่ assertion เดิมทุกตัว · ตัวช่วยเซ็น token ที่ซ้ำกันสองตัวใน
`shell.test.js` (`tokenOf` ของ #99 กับ `aged` ของ #51) ถูกรวมเหลือตัวเดียว แล้วกวาด
`99:alwaysrenew` ซ้ำ — ยังฆ่าแถวเดิม

## #167 — กล่องที่ปิดแล้วยังจำรหัสที่พิมพ์ (28 กันยายน 2569)

การเดินด้วยมือของ [#47](https://github.com/khthana/Deep-QA/issues/47) เจออาการเดียวกันในสองกล่อง
แต่กลไกคนละอย่าง กล่องรูปเป็นคอมโพเนนต์: ถ้ามันถูกถอด `useState` จะล้างให้เอง
ส่วนกล่องเปลี่ยนรหัสผ่าน**ไม่ใช่คอมโพเนนต์** มันเขียนอยู่ใน `Navbar.js` ค่าที่พิมพ์อยู่ใน
`pwdData` ของ navbar และ navbar ไม่เคยถูกถอดด้วยสิ่งที่คนทำบนหน้าจอ — ไม่มี lifecycle
ให้พึ่ง ทางออกจึงต้องล้างเอง และ**ล้างตอนออก ไม่ใช่ตอนเข้า** ด้วยเหตุผลของ [#164](https://github.com/khthana/Deep-QA/issues/164):
`showChangePwd` คือสิ่งที่กล่องถูกวาดขึ้นมาจาก effect ที่ผูกกับการเปิดจึงทำงาน**หลัง**จากที่ช่องถูกวาดด้วยค่าเก่าไปแล้ว

### คำถามที่ตั๋วขอให้วัดก่อนแก้ และคำตอบที่วัดได้

ข้อ 2 ของตั๋วถามว่า `ContentMotionDIV` ซึ่งรับเฉพาะ `children/className/role/id`
ทำให้ `AnimatePresence` **ไม่มีอะนิเมชันขาออกที่จะจบได้เลยหรือเปล่า** คำตอบคือ **ไม่ใช่**
คอมโพเนนต์นั้นประกาศ `exit={{ opacity: 0, y: -4 }}` ของตัวเอง พร้อม tween 0.18 วินาที —
มีอะนิเมชันขาออก มันอิงกับเวลา และมันต้องการเฟรม นั่นคือเหตุผลที่แท็บซึ่งรายงาน
`visibilityState: "hidden"` ไม่เคยจบมัน — **แต่เลขนั้นวัดกับกล่องรูปโปรไฟล์ที่ #47 ไม่ใช่กล่องนี้**
ทั้งสองเป็นลูกของ `AnimatePresence` เดียวกันและห่อด้วย `ContentMotionDIV` เหมือนกัน กลไกจึงตัวเดียวกัน
