# ตรวจรับด้วยมือ — #10 Application shell, role switching and sidebar

`docs/06-implementation-plan.md` §Acceptance กำหนดว่า ticket หนึ่งจะเสร็จเมื่อ automated test ผ่าน
**และ** checklist ที่ทำด้วยมือถูกเดินจนครบ เอกสารนี้คือครึ่งหลังของ #10

เหตุที่ต้องมีครึ่งนี้: docs/06 §Testing Decisions ระบุว่า seam เดียวที่ทดสอบอัตโนมัติคือ HTTP surface
ของ backend และ **"Frontend components are not unit-tested"** เกณฑ์ที่มีส่วนที่มองเห็นได้ —
ข้อ 1, 2, 5 และครึ่งหนึ่งของข้อ 8 — จึงพิสูจน์ด้วยเทสต์ไม่ได้โดยการออกแบบ ไม่ใช่โดยการละเลย

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js`

## รายการที่ต้องเดิน

ช่องสุดท้ายมีสี่ค่า

- **☑** เดินจบแล้ว
- **◐** ครึ่งของ server เดินแล้วและผ่าน ส่วนที่เหลือคือสิ่งที่หน้าจอวาด (แถบสี ตาราง dropdown) ยังต้องมีคนดู
- **☐** ยังไม่ได้เดิน
- **⚙** ครอบคลุมด้วย browser seam แล้ว (#65) ไม่ต้องเดินด้วยมือซ้ำ แถวบอกไฟล์ที่ครอบคลุมไว้ ถ้าแถวนั้นพูดถึงสิ่งที่วาดด้วย (เมนู ถ้อยคำ สี) ครึ่งนั้นยังเป็นงานของคนเดิน และแถวจะเขียนกำกับไว้

| 7 | เปลี่ยนรหัสผ่านตัวเองได้ และใช้ได้ครั้งถัดไป | เข้าด้วย `teacher.two@` → เมนูผู้ใช้ → เปลี่ยนรหัสผ่าน → ออกจากระบบ → เข้าด้วยรหัสใหม่ | เข้าได้ด้วยรหัสใหม่, รหัสเดิมถูกปฏิเสธ (**อย่าลืม `npm run seed` ใหม่หลังทดสอบข้อนี้**) — ครอบคลุมโดย `e2e/tests/10a-shell.spec.js` (row 7) ซึ่งเปลี่ยนรหัสผ่านผ่านกล่องจริง ออกจากระบบผ่านปุ่มจริง แล้วลองรหัสเดิมได้ 401 *อีเมลหรือรหัสผ่านไม่ถูกต้อง* และยังอยู่ที่หน้า `/` จากนั้นเข้าด้วยรหัสใหม่ได้ แล้ว **เปลี่ยนกลับ** ก่อนจบเทสต์ เพราะทุก spec ในชุดนี้ใช้ schema ที่ seed ร่วมกัน | ⚙ |

## สิ่งที่ยังไม่ปิดใน #10

1. **เมนูของ EXT_ASSESSOR ยังไม่มีข้อกำหนดรองรับ** — `docs/01` ROLE-6 และ R005 พูดถึงเฉพาะว่า
   บัญชีนี้มีอายุจำกัด ไม่มีเอกสารฉบับใดระบุว่าผู้ประเมินภายนอกเห็นหน้าจอใด
   `frontend/src/components/SidebarItem/ExtAssessor.js` จึงใส่ไว้หนึ่งรายการเป็นที่วางชั่วคราว
   **เกณฑ์ข้อ 2 จึงผ่านเพียงบางส่วน** ชุดเมนูจริงเป็นการตัดสินใจของเจ้าของข้อกำหนด — ตั๋ว #49
2. ~~**`/main/users` กับสิทธิ์ที่ไม่ตรงกัน**~~ — **ปิดแล้วที่ #11** `backend/routes/users.js` รับทั้ง
   FULL_ADMIN, FACULTY_ADMIN และ DEPT_ADMIN ตาม `docs/05` A11 แล้วกรองรายชื่อด้วยขอบเขตของ
   ผู้เรียกแทน ดู `docs/acceptance/11-user-accounts.md` เกณฑ์ข้อ 8
3. **การต่ออายุ token ทับการสลับบทบาท** — ถ้า request ที่ค้างอยู่จบหลังการสลับ และตอนนั้นเหลือ
   อายุน้อยกว่า 10 นาที cookie ที่ต่ออายุจะพา `acting` ตัวเก่ากลับมา เป็น race ที่แคบ
   แต่แก้ไม่ได้ด้วยเทสต์ที่ seam เดียว — ตั๋ว #51
4. **หน้าจอเข้าสู่ระบบของ #8 ถูกสร้างขึ้นใน #10** — `Login.js`, `LoginForm.js`, `LoginGoogle.js`,
   `UserNotFound.js` และ `SelectApp.js` เป็นครึ่ง UI ของ #8 แต่เกิดในตั๋วนี้ #8 ปิดไปแล้ว
   เกณฑ์ฝั่งหน้าจอของมันจึงไม่มีตั๋วใดถือไว้ — ตั๋ว #50
5. **ไม่มีการปรับ acting ให้ตรงกันข้ามแท็บ** — สลับบทบาทในแท็บหนึ่ง แท็บที่เปิดค้างอีกแท็บยังวาด
   sidebar เดิมจนกว่าจะโหลดใหม่ server ไม่ได้ผิด (มันบังคับตาม cookie ล่าสุดเสมอ) แต่คนที่หน้าจอ
   เห็นเมนูที่ไม่ตรงกับสิ่งที่กดได้
6. **URL ของระบบ portfolio ฝังไว้ในโค้ด** — `https://portfolio.deep-core.net/teacher` อยู่ใน
   `Navbar.js:146` และ `SelectApp.js:411` ควรมาจาก environment เหมือน `REACT_APP_API_URL` (ฝากไว้ที่ #50)
7. **เส้นทางต่ออายุ token ยังไม่มีเทสต์** — `RENEW_BELOW_SECONDS` ไม่มีเทสต์ใดเดินผ่าน และเกณฑ์ข้อ 4
   ส่วนใหญ่พิสูจน์กับ `guardedApp` ที่เป็น route จำลอง มากกว่ากับ `/api/users` ที่ส่งมอบจริง
8. **โค้ดที่ไปไม่ถึง** — `Mainpage.js:321` มีสาขา `alert.messages` ที่ไม่มีใครตั้งค่าให้
   และ `/user-not-found` อ่าน `?reason` ได้แต่ไม่มีที่ใดพาไปที่นั่น (ข้อหลังฝากไว้ที่ #50)
9. **เกณฑ์ข้อ 6 ครึ่งที่ว่าด้วยการหมดอายุจริง ยังไปไม่ถึงจาก browser** — `cookieOptions()` ตั้ง
   `maxAge: LIFETIME_SECONDS * 1000` ซึ่งเท่ากับ `expiresIn: LIFETIME_SECONDS` ของ token พอดี
   browser จึงทิ้ง cookie ในวินาทีเดียวกับที่ token ตาย และ `requireSession` ไม่มีทางได้เห็น
   `TokenExpiredError` จากคนที่นั่งอยู่หน้าจอเลย ผลคือแท็บที่เปิดค้างข้ามครึ่งชั่วโมงแล้วโหลดใหม่
   **ถูกพากลับไปหน้า login เงียบ ๆ** ซึ่งเป็นสิ่งที่เกณฑ์ข้อ 6 ห้ามไว้ตรง ๆ และตรงข้ามกับที่
   `AuthContext.load()` เขียนกำกับตัวเองไว้ แถวที่สองของข้อ 6 จึงบรรยายผลลัพธ์ที่เกิดไม่ได้
   — ตั๋ว #69

## ที่มาของเครื่องหมาย ⚙

แถวเจ็ดแถวข้างบนถูกยกให้ browser seam ที่ #65 วางไว้ หกแถวอยู่ใน `e2e/tests/10a-shell.spec.js`
ที่เพิ่มเข้ามาพร้อมบันทึกนี้ อีกหนึ่ง (เกณฑ์ข้อ 8) ชี้ไปที่ spec ของ #11 ที่เดินแถวเดียวกันอยู่แล้ว —
แถวนั้นเป็น ⚙ ที่ยืมมา จึงถูกพิสูจน์ด้วยการกลายพันธุ์ของมันเองที่นี่ (`adminteacher`) ไม่ได้ติดเครื่องหมาย
เพียงเพราะ spec ของ #11 มีอยู่

ห้าแถวที่ยัง ☐ ยังเป็นงานของคนเดิน และไม่มีแถวใดใน `10a-shell.spec.js` ที่จะครอบคลุมได้:
เกณฑ์ข้อ 1, 2 และ 5 พูดถึงสิ่งที่หน้าจอ **วาด** — sidebar มีอะไรอยู่บ้าง breadcrumb อ่านว่าอะไร
เมนูของบทบาทหนึ่งมีของอีกบทบาทปนหรือไม่ — ซึ่ง seam ที่ assert เมนูจากรายการเดียวกับที่ใช้วาดเมนู
คือการเอาหน้าจอไปยันตัวเอง แถวข้อยกเว้นของข้อ 2 ยังติดคำถามข้อกำหนดที่ #49 ถืออยู่
และแถวที่สองของข้อ 6 ติดข้อ 9 ข้างบน

ทุกข้ออ้างใหม่ถูกพิสูจน์ด้วย mutation test ก่อนติด ⚙ เก้าตัวกลายพันธุ์ แต่ละตัวทำให้ assertion
