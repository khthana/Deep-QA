## สิ่งที่ต่างจาก #19 และเป็นเรื่องที่พลาดง่ายที่สุดในตั๋วนี้

**รหัส Rubric ห้ามซ้ำ *ทั้งระบบ* ไม่ใช่แค่ในหลักสูตรเดียวกัน** ซึ่งตรงข้ามกับ #19 ทั้งข้อ
`rubrics.rubric_code` เป็น `UNIQUE` เดี่ยว ๆ และ `db/migrations/0003` เขียนเหตุผลไว้ว่าโค้ดที่รับช่วงมา
เรียก `findRubricByCode(rubric_code)` โดยไม่มีหลักสูตรอยู่ในมือ รหัสที่แปลว่าคนละอย่างในคนละหลักสูตร
จึงจะถูกอ่านเป็นแถวไหนก็ได้ที่เจอก่อน `program_id` บอกว่า Rubric *เป็นของ* หลักสูตรไหน
ไม่ได้บอกว่ามันถูกนับรหัสอยู่ในขอบเขตไหน

ผลที่ตามมาคือ **ประโยคปฏิเสธของหน้านี้เป็นประโยคเดียวในระบบที่ต้องบอกคนถึงแถวที่เขาไม่มีสิทธิ์เห็น**
ถ้ามันอ่านเหมือนประโยคของ #19 (*ในหลักสูตรนี้*) กรรมการหลักสูตรจะไปค้นรายการของตัวเอง
ไม่เจอรหัสนั้น แล้วสรุปว่าหน้าจอโกหก

## สิ่งที่ตั๋วเขียนไว้แล้วโค้ดไม่ทำตาม และทำไม

**เกณฑ์ข้อ 7 ของตั๋วเขียนว่า *"Faculty and Department Admins can manage Rubrics within their
scope"* แต่โค้ดไม่ให้ `FACULTY_ADMIN` เข้าหน้านี้เลย** — [#79](https://github.com/khthana/Deep-QA/issues/79)
กลับคำตัดสินนั้นหลังจากตั๋วนี้ถูกเขียน และระบุ **A04 ซึ่งคือหน้านี้** ไว้ตรง ๆ ว่าห้ามใส่
`FACULTY_ADMIN` ลงใน `MAINTAINERS` ของ route และห้ามเพิ่มรายการเมนูลง `FacultyAdmin.js`
เหตุผลคือคณะถือ *รายชื่อ* ภาควิชาและหลักสูตร ส่วนสิ่งที่อยู่ *ข้างใน* หลักสูตรเป็นของภาควิชากับกรรมการหลักสูตร
ข้อความในตั๋วเก่ากว่า #79 จึงถือ #79 เป็นข้อยุติ และเขียนไว้ตรงนี้แทนที่จะให้ checklist ขัดกับโค้ดอย่างเงียบ ๆ

**การลบ Rubric ลบจริง และลบเกณฑ์ย่อยไปด้วย ไม่มีทางเลือกที่สาม** ทุกหน้าข้อมูลหลักอื่นตอบการลบได้
สามแบบ เพราะมีอะไรอ้างอิงอยู่ แล้ว `deleteOrDeactivate` เปลี่ยนการชนกุญแจนอกให้เป็น *ปิดการใช้งานแทน*
ที่นี่ใช้ไม่ได้ทั้งสองครึ่ง — `rubrics` **ไม่มีคอลัมน์ `is_active`** จึงไม่มีอะไรให้ปิด และตารางเดียวที่อ้างถึง
Rubric คือ `rubric_details` ซึ่งเป็น `ON DELETE CASCADE` แถวจึงหายไปพร้อมเกณฑ์ย่อยของมัน
route นับเกณฑ์ย่อยไว้ก่อนใน transaction เดียวกันแล้วบอกว่าไปกี่ข้อ เพราะแถบที่บอกแค่ *ลบแล้ว*
ทับเกณฑ์สามข้อที่เพิ่งถูกทำลายไปคือการบอกความจริงครึ่งเดียว
`grep "REFERENCES rubrics" db/migrations` คือการตรวจ และวันนี้มันตอบบรรทัดเดียว

**Rubric ต้องระบุหลักสูตร แม้คอลัมน์จะยอมให้ว่าง** `rubrics.program_id` เป็น nullable
แถวที่ไม่มีหลักสูตรไม่ได้แค่ไม่มีเจ้าของ — ตัวกรอง reach คือ `program_id = ANY($1)` ซึ่งได้ NULL
ไม่ใช่ false เมื่อคอลัมน์เป็น NULL แถวนั้นจึง **มองไม่เห็นจากทุกบัญชีในระบบ** รวมทั้งบัญชีที่สร้างมันเอง
route จึงบังคับให้ระบุ ซึ่งคือ route เข้มกว่า schema ของตัวเองโดยตั้งใจ

**แถวปลายทางของเกณฑ์ถูกเขียนใหม่ 2026-08-24** เดิมมันเขียนว่าปลายทางต้องบอกว่า *ส่วนนี้ยังไม่ถูกสร้าง* และอ้างถึง #22 ซึ่งเป็นจริงตอนที่เขียน ตอนนี้ #22 ลงแล้ว แถวที่ขอให้เห็นข้อความที่ไม่มีอยู่แล้วจึงเดินไม่ได้ แถวนี้จึงบอกสิ่งที่ยังเป็นงานของ #21 แทน คือประตูบานนี้พาไปถึง Rubric ตัวที่กดจริง

**หน้านี้ไม่มีการนำเข้าไฟล์** ตั๋วไม่ได้ขอ ถ้าจะทำควรเป็นตั๋วของตัวเอง

## ข้อจำกัดที่รู้อยู่ ไม่ใช่บั๊กของตั๋วนี้

**บันทึก Rubric ที่ลำดับทำให้มันไปอยู่หน้าสอง แล้วหน้าจอยังอยู่หน้าหนึ่ง** จะไม่เห็นแถวที่เพิ่งบันทึก
ทุกหน้าที่แบ่งหน้าในระบบนี้เป็นเหมือนกันหมด (`ข้อมูลรายวิชา`, `ข้อมูลผู้ใช้งาน` ฯลฯ) ไม่ใช่เรื่องที่ #21
ทำให้เกิดหรือควรแก้คนเดียว — `21a-rubrics.spec.js` จึงตั้งลำดับของแถวที่มันสร้างเป็น `0`
เพื่อให้แถวนั้นอยู่หน้าหนึ่ง และเขียนเหตุผลกำกับไว้

## ตั้งต้น

```
docker start deep-core-postgres
cd db      && npm run reset && npm run migrate && npm run seed
cd backend && npm start          # http://localhost:3000
cd frontend && npm start         # http://localhost:5000
```

ทุกบัญชีใน seed ใช้รหัสผ่านเดียวกัน คือค่า `PASSWORD` ใน `db/seed.js:58`
อีเมลต้องพิมพ์เต็มรวมโดเมน `@kmitl.ac.th` — อีเมลหรือรหัสผ่านที่ผิดทำให้หน้าจอขึ้นกล่อง
*Session หมดอายุ* ทับประโยคจริงไว้ หลงทางง่ายมาก ([#97](https://github.com/khthana/Deep-QA/issues/97) ยังไม่แก้)
เมนูที่ใช้ตลอดเอกสารนี้คือ *ข้อมูล Rubric กลาง* (`/main/rubrics`)

**ต้อง restart backend ก่อนเดิน** — process ที่ค้างจากตั๋วก่อนจะตอบ *ไม่พบเส้นทางที่เรียกบนเซิร์ฟเวอร์นี้*
ให้ทุก route ของ #21 และ **`Server running` ใน log ไม่ใช่หลักฐานว่า route ใหม่อยู่ในนั้น**
ยิง `/api/rubrics` ด้วย cookie จริงแล้วต้องได้ 200 ก่อนจึงเริ่มเดิน

**seed เปลี่ยนไปในตั๋วนี้ ต้อง `npm run seed` ใหม่ก่อนเดิน** — Rubric ทั้งสิบสามแถวเพิ่งมี

- `0501` มี `RUB-01` ถึง `RUB-11` **สิบเอ็ดแถว** ซึ่งเกินหนึ่งหน้าไปหนึ่งแถว นั่นคือเกณฑ์ข้อ 8 ทั้งข้อ
  ถ้ามีสิบพอดี ตัวแบ่งหน้าที่พังจะวาดตัวเองแล้วบอกว่า *หน้า 1 จาก 1* และผ่านทุก assertion
- **ลำดับไม่ตรงกับรหัสสองที่** `RUB-02` อยู่เหนือ `RUB-01` และ `RUB-05` อยู่เหนือ `RUB-04`
  บทเรียนจาก [#96](https://github.com/khthana/Deep-QA/issues/96) — ถ้าลำดับเท่ากับเลขในรหัสทุกแถว
  เรียงสองแบบจะให้ผลเหมือนกันและ assertion ไหนก็ผ่านทั้งคู่
- **`RUB-06` กับ `RUB-07` มีลำดับเท่ากัน (6 ทั้งคู่)** `display_order` เป็น `NOT NULL DEFAULT 0`
  ลำดับซ้ำจึงเป็นสภาพตั้งต้นของทุกแถว ไม่ใช่กรณีขอบ และรายการที่แบ่งหน้าโดยไม่มีตัวตัดสินลำดับซ้ำ
  จะแสดงแถวหนึ่งสองหน้าและอีกแถวหายไปเลย
- **`RUB-01` มีเกณฑ์ย่อย 3 ข้อ และ `RUB-02` มี 2 ข้อ** ที่เหลือยังว่าง — สำหรับแถวที่ต้องเห็นตัวเลข
  และแถวที่ลบแล้วต้องบอกว่าเกณฑ์ไปกี่ข้อ
- **`0503` มี `RUB-51` กับ `RUB-52`** รหัสไม่ซ้ำกับของ `0501` เลย เพราะกุญแจเป็นระดับระบบ
  seed ที่ให้ทั้งสองหลักสูตรมี `RUB-01` จะโหลดไม่ผ่านตั้งแต่แรก

หลายข้อข้างล่างเขียนข้อมูลจริงลงฐานข้อมูล — **`npm run seed` ใหม่หลังเดินจบ** ก่อนเริ่มตั๋วถัดไป

## คำขอที่ถูกแทนที่ — #139 (17 ก.ย. 2569)

*แก้ไข* อ่าน Rubric ใหม่ก่อนเปิดฟอร์ม และไม่มีปุ่มไหนในตารางถูกปิดระหว่างที่คำขอยังไม่กลับ คำตอบที่
**มาถึง**ทีหลังจึงเคยชนะคำขอที่**ขอ**ทีหลัง ตอนนี้ `Rubrics.js` จำไว้ใน `asked` ว่าฟอร์มถูกขอด้วย
การกด *แก้ไข* ครั้งไหนเป็นครั้งสุดท้าย — *แก้ไข* ทุกครั้งเป็นคำขอใหม่ แม้กดแถวเดิมซ้ำ ส่วน *เพิ่ม Rubric* กับ *ลบ* เขียนว่าไม่มี — และคำตอบของการอ่าน
รวมทั้งคำปฏิเสธของมัน ถูกวาดก็ต่อเมื่อยังเป็นคำขอนั้น ส่วนรายการยังโหลดใหม่หลังคำปฏิเสธเสมอ (#131)

ตั๋วนับทางเข้าไว้ทางเดียว วัดแล้วมีห้าทาง (สี่ทางในรอบแรก ทางที่ห้ามาจาก code review) และ*แถวที่เรียกสองทางเข้าคือสองแถว* (#66) ทุกแถวข้างล่าง

## รายการที่โหลดใหม่ถูกแทนที่ — #140 (17 ก.ย. 2569)

## บันทึกที่กดซ้ำได้ระหว่างที่การเขียนยังไม่กลับ — #142 (19 ก.ย. 2569)

`frontend/src/pages/Rubrics.js` เคยมีธง `busy` ตัวเดียว ทั้งการอ่านแถวของ *แก้ไข* และการเขียน (บันทึก ลบ)
ถือมันไว้ และ `finally` ของการอ่านปลดมันเสมอ ไม่ว่าหลังจากนั้นจะมีการเขียนหยิบธงไปแล้วหรือไม่ การอ่านที่
มาถึงช้าจึงคืนปุ่ม *บันทึก* ให้ระหว่างที่การเขียนยังไม่กลับ ตอนนี้การเขียนถือ `writing` การอ่านถือ `reading`
และปุ่มกับกล่องยืนยันปิดด้วย `writing || reading` การอ่านยังปลดธงของตัวเองเสมอเหมือนที่เคยปลด
ธงตัวเดียว สิ่งเดียวที่เปลี่ยนคือมันไม่ได้ปลด `writing` — JSX ไม่ได้เปลี่ยน เหตุผลอยู่บน
`frontend/src/pages/Departments.js`

วัดก่อนแก้บนข้อมูลภาควิชาที่ `8bb9a92` ลำดับของตั๋ว (อ่าน อ่านอีกแถว บันทึก) แดงตามที่ตั๋วบอก
ส่วน *อ่านแล้วลบ* กับ *บันทึกแล้วลบ* ไม่ใช่ทางเข้า กล่องยืนยันเปิดมาแบบถูกปิดทั้งสองกรณี สิ่งเดียวที่ปลดธง
ของงานอื่นก่อนเวลาได้จึงเป็นการอ่าน เพราะเป็นสิ่งเดียวที่ตารางยอมให้เริ่มระหว่างที่ธงยกอยู่ และมันทำได้
สองลำดับ — การอ่านที่ถูกแทนแล้ว (ลำดับของตั๋ว) กับการอ่านที่ยังเป็นคำขอปัจจุบัน ซึ่งเริ่มจากตารางหลัง
สิ่งที่ส่งการเขียนถูกปิดด้วย *ยกเลิก* ลำดับหลังมี *ยกเลิก* สองตัวให้กด — ของกล่องยืนยันซึ่งไม่เคยถูกปิด
และของฟอร์มซึ่งกดได้ระหว่างบันทึกแค่บนข้อมูลภาควิชา หลักสูตร และรายวิชา อีกสี่ฟอร์มปิดมันด้วยธง
*แถวที่เรียกสองทางเข้าคือสองแถว* (#66) จอนี้ปิด *ยกเลิก* ของฟอร์มระหว่างบันทึก — วัดจากแถวที่หมดเวลาที่การกดนั้นเมื่อรันกับโค้ดเก่า — ทางของกล่องยืนยันจึงเป็นทางเดียวบนจอนี้

ตั๋วเสนอให้นับงานที่ค้าง แต่ตัวนับจะปิดฟอร์มของแถวที่สองไว้จนกว่าคำตอบของแถวแรกซึ่งถูกทิ้งไปแล้วจะมาถึง

ที่หยิบธงไว้ ซึ่งเปลี่ยนสิ่งที่จอปิดแบบเดียวกัน (การอ่านที่ถูกแซงทิ้งธงไว้จนการอ่านที่ใหม่กว่ามาถึง) และ
ไม่มีมัตแตนต์ตัวไหนแตะมัน — code review เจอ และถูกเอาออกก่อน commit

### มัตแตนต์

ก่อนแก้ (19 ก.ย. 2569 ที่ `8bb9a92`) แถวที่อ่าน *บันทึก* ทุกแถวล้มที่ assertion ของตัวเอง
(`Received: false`) แถวที่สี่ไม่มีบนจอนี้ ส่วนแถวที่สามผ่าน — มันไม่ได้มีไว้จับข้อบกพร่อง แต่จับการแก้ที่ลอก guard
ของ #139 มา (`asked.current === ask`) ซึ่งตั๋วปฏิเสธไว้แล้ว เพราะเพิ่มกับลบเขียน `asked` และไม่ได้หยิบธง
ของตัวเอง `…letgowhileasked` คือการแก้แบบนั้น และเป็นหลักฐานเดียวว่าแถวที่สามล้มได้

กวาดเมื่อ 19 ก.ย. 2569 ด้วยแถวของจอนี้ใน `142a` `139a` `140a` รวมกับ spec เดิมของจอ (`21a-rubrics`) — baseline
**23 ผ่านทั้ง 23** **แต่ละตัวล้ม 1 ผ่าน 22** (3 ตัว) ทุกตัวล้มที่ assertion ของแถว ไม่ใช่ที่ timeout และตัวที่ล้มคือแถวที่
ชื่อของมันบอก อ่านจากชื่อเทสต์ที่ตาย ไม่ใช่จากจำนวน มัตแตนต์ทั้งสามยึด `setReading(false)` ใน `finally`
