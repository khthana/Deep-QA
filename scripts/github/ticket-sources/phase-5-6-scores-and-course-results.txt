Activity marks
## Parent
#1

## What to build
A Teacher records what each student scored. The screen adapts to how the work was actually marked: a toggle switches between one mark per Activity and a separate mark per CLO, and another switches between entering marks per student and per Work Group, where a group's mark applies to all its members.

Marks can also be imported from the Teacher's own spreadsheet. Because a misaligned sheet would silently corrupt the record, an import is checked before anything is applied: the number of students, the student codes, the names, and the CLO columns must all agree with the Section.

Re-saving corrects a mark rather than adding a second one.

## Acceptance criteria
- [ ] Marks can be entered and saved for every enrolled student
- [ ] The per-CLO toggle switches between one input per Activity and one per linked CLO, and both persist correctly
- [ ] The group toggle switches between per-student and per-group entry, and a group mark applies to every member
- [ ] Re-saving a mark updates it rather than creating a duplicate
- [ ] A mark above the Activity full mark is refused
- [ ] The import template downloads and reflects the current toggle state
- [ ] An import is rejected when the student count, any student code, any name, or the CLO columns disagree with the Section, and the message says which
- [ ] A rejected import applies nothing
- [ ] A valid import records every mark
- [ ] A Teacher is refused on a Section they do not teach, enforced at the server
- [ ] Tests cover both toggles, the four import checks and the update-not-duplicate behaviour

Assessment evidence
## Parent
#1

## What to build
A Teacher attaches the evidence that makes an assessment defensible at accreditation: the brief itself, and a sample of student work at each of the four achievement bands. Files can be replaced or removed as better examples appear.

Two security defects in the inherited implementation are fixed here rather than deferred. The upload middleware enforces a size limit but performs no file type check of any kind, so the PDF-only requirement is enforced nowhere on either side. And the evidence directory is served as static files with no authentication, so any document is retrievable by anyone who knows or guesses its path — including student work belonging to another Section.

## Acceptance criteria
- [ ] Evidence can be uploaded against an Activity under each of the five types
- [ ] A non-PDF upload is refused by the server, whatever the file is named or claims to be
- [ ] A file exceeding the size limit is refused with a clear message
- [ ] An uploaded file can be replaced, and the previous file stops being retrievable
- [ ] Evidence can be removed, and no longer appears
- [ ] Retrieving an evidence file requires an authenticated caller entitled to that Section
- [ ] An unauthenticated request for a known evidence path is refused
- [ ] A Teacher is refused on a Section they do not teach, both for listing and for retrieval
- [ ] Tests cover the type check against a mislabelled file and the unauthenticated retrieval refusal

Section results
## Parent
#1

## What to build
A Teacher sees how their Section performed against its outcomes: a radar chart of CLO attainment, the same Section compared against previous years, and the headline figures — mean score, pass rate and student count — beside it.

The hook that fetches the Section's student list is rewritten here. In the inherited code it calls an endpoint that does not exist and then discards its result unconditionally, so this screen and the individual-results screen receive an empty list in every case.

CLO scores are normalised to a five-point scale so outcomes assessed out of different totals can be compared, and a CLO counts as passed when more than sixty per cent of students meet its criterion.

## Acceptance criteria
- [ ] A radar chart shows attainment for every CLO of the Section
- [ ] Scores are normalised to a five-point scale
- [ ] Mean score, pass rate and student count are shown and agree with the underlying marks
- [ ] A CLO is reported as passed when more than sixty per cent of students meet its criterion, and not at exactly sixty
- [ ] Previous years of the same Subject can be selected and appear on the same chart
- [ ] The screen renders an explanatory empty state when no marks exist yet
- [ ] The student list loads correctly, replacing the broken inherited hook
- [ ] A Teacher is refused on a Section they do not teach, enforced at the server
- [ ] Tests seed known marks and assert the resulting figures, including the boundary at sixty per cent

Continuous improvement plan
## Parent
#1

## What to build
A Teacher records the improvement cycle for the Subject each year: what the results showed, what they make of it, what was changed following last year's reflection, and what they intend to do next. This is the narrative an accreditation panel reads alongside the numbers.

The cycle belongs to the Program, Subject and academic year, matching the grain of the CLOs it discusses.

## Acceptance criteria
- [ ] Entries can be recorded under each of the four types for a chosen CLO and year
- [ ] An entry can be edited and removed, with confirmation before removal
- [ ] The cycle for a year is created on demand rather than requiring separate setup
- [ ] The previous year's entries are visible for reference when writing this year's
- [ ] Entries are shared across Sections of the Offering, matching the CLO grain
- [ ] A Teacher is refused on a Subject they do not teach, enforced at the server
